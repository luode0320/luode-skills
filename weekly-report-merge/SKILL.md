# 周报双源合并生成

## 概述

把两份定位不同的周报合并为一份最终 docx：

- **叙事版**（来源：聊天记录/邮件/在线文档，常见为 docx 或 md）：主线概览、工作展开、下一步计划。
- **Git 事实版**（来源：`work-report-summary-rules` 脚本生成的 txt）：按项目分组的提交证据、总体归纳统计、执行/追踪附录。

合并原则：以叙事主线为骨架、Git 事实为证据层，两套口径都保留，不互相覆盖。

## 前置

- 需要 `python-docx`。Windows 隔离 venv：`C:\Users\luode\.workbuddy\binaries\python\envs\default\Scripts\python.exe`（缺失时先 `-m venv` 创建并 `pip install python-docx`）。
- 读 docx 用 `zipfile` 提取 `word/document.xml` 中 `<w:t>` 文本即可，无需额外依赖。
- 用户给的 WSL/UNC 路径（`\\wsl.localhost\...`）可能是**文件而非目录**，先 `ls` 确认类型再读。
- 本机无 LibreOffice 时不做页面渲染检查，生成后必须如实告知用户排版未经页面级校验。

## 工作流

1. **读取来源**：docx 用 zipfile 解出段落文本；txt/md 直接读。识别两份内容分别覆盖哪些主题。
2. **抽取两类内容**：
   - 叙事线：概览表格、主线展开条目、下一步计划表。
   - 事实线：总体归纳统计、各项目明细（保留 `进行中:` 标注）、执行附录、追踪附录。
3. **组织 report.json**：按 `references/format.md` 的格式规范把内容结构化（JSON 结构见脚本 docstring）。
4. **生成 docx**：运行 `scripts/build_report_docx.py report.json 输出.docx`。
5. **回读校验**：用 python-docx 检查标题结构、表格行列数、关键项目名齐全；通过后交付。

## 输出格式（docx 章节顺序，固定）

1. 标题 `周报（YYYY.MM.DD 星期X - YYYY.MM.DD 星期X）` + 副标题（姓名 · 公司 · 部门）
2. **结论摘要**：八项白话开场（结论/影响/范围/非范围/变化/完成标准/术语说明/验证状态），H1 后首个章节，唯一开场段
3. **一、本周概览**：表格（事项 | 本周关键进展）
4. **二、总体归纳统计**：待发布进度口径（`项目: 未完成事项 -> 项目完成度: xx%`），非数量统计口径
5. **三、本周工作展开**：按主线分小节，编号标题 + 条目列表
6. **四、各项目明细（Git 提交维度）**：每项目 `项目名:` + `报告内容点:` + 条目列表
7. **五、下一步计划**：表格（# | 计划事项 | 所属 | 截止时间），进行中事项标"进行中"
8. **执行附录**（生成方式、过滤口径、核对方式）
9. **追踪附录**（项目配置来源、提交证据、工作区证据、叙事来源）

## 关键规则

- 未提交事项必须标注 `进行中:`，不得写成已完成。
- 保留 Git 事实版的作者精确匹配与低价值过滤口径（重命名/回滚/构建/纯文档/纯测试默认不入报告）。
- 已提交事项可回溯到提交记录；叙事事项可回溯到聊天/邮件/文档。
- 报告周期取用户给定范围；未给时默认本周一至今天（北京时间）。
- 附录必须位于正文之后，顺序固定：执行附录 → 追踪附录。
- 输出文件名建议 `周报（YYYY.MM.DD-YYYY.MM.DD）合并版.docx`，与输入 docx 放同目录便于查找。

## 脚本与参考

- `scripts/build_report_docx.py`：report.json → docx 生成器，固定样式（微软雅黑/Calibri、Table Grid 表格、层级标题）。JSON 结构与用法见脚本 docstring。
- `references/format.md`：格式规范细节与章节示例，组织 report.json 前先读。
