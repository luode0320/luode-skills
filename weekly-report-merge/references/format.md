# 周报输出格式规范（docx）

本文件定义合并周报的固定输出格式，供组织 report.json 时对照。结构对齐《白话文档与附录分层契约》：正文给人读，附录收尾。

## 一、标题与副标题

- 标题：`周报（2026.08.17 星期一 - 2026.08.21 星期五）`（日期 + 星期，缺省时用本周一至今天）。
- 副标题：`姓名 · 公司 · 部门`（如 `罗德 · 深圳市芯跃互动科技有限公司 · 研发部门`）。

## 二、结论摘要（八项白话开场，唯一开场段）

H1 后、首个 H2 前，只放一段带标签的短文，八项必须齐全、有具体内容：

| 标签 | 内容要求 |
|---|---|
| 结论 | 本周三大主线是什么、完成了什么 |
| 影响 | 影响哪些业务/系统/稳定性 |
| 范围 | 覆盖哪些来源（Git 提交 + 工作区未提交 + 聊天/邮件/文档） |
| 非范围 | 不含他人提交、设计/文档类改动、未提交不写成已完成 |
| 变化 | 相对上周的呈现方式变化 |
| 完成标准 | 每个条目可回溯到提交/代码/聊天/邮件/文档 |
| 术语说明 | 首次出现的技术词给一句业务解释；无术语写"无技术术语需要解释" |
| 验证状态 | 已按哪些证据逐项核对 |

禁止在开场出现：稳定 ID、机器状态、命令、日志、SQL、行号、代码块。

## 三、正文章节（顺序固定）

1. **一、本周概览**：两列表格 `事项 | 本周关键进展`，6 行左右主线。叙事版有主线表时优先沿用并补充 Git 事实新增的主线（如目录迁移整改、市场活动工程重建）。
2. **二、总体归纳统计**：待发布进度口径，格式 `项目名: 未完成事项 -> 项目完成度: xx%`；未配置时 `项目完成度: 未配置`。不写"完成 X 项/修复 X 项"数量口径。
3. **三、本周工作展开**：按主线分小节，标题带编号（`1. APP 5.0 发现页开发`），内容用条目列表。叙事版与 Git 事实版重叠的主线要互相补充而非重复（例如叙事版提"数据清洗多版本迭代"，事实版补具体修复条目）。
4. **四、各项目明细（Git 提交维度）**：每项目：
   ```
   项目名:
   报告内容点:
   - 修复: ...
   - 功能: ...
   - 进行中: ...（未提交事项必带此前缀）
   ```
   该章节开头附一行灰色小字说明作者过滤与低价值过滤口径。
5. **五、下一步计划**：四列表格 `# | 计划事项 | 所属 | 截止时间`，按截止时间排序；进行中收尾项在截止时间列写"进行中"。

## 四、附录（正文之后，顺序固定）

- **执行附录**：报告周期与生成时刻、生成方式与来源、作者筛选口径、低价值过滤明细、未提交事项核对方式、无未提交改动的项目说明。
- **追踪附录**：项目配置来源路径、提交证据（git log 口径）、工作区证据（各项目变更文件数与变更内容）、叙事来源（聊天条数/邮件封数/文档篇数）。

## 五、合并规则

- 叙事线为骨架，事实线为证据层，两套都保留、不互相覆盖。
- 同一事项两种表述并存时：叙事版放"工作展开"，事实版放"项目明细"，正文摘要处可互相引用。
- 只存在于 Git 事实版的事项（如市场活动工程重建）要补成独立主线小节，不能漏。
- 只存在于叙事版的事项（如服务器故障排查、华为云存储调试）直接保留在对应主线。
- 报告周期冲突时（如叙事版到周五、事实版到周日）：以用户给定为准，未给定用本周一至今天。
