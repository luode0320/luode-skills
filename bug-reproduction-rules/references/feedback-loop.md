# 反馈回路（Feedback Loop）构建

> 归属 owner：`bug-reproduction-rules`。本文件是「复现」阶段的核心方法论，吸收自 `mattpocock/skills` 的 `diagnose`（v1.0.0，2026-08-22 吸收）。负责在开始假设与插桩之前，先构建一个快速、确定性、agent 可运行的 pass/fail 信号。

## 核心原则：反馈回路优先

调试的第一优先动作不是读代码，而是**构建反馈回路**：一个快速、确定性、agent 可运行的 pass/fail 信号。

- 有回路，定位就能靠二分、假设检验和插桩机械推进；没有回路，看再多代码也找不到原因。
- 在回路构建上投入不成比例的精力——回路构建是 debug 的核心技能，其余阶段只是消费这个信号。
- 在拿到可信回路之前，不进入根因假设与插桩阶段。

## 构建回路的方式（按此顺序尝试）

1. **失败测试**：在任何能触达 Bug 的接缝处写单测 / 集成 / e2e。
2. **Curl / HTTP 脚本**：对着运行中的 dev server 打请求。
3. **CLI 调用 + fixture 快照**：用固定输入跑 CLI，diff 输出与已知正确快照。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，断言 DOM / console / network。
5. **重放捕获的 trace**：把真实网络请求 / payload / 事件日志存盘，隔离回放。
6. **一次性 harness**：拉起系统的最小子集（单服务、mock 依赖），用一次函数调用触达 Bug 路径。
7. **属性 / fuzz 循环**：Bug 是"偶尔输出错"时，跑 1000 个随机输入找失败模式。
8. **二分 harness**：Bug 出现在两个已知状态之间（commit、数据集、版本）时，自动化"启动到状态 X → 检查 → 重复"，供 `git bisect run` 使用。
9. **差分循环**：同一输入分别跑旧版本 vs 新版本（或两套配置），diff 输出。
10. **HITL bash 脚本**：最后手段。必须人工点击时，写结构化脚本记录人工交互，让循环仍有结构。

## 迭代回路本身

把回路当产品对待，构建出第一版后持续优化三问：

- **更快**：缓存 setup、跳过无关初始化、缩小测试范围。
- **信号更尖锐**：断言具体症状，而不是"没崩溃"。
- **更确定**：固定时间、固定 RNG 种子、隔离文件系统、冻结网络。

30 秒的偶发回路接近没有回路；2 秒的确定性回路是调试的超级武器。

## 非确定性 Bug：目标是提高复现率

非确定性 Bug 的目标不是干净复现，而是**更高的复现率**：

- 循环触发 100 次、并行化、加压力、窄化时序窗口、注入 sleep。
- 50% 概率的 flake 可调试，1% 概率不可调试——持续把复现率抬到可调试水平为止。

## 性能回归：先测量后修复

性能回归用日志通常是错的，改用测量回路：

1. 先建立基线测量：timing harness、`performance.now()`、profiler、query plan。
2. 基于测量结果二分，而不是靠猜测加日志。
3. 先测量，后修复。

## 无法构建回路时

尝试过上述方式仍无法构建回路时，**停下并明确说明**：

1. 列出已尝试的回路构建方式。
2. 向用户索取三类资源之一：
   - (a) 能复现该 Bug 的环境访问权限；
   - (b) 捕获产物（HAR 文件、日志 dump、core dump、带时间戳的录屏）；
   - (c) 临时生产插桩权限。
3. 在拿到回路之前，不进入假设与插桩阶段；不靠"盯代码"硬猜。

## 复现确认（回路构建后的验收）

运行回路后确认三件事，缺一不可：

1. 回路产生的是**用户描述的失败模式**——不是恰好相邻的另一个失败。错 Bug = 错修复。
2. 失败可跨多次运行复现（非确定性 Bug 至少达到可调试的复现率）。
3. 已捕获确切症状（报错信息、错误输出、慢耗时）供后续阶段验证修复是否真正解决它。
