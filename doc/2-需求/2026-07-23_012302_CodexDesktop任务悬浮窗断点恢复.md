# Codex Desktop 任务悬浮窗断点恢复需求

结论：把“首次持久化即显示悬浮任务列表”设为默认执行模式的硬闸门，并保留十分钟入口作为异常修复闸门；影响：任何已确认、未完成的执行任务都会在第一个领域动作前留下当前会话投影并立即同步 UI，不再因任务被误判为简单而长时间无列表；范围：首次投影持久化与 `update_plan` 顺序、UI 同步失败状态、会话解析、Plan Mode 退出和十分钟异常修复；非范围：修改 Codex Desktop 产品代码、后台定时唤醒、增加 registry v4 字段或持久化计时事实；变化：默认首显从“等待超时补建”改为“持久化后立即刷新”，十分钟入口降为异常修复；完成标准：首次持久化、立即刷新、失败保护、会话冲突失败关闭和活动/阻断状态可见性均有本地行为与真实 Desktop 证据；术语说明：首次领域动作是取得执行许可后准备执行的第一个会改变项目、代码、文档、测试或外部运行时的动作；验证状态：本次需求变更已冻结，实施周期 07 负责规则接入和回归，真实 Desktop 可见性仍需单独放行。

## 业务规则与优先级

- `RULE-RTP-001`：步骤状态只允许 `pending`、`in_progress`、`completed`，最多一个 `in_progress`。
- `RULE-RTP-002`：最多 20 个步骤，每条文案最多 256 个字符，最终文件不得超过 51,200 字节。
- `RULE-RTP-003`：指纹只使用有序任务 ID 和文案计算 SHA-256，进度变化不改变指纹。
- `RULE-RTP-004`：投影禁止保存 prompt、响应、凭据、线程 ID、业务数据和原始用户输入。
- `RULE-RTP-005`：状态迁移时先原子更新磁盘，再调用 `update_plan`；工具失败不得声称 UI 已刷新。
- `RULE-RTP-006`：UI 重建不恢复执行授权，也不等同于 L5 检查点续接。
- `RULE-RTP-007`：计时起点固定为取得执行许可后的首次真实执行动作；需求澄清、Plan Mode 和尚未取得执行许可的阶段不得提前计时。
- `RULE-RTP-008`：主动执行秒数固定为 `observed_at - started_at - paused_seconds`；等待用户、`blocked` 以及归属于等待用户的 `manual_handoff` 计入暂停，结果严格大于 600 才到期，恰好 600 秒不升级。
- `RULE-RTP-009`：每次工具返回、阶段进度更新和准备结束当前回合前检查一次；任务已完成、许可不是 `confirmed`、处于 Plan Mode 或当前 `session_id` 已有活动 projection 时不得创建重复投影。
- `RULE-RTP-010`：计时事实只保存在当前执行上下文，不新增 registry 或 projection 字段，不写入步骤文案和项目长期状态；跨回合丢失计时上下文时不得猜测补齐。
- `RULE-RTP-016`：默认执行取得 `confirmed` 后，首次领域动作前先调用 `ensure-start`（或等价唯一 Owner 入口）持久化当前 session 的 `active` 或 `blocked` projection；Plan Mode、等待用户、许可非 `confirmed` 和任务已完成不得进入该入口。
- `RULE-RTP-017`：`ensure-start` 持久化成功后，下一动作固定为使用已验证 payload 调用 `update_plan`；持久化与 UI 调用之间禁止代码、文档、测试、委派、服务启动及其它领域写操作。
- `RULE-RTP-018`：`update_plan` 失败时保留已持久化 projection，当前执行状态为 `UI_SYNC_BLOCKED`，不得声称悬浮窗已出现或继续执行下一领域写；该运行时状态不扩展 registry v4 schema。
- `RULE-RTP-019`：`active` 和 `blocked` projection 必须同步悬浮任务列表；`inactive` 只作为终态磁盘状态，不触发新列表；恢复活动/阻断 projection 时仍须重新调用 `update_plan`。
- `RULE-RTP-020`：session 解析严格按 `--session-id` 优先、`CODEX_THREAD_ID` 回退；显式值与环境值冲突、两者缺失或值非法时非零退出且不写文件、不调用 `update_plan`。
- `RULE-RTP-021`：十分钟 `ensure-timeout` 仅用于检测首次列表缺失的异常修复，不是默认首次显示路径；主动执行时间仍按既有 `>600` 秒、暂停扣除和可执行检查点规则计算。
- `RULE-RTP-022`：任何子 Agent 不得调用主悬浮窗 `update_plan` 或替换当前 session projection；主 Agent 对“持久化后立即刷新”顺序和 `UI_SYNC_BLOCKED` 负责。

## 非功能要求、风险与阻断

| 项目 | 约束 | 处理 |
|---|---|---|
| 用户内容保护 | 非托管正文必须逐字保留 | 使用唯一标题和 fenced JSON 区块窄范围替换 |
| 崩溃一致性 | 持久化后、工具调用前崩溃仍可恢复最新状态 | 临时文件写入、刷新并原子替换 |
| 安全 | 敏感字段和未知字段不得进入投影 | 白名单 schema 校验并拒绝写入 |
| 阻断 | 投影重复、损坏、过期或来源无法确认 | 不调用工具，不继续未知写操作 |
| 时间准确性 | 起始时间、观察时间或暂停秒数缺失、非 UTC、为负或互相矛盾 | 命令非零退出，原文件字节不变，不猜测墙钟时间 |
| 唤醒能力 | Skills 没有后台定时器，也不能在工具阻塞期间精确唤醒 | 仅在可执行检查点判断；不承诺第 601 秒即时出现悬浮窗 |
| 兼容性 | 现有 v4 registry 与 v1-v3 读取兼容不得被超时能力改变 | 复用 `synthesize`、原子写入和 payload，不修改 schema |

## 决策冻结

- `DEC-RTP-001`：新增 `task-plan-rehydration-rules`，投影 schema、指纹、原子写入和 payload 由它唯一负责。
- `DEC-RTP-002`：正式实施文档仍是真实计划源，`PROJECT_CURRENT.md` 只保存当前周期运行状态。
