本仓库原有 **138 个含 SKILL.md 的技能目录**（25 个 `__skillhub` 市场安装 + 113 个本地自建）。经三域只读扫描（代码质量域 / 研发流程域 / 元规则与工具域）与逐组核验，按用户确认的「标准收敛」力度执行了 **4 组合并**：

| 组 | 合并前 | 合并后 | 节省目录 |

| 组 1 | api-endpoint-rules、api-request-rules、api-response-rules、api-swagger-rules | api-contract-rules | 3 |

**目录数：138 → 131**。全仓引用同步完成：`static_owner_router.py` OWNER_NAMES 已更新（22 个）、`skill-dictionary/data.js` 与 `字典.md` 已重跑生成脚本刷新、17 个契约测试全部通过、旧 skill 名零残留（仅新 skill 内的合并来源说明保留）。

## 合并组分析依据

### 组 1：api-* 四件套 → api-contract-rules

- **重叠证据**：四个 SKILL.md 正文结构 100% 同模板（作用/触发/流程/边界/暂停/通过/归档/references）；"强制 POST""禁 map/any/RawMessage""Swagger 同步"三组声明在多个文件重复；触发按接口生命周期有序（入口→请求→响应→文档）。
- **合并方式**：SKILL.md 总纲 + 生命周期四阶段路由（entry/request/response/swagger），12 个 references 保留原文件名（保护 inventory.yaml 等证据路径）。
- **保留独立**：`swag-openapi-maintainer-rules`（管 swag/ YAML 文档产物，与代码侧注解互补，description 已互相排除）。

### 组 2：注释三件套 → comment-rules

- **重叠证据**：三者触发条件同为"注释"；placement 与 completion 均【强制联动】命中；正文互相转交，边界靠声明维持。
- **硬约束**：`comment-completion-gate-rules` 是强制闸门，`code-change-finalization-gate-rules` 消费其 PASS/FAIL——合并后保留"补齐闸门分区"完整语义（函数头清单/步骤编号/三类核对清单），收口闸门引用同步指向新分区。

### 组 3：minimal + readability → code-quality-rules

- **重叠证据**：都管"该不该抽象/封装"——minimal 默认反对过度封装和接口，readability 禁止无脑新增接口层/helper/factory，且都含"已存在公共工具禁止重复封装"。
- **保留独立**：`common-util-rules`（"7 天冻结 + 复用检索"机制独特）。

### 组 4：skill-evolution → skill-absorption

- **重叠证据**：absorption 的 description 已含"更新、调整、重构、合并、瘦身我们自己的 skill"，与 evolution 的"补旧 skill / 新增相邻 skill"职责重叠。
- **合并方式**：evolution 的 4 个 references（gap-signals / evolution-decision-matrix / improvement-output-template / resume-workflow）迁入 absorption，新增第三通道「执行中 gap 回补」，SKILL.md 双通道判定升级为三通道。

## 刻意不动的管线（职责边界清晰）

- **bug-* 五件套**：intake→reproduction→root-cause→fix-proposal→validation 完整管线，各含转交边界声明。
- **requirement-* 四件套**：intake 为主 Owner + boundary/change/splitting 三专项，intake 明示"不吞并专项信号"。
- **TAPD 四件套**：tapd-openapi 主入口 + cli/addcomment 联动工具 + env-bootstrap 本机环境事实，一主三支撑合理组合。
- **db/redis 三件套**：query/schema/redis 三域互斥。
