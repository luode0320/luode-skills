# 测试主文档：组件菜单二级化与示例可用性收口

结论：二期验证通过。组件库菜单已经是「父分类 + 子组件分类」两级，十个父分类下共三十九个可点示例页；一百五十一个组件共五百七十九组示例，平均每个组件三点八三组，且三十九个页面逐格扫描后没有任何两组示例渲染相同；三十九个示例页在 320、400、620、900、1280 五档窗口宽度共一百九十五组测量中，没有出现零尺寸内容、没有出现内容被裁掉、页面没有出现横向溢出。影响：侧栏组件库分组由十条一级菜单扩展为十个父目录加三十九个子页面；示例卡超出内容改为滚动可见而不是切掉；示例页面包屑不再指向无法路由的页面；修复了树选择组件收起状态下选中值不显示的真实缺陷。范围：本轮验证覆盖两级分类守卫、示例变体守卫、后台可达性守卫、目录索引校验、还原度守卫及其自测、类型检查、生产构建、单元测试、污染扫描，以及真实浏览器内的两级菜单点击、逐格渲染签名扫描、浮层打开态实测与五档宽度实测。非范围：不改上游冻结文件、不补上游列排序能力、不执行版本提交。变化：示例从「数量够但可能有凑数格」变为「每一格都必须看得区别」；窄窗口从可能丢样式变为内容一律可达。完成标准：见验收结论表十二条全部为通过且都有可复核依据。术语说明：可见差异指同屏或同一操作状态下能用肉眼或数值读出区别；打开态实测指用真实事件把浮层、下拉、弹层点开之后再读取位置与尺寸。验证状态：全部结论来自本轮真实命令输出与本地真实浏览器实测，无仅凭静态阅读得出的通过项。

## 通过标准

- 两级分类必须当场与磁盘组件全集双向对账：每个组件恰好归入一个子分组、子分组键全局唯一、父分类不少于八个、无空子分组、菜单图标必须在图标注册表中存在，任一不满足即失败。
- 示例组数判据以验收面为准：每个组件含基础示例不少于三组；只有单一可覆盖维度的契约组件允许降档到一组，但必须在守卫输出中逐个点名并给出不加码的理由。
- 可见差异判据以渲染结果为准，不以属性写了什么为准：扫描签名同时包含卡片根节点整段标记、该页应用根节点长度、以及格内所有输入控件的真实取值，缺任一口径都会把真实差异误判为重复。
- 只在打开态才可见的差异，不得因为收起态渲染相同就判为伪变体，也不得计入重复；必须给出打开后的实测数值，或在派生侧登记为不可见候选并说明门控条件。
- 窄窗口判据同时看四点：卡片内容区高度不为零、内容不被以裁切方式隐藏、文档不出现横向溢出、各档读到的卡片格次必须与基准档对账相等；缺第四点时「页面没加载」会伪装成全零通过，只测单一宽度同样不算通过。
- 类型检查、构建、单元测试、污染扫描、还原度守卫五项必须全部为真实命令退出码与真实计数，不接受口头说明。

## 图片资产决策与未覆盖风险

- 图片资产决策：`N/A + 原因 + 证据`。原因：本轮验收面为导航层级、示例差异可见性与内容可达性，全部由命令输出与文档对象模型数值判定，不引入外观基线对比；证据：分类守卫与变体守卫计数、三十九页扫描结果、五档宽度二十组几何测量，均为数值结论。
- 全量点击自动化未做：五百七十九格逐格交互会触发浏览器工具超时，本轮改为「全量渲染签名扫描 + 六个代表组件的打开态与取值实测」；其余组件以渲染签名互不相同、挂载异常为 0 作为最低证据，不声称已完成逐组件交互验证。

- 上游列排序能力缺失仍为既有缺口，本轮不处理：该组件属上游冻结层且被多个业务页面消费，改动会破坏逐字节还原基线，需以独立需求另行立项评估。
- 十九个本地扩展组件文件长度超过 200 行基准属存量，本轮未纳入处置范围：只对本轮改动位点负责，批量重构会扩大无关差异。

- 渲染签名口径为三段拼接：卡片根节点整段标记（去掉作用域样式标记属性与自动生成的标识）、该页应用根节点字符串长度、格内全部输入控件取值。只用其中任一段都会误判——去掉 `style` 会把宽度类差异误判为重复，只比长度会把文本差异误判为重复，只看卡片标记会把改变根标签的属性误判为重复。
- 组件默认真实值一律从组件自身契约取，不从文档手抄：本轮为派生器增加的门控配对表与不可见候选黑名单，每条都在注释里写明对应的组件模板分支条件，并可被源码检索复现（例如多行文本行数属性只挂在多行分支、半选态样式条件包含未勾选、环形进度尺寸只参与圆环几何、多选摘要只在数组取值时展开）。
- 泳道隐藏提示挂在 `hiddenCount` 上，只有样本泳道数超过显示上限才渲染，因此把样本从两条补到三条是让该维度成为可用示例的前置条件，而不是为了凑差异而加数据。
- 表单示例此前把输入框取值写死为空串，导致「已填全」与「只填姓名」两格渲染完全一致；改为读本格样本后才出现真实差异，该缺陷属示例侧而不是组件侧，组件的校验逻辑本轮未改。
- 树选择缺陷属组件侧真实实现问题：原查找走可见行列表，而该列表会剔除折叠节点的子行，因此收起状态下选中二级节点时触发区退化为占位符；改为在完整数据树中递归查找后修复，本轮未改其对外契约。
- 本轮删除了分类数据源中一个全仓无消费者的派生反查表：页面归属直接按路由两段在子分组结构上查，不需要第二张索引；删除后类型检查、两级分类守卫与覆盖率守卫复跑全部仍为通过。
- 污染扫描对本轮改动面为放行（`--root . --diff-only` 输出 `POLLUTION: PASS`，并显示上游冻结脚本的口令分支为「已登记豁免」）。把扫描根收窄到 `frontend-design/component-library/src` 时会出现两条非阻断的「疑似死代码」提示：`composables/motion.ts` 的 `revealPage` 属上游 139 文件冻结基线，删除会立刻让还原度守卫失败，只能转评估；`data/component-categories.ts` 的 `COMPONENT_SUB_GROUPS` 是扫描根造成的口径假象——它的真实消费者是扫描根之外的 `frontend-design/scripts/check_demo_variants.mjs`（该脚本 import 它做子分组闭合校验），因此不是死代码，已实测确认。本轮删除的只有全仓确实无消费者的 `COMPONENT_SUB_GROUP_OF`（删除前对符号名全仓检索命中 0）。
- 单元测试入口是项目自带的 Node 原生测试脚本；仓库未配置第三方浏览器测试运行器，本轮未新增测试文件，验证通道沿用「命令输出加变异自证加浏览器实测」这一既有守卫家族口径。
