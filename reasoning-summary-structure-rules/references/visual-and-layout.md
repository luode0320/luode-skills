# 总结视觉规范（强制）

最终总结必须与上方推理过程、中间进度在视觉上明确分界，并采用统一的严谨 markdown 排版，让用户一眼分辨“哪里开始是总结”。本节只约束排版与分界，不改变「输出要求（固定顺序）」的字段与顺序。

### 视觉分界

- 总结区块前必须插入一条 `---` 水平分隔线，与推理过程、工具叙述、中间进度切开。
- 分隔线下用固定一级主标题作为容器起点：`# 📋 本轮总结`（一级标题，字号最大、天然加粗；标题文案固定，便于辨认）。
- 容器外不得再散落总结性结论；工具调用叙述与中间进度不套用总结容器。

### 排版要求

- 紧随主标题直接输出“一句话结论”引用块，不要再插合规打分或闸门结论行。
- 用一个 `>` 引用块写“一句话结论”，让核心结果最突出。
- 固定字段一律用二级标题 `## ` 小节承载，字号明显大于正文且天然加粗；形成“一级主标题 > 二级小节标题 > 正文”的三级字号层级，层级之间字号必须有明显区分。
- 标题必须使用 markdown 标题语法（`#` / `##`），禁止用加粗文本冒充小标题；确保标题比正文更大且加粗。
- 小节可配区分性 emoji（条件小节仅在实际出现时使用）：📊 图形化总览 / 🛠 执行证据 / 🎯 要解决的问题 / 🔧 方案与根因（T1 为 🔧 方案与结果）/ ✅ 验证 / 📌 结果与结论 / 🔄 后台异步任务 / 📦 改动点 / 📚 知识引用；T0 极简档只出现实际输出的条件尾节 emoji。
- 多文件改动、需求对照、状态对照优先用 markdown 表格，不堆长串冒号列表。
- 改动点表格与正文中的项目内生成/修改文件路径必须用 Markdown 可点击链接 `[文件名](file:///完整路径)` 输出，不得只用行内代码反引号包裹路径；本地文件用 `file:///F:/...`（正斜杠），WSL 项目用 `file://wsl.localhost/<distro>/...`；链接文本取文件名，完整路径通过鼠标悬浮查看。
- 状态用徽章式标记：通过 ✅、警告 ⚠️、失败 ❌、阻断 ⛔。
- 无真实阻断时，末尾顺序按引用台账是否非空分流：台账非空时「知识引用」放在所有内容节点的最后、「本次改动点」紧邻其前；台账为空时「本次改动点」放在最后。真实阻断时两者都置于最终阻断区块之前。
- `knowledge-flow` 的检索与沉淀事实统一由「知识引用」小节的两张表承载；该小节只列引用台账条目，不得输出笔记正文、不得摘录笔记片段，也不得在其它小节重复同一事实。
- 不再单列“函数注释核对”节点；该核对作为闸门内部证据完成，不在总结展示。
- 统一使用 markdown，不依赖 HTML 渲染：HTML 在 Claude Desktop、纯 CLI、Codex 等多数 agent 不渲染，会退化成原文噪声并破坏机器解析；视觉靠语义层级（`#` / `##` 标题、`---` 分隔线、表格、`>` 引用块、徽章 emoji）而非绝对字号，字号由各 agent 渲染端决定，不在输出里塞裸 HTML 标签。宿主原生可视化工具（WorkBuddy Visualizer / `show_widget`）调用不属于「正文内嵌 HTML」，图形化总览按「渲染通道优先级」小节执行。
- 普通说明、方案、流程、总结、审查报告、线程拆分和状态回报必须使用普通 Markdown 段落、列表、表格或引用块；不得用 ` ```text `、无语言代码围栏、缩进代码块或 HTML 包裹整段自然语言输出。
- 代码围栏只用于真实代码、命令、配置片段、日志片段、JSON/YAML 等需要等宽保真的内容；若只是为了展示可读结构，应改用 Markdown 列表或表格。
- 字段顺序严格遵循当前档位的小节集与「通用尾部顺序」；T2 图形适用时必须先于执行证据和长段文字，视觉规范不得省略当前档位必填项。
- 若存在真实阻断，`## ⛔ 任务阻断收口` 必须位于总结最后，替代“后续内容”；本次改动点与知识引用（如有）必须置于其前，避免任何文本覆盖最终状态。
