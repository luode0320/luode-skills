# 推理总结结构闸门规则

只在“本轮准备输出最终总结”时使用这个 skill。
目标是区分任务性质并按复杂度分档输出高密度总结：
- **工程执行任务**：按 T0 极简 / T1 标准 / T2 完整分档，消除“小节堆叠、三处复述同一信息”的冗余；若总结/结论中出现需用户裁定的事项，强制给出明确建议倾向与选项选择，严禁只抛问题不给建议；
- **决策研判与建议任务**（如字段是否拆分、架构选型、表设计裁定）：强制使用**极简断言**（简单场景“拆/不拆+1句理由”）或**强制三段式极简结构**（复杂场景“决策点 -> 跨成员影响 -> 明确建议与选项选择”），坚决剔除核实排查流水账与反复论证，篇幅压到最短，只留结论与决策依据。

## Skill 作用与适用场景

- 在最终回复前检查总结结构字段是否齐全。
- 强制字段缺失时不允许给出“已完成”式收口结论。
- 任务性质分流：工程执行任务走 T0/T1/T2 档位判定；决策研判与建议任务（字段拆分、选型、方案评估、口径裁决）强制走决策收敛结构。
- 决策研判任务严格落实“反铺垫、反探查流水账、反重复论证”三反铁律，禁止倾倒代码排查过程，只留决策结论与依据。
- 待裁定事项建议与兜底闭环：无论处于工程执行任务（T1/T2）、阶段收口、周期边界还是中断点，凡列出需用户裁定/决策的事项（如“两件仍需你裁定的事”），严禁仅罗列问题或单向抛出疑问，必须逐项给出 Agent 明确推荐建议（加粗倾向与理由）、简洁可选项（A/B）以及**若未做裁定默认推进的最安全兜底方案**，确保用户可直接拍板决策，且在未回复具体选项或仅回复“继续”时系统具备确定性、安全可靠的推进路径。
- 对“有条件字段”按本轮真实上下文做显式判定，避免漏报或伪报；需求对照默认不输出，仅偏差时给一行说明。
- 让不同任务类型（需求、Bug、实现、评审、测试、交付、决策研判）都能输出可复核总结，且每个小节只承载增量信息。
- 对流程、依赖、状态、执行链、跨角色交互和量化结果执行图形适用性判断；适用时先图后文，简单单点任务保持简洁。
- Plan Mode 负向退出：当前上下文只要处于 `Plan Mode`，本 Skill 必须判定为 `NOT_APPLICABLE`，不得命中、读取模板、生成总结型 `final_answer` 或参与计划出口；正式、受限和阻断计划均由 `implementation-planning-rules` 独占。
- `SUMMARY-GATE-PMW-001`（承接 `AC-PMW-006`）：最终总结前必须检查是否仍有未决 `request_user_input` / `WAITING_DECISION`；只要存在空答案、缺失答案或宿主隐式超时尚未解决，就拒绝冻结集合内的任何可见输出（`commentary`、`limited_plan`、`pending_summary`、`proposed_plan`、`final`、`summary`、`final_answer`、`task_complete`、`result_and_conclusion`），不得把推荐项或文本总结当作完成信号。
- `SUMMARY-GATE-PMW-002`（收口前任务状态检查）：输出最终总结前必须检查宿主任务列表（TaskList）pending / in_progress 任务与 `PROJECT_CURRENT.md` 投影 registry 中当前 session 的 active projection 未完成 step。存在未完成必需项时：执行授权为 `confirmed` 且无真实阻断 → 不得输出最终总结，继续执行；因真实阻断、需用户决策或平台硬限制（上下文/token 上限、单回合步数上限、超时、额度、非交互模式进程退出）无法继续 → 必须输出显式中断点（已完成清单 + 剩余任务清单 + 下一动作 + 重入入口/投影 ID），禁止“已完成”式收口。任务全部完成（TaskList 全 completed、投影 inactive）才允许“已完成”式收口。

## 自动触发信号

- 首条命中检查阶段：非 Plan Mode 的实质任务轮，本 skill 应被 `skill-hit-check-rules` 按延迟触发 gate 注册表预声明为收口候选 Owner，并在 `闸门预告:` 字段登记；不得等到回合末端才首次意识到应命中本 skill。
- 准备输出本轮最终回复。
- 输出中出现“总结”“结论”“收口”“最终说明”“最终回复”“决策建议”等结束信号。
- 任务涉及字段判断、架构选型、拆表评估、方案建议，需要给出定夺结论。
- 本轮启动了后台异步任务（`run_in_background` 轮询、CI 等待、长任务后台执行）且准备收口：即使本轮同步动作已全部完成，也必须触发本 skill，以输出「🔄 后台异步任务」分流小节，并校验异步任务已在宿主任务列表登记（`TaskCreate` 描述含做什么 + 任务标识 + 何时查看）、任务列表条目可回指任务标识，明确「同步已完成、异步在跑、结果回流渠道」，避免用户把异步等待误读为会话未完成或被阻断。

## Plan Mode 排除

- `Plan Mode` 是本 Skill 的硬排除条件，不因“最终回复”“总结”“压缩恢复”或用户要求按计划执行而重新触发。
- `Plan Mode` 下不得输出 `# 📋 本轮总结`、`final_answer`、`summary` 或其它总结容器；无未决项时只能由计划 Owner 输出完整 `<proposed_plan>...</proposed_plan>`。

## 任务性质分类与档位判定（强制）

进入总结输出前，先识别任务性质属于「决策研判与建议任务」还是「工程执行任务」：

---

### 一、 决策研判与建议任务（强制极简结构）

凡涉及字段拆分/保留（如手机维度 4 列是否拆分）、数据表设计、架构选型、技术方案建议、口径确认，或用户直接要求定性（如“你说个拆或不拆就行”）的场景，**一律禁止套用工程执行的多节模板（禁止输出执行证据、问题根因、验证结果等流水账）**，按复杂度分为两档：

#### 1. 简单决策（极简断言档）
- **触发条件**：用户明确要求二选一（“你说个拆或不拆就行”）、单点事实定性、或结论明确无复杂分支。
- **输出格式**：
  ```markdown
  ---
  # 📋 决策结论

  > **建议：<拆 / 不拆 / 方案A>**。
  > **核心理由**：<1 句话直接讲透核心技术/业务依据，严禁背景铺垫与推导过程>。
  ```
- **硬约束**：全文篇幅不得超过 3 行，零废话，直击答案。

#### 2. 复杂决策（三段式极简结构）
- **触发条件**：涉及多字段/多表关系梳理（如手机维度 4 列拆成员案例）、跨模块波及、或存在多个备选方案需用户决策。
- **强制三段式结构**：
  1. **待判断字段 / 决策点**：精准锚定具体的字段、表或设计争议点；直奔主题，严禁背景铺垫与前戏；
  2. **其作用与跨成员影响**：说明该字段在系统中的业务/存储定位，直接陈述对跨表、跨模块或关联成员的具体波及与矛盾，严禁叙述“我查了哪些表/看哪行代码”等核实过程；
  3. **明确建议与倾向（给用户选择）**：必须亮出鲜明倾向（如加粗“**建议拆分为 reportuserphone + reportuserphonemodel**”），并用 1-2 句给出硬核理由；若存在可替代方案，列出简洁选项（A/B）供用户决断，绝不模棱两可。
- **硬约束**：总篇幅严格控制在一屏以内（通常 200~350 字），三段式之外严禁增加其他主节。

---

### 二、 工程执行任务（T0/T1/T2 分档）

非决策建议类的代码编写、文件修改、Bug 修复等任务，继续按复杂度严格判定：

#### T2 完整档（命中任一硬条件即判 T2）
1. 存在真实 `blocked` / `manual_handoff`（需渲染任务阻断收口）。
2. 命中 `skill-execution-compliance-gate-rules` 或 `code-change-finalization-gate-rules`（需完整闸门证据与合并收口）。
3. 存在流程、依赖、状态迁移、跨角色/跨服务交互或量化结果对照等适合图形表达的内容（需图形化总览）。
4. 跨模块 / 跨服务改动，需要依赖或影响面表达。
5. 用户当前轮明确要求完整结构或详细报告。

#### T0 极简档（全部满足才判 T0）
1. 任务属单点之一：单文件文字修正、简单保存（仅写一个文件并读回）、纯问答、单命令/单配置说明。
2. 改动文件数 ≤ 1 且仅一处简单改动。
3. 实质动作 ≤ 1 步。
4. 无独立验证动作（或仅“读回确认”级，不单列验证）。
5. 未命中任何 T2 硬条件。
6. 无需求理解偏差（无 ⚠️）。

#### T1 标准档（非 T2 且非 T0）
普通多步任务（2–5 个实质动作）、改动集中同一主题、验证可并入执行证据或方案与结果。默认档位：不满足 T0 全部条件且未命中 T2 任一硬条件时，一律判 T1。

---

### 档位与全局条件尾节的关系

- 后台异步任务、知识引用台账、真实阻断是全局条件尾节，不随档位省略：T0/T1/决策型 命中时同样必须输出对应小节。
- 档位只决定主链路小节的数量与粒度，不豁免任何全局条件尾节；未命中的条件尾节整节省略。
- 决策研判任务无文件改动时整节省略改动点；无知识引用时省略知识引用。

## 进入后先做什么

1. 先收集本轮事实：命中 skill、执行动作、问题定义、处理方案、结果状态。
2. 判断条件字段是否适用：
   - 是否存在适合图形表达的流程、依赖、状态、执行链、跨角色交互或量化结果。
   - 是否有代码/文档改动。
   - 是否有验证动作与验证结论。
   - `knowledge-flow` 的引用台账是否非空；只有台账存在真实登记条目时才输出「知识引用」小节，台账为空时整节省略，不输出空表或占位行。
   - 是否存在真实状态为 `blocked` 或 `manual_handoff` 的共享阻断事实；只读 `artifact-delivery-gate-rules/references/task-blocker-closure-contract.md` 定义的字段，不重建平行字段。
   - 是否启动了后台异步任务（`run_in_background` 轮询、CI 等待、长任务后台执行）；存在时必须输出「🔄 后台异步任务」分流小节，且该小节只描述异步任务状态，不等同于任务阻断、不构成未完成必需项、不触发“后续内容”。启动异步任务后必须先用 `TaskCreate` 在宿主任务列表登记（条目描述三段式：做什么 + 任务标识 + 何时查看），等待/回收阶段用 `TaskUpdate` 推进状态；收口时校验登记已发生、条目可回指任务标识。未登记的任务列表条目视为异步状态不可见，需补登记后再收口。
   - 阻断事实必须包含“用户授权操作”字段；渲染时突出“请直接回复：`同意授权`”与“请直接回复：`暂不授权`”，并写明授权边界（仅最近一条、唯一有效、仍未解除的 `BLK-*` 记录列明的恢复动作；授权后走原验证入口，失败保持阻断；授权不构成跨任务、跨会话或未来写入的通用许可）。
   - 是否存在仍处于 `WAITING_DECISION` 的 `request_user_input`；若存在，按 `AC-PMW-006` 驳回总结并回到同一选择框重发循环，而不是输出任何总结性消息。
3. 按档位判定结果组织对应小节集：T2 按「输出要求（固定顺序）」的基线主顺序，T0/T1 按各自紧凑结构与「通用尾部顺序」。
4. 若必填字段缺失，先补信息再输出最终总结。
5. 需求一致性判定：默认视为一致，不输出任何对照内容；仅当模型理解与用户原始需求存在实际偏差（⚠️）时，在 T1 的「方案与结果」末尾或 T2 的「当前要解决的问题」小节内输出一行 `⚠️ 需求理解偏差：<模型理解为 X，用户原意为 Y>`。禁止默认输出“用户原始需求 / 模型理解的需求 / 是否一致”三行仪式性表格。
6. 若当前运行环境存在 goal / plan / task 等显式状态收口机制，且总结结论准备写“任务已完成”，必须先确认该运行时状态已被真实收口；总结结构不能替代对应工具或协议收口动作。
7. 执行 `SUMMARY-GATE-PMW-002` 收口前任务状态检查：检查宿主任务列表（TaskList）是否存在 pending / in_progress 任务，以及 `PROJECT_CURRENT.md` 投影 registry 中当前 session 的 active projection 是否存在未完成 step；存在未完成必需项时，执行授权为 `confirmed` 且无真实阻断 → 不得输出最终总结，先继续执行；因真实阻断、需用户决策或平台硬限制无法继续 → 输出显式中断点（已完成清单 + 剩余任务清单 + 下一动作 + 重入入口/投影 ID），禁止“已完成”式收口；任务全部完成（TaskList 全 completed、投影 inactive）才允许“已完成”式收口。
8. 最终收口默认不输出后续内容；只有存在原执行计划内未完成必需项、阻断项，或用户明确要求提供后续建议时，才允许输出后续内容。若用户明确说“结束”“停止”“到此为止”“不要继续”“不要下一步建议”“不要扩散”等结束指令，或原始用户目标已完成且仅剩可选优化，本 skill 只允许组织最小收口结论；不得输出“下一步状态 / 下一步建议”区块，也不得用“等待用户新指令 / 无需继续动作”替代。
9. 若本轮判定为 T0 极简档（单文件修正、简单保存、纯问答、单命令说明等单点任务），映射到 `references/summary-structure-template.md` 的 T0 极简模板：只保留 `---`、`# 📋 本轮总结`、状态摘要行与一句话结论（含验证状态），再按「通用尾部顺序」接条件尾节（改动点/知识引用/异步）；省略执行证据、要解决的问题、方案与根因、结果与结论、图形化总览。

## 默认执行流程

1. 先按「档位判定（T0/T1/T2，强制）」确定本轮档位。
2. 读取 `references/summary-structure-template.md`，按当前档位对应模板组织输出框架。
3. 读取 `references/conditional-sections-rules.md`，判定条件字段是否必须出现（第 0 节为档位与对照表降级规则）。
4. 仅 T2 做图形适用性判断：适用时选择最贴合事实的一种图形；只有两种图分别承载不同且必要的信息时才允许输出第二张图，总数最多 2 张。T0/T1 不输出图形化总览。
5. 按当前档位模板输出最终总结：状态摘要和一句话结论之后，T2 先输出图形化总览再输出执行证据与文字字段，T1 依次输出执行证据与方案与结果，T0 直接进入条件尾节。
6. 按「总结视觉规范」对最终总结排版：先输出 `---` 分隔线，再用 `# 📋 本轮总结` 容器承载固定字段，与推理过程视觉分界。
7. 发送前强制自检（硬闸，不可跳过）：在最终回复真正发出前，逐条核对草稿是否满足以下项目；任意一项不满足，立即判定 `reasoning-summary-structure-rules:FAIL`，禁止发送，必须先改写为当前档位标准模板再输出，不允许以“先前已声明命中”为由直接放行：
   - 是否已以 `---` + `# 📋 本轮总结` 开头，与推理过程 / 中间进度视觉分界；
   - 是否已覆盖当前档位的全部必填小节（T0/T1 见「档位判定」，T2 见「输出要求（固定顺序）」），且顺序未错乱；
   - T0 极简档是否已使用 T0 模板，T1 主节是否 ≤ 4 个；不得用“已保存到...”“已完成...”等普通确认句替代总结容器；
   - T2 是否已按事实判断图形适用性；适用时图形是否先于长段文字，不适用时是否按条件规则省略或说明 `N/A + 原因 + 证据`；
   - 每张图是否有图形目的、关联 ID、完整节点/连线，且图内术语、状态和结论与正文及真实证据一致。
   - 反重复铁律：是否仍有同一事实在多个小节重复出现（「知识引用」登记行与异步任务标识字段按口径豁免）；存在即判定 `FAIL`。
   - 一句话结论是否承载“结果 + 关键数字/文件 + 验证状态”；只有“已完成”“已修复”等状态词而无具体对象时判定 `FAIL`。
   - 文字风格：是否残留填充词（“此外”“总体而言”“值得注意的是”）或空泛形容（“显著提升”“大幅优化”“完善”“丰富”）；应改写为具体名词与数字后再发送。
   - 对照表条件化：是否存在 ⚠️ 偏差却未输出偏差行，或无偏差却输出三行一致性对照表；后者判定 `FAIL`。
   - 引用台账非空时是否已输出「知识引用」小节，且每一行都能回指本轮一次成功返回的文件读/写调用；台账为空时是否已整节省略。任何无法回指真实调用的引用行，判定 `FAIL`。
   - 待裁定事项闭环自检（硬闸）：若总结、结论、中断点或方案结果中列出了需用户裁定/决策的事项（如“两件仍需你裁定的事”“待决策项”），是否逐项落实了「裁定点与影响 + 加粗明确建议倾向与1句理由 + 选项选择（选项 A/B） + 默认最安全兜底方案（未裁定/回复继续时的安全推进方案）」四要素闭环？是否存在“只提问题、只列矛盾、不给建议、不给选项、缺默认安全兜底”的现象？一旦存在，立即判定 `reasoning-summary-structure-rules:FAIL`，禁止发送，必须改写补齐后再输出。
   - 决策研判自检（硬闸）：若本轮任务涉及字段判断、架构选型、拆表建议或方案决断，是否严格执行决策收敛结构：简单场景是否使用 ≤ 3 行的极简断言（直奔建议+理由，零铺垫）；复杂场景是否严格使用三段式（1.决策点 2.跨成员影响 3.明确建议与选项选择）；是否彻底排除了查看代码、翻找文件、SQL查询等核实过程流水账；是否在多个段落重复论证同一理由。一旦违背三反铁律或套用工程执行流水账，立即判定 `FAIL`。
   - 本轮启动了后台异步任务时，是否已输出「🔄 后台异步任务」分流小节（T2 位于「结果与结论」之后，T0/T1 位于一句话结论之后的首个条件尾节位置），并写明任务标识、轮询节奏、结果回流渠道、用户等待语义与宿主任务列表映射，且已在宿主任务列表登记（`TaskCreate` 描述含做什么 + 任务标识 + 何时查看）；缺失、位置错误、未登记任务列表、或把异步等待写成“任务未完成 / 阻断 / 后续内容”时，判定 `FAIL`。
   - 推理过程、中间进度与最终总结正文是否为简体中文；发现成段非中文（英文 / 日文等）自然语言必须改回简体中文再发送，代码符号、命令、路径、原始字段名、报错原文等技术片段除外。
   若本轮同时命中 `skill-execution-compliance-gate-rules` 或 `code-change-finalization-gate-rules`，本步骤与其收口检查合并执行、共用同一份证据，不重复渲染两套结论。

## 输出要求（固定顺序）

只要本轮已经触发本 skill，最终总结按当前档位输出对应小节集。下方编号清单是 T2 完整档的基线主顺序；T0/T1 在其后定义；所有档位共用「通用尾部顺序」。

### T2 完整档基线主顺序

1. Skill 命中检查（必须，主标题后的状态摘要行）
2. 图形化总览（内容适用时必须，位于一句话结论之后、执行证据之前；判断为不适用或无法可靠表达时按条件规则写 `N/A + 原因 + 证据`）
3. Skill 执行证据（必须；1-3 条关键动作与证据，不写流水账）
4. 当前要解决的问题（必须，但只写 1-2 行：用户原始目标一句话；存在 ⚠️ 需求理解偏差时附一行偏差说明；禁止输出三行一致性对照表）
5. 当前问题的解决方案、问题根因（必须；只写方案与根因本身，不复述执行证据已记录的动作流水账）
6. 验证结果（有验证时必须；只写验证了什么、结果如何、是否通过、是否有残留风险）
7. 当前解决结果、结论（必须）
   - 结果区使用单个引用块，只写一句话结论未覆盖的增量信息（范围边界、残留卡点、关键限制），默认 1-2 句，最多 3 句；一句话结论已按「结论为主」承载结果、关键数字/文件与验证状态，本节不得复述。
   - 若仍未完全解决，必须说明剩余卡点；禁止只写“已完成 / 已解决 / 请查看文件”。
   - **待裁定事项闭环（强制）**：若结果区或中断点中包含需用户裁定/决策的事项（如待裁定技术方案、操作许可、表重建等），**严禁只罗列问题而不给建议**（禁止单向抛出“两件仍需你裁定的事：xx 是否 xx... 动手前必须有答案”）。必须逐项严格执行「① 裁定点与影响 + ② 推荐建议（加粗）与理由 + ③ 选项选择（A/B 方案供直接回复） + ④ 默认最安全兜底方案（未做裁定/回复继续时按最保守安全方案推进）」四要素闭环。
   - 禁止复制命令、完整测试清单、逐文件改动或执行流水账；详细证据分别留在对应小节。
   - 知识库检索与沉淀事实统一由「知识引用」小节承载，不在本节写摘要行，也不占用句数上限。
8. 后台异步任务（本轮启动了后台异步任务时必须，位于「结果与结论」之后）
   - 用 `## 🔄 后台异步任务` 二级标题承载，紧随「结果与结论」之后输出，让用户先看到“本轮同步收口结论”再看到“后台还有异步任务”。
   - 必须逐项写明：任务标识（任务 ID / CI run 编号 / 后台进程）、任务类型（轮询 / CI 等待 / 长任务）、轮询节奏（如每 30s 一次）、预计完成信号、结果回流渠道（系统通知 / 下一会话 / 用户指令）、用户等待语义（“无需等待，完成后会另行通知”或“需要在本会话等结果”）与宿主任务列表映射（对应 `TaskCreate` 登记的条目名 / 任务列表 UI 查看位置）。
   - 任务列表桥接（强制）：启动异步任务时必须先用 `TaskCreate` 在宿主任务列表登记为可追踪条目，条目描述统一按「做什么 + 任务标识 + 何时查看」三段式；『启动异步任务』『等待/轮询结果』『回收并汇报结果』三个阶段用 `TaskCreate`/`TaskUpdate` 推进状态（pending → in_progress → completed），让任务列表 UI 实时反映进度。异步子会话、异步下载、异步发布、异步构建、CI 轮询等同等待处理；禁止把裸 `run_in_background` 后台进程当作唯一进度可见手段。
   - 明确该小节是「同步已完成 + 异步在跑」的收口信号：不得写成“任务未完成”、不得升级为 `blocked`/`manual_handoff`、不得触发「后续内容」、不得让用户误判会话被阻断。
   - 后台异步任务的小节不属于“扩散性后续”，与「后续内容」的合法条件互不影响；但若同步任务本身存在计划内未完成必需项，仍按「后续内容」条件处理。
9. 本次改动点（有改动时；不存在真实阻断且没有知识引用小节时放在总结最后）
10. 知识引用（`knowledge-flow` 的引用台账非空时必须；不存在真实阻断时作为总结最后一节，位于本次改动点之后）
11. 任务阻断收口（仅真实 `blocked` 或 `manual_handoff` 时必须出现，并作为总结最后的最终状态区）

> 后续内容（条件节，不占编号）：仅非阻断状态下存在原执行计划内未完成必需项，或用户明确要求后续建议时出现；无合法后续时强制不输出，也不得输出“等待用户新指令 / 无需继续动作”占位文案。存在时插在第 8 项之后、第 9 项之前。

### T1 标准档紧凑结构（主节 ≤ 4 个）

容器开场（`---` + `# 📋 本轮总结` + 状态摘要行）→ `> 一句话结论`（信息密度主行：结果 + 关键数字/文件 + 验证状态）→ `## 🛠 执行证据`（1-3 条，含关键验证动作与结果）→ `## 🔧 方案与结果`（合并原“方案与根因”与“结果与结论”：方案一句话 + 根因或触发原因一句话 + 结果与验证状态一句话；存在 ⚠️ 需求理解偏差时在本节末尾附一行偏差说明；存在待裁定事项时严格附规范的四要素闭环：裁定点+加粗建议+选项选择+默认最安全兜底）。之后按「通用尾部顺序」接条件尾节。T1 不输出图形化总览，不单列问题定义与验证小节。

### 决策研判与建议结构（极简收敛）

面向字段切分、架构选型、表设计建议、口径确认等任务，完全脱离工程执行模板，强制使用以下两种形态之一：

- **简单建议（极简断言）**：
  容器开场（`---` + `# 📋 决策结论`）→ `> 建议：<拆 / 不拆 / 选型结论>` → `> 核心理由：<1句话点透>`。无其他任何小节，篇幅 ≤ 3 行。
- **复杂建议（三段式极简结构）**：
  容器开场（`---` + `# 📋 决策建议`）→ `### 1. 待判断字段/决策点`（直击目标）→ `### 2. 作用与跨成员影响`（业务定位 + 跨表/跨成员波及与矛盾）→ `### 3. 明确建议与倾向`（加粗明确倾向 + 1-2句硬核依据；若有多方案，列出方案选项供用户选择）。篇幅一屏以内，严禁插入执行证据或排查流水账。

### T0 极简档（最短收口）

容器开场 → `> 一句话结论`（含验证状态）。之后按「通用尾部顺序」接条件尾节。省略执行证据、要解决的问题、方案与根因、结果与结论、图形化总览。

### 通用尾部顺序（所有档位共用）

一句话结论块之后依次为：`🔄 后台异步任务`（若启动）→ 后续内容（仅合法）→ `📦 本次改动点`（若有改动）→ `📚 知识引用`（若台账非空）→ `⛔ 任务阻断收口`（若真实阻断，永远最后）。未命中的条件尾节整节省略，不输出空表或占位行；T0/T1 命中条件尾节时完整输出对应小节字段，不因档位降级而缺字段。

> `任务阻断收口` 只由本 skill 渲染。审查、验收、验证、失败恢复和合规闸门只能按共享契约提供或校验结构化事实，不得生成第二套用户可见的阻断模板、后续内容或解决计划。

> `任务阻断收口` 必须完整渲染共享契约字段，其中“用户授权操作”必须突出显示“请直接回复：`同意授权`”或“请直接回复：`暂不授权`”，并注明授权边界；只渲染最近一条、唯一有效、仍未解除的 `BLK-*` 记录。

> 不再单列“函数注释核对”节点：函数注释核对仍由 `code-change-finalization-gate-rules` 与 `comment-rules` 作为闸门内部执行证据完成，但不在最终总结中展示为节点。

## 反重复铁律与文字风格约束（强制）

### 决策研判三反铁律（反铺垫、反探查流水账、反重复论证，强制）

针对字段判断、架构选型、表拆分与设计建议等场景，强制执行三反铁律，任何一条违反应判定 `FAIL` 阻断：

1. **反铺垫（零废话开场）**：
   - 严禁出现“经过深入分析”、“针对您提出的关于某某的问题”、“为了保证高可用与扩展性”等仪式性前戏；
   - 第一行直接定调：简单场景直奔“建议：拆/不拆”，复杂场景第一段直接列出“待判断字段/决策点”。
2. **反探查流水账（严禁 Proof of Work 倒苦水）**：
   - 严禁在总结中叙述排查代码、SQL查询、文件翻找的过程（如“查看了某某代码第几行发现”、“查了数据表有这几个列”、“起初考虑了方案A后来排除了”等自言自语式排查记录）；
   - 工具探索与排查过程只留在工具调用和思考中，面向用户的总结**只留系统现状、跨成员影响与确定性建议**。
3. **反重复论证（一次讲透）**：
   - 决策依据有且仅在第 3 段“明确建议与倾向”中表达一次（1-2句硬核理由点透本质，如读写热度不均、行膨胀、反序列化损耗）；
   - 严禁在第 1 段铺垫一遍原因、第 2 段解释一遍理由、第 3 段又复述一遍论据的车轱辘话。
4. **决策弹性（简单极简断言，复杂选项抉择）**：
   - 简单场景（二选一/确定性/用户要求直说）：直接极简断言（如“**建议：拆**。理由：...”），篇幅 ≤ 3 行，零模板包袱；
   - 复杂场景（多表关系/多方案）：严格执行三段式，并给出明确倾向（推荐方案加粗），同时清晰罗列方案 A/B 供用户定夺，绝不模棱两可。

### 待裁定事项处理铁律（建议、选项与默认最安全兜底闭环，强制）

无论是工程执行任务收口、周期/阶段边界、任务中断点，还是独立结论区，凡列出“需用户裁定的事 / 待决策项 / 阻断决策”，**严禁“只抛问题、不给建议”的传声筒行为**。Agent 作为具备专业判断力的工作搭档，必须体现主见（带着答案回来，而不是带着问题回来）。

每项待裁定事项必须严格落实**四要素闭环**：

1. **裁定点与影响**：一句话精准锚定决策争议点，明确为什么必须现在定夺（阻塞什么后续动作、有什么业务/技术波及）；
2. **明确建议与理由（加粗倾向）**：Agent 必须亮出鲜明判断（加粗标注，如“**建议：改为包级单例共享**”或“**建议：立即重启服务触发 AutoMigrate**”），并用 1 句话讲透硬核技术/业务依据，绝不模棱两可；
3. **选项选择（清晰 A/B 方案）**：必须提供简洁、互斥的方案选项供用户选择，并明确标注推荐项：
   - **选项 A（推荐）**：<方案描述> —— *<核心收益与操作>*
   - **选项 B（备选）**：<替代方案描述> —— *<代价与适用条件>*
   （若是操作确认类，如重建表或服务重启：`选项 A（推荐）：重启服务完成自动迁移；选项 B：手动执行 DDL 脚本`）。
4. **默认最安全兜底方案（防死锁与盲目冒进）**：必须明确声明“**若未做裁定（如直接回复‘继续’或未选选项），默认按【选项 X / 保守安全方案】推进**”，并说明其安全性保证（原则：**防限流、防击穿、防破坏性误删、改动影响最小、保持系统安全稳定**）。

用户只需直接回复“选 A”、“按推荐”或直接回复“继续”，系统都能有明确且安全的方向推进，既把决策权交给用户，又彻底避免因未裁定导致的停滞死锁或无序冒进。

### 反重复铁律

- 任何事实（文件路径、命令、数字、结论、验证状态、改动点）在总结中最多出现一次；首次出现处为权威位置（通常是一句话结论或执行证据），其余小节只引用其含义，不复述原文。
- T2 的「方案与根因」「结果与结论」不得复述一句话结论或执行证据已记录的同一事实；T1 的「方案与结果」只写增量；T0 除结论行与条件尾节外无其他复述机会。
- 例外：「知识引用」小节的登记行按台账口径重复笔记名属于登记需要，不算重复；异步小节的任务标识属于字段要求，同样豁免。
- 关键事实不得因反重复而丢失：验证状态必须出现在一句话结论或执行证据中，改动文件必须出现在一句话结论或改动点中，二者择一即可，不要求双写。

### 结论为主

- 一句话结论是信息密度主行，格式 = 结果 + 关键数字/文件 + 验证状态（如“已修复 `auth.go:42` 空指针，3 个单测通过 ✅”），不是单纯的口号句。
- 用户只读一行时，结论行就能给出核心结果；其余小节是审计证据，不是结论的展开重复。

### 文字风格（去 AI 味）

- 砍填充词与空话连接词：删除“此外”“总体而言”“值得注意的是”“显而易见”“在此基础上”等，不损失信息量。
- 用具体名词和数字替代空泛形容：“p99 从 320ms 降至 90ms”而不是“性能大幅提升”；“迁移 6 个测试文件”而不是“完善了测试体系”。
- 禁止 AI 套话：禁止排比式总结（“不仅…而且…更…”连用）、禁止小节末尾加意义升华句、禁止用感叹号堆情绪。
- 结论先行：任何小节的第一句是该小节的重点句，细节后置。

## 图形化优先规则（强制）

### 适用性与图形选择

| 内容特征 | 默认表达 | 使用要求 |
|---|---|---|
| 多步骤处理、闸门、分支、回滚 | Mermaid `flowchart` | 突出主流程、关键分支和停止条件 |
| 跨角色、跨服务、异步调用、工具链 | Mermaid `sequenceDiagram` | 展示调用顺序、责任边界和结果回流 |
| 状态迁移、阻断、恢复、验收状态 | Mermaid `stateDiagram-v2` 或状态流转图 | 展示状态、进入条件和恢复路径 |
| 任务依赖、执行阶段、文件或模块影响面 | Mermaid `flowchart` / 依赖图 | 展示执行顺序、依赖关系和最大推进边界 |
| 有真实数字对照或趋势 | 当前渲染端可靠支持时使用 Mermaid 图表；否则在图形化总览中写 `N/A + 原因 + 证据`，并用 markdown 表格承载数据 | 不得把表格伪称为图形，也不得虚构、补齐或推算未验证数据 |
| 单文件简单修改、单命令说明、纯问答 | 不强制生成图 | 保持简洁，必要时使用表格或列表 |

- 复杂任务默认输出 1 张主图；只有第二张图表达不同且必要的信息时才允许增加，总数最多 2 张。
- 图形只表达本轮已确认事实，不得补造不存在的动作、角色、状态、结果、数字或依赖。
- 流程、时序、状态、依赖和执行关系优先经宿主内联可视化通道渲染（WorkBuddy Visualizer / `show_widget` 等）；仅当宿主不支持内联可视化时降级使用 Mermaid；表格是结构化数据的补充，不得把“只有表格”宣称为已完成图形化总览。
- 真实图片只用于 Mermaid 无法准确表达的视觉证据或已有产物，不替代流程、时序、状态和依赖图。

### 图形标注与一致性

每个 Mermaid 图形前必须紧邻写明：

- `图形目的：...`
- `关联 ID：...`

并同时满足：

- 图形代码块使用 `mermaid` 语言标记，不得嵌套进 `text`、无语言代码围栏或 HTML。
- 图形必须非空，节点、参与者、状态和连线完整；图内术语必须与正文、证据和稳定 ID 一致。
- 节点、边、条件标签中若需表达比较运算符（`<`、`>`、`<>`、`<=`、`>=`）等会被误判为 HTML 标签的符号，必须转义为 HTML 实体（`&lt;`、`&gt;`）或替换为文字/符号表达（如 `!=`、`≠`、"不等于"），禁止在标签内裸写，避免被当作畸形标签导致整图解析失败。
- 图形位于状态摘要和一句话结论之后、`## 🛠 执行证据` 之前，确保用户先看到主链路再阅读细节。
- 若复杂任务已进入图形适用性判断但 Mermaid 无法准确表达、数据不足或当前渲染能力不可靠，输出 `图形化表达：N/A`、`原因：...`、`证据：...`；不得用无意义占位图绕过。
- 明确属于简单单点任务时可以省略整个图形化总览小节，不要求输出形式化 N/A。

## 图形渲染通道与可读性约束（强制）

> 用户反馈的核心痛点是「图表小、看不清」。根因是 Mermaid 代码块在聊天容器中被**整图等比缩放**，`%%{init}%%` 字号配置只影响节点内文字的相对大小，无法对抗容器缩放。本节分两层解决：优先切换渲染通道（内联可视化），降级通道才用 Mermaid 并遵守可读性硬约束。

### 渲染通道优先级（第一优先）

- 宿主工具列表存在可视化 / 绘图类工具（WorkBuddy Visualizer / `show_widget` 等）时，图形化总览**必须**优先经该通道输出内联 SVG / 组件图形：画布定宽（680px）不随内容缩放、正文文字 ≥ 13px、节点 ≤ 5 个，天然满足「用户一眼看清主链路」。
- 经可视化通道输出后，**不得**在 markdown 正文再输出同一张 Mermaid 图（双图冗余）；「图形目的 / 关联 ID」标注照常写在正文、紧邻图形说明。
- 仅当宿主不支持内联可视化（纯文本 / CLI 环境）时，降级为 Mermaid 代码块，并遵守下方「Mermaid 降级可读性约束」。
- 「不依赖 HTML 渲染」红线仅约束 markdown 正文（禁止裸 `<div>` / `<svg>` 标签污染正文流）；宿主原生可视化工具调用属于受支持渲染通道，不违反红线。

### Mermaid 降级可读性约束（仅降级通道适用）

> Mermaid 默认按节点数自适应字号与节点尺寸，节点过多时单图节点挤压、文字字号过小，违反「用户一眼看清主链路」的目标。本节只规定降级通道的可读性硬约束，不引入 HTML 缩放或客户端依赖，与「统一使用 markdown、不依赖 HTML 渲染」红线保持一致。

- **方向选择**：复杂流程图默认用 `flowchart LR`（左到右），禁止默认 `TD`（顶到底）——横向布局节点不会被纵向挤压，单节点尺寸更易放大；只有状态迁移或单一链路（≤ 5 节点）允许 `TD`。
- **节点数量上限**：单图节点 ≤ 8 个；超过时按主要阶段用 `subgraph` 分组（每个 `subgraph` 是一个语义段，标 `direction LR` 强制横排），或拆成主图 + 阶段图（总数仍 ≤ 2 张）。
- **节点文字长度**：每个节点 ≤ 8 个汉字 / 5 个英文单词；长描述放正文里，节点只保留关键词。禁止把完整句子、命令、代码、多行字段塞进节点（`<br/>` 强行换行也只能用于 2 行以内）。
- **基础字号与间距**：每张 Mermaid 图必须在首行配置 `%%{init: {'themeVariables': {'fontSize': '20px', 'fontSizeLabel': '16px'}, 'flowchart': {'nodeSpacing': 50, 'rankSpacing': 70}}}%%`（**Mermaid 原生 init 配置，不是 HTML**），强制基础字号 ≥ 18px、节点间距 ≥ 50、层级间距 ≥ 60。
- **subgraph 分组**：主流程 > 5 个节点时必须用 `subgraph` 把同阶段节点包成逻辑段（如「裁决」「落盘」「验证」），避免平铺成扁平长链；subgraph 标题同样遵循节点文字长度约束。
- **图总数硬限**：仍遵守「最多 2 张」现有规则，`subgraph` 不算独立图。

### 降级通道自检（Mermaid 发送前必跑）

输出 Mermaid 图形前、发出前必须自检：

0. 是否已确认宿主**无**内联可视化工具？若工具列表存在 Visualizer / `show_widget` 等却仍输出 Mermaid，直接 FAIL（违反渲染通道优先级）。
1. 是否用了 `flowchart LR`（或合理的 `sequenceDiagram` / `stateDiagram-v2`）？
2. 节点数是否 ≤ 8？
3. 每个节点文字是否 ≤ 8 个汉字 / 5 个英文单词？
4. 是否已加 `%%{init:...}%%` 基础字号与间距配置？
5. 超过 5 个节点是否用 `subgraph` 分组？

任意一项不满足，先改写 Mermaid 源码再输出，不得以「渲染端缩放」或「用户可以放大」为由放行。

## 总结视觉规范（强制）

最终总结必须与上方推理过程、中间进度在视觉上明确分界，并采用统一的严谨 markdown 排版，让用户一眼分辨“哪里开始是总结”。本节只约束排版与分界，不改变「输出要求（固定顺序）」的字段与顺序。

### 视觉分界

- 总结区块前必须插入一条 `---` 水平分隔线，与推理过程、工具叙述、中间进度切开。
- 分隔线下用固定一级主标题作为容器起点：`# 📋 本轮总结`（一级标题，字号最大、天然加粗；标题文案固定，便于辨认）。
- 容器外不得再散落总结性结论；中间进度（首条命中检查两行、工具调用叙述）不套用总结容器。

### 排版要求

- 紧随主标题输出一行状态摘要：`**命中检查:通过** · <闸门>:PASS ✅`（存在合规闸门时带上结论）。
- 用一个 `>` 引用块写“一句话结论”，让核心结果最突出。
- 固定字段一律用二级标题 `## ` 小节承载，字号明显大于正文且天然加粗；形成“一级主标题 > 二级小节标题 > 正文”的三级字号层级，层级之间字号必须有明显区分。
- 标题必须使用 markdown 标题语法（`#` / `##`），禁止用加粗文本冒充小标题；确保标题比正文更大且加粗。
- 小节可配区分性 emoji（条件小节仅在实际出现时使用）：📊 图形化总览 / 🛠 执行证据 / 🎯 要解决的问题 / 🔧 方案与根因（T1 为 🔧 方案与结果）/ ✅ 验证 / 📌 结果与结论 / 🔄 后台异步任务 / 📦 改动点 / 📚 知识引用；T0 极简档只出现实际输出的条件尾节 emoji。
- 多文件改动、需求对照、状态对照优先用 markdown 表格，不堆长串冒号列表。
- 状态用徽章式标记：通过 ✅、警告 ⚠️、失败 ❌、阻断 ⛔。
- 无真实阻断时，末尾顺序按引用台账是否非空分流：台账非空时「知识引用」放在所有内容节点的最后、「本次改动点」紧邻其前；台账为空时「本次改动点」放在最后。真实阻断时两者都置于最终阻断区块之前。
- `knowledge-flow` 的检索与沉淀事实统一由「知识引用」小节的两张表承载；该小节只列引用台账条目，不得输出笔记正文、不得摘录笔记片段，也不得在其它小节重复同一事实。
- 不再单列“函数注释核对”节点；该核对作为闸门内部证据完成，不在总结展示。
- 统一使用 markdown，不依赖 HTML 渲染：HTML 在 Claude Desktop、纯 CLI、Codex 等多数 agent 不渲染，会退化成原文噪声并破坏机器解析；视觉靠语义层级（`#` / `##` 标题、`---` 分隔线、表格、`>` 引用块、徽章 emoji）而非绝对字号，字号由各 agent 渲染端决定，不在输出里塞裸 HTML 标签。宿主原生可视化工具（WorkBuddy Visualizer / `show_widget`）调用不属于「正文内嵌 HTML」，图形化总览按「渲染通道优先级」小节执行。
- 普通说明、方案、流程、总结、审查报告、线程拆分和状态回报必须使用普通 Markdown 段落、列表、表格或引用块；不得用 ` ```text `、无语言代码围栏、缩进代码块或 HTML 包裹整段自然语言输出。
- 代码围栏只用于真实代码、命令、配置片段、日志片段、JSON/YAML 等需要等宽保真的内容；若只是为了展示可读结构，应改用 Markdown 列表或表格。
- 字段顺序严格遵循当前档位的小节集与「通用尾部顺序」；T2 图形适用时必须先于执行证据和长段文字，视觉规范不得省略当前档位必填项。
- 若存在真实阻断，`## ⛔ 任务阻断收口` 必须位于总结最后，替代“后续内容”；本次改动点与知识引用（如有）必须置于其前，避免任何文本覆盖最终状态。

## 权责边界与不负责事项

- 只负责“最终总结结构完整性”，不替代业务执行。
- 不替代需求澄清、Bug 根因分析、编码实现、测试执行。
- 不要求虚构字段；不存在的条件字段应明确“本轮不适用”或按规则省略。

## 执行通过 / 驳回标准

- `SUMMARY-GATE-PMW-001` 是总结闸门硬失败条件：存在任何未决 `request_user_input` / `WAITING_DECISION`，包括空答案、缺失答案或宿主隐式超时未解决时，不得输出冻结集合内的任何可见内容（`commentary`、`limited_plan`、`pending_summary`、`proposed_plan`、`final`、`summary`、`final_answer`、`task_complete`、`result_and_conclusion`）或“结果与结论”；必须回到同一选择框重发循环。
