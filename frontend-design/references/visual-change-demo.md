# 视觉改动对比 Demo 规则

> 归属 owner：`frontend-design`。本文件是"改样式 / 改组件 / 调 CSS 前必须先给新旧对比 demo"的唯一权威细则。
> `frontend-ui-visual-rules` 只保留一句引用，不复制正文，避免形成第二套口径。

## 要解决的问题

样式改动的描述天然有损。`阴影改成更柔和`、`间距收紧一档`、`圆角调小` 这类说法，双方各自脑补的画面一定不同；等生产代码改完、页面刷新出来才发现方向不对时，返工成本已经是初始沟通的数十倍。
对比 demo 的作用不是"展示代码"，而是把一次视觉判断从"读文字想象"降级成"看两个画面选一个"，让用户在成本最低的时点否决错误方向。

## 一、触发面与免触发面

**必须出 demo**（改完界面看起来或动起来会变）：

| 类别 | 举例 |
|---|---|
| 尺寸与间距 | 宽高、padding、margin、gap、行高、字号、字重 |
| 颜色与材质 | 主色、背景、边框、透明度、阴影、模糊、渐变 |
| 形状 | 圆角、描边粗细、图标形状 |
| 布局结构 | 分区重排、列数变化、密度调整、栅格与断点 |
| 组件外观 | 换变体、换组件、改状态样式（hover / focus / 禁用 / 空态） |
| 动效 | 时长、缓动、弹簧参数、进出场顺序 |

**免 demo**（满足任一即可，且必须在回复里写明依据）：

- 用户已在指令里给出无歧义目标值，例如"圆角从 8px 改成 4px""背景换成 #0F172A"——目标唯一，无判断空间。
- 纯内部重构：改类名、抽组件、调样式层归属，渲染结果不变。
- 看不见的改动：接口接线、状态归属、组件拆分、类型修正。
- 新增页面 / 新增组件且不存在旧版本：无 before 可比，按下方 `M4` 处理。

免 demo 必须说明理由，不允许"我觉得这个不用看"就跳过。

## 二、对比形态四级

按场景选最小可行形态，不为了形式升级复杂度。

| 形态 | 做法 | 适用 |
|---|---|---|
| `M1` 单文件左右并排（默认） | 一个 HTML，同一份 DOM 复制两份，只切样式类，中间加分隔标签 | 绝大多数样式改动 |
| `M2` 单页 toggle 切换 | 一个 HTML，一个开关切换 before / after 类 | 页面级改动、整块布局重排 |
| `M3` 静态并排截图 | 真实页面同尺寸、同视口截两次，横向拼接 | 依赖登录态、真实数据、真实字体加载，单文件无法复现 |
| `M4` 仅 after | 只给新样子 | 新增页面 / 新增组件，无 before |

选择顺序：能用 `M1` 就不用 `M2`，能用 `M1`/`M2` 就不用 `M3`。`M3` 成本最高，只在单文件无法复现真实效果时才用。

## 三、可判定性硬约束

demo 的价值取决于"变化是否只来自样式"。以下几条任一不满足，用户就无法做出有效判断：

- **完全同源对照**：两版必须共用同一份文案、同一份数据、同一视口尺寸。内容或宽度不同，用户分不清差异来自样式还是内容。
- **带真实上下文**：必须放进真实场景里看——真实字号、真实内容密度、真实的相邻元素与容器宽度。只画一个孤立按钮，用户会在错误的尺度上判断，落地后仍然不对。
- **覆盖受影响状态**：hover、focus、禁用、空态、长文本溢出、暗黑模式——涉及哪个就画哪个。默认态好看但 hover 崩掉的改动，等于没验证。
- **差异可指认**：改动点多处时，在 demo 里标注改了什么，不要让用户自己找茬。

## 四、保真约束（最容易失守的一条）

demo 必须长在项目自己的样式上，禁止手搓近似样式。
用户判断的是"这个改动放进我的产品里好不好看"，不是"这个改动在裸 HTML 里好不好看"。demo 一旦自带一套外观，通过与否都不代表真实效果。

### 样式来源优先级（从上到下取第一条可行的）

| 优先级 | 做法 | 说明 |
|---|---|---|
| 1 | `<link>` 引入项目真实构建产物 CSS | 如 `dist/assets/index-*.css`；颜色、字距、圆角、阴影、reset 全部原样继承，连浏览器默认样式差异也一并消除 |
| 2 | `@import` 项目 token / 主题源文件 | 如 `tokens.css`、`variables.scss`、Tailwind 编译产物；项目未构建但 token 文件可直接用时走这条 |
| 3 | 把 demo 挂进项目跑真实组件 | 框架组件（Vue/React SFC）无法在独立 HTML 里运行时，在项目内建临时调试路由（如 `/__demo`）用真实组件渲染；用完删除 |
| 4 | `M3` 真实页面截图 | 依赖登录态、真实数据或复杂运行时，独立 HTML 无法复现时，直接在真实页面上改样式截图对比 |
| 5 | `getComputedStyle` 抽取关键属性 | 以上都不可行时的兜底：从真实页面取 `font-family` / `font-size` / `line-height` / `color` / `background` / `border-radius` / `box-shadow` / `padding`，写进 demo，并在文件头注明「取自 <页面路径>，<日期>」 |

除第 5 档外都要求复用**项目真实 class 名与 DOM 结构**：从真实页面复制 HTML 片段，保留原有 class，不改名、不简写、不重排。

### 禁止

- 凭记忆写 token 名或变量名（写错会静默回退到浏览器默认值，比不写更危险）。
- 肉眼估算色值、圆角、阴影参数。
- 用浏览器默认字体冒充项目字体。
- 抄一份"看起来差不多"的样式另起一套 class。

### before 版是校准基准

**改前的样子必须与真实页面近乎一致。** 出完 demo 后先自校一次：把 before 版与真实页面同尺寸并排看，确认没有肉眼可见差异，再交给用户。

理由：before 版就是"项目现在长什么样"的声明。before 偏了，用户看到的差异里就混进了 demo 自身的失真，他否决 or 通过的都是假象，after 的判断随之失效。校准动作的成本很低——并排看一眼即可，但它决定整份 demo 有没有意义。

### 真实字体与资源必须加载

引入真实 CSS 后仍要确认字体、图标字体、背景图真的加载出来了：产物 CSS 里的资源路径可能因 demo 所在位置而失效。
判断方法：打开 demo 看字体是否与真实页面一致，或检查浏览器网络面板有无 404。字体没加载出来的 demo，用户判断的是错误画面。

失守后果比"不出 demo"更严重：demo 显示通过，落地却不符，用户会认为已经确认过，问题被推迟到验收甚至线上才暴露。

## 五、闸门语义

- demo 未获用户确认前，**不得修改生产代码**。允许先写 demo 文件，不允许先改业务文件再补 demo。
- 用户提出修改时，**回到 demo 迭代**，不回生产代码上反复试错。生产代码只在方向确认后改一次。
- 用户直接说"就按这个改，不用看 demo"时按用户指令执行，但在回复里记一句"按用户指令跳过对比确认"。
- 用户已给出无歧义目标值（见第一节免触发面）时同样跳过，不必为了流程完整硬造 demo。

## 六、产物纪律

- demo 是**临时产物**，不是交付物。收口时按 `runtime-process-cleanup-rules` 清理，或移到项目约定的临时目录，不留在源码树、不提交 Git。
- 渲染通道按当前环境能力降级，不绑定单一 agent 工具：
  1. 宿主提供可视化预览能力 → 直接用；
  2. 否则写本地单文件 HTML，给出可打开的绝对路径，让用户自己在浏览器打开；
  3. 依赖登录态或真实数据时 → 用 `M3` 截图，并说明截图来源页面与视口尺寸。
- 只给路径不给说明不算交付：要同时说明"哪个是改前、哪个是改后、改的是哪几处"。

## 与其他 skill 的边界

- `design-review:visual-regression-review`（宿主插件 skill，非本仓库目录）面向**改动后**的回归比对（基线 vs 现状），本文件面向**改动前**的方案确认，两者不重叠。
- `frontend-component-rules` 管组件工程边界（拆分、props、状态归属），不涉及视觉确认，本文件不介入。
- 本文件不判断视觉好不好看，只规定"改动前必须先让用户看见两个画面"这个流程。
