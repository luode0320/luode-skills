#### Go 审查原则
> 精准优先于召回：只报告改动代码及可达上下文中很可能是真实缺陷的问题。误报会消耗审查者的信任。将正确性和安全问题视为阻断级；纯风格建议为非阻断级。专注于那些普通格式化和确定性工具无法覆盖的语言特定风险。

在报告非局部断言前，使用 `file_read` 和 `code_search` 建立相关的调用点、所有权、同步和输入边界。不要仅凭函数名或包导入推断并发调用、攻击者控制、资源所有权或错误契约。不要重复 `go vet`、`Staticcheck`、`go test -race`、编译器或 `gofmt` 已经能可靠检测出的问题，除非 diff 显示了这些工具不会表达的具体的用户可见的后果。

#### 错误、Panic 和 API 契约
- 调用返回的错误被忽略、覆盖或转换为隐藏失败的成功/默认值。故意的最佳努力操作只有在忽略的失败是安全的且从文档或上下文中明显可见时才可接受。
- 错误包装丢失了原始原因（调用方需要 `errors.Is`/`errors.As` 时使用 `fmt.Errorf("...: %v", err)`）、包装了 nil、返回了误导性的哨兵值、或在公共边界暴露了内部/敏感详情。当需要保留错误身份时优先使用 `%w`。
- 在请求、工作线程、库或清理路径中，本可以返回可恢复错误的地方使用了 `panic`、`log.Fatal`、`os.Exit` 或 must 风格的辅助函数。不要标记不可能发生的内部不变量或已文档化的程序员契约。
- 延迟清理覆盖了主错误、丢弃了有意义的 `Close`/`Commit`/`Rollback` 错误、或在清理使结果无效后返回了成功。

#### Nil、接口和值语义
- 类型化的 nil 指针、map、slice、函数、channel 或错误存储在非 nil 接口中，随后被当作不存在处理。先检查具体赋值和所有接口检查。
- 对 nil map 进行写入、非故意使用 nil channel（会永远阻塞）、或在输入或构造器实际可能产生的路径上解引用 nil 指针。
- 在首次使用后复制包含 `sync.Mutex`、`sync.RWMutex`、`sync.Once`、`sync.Pool`、`atomic` 状态或其他不可复制同步原语的值。当该值可能已被首次使用时，标记通过值接收者、赋值、返回、append、map 值或序列化的复制。
- 值接收者或复制在调用方期望共享状态时静默地仅修改副本，特别是持有 maps、slices、指针、锁或原子状态的 struct。不要标记有意的不可变值对象。
- `sync.Once` 用于失败后需要重试的工作。`Once.Do` 将其 `func()` 视为已完成即使它 panic 了；该闭包捕获的错误也不会让后续的 `Do` 重试它。

#### 上下文、Goroutine 和取消
- 在应该继承调用方的截止时间、取消、值或追踪时，使用 `context.Background()`/`TODO()` 或全新的 context 启动了请求范围的工作。独立的后台工作是合法的。
- `context.Context` 存储在 struct 中或用自定义上下文接口替代，而本应显式作为第一个参数传递。只在必需的外部接口固定了签名或所有权/生命周期明确时才允许。
- `context.WithCancel`、`WithTimeout` 或 `WithDeadline` 的 cancel 函数在派生上下文不再需要后未被调用，除非所有权转移和最终取消是显而易见的。
- 在请求/工作者路径上，当依赖可能挂起时，缺少取消或截止时间的阻塞 I/O、等待、重试、select 或循环。先确认操作可以比调用方存活更久。
- 由于在 channel、锁、I/O 操作或无限制重试上永远等待而可能比其所有者存活更久的 goroutine；缺少关闭机制；或者在需要时没有让错误/完成被观察到的方式。
- 发射后不管的 goroutine 捕获了请求局部的可变数据、在处理器返回后写入响应、在进程边界 panic 而没有恢复、或与清理产生竞争。不需要加入独立的后台工作。
- goroutine/callback 中的循环变量或可变外层变量捕获，其中闭包可能观察到之后的值。验证模块的 `go` 指令以及是否每次迭代都创建了新变量；Go 1.22 语言语义改变了 range 循环变量，而较旧模块语义可能保留共享变量。

#### Channel、锁和共享状态
只有在可达并发的证据条件下才报告竞态或死锁；检查周围的调用点（如果不是局部的）。不要标记不可变数据、per-goroutine 本地变量或所有权保证的同步。

- 对 maps、slices、指针、counter、缓存或复合状态的未同步并发读/写；可以交错执行的检查-执行序列。
- 在持有 mutex/RWMutex 时跨阻塞 I/O、channel 操作、callback、网络/数据库调用或长 CPU 工作，而另一条路径需要该锁才能推进。先检查锁顺序再声称死锁。
- 在修改受保护数据时使用了 `RLock`；对其同伴保护字段的未加锁修改；或对同一状态混合使用原子和非原子访问。
- 由于对端可能停止、缓冲区可能填满、或未选择关闭/取消，发送/接收可能无限期阻塞。不要标记有已证明对端的同步握手。
- 多个可能的 channel 关闭者、关闭已关闭 channel 的风险、或双重关闭。先确定发送者/所有者责任。
- 忙等待、丢弃必要工作或绕过取消的 `select` defaults；没有 backoff/取消的无限重试。
- WaitGroups 中 `Add` 与 `Wait` 竞态、缺少 `Done`、首次使用后复制、或无法完成的计数器。

#### 定时器、Ticker 和资源生命周期
- 一个定时器/ticker 被其所有者保留并在工作结束后继续运行，因此它可以触发、tick、保留可达状态或保持关联的工作存活。不要仅将缺失 `Stop` 报告为 GC 泄漏：Go 1.23+ 可回收未引用未停止的定时器/ticker；旧版语义和 `GODEBUG=asynctimerchan=1` 不同。
- 在重复/select 循环中的 `time.After`，只有在有成本证据时才报告：Go 1.23 之前语义有许多未过期的定时器、高频分配路径或保留的定时器所有者。在 Go 1.23+ 上不要单独称之为泄漏。
- 假设跨 Go 版本行为一致的定时器重置/停止代码。Go 1.23+ 上的 Channel 定时器在 `Reset`/`Stop` 后消除了过期值；旧版语义需要停止并 drain 的协调。`AfterFunc` 的 reset/stop 不会等待已启动的回调，因此回调可能重叠，除非已同步。
- `http.Response.Body`、`sql.Rows`、文件、socket、压缩 reader/writer、事务、锁或其他可关闭资源在获取后未在所有可达路径上关闭。不要标记交给调用方/框架拥有关闭的资源。
- 循环内的 `defer`，其外层函数可运行多次迭代或无限期运行，特别是当它延迟关闭文件、响应体、rows、锁或事务直到函数返回时。不要标记小规模静态有界循环或每次迭代返回的辅助函数。
- `sql.Rows` 迭代在循环后省略了 `rows.Err()`，或者当迭代可以提前停止时 rows 未关闭。
- 缺少 body 清理、请求上下文或超时的出站 HTTP 调用在服务器路径上可能挂起；`Begin` 后缺少 rollback/commit 的返回路径上的事务。

#### 集合、切片、字节和数值边界
- 返回、缓存或传递一个 slice/map/byte buffer，其底层存储稍后被重用/修改，改变了另一所有者观察到的数据。确认所有权；零拷贝 API 可能是有意的。
- `append` 到别名字调用方/共享底层存储的 slice，其中修改会逃逸；保留巨大 buffer 的一个 tiny 子 slice，其中保留的内存很重要。
- 在空/边界输入上超出边界的可达索引、切片、长度算术或容量假设。
- 可能溢出、截断、有符号/无符号比较、大小计算、分配或偏移算术使负输入变成巨大尺寸的整数转换、收窄、减法。考虑架构相关的 `int` 宽度。
- 并发或在返回的输出依赖于其生命周期时重用了可变 buffer、编码器、解码器、扫描器或包/全局状态。

#### 安全敏感边界
在报告前确认攻击者控制或信任边界。优先给出具体漏洞路径和修复建议。

- 从不可信输入组装的 SQL、shell 命令、URL、路径、header、模板、正则表达式或序列化数据，没有适当的参数化、验证、转义、白名单或 scheme/host/path 限制。`os/exec` 参数数组比 shell 更安全，但参数仍可能需要验证。
- 路径遍历、符号链接跟随、不安全的归档提取、不安全的临时文件、或暴露/覆盖文件的权限/所有权假设。
- 为 HTML 使用 `text/template` 替代 `html/template`、从不可信内容构造可信模板类型、或上下文不适当的转义。默认情况下不要标记非 HTML 输出的 `text/template`。
- 通过出站 URL 的 SSRF 或凭据泄漏：不可信目的地、缺少必需的白名单、重定向到内部服务、或跨主机转发敏感 header。
- 密码、凭据、令牌、授权 header、私钥或敏感个人数据被记录、在错误中返回或嵌入源代码/配置。
- `math/rand` 或 `math/rand/v2` 用于安全敏感的 key、token、session ID、重置码、nonce 或盐；应使用 `crypto/rand` 或经过审查的加密构造。不要标记模拟、采样、负载均衡或测试。
- `reflect`、`unsafe`、cgo、不安全的指针转换、手动内存/布局假设或自定义加密，没有狭窄的文档化不变量和必需的边界/生命周期检查。不要单独标记普通的反射。

#### 测试和审查范围
- 默认审查生产 Go 代码。`*_test.go` 文件默认被 OCR 的路径过滤器排除，仅在用户配置明确包含时审查。
- 仅为具体的已变更的正确性、并发、错误或边界故障模式建议测试。优先使用确定性测试；不要要求基于定时的不确定竞态测试。
- 不要将格式、导入顺序、命名偏好、简化或已被 `gofmt`、`go vet`、`Staticcheck`、linter 或编译器强制执行的建议作为阻断性发现。
