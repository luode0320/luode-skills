#### 明显的拼写或拼写错误
- 变量名、函数名、类名或模块名在声明处的拼写错误；不要报告引用处的拼写错误
- 日志或异常消息中包含影响可读性的拼写错误的字符串

#### 死代码
- 永远不会被执行的代码块（条件始终为 false 的分支、return/raise/break/continue 后的代码）
- 声明但从未读取或引用的变量、导入或函数参数
- 大块被注释掉的代码且没有明显的保留意图
- 不要在 `.pyi` 存根文件中报告未使用的导入、变量或参数；存根声明了一个它从不执行的接口

#### 可变默认参数和共享状态
- 可变默认参数如 `def f(x=[])` 或 `def f(x={})`；默认值被创建一次并在每次调用间共享。默认为 `None` 并在函数体内构建值
- 类级别的可变属性在实例间非故意共享，而预期是按实例独立的
- 跨请求或线程修改的模块级可变全局对象（列表、字典、缓存），以令调用方惊讶的方式保留状态
- 通过引用捕获循环变量的闭包，所有闭包最终都看到其最终值
- 当函数从不修改参数，或共享默认值是故意且已文档化的缓存或哨兵时，不要报告

#### 边界和边缘情况处理
- 假设输入非空：在没有先处理空 `list`、`str`、`dict` 或迭代器的情况下索引 `xs[0]`、`max()`/`min()` 或切片
- 索引、range 或 slice 上的差一错误和越界访问，尤其是首/末元素
- `None` 到达假设有值的代码，当上游调用或默认值可以合法返回 `None` 时（在使用 `file_read` 确认数据源前不要标记）
- 使用 `==` 精确比较浮点数；使用 `math.isclose` 或显式容差
- 整数/浮点和除法假设：使用 `//` 导致的非预期截断，或除数为零时的 `ZeroDivisionError`
- 集合中的异构或非预期元素类型，而代码假设它们是一致的（例如混合 `None`、数字和字符串）
- 不处理缺失 key 情况的字典访问（`d[k]` 对比 `d.get(k)`），或假设 key 存在的 set/dict 操作
- 不要报告调用方或类型契约已经排除的边缘情况，或给定上游验证边界不可能发生的输入

#### 错误处理和异常
- 裸 `except:` 会吞掉所有异常，包括 `KeyboardInterrupt` 和 `SystemExit`；至少捕获 `except Exception`，最好捕获你期望的具体异常类型
- 仍然比所处理的失败更宽泛的 `except Exception`；将其收窄到受保护调用实际引发的异常
- 捕获后静默丢弃（`pass`）且不记录或不重新引发的异常
- 重新引发时丢失原始 traceback；优先使用 `raise NewError(...) from err` 以保留原因
- 宽泛的 `try` 块包裹了远超实际可能失败的行，隐藏了错误的起源
- 使用 `assert` 进行外部输入的运行时验证——断言在 `python -O` 下会被去除

#### 身份和相等比较
- 使用 `is`/`is not` 比较字符串、数字或元组等字面量；这依赖实现特定的驻留，而非值相等——使用 `==`
- 使用 `==` 比较 `True`/`False`，其中 truthy 但非 `True` 的值（如 `1`、非空容器）会比较为不等；优先使用普通的真值检查
- 将 `is` 保留给单例和哨兵的身份检查
- 使用 `==`/`!=` 而非 `is`/`is not` 比较 `None` 是风格偏好；报告为次要而非阻断

#### 资源管理
- 没有使用 `with` 语句打开的文件、socket、锁或数据库连接，存在提前返回或异常时泄漏的风险
- 有可用的上下文管理器但绕过，手动调用 `open()`/`close()` 对
- 在 `try` 中获取的资源，其 `finally` 清理在错误路径上缺失或不完整
- 持有资源时间过长而无需的迭代器或生成器
- 不要报告简短脚本，或已被外围 `with` 或框架管理生命周期处理的句柄（用 `file_read` 确认外围作用域后再标记）

#### 性能
在标记前确认数据规模且代码在热路径上：
- 在循环中使用 `+=` 构建字符串，而非累积到列表然后 `"".join(...)`，或使用 f-string
- 对列表进行重复成员测试，而 set 或 dict 可以将 O(n) 查找变为 O(1)
- 构建完整列表而生成器可以避免将所有内容保存在内存中
- 在循环内重复计算循环不变的值（如编译正则表达式、热路径中的属性查找）
- 将急切格式化的 f-string 传递给 `logging`（如 `logging.info(f"...")`）而非 `logging.info("%s", value)`，这在该级别禁用时破坏了延迟格式化

#### 并发和异步
仅在有并发调用的证据时才标记并发问题（在报告前确认调用上下文）：
- 在 GIL 下使用 `threading` 进行 CPU 密集型工作并行化，而 `multiprocessing` 或进程池是正确的工具；I/O 密集型工作才是线程真正有用的场景
- 没有 `Lock` 的检查-执行竞态，或假设为原子的非原子复合更新
- `async def` 中的阻塞调用（同步 I/O、`time.sleep`、`requests`、CPU 密集型工作），阻塞了事件循环；使用异步等效版本或在执行器中运行
- `asyncio` 任务被创建但从未 await，因此异常被吞掉且工作可能在完成前被垃圾回收
- 跨线程或任务的共享可变状态，没有同步或线程安全的结构
- 不要报告局部变量、只读共享数据访问、或无并发使用证据的代码

#### 安全敏感代码
在标记前验证数据源；确认输入实际上是攻击者控制的而非可信常量：
- 不可信输入上的 `eval`、`exec` 或 `compile`；这是任意代码执行
- 使用来自未净化输入的 `shell=True` 的 `subprocess`；传递参数列表并避免 shell
- 不可信数据上的 `pickle`、`marshal` 或 `yaml.load`（没有 `SafeLoader`）；反序列化可以执行任意代码
- 通过字符串拼接或 f-string 构建的 SQL，而非参数化查询
- 记录或提交到源码的密码、令牌、密码或 PII
- 弱或误用的密码学（`hashlib.md5`/`sha1` 用于密码，`random` 用于安全令牌）；使用 `secrets` 和经过审查的库
- 未经验证的不可信文件路径拼接，允许路径遍历
