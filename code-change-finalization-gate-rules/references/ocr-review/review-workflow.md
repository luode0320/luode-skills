# 代码审查工作流

本工作流在 `code-change-finalization-gate-rules` 收口闸门中自动触发，用于对当轮代码改动执行行级审查。
审查由当前 Agent 基于 OCR 规则自行执行，不依赖外部 CLI 或额外 LLM 配置。

## 触发时机

在 `code-change-finalization-gate-rules` 的默认执行流程中，完成测试目录一致性检查后、生产代码污染扫描前自动执行。

## 审查步骤

### Step 1: 收集改动清单

运行以下命令获取当轮改动的文件列表：

```bash
# 查看 Git 改动的文件列表
git diff --name-only
git diff --cached --name-only   # 已暂存
git diff --name-only            # 未暂存
git ls-files --others --exclude-standard   # 未跟踪
```

或直接读取已冻结的 diff 范围。

### Step 2: 匹配审查规则

对每个改动文件：

1. 取文件扩展名或文件名模式
2. 查阅 `rule-path-map.md` 找到对应的 glob 模式
3. 确定对应的规则文件（如 `go.md`、`python.md`、`ts_js_tsx_jsx.md`）
4. 如果未匹配到任何模式，使用 `default.md`（通用规则）
5. 读取 `rule_docs/{对应规则}.md` 中的审查规则内容

### Step 3: 逐文件审查

对每个改动文件执行：

1. 获取文件 diff（新增/修改行，以 `+` 开头的行）
2. 对照该语言规则的各分类逐条核验：
   - 正确性 / 逻辑错误
   - 安全漏洞
   - 性能问题
   - 线程安全 / 并发
   - 资源管理
   - 可维护性
   - 死代码 / 拼写错误
   - 安全敏感代码
3. 对于非局部的断言（如"这个方法可能被并发调用"），使用工具调用（`file_read`、`code_search`）建立证据链
4. 只关注新增代码行的潜在问题，不评论正确的代码或无改动的代码

### Step 4: 交叉文件审查

检查相关文件间的一致性：
- MyBatis Mapper XML ↔ Java/Kotlin DAO 接口
- API 路由 ↔ handler 实现
- 接口定义 ↔ 实现类
- 配置变更 ↔ 业务代码改动
- 前端 API 调用 ↔ 后端接口定义

### Step 5: 格式化输出

按严重级别分组输出审查结果：

```markdown
OCR 审查结果

审查文件数：N
发现问题：X Critical，Y High，Z Medium

### Critical（必须修复）
- **path/file:行号** [类别] 问题描述
  > 修复建议

### High（建议修复）
- **path/file:行号** [类别] 问题描述
  > 修复建议

### Medium（仅供参考）
- **path/file:行号** [类别] 问题描述
```

若未发现 Critical/High/Medium 级别问题，输出：
```
OCR 审查通过：N 个文件中未发现中高严重级别问题。
```

### Step 6: 阻断判断

- 存在 **Critical** 级别问题 → 阻断收口，要求在继续前修复
- 仅 High/Medium 级别问题 → 非阻断，但在最终回复中提示
- 无问题 → 顺利通过

## 审查规则分类说明

每个 `rule_docs/{语言}.md` 文件包含针对该语言的审查要点，一般按以下分类组织：

| 分类 | 说明 |
|------|------|
| 拼写错误 | 标识符声明处的拼写错误 |
| 死代码 | 不可达代码、未使用变量、注释掉的代码 |
| 正确性/逻辑错误 | 条件错误、边界处理、空指针等 |
| 性能 | N+1 查询、循环内操作、资源泄漏 |
| 线程安全/并发 | 竞态条件、同步问题、原子性 |
| 安全 | SQL 注入、XSS、敏感信息泄漏 |
| 资源管理 | 连接未关闭、事务未提交 |
| API 设计 | 公共接口的合理性和安全性 |
| 可维护性 | 命名、注释、代码组织 |

## 注意事项

- **精准优先于召回**：只报告有信心的真实缺陷，上下文不清晰时保持沉默
- **跳过 low 级别**：自动丢弃低严重级别的问题
- **不出格**：只审查同仓库内本次改动的文件，不审查外部依赖或未改动文件
- **行级精确**：问题必须定位到具体的文件路径和行号
- **修复建议**：对 Critical/High 问题尽可能附带修复代码建议
