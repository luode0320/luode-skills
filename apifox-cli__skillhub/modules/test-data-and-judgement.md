# 测试数据构造与响应判定（吸收自上线前测试规则）

> 归属 owner：`apifox`。本模块定义在 apifox 中构造测试请求参数的数据来源优先级，以及如何判定接口响应是否符合预期（通过/不通过/待确认 + 阻断分类）。吸收来源：`project-interface-release-execution-rules/references/test-data-construction-rules.md` 与 `agent-response-judgement.md` 的方法论，转换为 apifox 项目场景。

## 何时加载

- 构造测试用例的请求参数，需要真实可追踪数据时
- 用例运行后需要判定"是否通过"，或结果与预期不符时
- 用户要求"用真实数据测""不要用不存在的数据测""禁止伪通过"时

## 〇、测试库数据准备：local 基准灌入 + 双无自造（local → apifox，强制）

> 被测服务 `-env apifox` 启动时连接的是**独立的 apifox 测试专用库**（库名约定 `apifox`，见 `modules/environment.md`），该库是独立新库，默认没有数据。**apifox 以 local 数据库数据为基准**：local 库通常同步正式环境线上数据（测试更准确），apifox 环境只是**隔离测试写入**（测试数据不污染 local），**不隔离数据来源**——数据可从 local 单向流通到 apifox，供 apifox 环境使用。**「有 apifox 配置默认用 apifox」仅指被测服务启动环境**（见 `modules/environment.md`），**不代表禁止使用 local 配置/数据**；恰恰相反，local 是 apifox 的首选数据源。

**数据准备优先级（强制，默认路径）**：

1. **apifox 库无数据 + local 库有数据 → 优先从 local 库取数据灌入 apifox 测试库**：这是**默认且常见**的路径，不限于「测试旧接口 / 历史数据依赖型接口」——凡 apifox 库查不到测试所需数据（如查询历史订单、历史记录、按旧 ID 查详情），先检查 local 库，有则从 local 单向灌入作为测试前置数据。
2. **apifox 与 local 都无数据 → apifox 自行创造测试数据**：按接口字段规范构造合法样本（标注「自造数据」，可追溯），**不得因无数据而接受空结果 / record not found 伪通过**。
3. **模型测试宽权限场景 → apifox 环境可自建 `tmp` 临时库（前提：项目已有 apifox 环境配置）**：需要建表、复杂数据构造、大范围写操作等宽泛权限时，允许 apifox 环境**自行新建 `tmp` 前缀临时库**测试使用（如 `tmp_model_test`），测试完成后**必须删除**（`DROP DATABASE`）；**正常库（非 `tmp` 前缀，含 apifox 测试专用库与 local 库）一律禁止删除**。临时库删除动作记录到 `PROJECT_TEST.md`（库名/用途/删除时间）。见 `modules/environment.md`「临时库特权」。

灌入约束（保留，强制）：

- **方向唯一（强制）**：只允许 **local → apifox 测试库**单向灌入；**禁止反向**（apifox 测试数据不回灌 local 库）。
- **local 库只读（强制）**：灌数据仅对 local 库做 `SELECT` 读取，**禁止写入 / 修改 / 删除 local 库任何数据**；灌入是「按需拷贝」，不是「持续同步」，不改变 local 库。
- **目标固定**：灌入目标只能是 `config.apifox.yaml` 指向的 apifox 测试专用库；apifox 库名与 local 相同未分离时，仍按库分离规则**阻断**，不因灌数据需求而豁免。
- **取数源只允许 local 配置**：灌数据只从 `config.local.yaml`（或 local 配置）声明的本地库取数，**禁止从 test / prod / staging 配置取数灌入**（环境红线一致）。
- **脱敏（强制）**：userId / token / 手机号 / 身份证 / 银行卡等敏感字段灌入前脱敏（`***`），与参数输出脱敏规则一致。
- **可追溯（强制）**：灌入动作记录**来源库 / 表、灌入条数、时间**到 `PROJECT_TEST.md` 或测试主文档，作为测试数据来源证据。
- **性质**：按需、可重复的测试前置数据准备；灌入后 apifox 测试库仍独立，后续测试写入只落 apifox 库。

## 一、测试数据构造：参数来源优先级（强制）

**核心原则**：真实可追踪优先；正常路径优先（先用真实数据验证成功响应，再验证异常路径）；禁止伪通过（不得用不存在的数据测查询接口，然后接受"record not found/空列表"为通过）。

按优先级从高到低尝试，任何必填参数无法确定时，不得手写猜测值：

| 优先级 | 来源 | apifox 场景说明 |
|--------|------|------------------|
| 1 | **可复用参数** | 之前用例中已验证可用的样本（开发环境环境变量/全局变量/数据文件中标记 reusable 的；开发环境环境变量清单见 `modules/environment.md` 与项目根 `PROJECT_TEST.md`「环境变量登记」表） |
| 2 | **上游接口返回数据** | 先调用 provider 接口，用 extractor 提取 `$.data.id` 等字段作为下游参数（见 `modules/test-case.md` 提取器） |
| 3 | **数据库最近记录** | 从 local 数据库按时间倒序取最近 5-10 条，提取请求参数字段 |
| 4 | **本地缓存数据** | 从 local Redis/缓存读取候选值 |
| 5 | **OpenAPI 示例** | 读取接口的 example、schema default、枚举值，只作形状/格式参考 |
| 6 | **fixture 样本** | 项目已维护的 mock/fixture 样本 |
| 7 | **明确业务规则生成** | 仅当规则明确时按规则生成 |
| 8 | **不存在的测试数据** | 仅用于验证错误处理和边界，不能作为通过判定主依据 |

## 二、参数解析协议

- 每个必填参数都要有**可追溯来源**：来源类型、来源接口/表、提取路径、选择规则、脱敏值。
- 使用上游接口数据时：先执行 provider，保存请求与响应，再按提取规则选值。
- 使用数据库/缓存时：只能连接 **local 配置**（`test-strategy-rules` 红线），禁连 test/prod/staging。
- 使用 OpenAPI 示例时：P0/P1 和写接口仍必须用真实数据或轻量复验确认，不能只靠示例给 PASS。
- 参数解析失败：记录失败阶段，**不得用空值或猜测值继续执行目标接口**。
- **断言的期望值也要有来源**：先用真实请求（本地 curl 或先跑一次用例）实测出该输入对应的真实响应，再把响应里的值写进断言；**禁止只读代码推断期望值**。推断出的期望值一旦写错，用例会长期"稳定失败"或掩盖真实缺陷，排查成本远高于先跑一次。
- **构造 / 变更前置数据后必须确认生效**：被测链路常有进程内缓存或 Redis 缓存（TTL 几十秒到几分钟），改完数据立刻跑读到的是旧值。改完先查 TTL，等过期或真正重启服务（按 `modules/environment.md`「服务重启与关停核验」），再复验一个已通过用例，确认新数据真的生效（陷阱见 `modules/testing-pitfalls.md` 18-1）。

## 二之二、fixture 优先级反向设计（多过滤维度接口，推荐）

被测接口带多个过滤维度（时间窗 / 开关 / 版本灰度 / 地区白名单 / 租户）且**只返回一条命中结果**时，不要为每个维度单独造一条数据再各写一个用例——**把闸门对照数据的优先级字段（sort / weight / priority）刻意设得比"期望命中"的那条更高**：

- 期望命中的主记录：优先级最低，且不受任何闸门限制
- 每个闸门各造一条对照记录：优先级更高，但各自被一个维度挡住（版本高于客户端、地区不匹配、窗口已过期……）

这样只要请求命中的是主记录，就同时证明了所有闸门都真的生效——否则优先级更高的对照记录会抢先返回。一份数据同时承担正向断言与多维度拦截验证，用例数不随维度数线性增长。

- **适用**：单结果 + 多维度过滤 + 有优先级排序字段的接口（活动曝光、灰度配置、路由策略、券/权益匹配）。
- **不适用**：返回列表的接口（拦截失败不会被"抢占"掩盖，应逐维度断言列表内容）；无优先级字段的接口。
- **代价**：断言失败时不能直接看出是哪个闸门失效，需回查数据。因此**必须在测试主文档里写清这套 sort 设计意图**，否则后人看到"只断言了一个 activityId"会误以为覆盖不足。
- 无法用该技巧覆盖的维度（如需要真实凭据才能测的放行路径），照常登记为待补测，不要用间接验证冒充已覆盖。

## 三、响应判定规则

### 判定前置

1. 请求参数输出为 JSON，敏感字段脱敏（userId/token/手机号/身份证/银行卡用 `***`）。
2. 简要响应只保留参与判定的关键字段；完整响应落盘到证据文件。
3. 完全基于接口语义、业务预期、响应结构、状态变化判定，不依赖固定响应值。
4. 数据必须按上述来源优先级构造；用不存在的数据测查询接口并接受失败 ≠ 通过。

### 判定依据优先级

1. **HTTP 状态码**：2xx 成功，非 2xx 按语义判断（3xx/4xx/5xx）。
2. **业务返回码**：按接口基线的业务成功/失败规则判断。
3. **响应结构完整性**：必填字段存在、类型正确、无异常报错/堆栈/乱码。
4. **业务逻辑合理性**：响应与请求语义匹配、数据符合业务规则、状态符合预期、关联字段匹配。

### 判定「通过」的条件（同时满足）

1. HTTP 状态码符合预期（成功 2xx，预期失败接口按预期 4xx/5xx）。
2. 业务返回码符合业务成功规则。
3. 响应结构完整，必填字段存在且类型正确。
4. 响应数据符合业务逻辑：创建返回有效 ID、查询返回与请求匹配的数据、修改返回预期结果、删除返回成功、状态流转符合规则。
5. 无异常报错、无堆栈、无敏感信息泄露。
6. 响应与请求语义匹配，无逻辑矛盾。
7. 查询类必须基于真实存在的数据验证正常返回。

### 判定「不通过」的条件（任一即不通过）

1. HTTP 状态码不符合预期。
2. 业务返回码符合失败规则。
3. 响应缺失必填字段、类型错误、有报错/堆栈/乱码。
4. 响应数据不符合业务逻辑（无效 ID、数据不匹配、空数据、状态错误）。
5. 敏感信息泄露（明文密码、密钥、隐私未脱敏）。
6. 响应与请求语义矛盾。
7. 用不存在的数据测查询得到"not found/空列表"却判定通过。
8. **接口 schema 定义了参数（query/path/body）而用例无参/缺必填（含 POST body 空壳 `{}`）→ 用例本身无效**，属于"无参测试"，结果不通过；先补全参数再判定（校验闸门见 `modules/test-case.md`「参数完整性校验（强制）」节）。

### 判定「待确认」的条件（必须说明缺什么）

- 无接口基线/业务规则，无法判断
- 结构符合但业务含义不明
- 前置数据不确定
- 部分字段含义不明
- 业务错误码无法区分预期/异常
- 外部超时但未排查代理配置，无法区分环境还是代码问题

### 参数依赖与环境阻断分类（强制，不算目标接口自身失败）

| 分类 | 含义 | 处理 |
|------|------|------|
| `BLOCKED_BY_DEPENDENCY` | provider 失败/未执行，无法构造参数 | consumer 未执行，不算 FAIL；provider 按自身结果判定 |
| `PARAM_UNRESOLVED` | provider 成功但参数无法提取 | 参数规则或数据分布缺口，不得伪造参数继续 |
| `ENV_BLOCKED` | local 服务/数据库/缓存/代理不可用 | 环境阻断，不得连 test/prod 兜底 |
| `BASELINE_STALE` | 接口 schema/参数来源漂移未复验 | 先更新基线或复验再执行 |

## apifox 落地映射

- 上游数据提取：test-case 的 `extractor` 处理器（`shareScope=PROJECT`）实现优先级 2
- 环境变量：apifox「开发环境」环境变量承载 reusable 参数（优先级 1；鉴权签名/登录账号等必须在开发环境配置齐备，清单见项目根 `PROJECT_TEST.md`「环境变量登记」表，配置约定见 `modules/environment.md`）
- 断言：用 `modules/test-case.md` 的断言规则（httpCode/responseJson/responseText）落实判定依据
- 前置依赖：多接口数据流用 `modules/test-scenario.md` 编排，跨步骤传参
- 阻断标记：apifox 用例结果与判定不一致时，按阻断分类排查，不把环境问题（如环境变量缺失导致的 401/403/签名错误）算成接口失败
