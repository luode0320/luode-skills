# 测试数据构造与响应判定（吸收自上线前测试规则）

> 归属 owner：`apifox`。本模块定义在 apifox 中构造测试请求参数的数据来源优先级，以及如何判定接口响应是否符合预期（通过/不通过/待确认 + 阻断分类）。吸收来源：`project-interface-release-execution-rules/references/test-data-construction-rules.md` 与 `agent-response-judgement.md` 的方法论，转换为 apifox 项目场景。

## 何时加载

- 构造测试用例的请求参数，需要真实可追踪数据时
- 用例运行后需要判定"是否通过"，或结果与预期不符时
- 用户要求"用真实数据测""不要用不存在的数据测""禁止伪通过"时

## 一、测试数据构造：参数来源优先级（强制）

**核心原则**：真实可追踪优先；正常路径优先（先用真实数据验证成功响应，再验证异常路径）；禁止伪通过（不得用不存在的数据测查询接口，然后接受"record not found/空列表"为通过）。

按优先级从高到低尝试，任何必填参数无法确定时，不得手写猜测值：

| 优先级 | 来源 | apifox 场景说明 |
|--------|------|------------------|
| 1 | **可复用参数** | 之前用例中已验证可用的样本（环境变量/全局变量/数据文件中标记 reusable 的） |
| 2 | **上游接口返回数据** | 先调用 provider 接口，用 extractor 提取 `$.data.id` 等字段作为下游参数（见 `modules/test-case.md` 提取器） |
| 3 | **数据库最近记录** | 从 local 数据库按时间倒序取最近 5-10 条，提取请求参数字段 |
| 4 | **本地缓存数据** | 从 local Redis/缓存读取候选值 |
| 5 | **OpenAPI 示例** | 读取接口的 example、schema default、枚举值，只作形状/格式参考 |
| 6 | **fixture 样本** | 项目已维护的 mock/fixture 样本 |
| 7 | **明确业务规则生成** | 仅当规则明确时按规则生成 |
| 8 | **不存在的测试数据** | 仅用于验证错误处理和边界，不能作为通过判定主依据 |

## 二、参数解析协议

- 每个必填参数都要有**可追溯来源**：来源类型、来源接口/表、提取路径、选择规则、脱敏值。
- 使用上游接口数据时：先执行 provider，保存请求与响应，再按提取规则选值。
- 使用数据库/缓存时：只能连接 **local 配置**（`test-strategy-rules` 红线），禁连 test/prod/staging。
- 使用 OpenAPI 示例时：P0/P1 和写接口仍必须用真实数据或轻量复验确认，不能只靠示例给 PASS。
- 参数解析失败：记录失败阶段，**不得用空值或猜测值继续执行目标接口**。

## 三、响应判定规则

### 判定前置

1. 请求参数输出为 JSON，敏感字段脱敏（userId/token/手机号/身份证/银行卡用 `***`）。
2. 简要响应只保留参与判定的关键字段；完整响应落盘到证据文件。
3. 完全基于接口语义、业务预期、响应结构、状态变化判定，不依赖固定响应值。
4. 数据必须按上述来源优先级构造；用不存在的数据测查询接口并接受失败 ≠ 通过。

### 判定依据优先级

1. **HTTP 状态码**：2xx 成功，非 2xx 按语义判断（3xx/4xx/5xx）。
2. **业务返回码**：按接口基线的业务成功/失败规则判断。
3. **响应结构完整性**：必填字段存在、类型正确、无异常报错/堆栈/乱码。
4. **业务逻辑合理性**：响应与请求语义匹配、数据符合业务规则、状态符合预期、关联字段匹配。

### 判定「通过」的条件（同时满足）

1. HTTP 状态码符合预期（成功 2xx，预期失败接口按预期 4xx/5xx）。
2. 业务返回码符合业务成功规则。
3. 响应结构完整，必填字段存在且类型正确。
4. 响应数据符合业务逻辑：创建返回有效 ID、查询返回与请求匹配的数据、修改返回预期结果、删除返回成功、状态流转符合规则。
5. 无异常报错、无堆栈、无敏感信息泄露。
6. 响应与请求语义匹配，无逻辑矛盾。
7. 查询类必须基于真实存在的数据验证正常返回。

### 判定「不通过」的条件（任一即不通过）

1. HTTP 状态码不符合预期。
2. 业务返回码符合失败规则。
3. 响应缺失必填字段、类型错误、有报错/堆栈/乱码。
4. 响应数据不符合业务逻辑（无效 ID、数据不匹配、空数据、状态错误）。
5. 敏感信息泄露（明文密码、密钥、隐私未脱敏）。
6. 响应与请求语义矛盾。
7. 用不存在的数据测查询得到"not found/空列表"却判定通过。

### 判定「待确认」的条件（必须说明缺什么）

- 无接口基线/业务规则，无法判断
- 结构符合但业务含义不明
- 前置数据不确定
- 部分字段含义不明
- 业务错误码无法区分预期/异常
- 外部超时但未排查代理配置，无法区分环境还是代码问题

### 参数依赖与环境阻断分类（强制，不算目标接口自身失败）

| 分类 | 含义 | 处理 |
|------|------|------|
| `BLOCKED_BY_DEPENDENCY` | provider 失败/未执行，无法构造参数 | consumer 未执行，不算 FAIL；provider 按自身结果判定 |
| `PARAM_UNRESOLVED` | provider 成功但参数无法提取 | 参数规则或数据分布缺口，不得伪造参数继续 |
| `ENV_BLOCKED` | local 服务/数据库/缓存/代理不可用 | 环境阻断，不得连 test/prod 兜底 |
| `BASELINE_STALE` | 接口 schema/参数来源漂移未复验 | 先更新基线或复验再执行 |

## apifox 落地映射

- 上游数据提取：test-case 的 `extractor` 处理器（`shareScope=PROJECT`）实现优先级 2
- 环境变量：apifox 环境变量/全局变量承载 reusable 参数（优先级 1）
- 断言：用 `modules/test-case.md` 的断言规则（httpCode/responseJson/responseText）落实判定依据
- 前置依赖：多接口数据流用 `modules/test-scenario.md` 编排，跨步骤传参
- 阻断标记：apifox 用例结果与判定不一致时，按阻断分类排查，不把环境问题算成接口失败
