# 需求文档→测试用例生成（吸收自 skillmd test-cases）

> 归属 owner：`apifox`。本模块用于从**需求文档**（PRD / 用户故事 / 验收标准 / 功能拆分文档）系统化生成可执行、可评审的功能测试用例，并在 apifox 中落地为真实用例。吸收来源：`skillmd.ai/skills/test-cases`（MIT，作者 cexll）的测试用例生成方法论。与 `modules/test-case-generation.md` 的关系：后者从**接口定义**（OpenAPI/Swagger/endpoint）出发生成用例，本模块从**需求文档**出发生成用例，两者互补；接口已完善时优先用后者，只有需求文档时用本模块，两者都有时先本模块提取需求与场景、再用后者补接口级细节。

## 何时加载

- 用户提供 PRD / 用户故事 / 验收标准 / 功能拆分文档，要求"生成测试用例""完善测试覆盖""规划 QA""做测试设计"
- 只有需求文档、没有接口定义时，需要把需求转化为结构化用例
- 用户要求输出"可评审的测试用例表 + 需求追溯矩阵"

## 核心原则

1. **需求驱动，不实现驱动**：用例直接映射到需求条目（REQ-xxx），不围绕实现细节设计。
2. **完整覆盖**：每个需求至少一个用例，覆盖四类场景——正常路径、边界、错误处理、状态转换（有状态时）。
3. **可执行可评审**：每条用例能被 QA 无歧义执行，能被评审者对照需求核实。
4. **可追溯**：维护需求 ↔ 用例的双向映射（追溯矩阵 RTM），有需求无用例 = 覆盖缺口，有用例无需求 = 测试了不该测的东西。
5. **质量优于数量**：少量稳定、有意义的用例胜过大量易失败的用例。

## Step 1: 需求完整性五维预检（生成前必做）

拿到需求文档后，先检查以下五维信息是否齐全；**缺少会影响预期结果的必填信息时，主动向用户询问，不得凭猜测补齐**：

| 维度 | 检查项 | 缺失时询问示例 |
|------|--------|----------------|
| 业务规则 | 约束条件、计算逻辑、校验规则、必填/可选 | "XX 字段的必填规则和长度限制是什么？" |
| 角色权限 | 哪些角色可访问、可操作、不可见 | "普通用户与管理员在该功能上的权限差异是什么？" |
| 状态 | 业务对象有哪些状态、如何流转 | "订单的状态机（含终止态）是怎么定义的？" |
| 边界 | 字段范围、数量上限、超时、文件大小 | "上传文件的允许大小和格式是什么？" |
| 异常处理 | 无效输入、依赖失败、并发、无权限时的表现 | "重复提交 / 接口超时时的提示与处理是什么？" |

预检结果作为用例设计输入：五维齐全 → 直接进入 Step 2；缺失必填信息 → 先询问，得到答复后再继续；用户也无法确定 → 标注为"待确认假设"，在用例中显式标出，不静默编造规则。

## Step 2: 提取需求并建立追溯矩阵（RTM）

1. 从需求文档提取**需求条目清单**：每条赋予稳定 ID（`REQ-001`、`REQ-002`…），记录需求描述与来源位置。
2. 为每条需求生成**至少一个用例**，并记录用例 ID（`TC-xxx-NNN`）。
3. 输出追溯矩阵（RTM），行=需求，列=用例与覆盖状态：

```markdown
| 需求 ID | 需求描述 | 用例 ID | 覆盖状态 |
|---------|----------|---------|----------|
| REQ-001 | 用户可用邮箱+密码登录 | TC-F-001, TC-E-001, TC-ERR-001 | ✅ 完整 |
| REQ-002 | 密码需满足复杂度规则 | TC-F-002 | ⚠ 部分（缺边界） |
```

- **正向追溯**（需求→用例）：每个需求都有用例 = 无未测需求。
- **反向追溯**（用例→需求）：每个用例都有对应需求 = 无孤儿用例。
- **缺口判定**：需求无用例 = 阻断级缺口；用例无需求 = 删除或挂接需求。

## Step 3: 按风险选择测试设计方法

不机械铺满所有方法，按需求的风险等级选择方法组合：

| 需求特征 | 适用方法 | 用例类型前缀 |
|----------|----------|--------------|
| 输入字段有明确范围/格式 | 等价类划分 + 边界值分析 | TC-E- |
| 多条件组合决定结果（规则多、条件交叉） | 决策表（条件桩+动作桩，逐规则覆盖） | TC-D- |
| 业务对象有状态机 | 状态转换测试（所有有效转换 + 无效转换被拒） | TC-ST- |
| 业务流程、主流程+备选+异常流 | 场景法（基本流/备选流/异常流各一用例） | TC-S- |
| 核心用户流程、数据完整性、安全路径 | 等价类 + 边界值 + 错误处理组合 | TC-F-/TC-E-/TC-ERR- |

**方法定义要点**：
- **等价类**：有效类（合法输入）、无效类（非法输入）各至少一用例；示例：年龄有效 18-100，有效类 18/50/100，无效类 17/101/-1/"abc"。
- **边界值**：min-1、min、max、max+1、0、空、超长、空数组、单元素。
- **决策表**：条件桩全组合按规则行覆盖，不逐组合爆炸（按风险裁剪组合）。
- **正向组合（查询/过滤场景）**：多条件组合需求的正向用例另按 `modules/test-case-generation.md` 规则 E-1 分层组合（单参数/两两/全参数/过滤×分页）覆盖。
- **状态转换**：列出状态表，对每个有效转换与每个无效转换（应被拒绝）各生成用例，含终止态无后续转换验证、跨会话状态持久化。

## Step 4: 生成测试用例（字段模板）

每条用例必须包含以下字段，缺一不可（12 项）：

```markdown
#### TC-F-001: [清晰标题，说明测试内容]
- **需求链接**: REQ-001（必填，可追溯）
- **优先级**: P0 / P1 / P2（按风险赋值，见下）
- **用例类型**: 功能 / 边界 / 错误 / 状态转换 / 决策表 / 场景
- **前置条件**: 测试前必须为真的状态（具体：账号存在、已登录、数据记录、配置项）
- **测试数据**: 具体输入值，禁止占位符（禁止 "[有效邮箱]" 式模糊值）
- **测试步骤**:
  1. [具体可执行动作]
  2. [具体可执行动作]
  3. [验证动作]
- **预期结果**: 可测量、可验证（状态码、响应结构、页面表现、数据落库结果）
- **后置条件**: 测试完成后的状态
- **自动化建议**: 建议自动化 / 可自动化 / 保留人工（如"接口层可自动化，UI 层保留人工"）
- **依据**: 需求文档条款 / 业务规则出处（引用需求条目或文档位置）
```

**命名约定**：`TC-<类型前缀>-<三位序号>`。类型前缀：`F`（功能）、`E`（边界/等价类）、`ERR`（错误处理）、`ST`（状态转换）、`D`（决策表）、`S`（场景）、`SEC`（安全）、`PERF`（性能）。

**优先级赋值（风险导向）**：

| 优先级 | 条件 |
|--------|------|
| **P0** | 核心用户流程（登录、结账、数据提交）、数据完整性（增删改）、安全关键路径（认证/授权）、资金/支付类 |
| **P1** | 次要用户流程、P0 功能的边界情况、常见故障的错误处理、性能敏感操作 |
| **P2** | 罕见边界、外观问题、锦上添花功能、非关键错误场景 |

## Step 5: 覆盖验证（收口前自查）

- [ ] 每个需求都有对应用例（RTM 无空行）
- [ ] 所有正常流程 happy path 已覆盖
- [ ] 多条件组合需求：正向场景是否覆盖 单参数 / 两两组合 / 全参数 三层（规则 E-1），且不依赖仅分页正向
- [ ] 边界情况含空输入、min/max、最大限制
- [ ] 错误处理含无效输入、权限失败、依赖失败
- [ ] 有状态功能的状态转换（含无效转换）已测试
- [ ] 用例 ID 唯一且符合命名约定
- [ ] 测试步骤清晰可执行（QA 无歧义）
- [ ] 预期结果可测量可验证
- [ ] 覆盖矩阵显示完整覆盖
- [ ] 无编造的规则、无"已执行/完整覆盖"的虚假声明

## Step 6: apifox 落地

需求驱动的用例在 apifox 中落地，与接口驱动流程汇合：

1. 需求 → 接口：从需求定位对应 endpoint（已有接口）或按 `modules/api-design.md` 先建接口，再按 `modules/test-case-generation.md` 补接口级细节（schema 驱动数据、断言模板）。
2. 用例分类：按需求模块或优先级建 `test-case category`（P0/P1/P2 分开，便于先跑必测）。
3. 测试数据：按 `modules/test-data-and-judgement.md` 的参数来源优先级取真实数据，禁止伪通过。
4. 断言：按 `modules/test-case.md` 的断言规则（httpCode/responseJson/responseText + equal）生成。
5. 执行：每个用例 `test-case run` 真实运行；未完成真实验证的必须标记"待人工验证"（`functional-validation-rules` 红线）。
6. RTM 留痕：需求 ↔ 用例映射写进测试主文档（`doc/5-tests/` 口径），保持可评审。

## 常见恢复

| 现象 | 处理 |
|------|------|
| 需求文档信息不全 | 按五维预检询问用户，标注待确认假设，不猜测 |
| 用例过多/过少 | 按"每需求 ≥1 用例 + 四类场景"校准，按风险裁剪组合 |
| 追溯矩阵有空需求 | 补用例或与用户确认该需求是否在范围 |
| 用例运行失败但接口正常 | 检查环境/前置数据/断言字段（`modules/test-case.md`） |
| 需求变更 | 更新受影响用例与 RTM，删除过期用例，为 bug 修复补用例 |
