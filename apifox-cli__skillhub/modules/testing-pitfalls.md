# API 测试陷阱知识库（吸收自"180 陷阱知识库"）

> 归属 owner：`apifox`。本模块沉淀接口测试的高频陷阱类别与检查点，生成测试用例前/运行失败后按本清单排查。吸收来源：API测试自动化专家版（180 陷阱知识库）的方法论，转换为 apifox 场景可执行检查项。与 `modules/test-case-generation.md` 的关系：生成方法论负责"设计用例"，本模块负责"规避已知坑"，两者配合。

## 何时加载

- 生成测试用例前做陷阱自查
- 用例运行失败、断言不生效、结果与预期不符时排查
- 接口对接方报告异常但接口"看起来正常"时
- 用户要求"陷阱检查""看看有没有坑""为什么测不过"

## 一、请求构造陷阱

| # | 陷阱 | 表现 | apifox 检查 |
|---|------|------|-------------|
| 1 | 发送带 body 的请求未设 `Content-Type: application/json` | 静默 400 | 检查 requestBody 的 type 与请求头 |
| 2 | JSON body 写成了对象而非字符串 | 结构不合法 | `requestBody.data` 必须是字符串（`\n` 转义） |
| 3 | query/path/body 参数混用或位置错误 | 参数丢失 | 对照 endpoint schema 的 parameter 类型 |
| 4 | 枚举/格式值凭印象填写 | 非法值 400 | 用 `get_fields_info` / schema 枚举 |
| 5 | 必填字段漏填 | 400 但信息不全 | 用 schema `required` 清单核对 |
| 6 | 环境变量未注入 | 401/404/超时 | 显式 `--environment`，检查变量作用域 |

## 二、断言陷阱

| # | 陷阱 | 表现 | apifox 检查 |
|---|------|------|-------------|
| 7 | 用 `responseCode` 而非 `httpCode` | 断言不生效 | 断言 subject 用 `httpCode` |
| 8 | 用 `responseBody` 而非 `responseJson` | JSON 断言失败 | 用 `responseJson` + path |
| 9 | 比较符写 `equals` 而非 `equal` | 断言不生效 | comparison 用 `equal` |
| 10 | 只断言 2xx 不校验响应结构 | 字段缺失被忽略 | 补关键字段非空断言 |
| 11 | 断言了实现细节（顺序/临时字段） | 重构即挂 | 只断言稳定契约字段 |
| 12 | 错误路径断言成"符合预期" | 假通过 | 失败响应也要断言状态码+错误结构 |
| 12-1 | **用 grep 数 `√`/`×` 统计 runner 结果，把失败漏计成"全绿"** | apifox runner 报告里**通过**的断言前缀是 `√`，**失败**的却是 `1. 2. 3.` 编号（不是 `×`）；`grep -c '×'` 恒为 0，于是"12 个用例 fail=0"这类结论完全是假的 | 统计必须解析报告表格里的「断言数 总数 / 失败数」两列（`断言数\s*│\s*(\d+)\s*│\s*(\d+)`），或直接看 `失败数` 非 0；批量跑用例时**先用一个已知会失败的用例校准统计脚本**，再信它的汇总 |

## 三、数据与状态陷阱

| # | 陷阱 | 表现 | apifox 检查 |
|---|------|------|-------------|
| 13 | 测试数据污染生产/共享库 | 数据不一致 | 只用 local 环境（`test-strategy-rules` 红线） |
| 14 | 依赖前置数据未构造 | 404/空结果 | 先建后查，用 extractor 提变量 |
| 15 | 幂等/并发未考虑 | 偶发失败 | 重复执行验证稳定性 |
| 16 | 时间/日期字段硬编码 | 次日即挂 | 用动态值或相对时间 |
| 17 | 分页只测第一页 | 深层问题漏测 | page/limit 边界 + 筛选保留 |
| 18 | 空数据/空数组场景未测 | 空态崩溃 | 边界用例含空数组 |
| 18-2 | **上游只读依赖无权限/不可达，被服务静默降级成空值** | 字段级精确断言突然全挂（如文案 title 变空串），但接口 HTTP 200、业务 status 仍 true——因为业务代码对"取不到文案/配置"的处理是记日志后继续，不报错 | 断言从"通过"变"失败"而请求侧没改动时，**先看被测服务日志**再怀疑用例：本轮真实案例是 Mongo 账号对新库 `not authorized`（配置库名被改），文案静默降级为空。属 `ENV_BLOCKED`，不是接口缺陷；修配置或授权后复跑，不要把精确断言降级成"非空"来凑绿 |
| 18-1 | **改完前置数据立刻跑，被服务端缓存挡住** | 用例读到的是旧配置：新插的数据不生效，或删掉的数据仍生效；断言"稳定失败"或"稳定假通过"，看不出是缓存 | 改数据前先查被测链路有没有进程内缓存 / Redis 缓存及其 TTL（搜 `TTL`、`cache`、`SetWithTTL`）；改完**等 TTL 过期或真正重启服务**再跑；数据变更后至少复验一个已通过用例，确认新数据真的生效 |

## 四、鉴权与安全陷阱

| # | 陷阱 | 表现 | apifox 检查 |
|---|------|------|-------------|
| 19 | 无 Token/过期 Token 未测 | 鉴权逻辑漏测 | 认证场景用例（无/过期/权限不足/正确） |
| 20 | Token 硬编码在用例里 | 泄露/过期 | 从环境变量/提取变量取，不进仓库 |
| 21 | 权限不足场景未测 | 越权未发现 | 低权限角色用例 |
| 22 | 敏感字段出现在报告/日志 | 泄露 | 断言与报告脱敏，token 不进输出 |
| 22-1 | **用请求头伪造业务维度，顺带改变了鉴权判定** | 为测地区/灰度/租户等维度伪造 `X-Forwarded-For`、`X-Real-IP`、`Host`，结果直接被鉴权/风控拒绝（如内网免签服务改判为外网来源要求签名），该业务维度"看着有 bug"其实是测不了 | 先查鉴权中间件取客户端标识的函数与业务侧是否**同一个**（免签常按来源 IP 判定，而取 IP 的工具多优先读 `X-Forwarded-For`）；是同一个则该维度必须补签名/凭据才能测——把"无凭据被拒"固化成安全性用例，并把该维度的**放行路径**登记为待补测，不要写成接口缺陷 |

## 五、接口定义陷阱

| # | 陷阱 | 表现 | apifox 检查 |
|---|------|------|-------------|
| 23 | schema 是空对象 | 用例无数据依据 | 先分清两种情形：**spec 没写全** → `emptyObjectBodies` 风险，回 `import-export.md` 补；**接口本身无 body 业务字段、维度全在请求头** → 是真实契约，按 `test-case.md` 的 header-only 例外条款判定，不要当缺陷 |
| 24 | 路径完整但 spec 不完整 | 假完整 | 质量指标：schemas/withBody 覆盖 |
| 25 | tags 按 URL 机械分组 | 目录导航混乱 | operation tags 业务化 |
| 26 | 响应 schema 缺失 | 断言无依据 | 补响应 DTO/schema |
| 27 | 变更后未同步 spec | 契约漂移 | 重跑契约用例暴露 |

## 六、环境与执行陷阱

| # | 陷阱 | 表现 | apifox 检查 |
|---|------|------|-------------|
| 28 | 连到 test/prod 而非 local | 数据污染/阻断 | 只用 local 配置（`test-strategy-rules` 红线） |
| 29 | 未显式指定 environment | 变量错乱 | `apifox run --environment <envId>` |
| 30 | 报告没上传看本地了事 | 云端缺失 | CI 用 `--upload-report` |
| 31 | runner 未就绪 | 执行失败 | `runner check` 前置 |
| 32 | **以为重启了服务，其实测的还是旧实例** | 改完代码/配置重启，端口照样通、用例照样过，但改动完全没生效；新实例日志里是 `bind: address already in use` 后退出 | 关停必须核验：端口无监听 + 无残留进程，再启动。`go run`、`nodemon`、`python -m` 等包装式启动会派生子进程，杀父进程不释放端口，详见 `modules/environment.md`「服务重启与关停核验」 |

## 七、四层诊断（运行失败定位根因）

> 吸收自 API测试自动化专家版 DiagnosticAnalyzer。用例失败时按"网络 → 请求 → 业务 → 性能"四层逐层定位，不只看表面报错。

| 层 | 常见状态码/现象 | 根因 | 建议 |
|----|----------------|------|------|
| **网络层** | 超时、连接拒绝、ECONNREFUSED | 服务未启动、端口错误、网络不可达 | 先按 `modules/environment.md`「本地服务端口探测」三级链确认**实际监听端口**（登记值≠实际值先纠偏）；确认 local 服务已启动；WSL2 跨系统场景按环境适配表换地址路径 |
| **请求层** | 400/404/405/406 | 参数错误、路径错误、方法错误、Content-Type 不匹配 | 对照 endpoint schema 核 method/path/params/body |
| **请求层** | 401/403 | Token 缺失/过期、无权限 | 检查认证方式与变量注入，补权限用例 |
| **业务层** | 200 + 业务码失败 | 业务逻辑错误、前置数据不足 | 查业务码与状态流转，构造前置数据 |
| **业务层** | 429 | 限流 | 解析 Retry-After 等待重试，检查是否误触限流 |
| **性能层** | 500/502/503/504 | 服务端异常、上游超时、资源耗尽 | 重试区分偶发/稳定；稳定 5xx 记服务端 Bug 走 Bug 流程 |

## 八、异常 Fallback 策略（8 类）

> 吸收自 API测试自动化专家版。运行失败时按类执行恢复策略，禁止"见错就停"或"见错硬跑"。

| 异常类型 | Fallback 策略 |
|----------|---------------|
| 网络超时 | 重试 3 次 + 递增延迟（2s→4s→6s） |
| 429 限流 | 解析 Retry-After，等待后重试 |
| 500 服务端 | 重试 3 次并记录日志 |
| 401 认证失败 | 刷新 Token 后重新请求 |
| 404 资源不存在 | 标记 skipped，继续后续用例（先确认不是路径写错） |
| 模板/结构加载失败 | 使用默认结构兜底 |
| JSON 解析失败 | 回退到原始响应文本分析 |
| 配置缺失 | 使用默认值并提示 |

## 九、安全分类与检查要点（9 类）

> 吸收自 API测试自动化专家版 SecurityChecker 分类。安全用例按类构造，发现漏洞记入测试主文档并阻断上线。

| # | 安全类别 | 检查要点 |
|---|----------|----------|
| 1 | SQL 注入 | 输入 `' or 1=1--`、`id=1 or 1=1`，应返回参数错误而非全量数据 |
| 2 | XSS | 输入 `<script>alert(1)</script>`，应转义不执行 |
| 3 | 命令注入 | 输入 `; ls`、`$(id)`，应拒绝执行 |
| 4 | 路径遍历 | 输入 `../`、`..\\`，应拒绝越权访问 |
| 5 | LDAP 注入 | 特殊字符输入，应拒绝注入 |
| 6 | XXE | XML 外部实体输入，应拒绝解析外部实体 |
| 7 | SSRF | 内网地址/本地回环地址作为目标，应拒绝 |
| 8 | 业务逻辑漏洞 | 越权、重复提交、频率限制绕过 |
| 9 | 数据泄露 | 敏感字段明文返回/日志脱敏检查 |

> 与第四节"鉴权与安全陷阱"配合：第四节是 apifox 用例层检查，本节是漏洞类别层分类。

## 十一、自动化用例生成优先级（用例类型级）

> 吸收自 API测试自动化专家版。与 `modules/test-selection-policy.md` 的**接口级 P0/P1/P2 分级**不同：本节是**用例类型级**优先级，用于"每个接口先自动生成哪类用例"。两者配合：接口级定范围，用例类型级定顺序。

| 优先级 | 用例类型 | 覆盖易错点 |
|--------|----------|------------|
| P0 | 必选参数校验 | 缺失/空值/边界 |
| P0 | 权限校验 | 未登录、越权 |
| P0 | 幂等性校验 | 重复提交 |
| P0 | SQL/XSS 注入 | 安全基础 |
| P1 | 参数类型校验 | 类型/格式错误 |
| P1 | 边界值校验 | 最小/最大/超长 |
| P1 | 状态码与响应字段 | 状态码/业务码/字段完整性 |
| P2 | 性能边界 | 大页码/批量超限 |
| P2 | 兼容性 | 多客户端/多环境 |

## 十二、补充高价值陷阱（幂等/弱网/分布式）

> 从源 140 条陷阱中抽取本地未覆盖的高价值条目，apifox 场景化。

| # | 陷阱 | apifox 检查 |
|---|------|-------------|
| 1 | 幂等性-抽奖/下单重复提交 | 相同请求重复执行多次，应只成功一次（如 requestId 幂等键） |
| 2 | 幂等性-修改类操作 | 多次提交修改请求，数据最终一致无重复变更 |
| 3 | 弱网-网络中断 | 提交过程中断网，事务应回滚无脏数据（记录为待补测风险） |
| 4 | 弱网-支付场景 | 支付中断应不扣款或自动退款 |
| 5 | 分布式-数据同步 | 多节点操作数据一致 |
| 6 | 分布式-并发一致性 | 多用户同时改同一数据，无脏读脏写 |
| 7 | 接口未做限流 | 突发流量触发限流，服务稳定 |
| 8 | 第三方服务无超时控制 | 模拟第三方超时，本接口有兜底 |

## 使用方式

1. **生成用例前**：按一~五类 + 第十节 Top20 过一遍，把命中项转为用例（如命中 #4 → 补枚举非法值用例）
2. **运行失败时**：按第七节四层诊断定位层，对照检查项找根因；按第八节 Fallback 策略恢复
3. **对接反馈异常**：按"接口看起来正常但对方报错"优先查请求构造（一）与鉴权（四）
4. **安全类需求**：按第九节分类构造安全用例，漏洞阻断上线
5. **用例生成顺序**：按第十一节 P0/P1/P2 优先级推进
6. **持续沉淀**：团队新踩的坑按类别追加到本表，形成团队专属陷阱库（与 `code-style-consistency-rules` 用户反例库思路一致）
