# 接口测试范围选择策略（吸收自上线前测试规则）

> 归属 owner：`apifox`。本模块定义在 apifox 中为项目生成/完善测试用例时，"哪些接口必须测、哪些可选、哪些可跳过"的范围选择规则。吸收来源：`project-interface-release-execution-rules/references/test-selection-policy.md` 的 P0/P1/P2 风险分级方法论，转换为 apifox 项目场景。与 `modules/test-case-generation.md` 的关系：先按本模块选接口范围，再对选中接口按生成方法论设计用例。

## 何时加载

- 用户要求"为项目补全测试用例""上线前测试""全接口测试""完善测试覆盖"
- 需要确定"哪些接口该测、哪些可以跳"时
- 测试时间/资源有限，需要排优先级时

## 核心原则

- **风险导向**：风险越高的接口优先级越高，必须覆盖。
- **改动导向**：与本次改动直接相关、间接影响的接口必须覆盖。
- **核心导向**：系统核心链路接口无论是否改动，每次上线必须覆盖。
- **透明原则**：每个被选的接口必须说明选择理由，每个跳过的接口必须说明跳过理由。

## P0/P1/P2 风险分级

### P0（最高风险，必测无例外）

满足任一条件即 P0：

- 资金、交易、支付、结算、扣款、退款相关
- 用户身份、鉴权、权限、登录、授权相关
- 订单、合同、单据、核心数据写入
- 核心链路状态变更、流转
- 用户敏感信息（身份证、手机号、银行卡、密码）
- 影响全系统可用性的基础服务（网关、认证中心、配置中心）
- 线上出过严重故障的接口
- 业务方明确要求每次必测的接口

### P1（高风险，按改动影响面选择必测）

- 核心业务链路的查询、导出、统计类
- 非核心的写入类接口（只影响局部业务）
- 业务高频使用的查询接口
- 依赖外部服务的接口
- 本次改动模块内的所有接口

### P2（低风险，可选测或周期全量）

- 后台管理的低频操作接口
- 业务边缘功能接口
- 只读、静态数据查询接口
- 内部运维、监控类接口
- 已废弃即将下线的接口

## 必测接口选择规则（满足任一即必测）

1. 所有 P0 接口，无论是否改动，必测无例外。
2. 本次改动代码直接对应的接口。
3. 本次改动模块内的所有 P1 接口。
4. 调用了本次改动代码的上游接口。
5. 被本次改动代码调用的下游接口。
6. 与本次改动接口共享数据、共享逻辑的关联接口。
7. 业务方明确要求本次必须测试的接口。
8. 近 3 个月出过线上故障的接口。
9. 上次测试不通过、待确认的接口。

## 可选测接口

- 本次改动模块周边的 P2 接口
- 其他非关联模块的 P1 接口
- 近 6 个月未测试过的 P2 接口
- 用户主动要求补充测试的接口

## 可跳过接口（需全部满足，且报告说明理由）

1. 确认与本次改动无任何关联
2. 近 1 个月内已测试过且结论通过
3. 风险等级 P2
4. 近 3 个月未出过线上故障
5. 不属于本次需要覆盖的业务范围

> **禁止将任何 P0/P1 接口无理由跳过。**

## 输出要求（在 apifox 项目测试规划中体现）

1. P0 总数、必测 P0 列表、每个选择理由
2. P1 总数、必测 P1 列表、每个选择理由
3. P2 总数、可选测 P2 列表、每个选择理由
4. 跳过接口列表、每个跳过理由
5. 范围总览：必测数、选测数、跳过数、风险评估

## apifox 落地映射

- 分类组织：按 P0/P1/P2 或业务模块建 `test-case category`，便于按优先级运行
- 优先级运行：`test-case run --category <P0 分类>` 先跑必测，再跑可选
- 回归套件：P0 全集 + 必测 P1 纳入 `test-suite`，作为 CI 固定回归项
- 报告说明：选择理由写进测试主文档或套件说明，保持透明
