# 协作样例

## 更好

### 正例 1：按业务拆分成多次提交

假设同时修改了用户登录和订单创建两个功能，应该分成两次提交：

**第一次提交：**
```
feat: [用户登录] 新增密码与验证码双登录能力

说明：
- 支持手机号验证码登录
- 支持密码登录
- 登录成功后返回用户基本信息和 token
```

**第二次提交：**
```
feat: [订单创建] 新增普通与预约订单创建能力

说明：
- 支持创建普通订单
- 支持创建预约订单
- 订单创建成功后返回订单号
```

### 正例 2：提交消息格式正确

```
feat: [用户登录] 新增密码与验证码双登录能力

说明：
- 支持手机号验证码登录
- 支持密码登录
- 登录成功后返回用户基本信息和 token
```

```
fix: [订单结算] 修复订单创建时金额计算错误

说明：
- 问题：订单创建时优惠券折扣计算错误
- 原因：折扣计算逻辑中缺少对满减条件的判断
- 影响：已创建的订单金额可能不正确
```

### 正例 3：同一业务的实现、测试与文档合并为一笔提交

```
feat: [用户登录] 新增密码与验证码双登录能力

说明：
- 实现：支持手机号验证码登录与密码登录
- 测试：在根 test/ 补充正常、异常与验证码过期用例
- 文档：更新接口文档与使用示例
```

### 正例 4：PR 描述写清需求背景、风险点和验证方式

```
## 需求背景
用户反馈登录流程复杂，需要优化。

## 主要改动
1. 新增手机号验证码登录
2. 优化密码登录体验
3. 调整登录成功后的返回数据

## 测试结论
- 所有测试用例通过
- 性能测试达标
- 兼容性测试通过

## 风险点
- 验证码接口可能有并发问题
- 需要关注第三方短信服务稳定性

## 验证方式
1. 使用测试账号登录验证
2. 检查日志无异常
3. 验证 token 有效期正确
```

### 正例 5：提交前先补项目根目录 README 改动日志

假设本次准备提交的标题为：

```
fix: [订单结算] 修复订单创建时金额计算错误
```

那么提交前，应先在项目根目录 `README.md` 中追加：

```
2026-07-01 14:25:30 fix: [订单结算] 修复订单创建时金额计算错误
```

如果这次拆成两次提交，就应追加两条日志，且每条日志都和对应提交标题一致。

如果 README 中连续记录两次提交，正确写法是始终往末尾追加：

```text
2026-06-28 01:12:00 feat: [平台安全] 增加内网来源 IP 白名单中间件
2026-06-28 04:17:15 refactor: [租户会话与订单路由] 拆分注册函数
```

而不应把新日志插到最后一条旧日志前面：

```text
2026-06-28 04:17:15 refactor: [租户会话与订单路由] 拆分注册函数
2026-06-28 01:12:00 feat: [平台安全] 增加内网来源 IP 白名单中间件
```

✅ 结果：README 改动日志总是从末尾继续追加，执行动作稳定，不需要为了时间顺序回插历史位置。

### 正例 6：Go 提交前先做 `*_test.go` 归位扫描

提交前执行：

```powershell
rg --files -g "*_test.go" | rg -v "^test/" | rg -v "^doc/5-tests/"
```

结果为空，再继续提交。

### 正例 7：Go 提交前检查 staged 服务层落点

提交前执行：

```powershell
git diff --cached --name-only | rg "^internal/service/[^/]+\.go$"
```

结果为空，再继续提交。

### 正例 8：Windows/PowerShell 下多行提交说明换行正确

```powershell
git commit -m "fix: [订单结算] 修复订单创建时金额计算错误" -m @"
说明：
- 问题：订单创建时优惠券折扣计算错误
- 原因：折扣计算逻辑中缺少对满减条件的判断
- 影响：已创建的订单金额可能不正确
"@
```

✅ 结果：标题与说明之间由 git 自动分段，说明正文是可读的真实换行，没有 `\n` 字面量残留。

### 正例 9：收到“提交git”后分两次提交并清空工作区

假设当前有两组未提交改动：A（注释规则）和 B（前端规则），应执行：

1. 先提交 A，写入对应 README 改动日志。
2. 再提交 B，写入对应 README 改动日志。
3. 最后检查 `git status --short` 为空再结束。

✅ 结果：既按业务拆分提交，又没有遗留未提交改动。


### 正例 10：每次提交前完成当前 staged 改动的基础代码核查

当前 staged 文件包含：

- `git-collaboration-rules/SKILL.md`
- `git-collaboration-rules/scripts/pre_commit_gate.sh`

提交前先执行 `git diff --cached --check`，再直接读取 `git diff --cached` 和实际源码，按以下基础维度核查：

- 格式：空白错误检查通过；脚本改动遵循已有格式。
- 注释：关键规则、脚本函数注释和改动原因准确且未过期。
- 安全性：不会误放行、漏拦截、泄露敏感信息或开放危险路径。
- 并发安全性：没有共享状态竞态、锁顺序死锁、未取消异步任务或资源泄漏。
- 系统崩溃风险：异常/错误传播、空值和边界处理不会造成进程意外中断。
- 边界条件：README 日志、Go 测试落点和服务层落点仍受保护。

确认所有适用维度通过，纯文档提交的无关联源码维度已写明“不适用 + 原因”，且未发现 P0/P1、格式错误、关键注释缺失、安全/并发/崩溃风险、边界缺陷或明显潜在 bug，再继续提交。

✅ 结果：每笔提交都以当前 staged 改动的基础边界核对为准，不依赖业务审查文档。

### 正例 11：同一业务的实现、测试与文档合并为一笔提交

同一轮工作的实现代码、可执行测试和流程文档同属一个业务目标时，合并为一笔提交：

```text
feat: [费率计算] 新增稳定币清算规则

说明：
- 新增稳定币费率计算逻辑
- 补充结算回归用例（根 test/）
- 更新需求与实施记录
```

其中：

- 代码实现、运行配置、可执行测试和流程文档随同一业务目标合并提交
- 可执行测试文件仍必须位于根 `test/**`、`*_test.*`、`*.spec.*`、`*.test.*`
- `doc/5-tests/**` 仍只保存测试说明、日志、报告、截图和非可执行证据
- Git 提交不创建、替代或放行真实测试与 `6-review`；它们仍由实施计划的完成条件驱动

✅ 结果：一次提交完整承载一个业务目标，同时不放宽测试落点约束。

### 正例 12：同一业务的实现、测试与文档合并为一笔提交

当前 staged 文件属于同一业务目标：

```text
doc/2-需求/2026-08-02_订单创建规则.md
doc/3-实施/2026-08-02_订单创建规则_实施总览.md
doc/6-review/2026-08-02_订单创建规则_6-review.md
test/order/create_order_test.py
src/order/create_order.py
PROJECT_CURRENT.md
字典.md
README.md
```

可以整理为一笔提交：

```text
feat: [订单创建规则] 新增订单创建能力并同步流程文档

说明：
- 新增订单创建实现与回归用例
- 更新需求、实施与 6-review 记录
- 同步项目状态与字典
```

✅ 结果：同一业务目标的实现、测试、流程文档和状态同步集中在一笔提交里，不再按提交域拆成多笔。

### 反例 10：基础格式闸门已发现阻断问题，仍然继续提交

提交前检查当前 staged 改动时，已经发现：

```text
[P1] git-collaboration-rules/scripts/pre_commit_gate.sh:201 - 脚本把 `git diff --cached --check` 的失败忽略了
风险: 含空白错误的改动会绕过基础格式核查并进入提交。
建议: 将该检查纳入提交前机械闸门。
```

仍然继续提交。

❌ 问题：基础格式闸门已经发现明确阻断项，必须先修复再提交。

### 反例 11：只看状态和 README，没有直接读当前 staged 代码

提交前只执行了：

- `git status --short`
- `git diff --cached --stat`
- `README.md` 改动日志检查

但没有继续读取 `git diff --cached` 或实际文件内容，就直接提交。

❌ 问题：没有完成当前 staged 改动的基础代码核查，无法发现格式错误、注释缺失、安全/并发/崩溃风险、边界缺陷或潜在 bug。
## 较差

### 反例 1：一个提交里同时包含功能、重构、格式化和调试残留

```
fix: 修复一些问题

说明：修复了一些 bug
```

❌ 问题：一次提交包含用户登录、订单创建、代码格式化、调试代码等多个不相关的修改，应该按业务拆分成多次提交。

### 反例 2：提交消息格式不正确，只有标题没有说明

```
feat: 新增功能
```

❌ 问题：没有说明，不知道具体做了什么。

```
fix: 修复 bug
```

❌ 问题：没有说明，不知道修复了什么 bug、原因是什么、影响范围是什么。

### 反例 2.1：错误使用 `type(scope):` 括号 scope 格式

```text
feat(reqsend): 转账详细统计支持多Sheet导出错误明细
```

❌ 问题：标题格式不符合本规则。禁止 `type(scope): ...` 写法，必须改成 `type: [scope] ...`。

正确写法：

```text
feat: [reqsend] 转账详细统计支持多Sheet导出错误明细
```

### 反例 3：PR 只写"fix bug"或"update code"

```
fix bug
```

❌ 问题：PR 描述过于简单，没有需求背景、主要改动、测试结论、风险点等信息。

### 反例 4：一次提交所有业务修改

假设同时修改了用户登录、订单创建、商品管理三个功能，却只做了一次提交：

```
feat: 新增一些功能

说明：
- 用户登录
- 订单创建
- 商品管理
```

❌ 问题：应该按业务拆分成三次独立的提交，而不是一次提交所有。

### 反例 5：提交前没有更新项目根目录 README 改动日志

准备提交：

```
fix: [订单结算] 修复订单创建时金额计算错误
```

但项目根目录 `README.md` 没有追加任何本次改动记录，或者只写了下面这种模糊内容：

```
今天修了一个 bug
更新了一些内容
```

❌ 问题：日志没有直接复用本次提交标题，后续无法按 README 记录快速追溯每次提交的变更。

### 反例 5.1：README 改动日志没有追加到末尾

```text
2026-06-28 04:17:15 refactor: [租户会话与订单路由] 拆分注册函数
2026-06-28 01:12:00 feat: [平台安全] 增加内网来源 IP 白名单中间件
```

❌ 问题：新日志没有接在现有改动日志末尾，说明执行时没有遵守“始终最后追加”的规则。

### 反例 6：Go 项目命中禁放仍继续提交

扫描结果命中：

```text
internal/service/order_service_test.go
```

仍然执行提交。

❌ 问题：违反测试落点基线，应先按三级替代出路降级白盒诉求，并迁移到根 `test/` 镜像路径后再提交；不得靠改生产代码换取可测性。

### 反例 7：Go 项目命中服务层根目录直落仍继续提交

扫描结果命中：

```text
internal/service/create_order.go
```

仍然执行提交。

❌ 问题：违反服务层子目录化规则，应先迁移到 `internal/service/<domain>/` 后再提交。

### 反例 8：Windows/PowerShell 下把 `\n` 当换行写进提交消息

```powershell
git commit -m "fix: [订单结算] 修复订单创建时金额计算错误\n\n说明：\n- 问题：订单创建时优惠券折扣计算错误"
```

❌ 问题：在 PowerShell 中 `\n` 不是换行转义，通常会被当成普通字符写进提交消息，导致说明格式错乱、审查可读性下降。

### 反例 9：收到“提交git”后只提交一部分就结束

先提交了改动 A，但仍有改动 B 未提交，并直接回复“已提交完成”。

❌ 问题：完成标准不达标。对于“提交git”请求，必须继续提交剩余改动（可拆分多次）直到 `git status --short` 为空。

### 反例 12：把不属于同一业务的改动塞进一笔提交

当前 staged 文件分属两个互不相关的业务目标：

```text
internal/service/fee_rule.go
doc/6-review/2026-07-08_101500_订单导出修复_6-review.md
```

仍然尝试一次提交。

❌ 问题：`fee_rule.go` 属于费率业务，`订单导出修复` 的 6-review 文档属于另一个业务。提交粒度按业务目标划分，跨业务的改动应拆成多笔；只有同一业务目标内的实现、测试与文档才合并提交。

### 反例 13：把同一个业务拆成互相悬空的半成品提交

当前 staged 文件属于同一业务目标，却被拆成两笔：

```text
src/modules/order/create-order.ts
src/modules/order/create-order.spec.ts
doc/5-tests/2026-07-08_102300_订单创建回归.md
```

先提交实现，再单独提交测试与说明。

❌ 问题：实现、测试与说明属于同一业务目标，应合并为一笔提交。按业务拆分意味着“不同业务拆开、同一业务合并”，而不是把同一个业务切碎成多笔互相悬空的提交。
