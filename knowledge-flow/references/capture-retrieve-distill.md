# 捕获、检索与沉淀流程

以下流程适用于 `D:\谷歌云盘\知识库\` 的所有笔记操作。

## 引用台账

每次读取或写入笔记后，必须登记引用台账条目。台账格式：

| 笔记名 | 所在目录 | 本轮用途 | status | 操作 | readback |
|--------|---------|---------|--------|-----|---------|
| example.md | 20-Knowledge/ | 检索微业务架构 | active | read | verified |

### 登记时机

- 检索: 每次 `Get-Content` 或 `rg` 读取笔记内容后立即登记
- 捕获: 每次 `Set-Content` 或 `Add-Content` 写入后，回读验证通过后立即登记
- 沉淀: 同捕获
- 登记必须在对应操作成功返回的当下完成，不得延后到收口阶段再回忆补记

### 入表门槛

- 只有真实读取成功的笔记可以进「本轮引用」；检索命中但未读取的笔记一律不得入表，检索命中只是候选线索
- 写入类条目必须通过写后回读校验才能进「本轮沉淀」；回读不一致的写入不登记，也不得宣称沉淀成功
- 写入类条目还必须通过 `knowledge_index.py check`；`check` 退出码非零时该写入不登记，先修到合规再登记
- 笔记名一律取自读写笔记时所用的相对路径的文件名部分；只有存在同名笔记时才括注所在目录
- 台账是本轮会话内事实，不写入知识库、不落盘到项目文件；它只用于最终总结的「知识引用」小节渲染

### 台账字段

- 笔记名: 文件名（不含路径）
- 所在目录: 相对于知识库根目录的目录
- 本轮用途: 为什么读取或写入这篇笔记（如"检索微业务架构""沉淀执行失败案例"）
- status: 笔记 frontmatter 中的 status 字段（如 active、superseded）
- 操作: 读取 / 新建 / 追加 / 移动 / 删除 / 改属性
- readback: 操作后回读结果（verified / mismatch）

## 检索流程

1. 扩展检索词：别名、标签、实体名、来源名，以及中英文变体
2. 查机器索引（第一跳，覆盖全库）：`python knowledge-flow/scripts/knowledge_index.py query --keyword "<词>"`，逐个同义词都查一遍
3. 索引零命中时才退到兜底：`rg` 全文扫描、`rg "\[\[笔记名\]\]"` 查反向链接
4. 读取最强匹配笔记（`query` 的命中只是候选，未读取不得引用）
5. 登记引用台账

## 捕获流程

1. 判断内容是否值得保留：有未来检索价值时写入
2. 确定目录落点：按 knowledge-layout.md 的落点规则
3. 检索现有笔记：避免重复
4. 写入笔记（Set-Content 或 Add-Content）
5. 回读验证
6. 跑 `python knowledge-flow/scripts/knowledge_index.py check`，退出码非零则当轮修到合规再往下走
7. 登记引用台账
8. 索引会在下次 query 时自动重建；只有高价值笔记才顺手补 INDEX.md 入口

## 沉淀触发硬信号

「本轮是否形成了可复用经验」是主观描述，每轮重新做一次模糊判断，漏了不报错。实测后果是某段 25 天里只沉淀 6 篇，而同期至少 6 个大任务都产出了可复用经验。因此改用可对照的信号清单。

### 必须沉淀（命中任一即沉淀）

1. **修了一个不报错的隐蔽缺陷**：静默失败、假阴性、契约与实现不一致、退出码为 0 但结果不可信
2. **推翻了此前的结论或归因**：旧判断被证伪。这类必须沉淀，否则同一个错误归因会被下一轮再次采纳
3. **发现工具、API、命令的非直觉行为或陷阱**：默认行为与预期相反
4. **形成了可迁移的判断方法**：去掉项目名、表名、服务名后仍然成立
5. **同一个坑第二次踩到**：重复即固化，不再靠记忆
6. **用户明确纠正**了某个做法、口径或术语

### 明确不沉淀（命中则判不适用）

- 纯项目内部机制变更：本项目的目录约定、字段名、配置项、ID 编号规则
- 一次性执行流水：跑了哪些命令、改了几个文件、测试通过多少项
- 未确认的猜测、待验证的假设
- 已有笔记完整覆盖且本轮没有新增信息

### 判断依据要写出来

收口时把依据带进知识库状态字段，例如 `知识库:沉淀（命中信号2 推翻旧归因）` 或 `知识库:不适用（仅项目内部机制变更）`。只要求写明依据，**不要求每轮都必须有沉淀**——为凑信号而沉淀会污染知识库，比漏沉淀更难清理。

## 三态判定硬信号

「判定三态」原先只有补充 / 矛盾未裁决 / 取代三个名词，没有判定依据。实测后果是全库 63 篇笔记状态全为 `active`、`supersedes` 与 `superseded_by` 在全库出现 0 次——三态永远落在最省事的「补充」，知识库只增不改，同主题笔记持续累积成冲突候选。因此改用可对照的信号。

### 判「取代」（命中任一即成立）

1. **本轮结论与已有笔记的某条明确表述直接矛盾**：不是补充细节，是同一问题上的相反答案
2. **已有笔记依赖的工具、命令、路径或接口已废弃或不复存在**：笔记照着做已经跑不通
3. **本轮是同一问题的完整版本，且旧笔记不含任何独立于新笔记的信息**：旧笔记的每一条都能在新笔记中找到

命中后按 [conflict-staleness.md](conflict-staleness.md) 的分级处置执行，接替关系必须双向写入；只写一侧会被 `knowledge_index.py check` 拦下。

### 判「矛盾未裁决」

两个结论都有证据支撑，且本轮无法验证哪个正确。在双方笔记标记 `conflicted` 并写明另一观点，不要自行选一个方向落状态。

### 判「补充」（默认档）

以上都不命中时落此档。但**查重命中同主题笔记时，必须写出「为什么不是取代」**，不得跳过判定直接建新笔记。与沉淀触发硬信号同口径：只要求写明依据，不要求每轮都产生状态变更。

### 沉淀后的巡检时机

知识库状态判为「沉淀」的轮次，写入并回读通过后跑一次：

```bash
python knowledge-flow/scripts/audit_vault_knowledge.py --json
```

若**本轮新写或改写的笔记**出现在任一候选组，必须当轮完成三态判定并落状态。不要求裁决历史存量——历史候选走单独的清理轮次，避免每轮沉淀被存量拖住。

## 沉淀流程

1. 按上方硬信号清单判断，并记下命中的信号编号或排除原因
2. 查同主题近似笔记，判断是否已有承接笔记：`python knowledge-flow/scripts/knowledge_index.py query --keyword "<主题词>"`，重点看命中里与本轮结论同主题的那几篇。查重在写入前做，不要留给事后巡检
3. 按「三态判定硬信号」判定补充 / 矛盾未裁决 / 取代，并写出判定依据
4. 判为补充时：追加到现有笔记或创建新笔记
5. 判为矛盾未裁决时：在现有笔记中添加另一观点
6. 判为取代时：按分级处置处理旧笔记，创建新笔记并双向写入接替关系
7. 回读验证
8. 跑 `python knowledge-flow/scripts/knowledge_index.py check`，退出码非零则当轮修到合规再往下走
9. 登记引用台账
10. 跑一次巡检，本轮笔记若进入候选组则当轮裁决
