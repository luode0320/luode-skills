# 项目记忆同步

本文件说明 `project-memory-rules` / `project-style-rules` 标记为跨项目候选的条目如何同步到知识库。

`project-memory-rules/references/project-knowledge-source-contract.md`、`project-memory-rules/SKILL.md` 与 `project-style-rules/SKILL.md` 都把判断标准、标记字段、复核流程、落点目录和去重规则委派给本文件作为唯一事实源，因此本文件必须保持这五项完整可解析。

## 初判标准（project-memory-rules / project-style-rules 侧）

原先这里是四条必须同时满足的主观测试。实测证明它成本过高且漏做不报错：`bridge_candidate` 标记在全库**零次真实使用**、`20-Knowledge/project-rules/` 落点目录**从未创建**，跨项目通用判据因此全部堆在项目记忆里，把它撑到十几万字节——而项目记忆是每次会话启动必读。现改为可对照的硬信号清单。

写入 `PROJECT_MEMORY.md` / `PROJECT_STYLE.md` 条目的同一步骤里做判断。这一步只做本地文本判断，不写入知识库，可以每次增量更新都做。

### 该进知识库（命中任一）

1. **去名仍成立**：去掉全部项目专有名词（项目名、仓库名、表名、字段名、服务名、路径、skill 名）后，结论仍成立且仍能指导他人
2. **工具固有行为**：是某类工具、语言、平台的固有行为或陷阱，不随项目变化
3. **方法论判据**：是「凡是 X 必然 Y」式的判断方法，而非某次具体做法
4. **换项目会想查**：换一个项目遇到同类问题时，会想把它翻出来查

### 留在项目记忆（命中任一即不迁）

1. 本仓库的目录约定、文件名、字段名、ID 编号规则
2. 本仓库某个 skill 的配置、状态机、触发边界、命令入口
3. 本项目的技术选型与具体配置值
4. 会话启动时必须立即知道的项目约束

判断示例：「错误处理必须保留原始 error 链，禁止裸返回」命中信号 1 与 3，该进知识库；「某表的 `status=2` 表示已注销」命中排除项 1，留项目记忆；「某 skill 的会话默认策略是 `RequiredOnly`，只有 blocked/failed 不可继续」看着像平台知识，实为本仓库 skill 的状态机配置，命中排除项 2，留项目记忆。

### 判定通过后必须抽象化改写

**通过判断不等于可以直接搬运。** 这是本机制零使用在判断成本之外的第二层阻力，必须正视：多数条目的判据本身通用，但原文绑定了项目专有名词。例如「一条风格规则写进某 skill 的 SKILL.md 正文并不等于生效，取决于它是否落在写码前会被加载的入口」——判据通用，但表述绑定了本仓库的 skill 名与文件名。

写入知识库前必须：

1. 去掉项目专有名词，改为角色化表述（「某 skill 的 SKILL.md」→「规则文档正文」）
2. 保留判据本身与它的适用条件
3. 补上可迁移场景，说明换到别的系统时它长什么样
4. 原文里的项目细节作为「证据」小节保留，而不是混在判据里

原样搬运会把项目细节带进知识库，反而污染跨项目知识。

### 项目记忆侧只留指针

判定该进知识库并完成抽象化写入后，项目记忆侧**不保留完整表述**，改为一行结论加指针：

```
- 跨项目判据见知识库笔记 `<笔记标题>`；本仓库落地入口为 `<具体命令或文件>`。
```

这样通用知识只有知识库一份，项目记忆只保留本仓库怎么落地。两处各写一遍会导致口径漂移，且持续推高启动必读的体积。

## 标记字段

命中「该进知识库」信号且未命中任何排除项时，在该条目本身追加一个**可选字段**，不改变既有必填字段结构：

- `project-memory-rules` 机器索引区：对应 `entities[]` 记录里追加 `bridge_candidate: true`（缺省即视为 `false`，不需要在其余条目上出现该字段）。
- `project-style-rules` 风格条目：条目字段列表里追加可选字段 `跨项目候选: 是`（缺省即视为「否」）。

标记本身不写入知识库，写入方也不因为标记而改变本地写入流程或格式。字段名 `bridge_candidate` 是历史稳定标识；桥接层虽已废除，但改名会波及三个消费方，故保留原名。

## 复核标准（knowledge-flow 侧）

这是第二层复核，也是唯一真正写入知识库的地方。会话总结、阶段收口或最终回复前，按 [capture-retrieve-distill.md](capture-retrieve-distill.md) 的沉淀流程执行：

1. 把「本轮 `project-memory-rules` / `project-style-rules` 标记为 `bridge_candidate: true` / `跨项目候选: 是` 的条目」作为一类信息来源，与既有四类来源（稳定事实、用户偏好、决策流程、来源调试经验）并列扫描。
2. 对候选条目套用 `capture-retrieve-distill.md` 既有的排除规则（纯闲聊、未确认猜测、secret 等）做兜底过滤。
3. 即使第一层已标记候选，若第二层判断内容仍隐含项目专属信息（例如删除测试有遗漏），可以直接不沉淀，或降级为标 `confidence: medium` / `low` 留在所属主题；第一层标记不是「必须写」的强制通道，只是候选信号。
4. 本层不新增知识库四态之外的第五种状态，只是「沉淀」分支下的新增信息来源。

## 落点目录

- 来自 `project-memory-rules` 的项目规则条目沉淀到 `20-Knowledge/project-rules/`
- 来自 `project-style-rules` 的代码风格条目沉淀到 `20-Knowledge/code-style/`
- 两者都是裸相对路径，不带 `知识库/` 前缀
- 只选择性沉淀单条可复用事实，不整份同步或镜像 `PROJECT_MEMORY.md` / `PROJECT_STYLE.md`

## 去重规则

- 固定顺序：先检索、命中则追加、未命中才新建
- 按实体名与主题去重；已有承接笔记时更新该笔记，不新建同主题副本
- 知识库侧笔记只保留脱敏后的通用表述与 `source_refs` 来源引用，不摘录项目原文
- 冲突时按来源优先级裁决：用户当轮明确指令 > 当前项目代码与项目文件 > 近期已验证笔记 > 旧笔记 > 外部资料摘要
- 写入后登记引用台账，并按 [conflict-staleness.md](conflict-staleness.md) 判定补充、矛盾未裁决还是取代
