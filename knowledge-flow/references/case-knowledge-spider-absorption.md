# 案例: knowledge-spider 吸收（2026-08-19）

## 背景

用户安装 skillhub 源 `knowledge-spider v2.0.0`（SQLite 本地记忆库），要求先试用再吸收到 `knowledge-flow`。

## 吸收过程摘要

1. 读取外部 SKILL.md + src/index.py 原文，拆成 9 条原子规则
2. 临时 data_dir 实测全部核心动作（store/query/stats/recognize/context/forget）
3. 对照 knowledge-flow（SKILL.md + 9 references）产出三态裁决表：合并 2、保留本地 4、拒绝 3
4. 用户确认后落盘 capture-retrieve-distill.md 2 小节（+40 行）
5. 独立子 agent 评分：基线 84.7 → 吸收后 86.2（+1.5），棘轮通过
6. 登记裁决表/来源记录，删除源 skill

## 试运行暴露的外部缺陷（反例沉淀价值）

| 缺陷 | 现象 | 教训 |
| --- | --- | --- |
| 意图误判 | store 正则 `(?:记得|记住|别忘了|记一下|记牢)` 使「记录」命中，query/delete 被抢占：「我的知识库里有没有关于咖啡的记录？」误判为存储 | 中文正则意图路由要按「最特异性优先」排序，通用字（记/查）不能作强信号 |
| 中文未分词 | kb_context 把整句当 1 个关键词（`re.findall(r'[\u4e00-\u9fa5]{2,}')` 贪婪匹配整串），"帮我推荐一款咖啡" 0 命中 | 中文检索必须先分词或拆词，整句 LIKE 匹配必失败 |
| 宣称未实现 | SKILL.md 写「存储前自动去重检测」，代码只有 INSERT 无查重 | 吸收前必须跑真实场景验证，不能信 SKILL.md 自述（对应「双重评估」原则） |
| 分类顺序缺陷 | 「务必」命中 important 先于 task，会议任务被分为 important | 多分类正则按优先级串行判定时，要明确判定顺序并放测试用例 |

## 净增体积与整理

- 净增：capture-retrieve-distill.md +40 行（2 小节）
- 整理去重：新增内容与现有「引用台账」「沉淀触发硬信号」共用判定口径，未重复定义；SKILL.md 正文零改动
- 零新增目录、零复制外部工作流（拒绝 SQLite 架构与四类意图路由）

## 可复用判断方法

- 吸收任何「宣称具备 X 能力」的外部 skill：先构造 2-3 个**负例/边界输入**（含中文长句、易混淆词、空输入），比只跑正例更能暴露宣称与实现差异。
- 中文正则意图路由的「记录/记一下」歧义是通用陷阱，类似外部 skill 一律按此核查。
