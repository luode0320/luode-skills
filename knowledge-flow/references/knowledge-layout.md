# 知识库布局

本 skill 只使用一个固定的知识库根目录：`D:\谷歌云盘\知识库\`。
后续所有检索、捕获和沉淀都以该目录为主落点。

## 固定根目录

- 固定根目录：`D:\谷歌云盘\知识库\`
- 一旦确认，不再重新探测其他路径
- 如果目录不存在，允许创建；创建后必须验证可读写
- 笔记路径一律是相对该根的裸相对路径，不带 `知识库/` 前缀

## 禁止嵌套知识库目录

根目录本身已经是 `知识库`，所以 `D:\谷歌云盘\知识库\知识库\` 这类嵌套目录一律非法。它的成因是在笔记路径上又加了一层 `知识库/` 前缀，属于早期把 `知识库` 当作库内一级目录的历史遗留写法。

- 任何落点判断都不得产出以 `知识库/` 开头的笔记路径
- 巡检发现嵌套目录时，把其中笔记按真实主题合并回外层标准目录，再删除空的嵌套目录
- 合并时若外层已有同名笔记且正文不同，只报告候选，不自行合并正文

## 目录树

```text
D:\谷歌云盘\知识库\
├── 20-Knowledge/
│   └── execution-failure-cases/
├── 30-MOCs/
├── 50-Sources/
├── 90-Archive/
└── INDEX.md
```

目录树只列真实存在或会真实产生的落点。历史上这里还声明过 `00-Inbox/`、`10-Sessions/`、`40-Entities/`、`Attachments/`、`Templates/` 五个目录，实测全部从未创建过。声明不存在的落点不只是空转，还会**主动诱导写入者产生指向空气的链接**——`40-Entities/` 就让全库多出 8 处 `[[实体名]]` 死链。因此按用途归并后删除，不再声明。

## 落点规则

- 20-Knowledge/<固定主题>/: 保存长期概念、决策、流程和可复用模式；主题只能取下方固定清单，最多两级
- 30-MOCs/: 保存高价值主题地图；**实体导航也归这里**，反复出现的项目、仓库、工具用项目地图承接，不单独建实体笔记
- 50-Sources/type/: 保存来源摘要
- 90-Archive/: 只有笔记需要从当前检索中退出时，才移动到这里；当前为空是正常状态，分级处置的归档档位会真实往里写

分类不确定或材料尚未确认时，不另设收件箱目录：直接落到最贴近的主题下，用 `confidence: medium` 或 `low` 标出置信度，避免未确认内容伪装成高置信长期知识。

## 20-Knowledge 固定主题清单

主题目录统一用中文，且**只能从以下 7 个里选**。禁止为单篇笔记新造主题目录——历史上主题是自由变量，结果长出 17 个目录、其中 4 对语义重复（`code-style` 与 `代码规则`、`projects` 与 `项目`、`architecture` 与 `工程实践`、`codex-rules` 与 `研发流程`），同一主题散落 5 处，检索必须靠猜关键词。

| 主题 | 承载内容 | 判断依据 |
| --- | --- | --- |
| `项目/` | 具体项目的事实、配方、运行边界 | 笔记内容绑定某个具体项目名，脱离该项目不成立 |
| `代码规则/` | 语言编码规范与写法约定 | 讲「代码该怎么写」，跨项目通用 |
| `工程实践/` | 架构、中间件、数据库、部署、路径治理 | 讲系统与基础设施层面的做法 |
| `研发流程/` | 需求、实施、文档、skill 治理流程 | 讲「活儿该怎么推进」而非代码怎么写 |
| `AI协作/` | agent、Claude/Codex、skill 触发与恢复规则 | 讲与 AI 协作机制本身相关的规则 |
| `数据清洗/` | 数据治理与清洗口径 | 讲数据加工的断点、事务、索引口径 |
| `开发环境/` | Windows/WSL/PowerShell/工具链配方 | 讲本机环境与工具链怎么配 |

同一篇笔记同时贴合多个主题时，按「最强绑定」归类：绑定具体项目优先进 `项目/`，否则取语义最贴近的一个，不做多处复制。若确实无法归入任何主题，停下来请用户裁决是否需要新增第 8 个主题，不得自行新造。

`项目/` 允许按项目名开二级目录（如 `项目/EllipalFinance-go/`），其余主题保持一级。

## 契约固定落点（不参与中文化）

以下目录名被其它 skill 硬编码引用，改名会波及多处规则，因此保留英文并列为例外：

| 目录 | 引用方 | 用途边界 |
| --- | --- | --- |
| `20-Knowledge/execution-failure-cases/<owner>/` | `execution-failure-learning-rules` | 跨任务执行失败的追加式正反例笔记 |
| `20-Knowledge/project-rules/` | `project-memory-sync.md` | **仅**承载来自 `project-memory-rules` 的跨项目候选条目；目录缺失时首次沉淀再创建 |
| `20-Knowledge/code-style/` | `project-memory-sync.md` | **仅**承载来自 `project-style-rules` 的跨项目候选条目 |

`code-style/` 与 `代码规则/` 的边界：前者是契约窄用途（跨项目风格候选的落点），后者是通用编码规范。两者都存在是有意的，检索层通过机器索引的 `theme` 与标签同时命中，不要求执行方猜目录。

## 文件名规则

- 优先使用稳定、可读的 Markdown 文件名
- 标题使用用户主要语言；产品、仓库、人名等固定名称保持原样
- 删除 Windows 不安全字符
- 只有会话笔记和时间顺序重要的来源笔记才添加时间戳
- 除非用户明确要求，否则根目录下不要超过三级目录

## 索引规则

检索的第一跳是机器索引 `_index.json`，不是手写导航：

- `_index.json` 由 `knowledge-flow/scripts/knowledge_index.py build` 生成，覆盖全库 100%，是可再生成物
- 查询用 `knowledge_index.py query --keyword <词>`，按标题、别名、标签、topics、主题、路径六类结构化字段加正文匹配，并返回命中原因与相关性排序
- `query` 会自行比对笔记数与最新修改时间，索引缺失、损坏或过期时自动重建，不依赖人工记得重建
- 写入笔记后无需手动维护索引；只有需要立刻拿到统计口径时才显式跑 `build` 或 `stats`

手写导航退居辅助：

- INDEX.md 保持简短，只放入口、检索提示和少量高价值笔记，不追求覆盖全库
- 不要把 INDEX.md 变成完整目录，全量覆盖由机器索引负责
- 只有多个相关笔记已形成真实主题网络时才建 MOC；没有网络就不建，避免空导航

## 冲突副本处理

Google Drive 同步可能产生冲突副本。巡检时识别并标记这些副本为候选，人工确认后按分级处置处理。
