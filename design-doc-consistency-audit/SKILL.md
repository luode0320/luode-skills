# 单文件设计文档跨节一致性审计

只解决一个问题：**一份已被多轮增补的巨型设计文档，如何系统性地找出并修复跨节失同步**。

典型症状：文档有 5000~10000 行、几十个章节、多个同名概念表；每次新增章节都只改“功能章节”，忘改“基础设施章节”（注册表 / 目录树 / 接口表 / 测试清单 / 版本表）。

## 零、开工前必做两件事

1. **抽取章节骨架**：用 `^#{1,3} ` 正则列出全部标题行 + 行号，形成章节地图。没有地图就在写“局部正确、全局矛盾”的补丁。
2. **确认审计基线**：读项目记忆 / 上次日志，确认**当前版本号**、**上次审计已修清单**、**已确立的对照线**。重复审计已修项是纯浪费，且会掩盖新问题。

## 一、铁律：结构化清单必须全表列举，禁止用固定窗口 Read

**事故实录**：用 `Read(offset=8225, limit=16)` 读版本表尾部，窗口在第 8240 行截断，而真正的最后一行在第 8241 行。据此误判“版本表缺最新版本条目”，插入了一条重复行，还污染了变更记录。

**规则**：

- 版本表、信号表、清单表、目录树尾部、契约表 —— 一律用 `grep -n '^| v[0-9]'` / `grep -n '^signal '` / `grep -c` 之类**全表列举**，绝不依赖固定 `offset/limit`。
- 判断“某条是否缺失”之前，先做**计数自证**：`grep -n '<模式>' file | wc -l`，与预期数量比对。
- 一旦发现自己的结论基于截断内容，**必须同轮显式纠正**（删重复行、修复顺序、改写变更记录里基于误判的条目），不要留一个“看起来已记录”的假结论。

## 二、对照线清单（按发现率排序）

每条对照线都是“A 处声明 vs B 处实际”的机械比对。逐条跑，不要凭记忆。

| # | 对照线 | 典型缺陷 |
|---|--------|---------|
| 1 | **同一概念的“唯一标准”在几处不一致** | 一处写 Q16.16、一处写 Q32.32、代码里写 1000。**必须做技术可行性裁决**，不能只挑一个抄三遍 |
| 2 | **代码/示例里出现的全局调用 vs 注册表/清单** | 幽灵符号：代码 `emit` 了表里没有的信号；或表里有但无生产者 |
| 3 | **类内声明 vs 全局/总线声明** | 同名双栈：类内 `signal X` 与总线的 `X` 同名，导致消费者被触发两次 |
| 4 | **路径引用 vs 权威目录树** | 同一文件在两处不同路径（`config/loader.gd` vs `src/config/loader.gd`）；或路径与“所有源码必须在 src/”之类红线自相矛盾 |
| 5 | **目录树 vs 章节里出现的文件名** | 章节新增了 manager/plugin/脚本，树里没有；或树里有幽灵文件名 |
| 6 | **清单引用的文件 vs 树里实际存在的文件** | 测试清单/契约清单引用了不存在的文件；反向也查 |
| 7 | **目录树自身的重复与畸形** | 同一文件挂在两个目录；把 `.gd` 文件当目录挂子项；`.tscn` 同时出现在源码树与场景树 |
| 8 | **标识符合法性** | 用语言不允许的字符命名（如 GDScript 信号名含 `:`）；名字不符合本项目自定的命名规范 |
| 9 | **红线阈值 vs 实际结构** | 红线写“目录 ≤12 文件”，实际目录有 14 个文件。要么改阈值，要么拆目录，要么写豁免 |
| 10 | **强制门禁 vs 现状可行性** | 红线要求“每个源码文件 1:1 有测试”，实际差几十个。必须把门禁拆成可执行的分级 + 穷举豁免白名单 |
| 11 | **版本号 vs 版本记录表** | 头部已是 vN，记录表止于 vN-1（或重复条目） |
| 12 | **术语/枚举/精度在多节的表述** | LUT 点数与索引范围不符；代码块注释与代码值不符；重复词（“运行时运行时”“快照快照”） |
| 13 | **清单的多个载体之间互相对照**（v6.1） | 注册表同时存在“表格本体 + 顺序链 + 说明列表”多个载体时只改其一——版本记录声称已补登，表格仍缺行（v6.0 SceneManager 事故：改了顺序链漏了表格本体，15 行 ↔ 16 项）。**登记类修复必须覆盖全部登记载体** |
| 14 | **正文代码块路径声明头 vs 目录树（v6.1）** | 代码块首行 `# src/xxx/yyy.gd` 声明了路径，权威目录树却无此文件（basename 级双向比对；GDScript 代码块声明头、测试文件归属同查） |

## 三、执行纪律

### 3.1 同文件多编辑必须逐条串行

在**一条消息里对同一文件并行发多个 Edit 会相互覆盖**（返回成功但静默丢失）。铁律：

- 一条消息只对同一文件发 **1 个 Edit**。
- 每条 Edit 之后用 `grep` 或脚本验证落盘，再发下一条。
- 整段替换比多条局部替换更安全：**优先用「一次 Edit 覆盖一整块」（整张表、整段代码）**，把 5~10 次小编辑压缩成 1 次，减少覆盖风险与轮次。

### 3.2 全局重命名用占位符法，避免自污染

把 `config/loader.gd` 全量改成 `src/config/loader.gd` 时，若直接 `replace_all`，已正确的 `src/config/loader.gd` 会变成 `src/src/config/...`。

**三步法**：

1. `replace_all` 目标**已正确形式** → 占位符 `@@X@@`
2. `replace_all` 旧形式 → 新形式
3. `replace_all` `@@X@@` → 新形式

### 3.3 改完必须跑脚本化回归

不要靠肉眼看收敛。写一次性脚本做**规则化反向校验**（比 grep 更适合多规则交叉）。两条附加纪律（v6.1）：

- **残留/幽灵计数必须排除“变更记录区”**（§版本记录、变更日志）——那里描述缺陷本身的提及是合法的；正文区口径单算。
- **校验脚本报 FAIL 时，先查脚本自身缺陷再改文档**：变量笔误（genexpr 里误用未定义变量）、切分点吃掉首词（`split('：`')` 会吃掉链上第一个反引号词导致少计 1）、正则误匹配（`event_bus.gd` 文件名被当作 `event_bus.` 前缀捕获）都会制造假阳性。长脚本走文件执行，不用 heredoc 内联。字符串字面量发射（如 `EventBus.emit_signal("xxx")`）与动态拼名同罪，须单列扫描规则。

```python
import io, re
s = io.open('设计文档.md', encoding='utf-8').read(); L = s.split('\n')

# 规则1：代码里用的符号 vs 权威表登记（幽灵/未注册）
declared = set(re.findall(r'^\| `([a-z_]+)', s, re.M))
used     = set(re.findall(r'(?:Bus|bus)\.([a-z_]+)\.(?:emit|connect)', s))
# 规则2：类内声明 vs 权威表（同名双栈）
local    = set(re.findall(r'^signal ([a-z_]+)\(', s, re.M))

print('ghost   :', sorted(used - declared))
print('collide :', sorted(local & declared))
print('versions:', [l.split(' ')[1] for l in L if re.match(r'^\| v[0-9]', l)])
# 规则3：旧值残留计数（真实残留应为 0，变更记录中的“描述性提及”需人工排除）
for bad in ['旧路径.gd', 'OLD_SCALE = 1000']:
    print('residual[%s]:' % bad, len(re.findall(re.escape(bad), s)))
```

**关键判读**：残留计数不为 0 时，先定位每一处在哪一行——**变更记录里描述缺陷本身**的提及是合法的，不要误删。

## 四、修复时的四种处置策略（别只会“改成一致的”）

1. **裁决**：多标准冲突时，用技术分析选唯一正确解，并**把否定其他方案的理由写进文档**（防止下一轮又被改回去）。
2. **收敛**：同一物在两处 → 定权威处，另一处删除并留指引注释。
3. **补登**：代码有、表里无 → 补登到权威表，附签名 / 生产者 / 消费者。
4. **改码对齐**：表里有、代码用了别名 → 改代码用登记名，并在代码处注释“禁止另起别名”。

## 五、收尾

- **必须写变更记录**：记录本轮编辑**数量**、每类缺陷、处置结论、以及**过程教训**（含自我纠正）。数量要真实，不要写估算值。
- **区分“本轮回溯”与“历史追溯”**：本轮没做的历史补充不要写进本轮条目。
- **更新项目记忆**：版本号、新确立的红线、新增的约定、踩过的坑。
- 若本轮新确立了一条**可迁移的审计规则**（如“结构化清单必须全表列举”），沉淀进本 skill 或对应用户级 skill，而不是只写进项目日志。
