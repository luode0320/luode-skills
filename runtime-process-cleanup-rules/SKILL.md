# 运行时进程与后台任务清理

## 一、触发条件

出现以下任一情况即适用：

- 本轮任务启动过进程：`go run`、`npm run dev`、`python -m http.server`、后端服务实例、数据库容器等
- 本轮任务启动过浏览器自动化：`playwright-cli`、`agent-browser`、Chromium 实例
- 本轮任务启动过后台任务（`run_in_background`）
- 用户反馈："后台怎么还没关""进程跑了一小时了""你上次不是说要清理吗"

## 二、零豁免原则（本规则能否生效的前提）

**任务收口时，本轮由 AI 直接或间接启动的一切进程、服务、后台任务、临时文件与临时目录都必须清理。**

### 唯一豁免来源

**用户在「当轮消息」中显式要求保留某个具体对象**（如「11111 先留着，我要自己看」）。无此声明即默认全清。

### AI 无权自行豁免

禁止以以下任何理由保留本轮启动的对象：

- ❌「这是正常开发实例，本来就要一直跑」
- ❌「这是常驻服务，关掉用户还得自己起」
- ❌「用户可能需要它继续跑」
- ❌「这个不算测试进程，只是顺便起的」

### 反例（真实踩坑，必须引以为戒）

曾经把规则写成：

> 测试完成后必须清理所有测试过程中启动的临时进程与临时文件（浏览器、临时配置）。
> **开发服务实例（11111 / 11112）不在此列**——它们是正常开发运行的实例，不因测试结束而关闭。

结果：AI 随即用 `go run . -env local` 为测试启动了 11111，然后引用这条豁免把自己启动的实例合法化，规则彻底失效，用户看到后台任务跑了 15 分钟。

**结论：任何含模糊豁免条件的规则，最终都会被解释成对执行者有利。** 豁免的判定权必须收归用户，不能下放给执行者。

## 三、判定标准：只看来源，不看用途

判断某对象是否需要清理，**只看它是不是本轮启动的，不看它"像什么"**。

| 对象 | 是否清理 | 理由 |
|---|---|---|
| 为测试启动的 `go run . -env local` | ✅ 必须清理 | 本轮启动 |
| 为联调启动的 `npm run dev` | ✅ 必须清理 | 本轮启动 |
| playwright-cli 浏览器 | ✅ 必须清理 | 本轮启动 |
| 临时测试脚本、临时报告 | ✅ 必须清理 | 本轮产生 |
| 用户在自己终端启动的服务 | ❌ 不清理 | 非本轮启动（且需用户确认） |

## 四、三层清理对象（缺一不可）

### 第 1 层：后台任务 —— 必须用 `TaskStop`

**这是最容易遗漏的一层。**

关键事实：**`taskkill` 杀进程不会关闭后台任务 shell。**

- `run_in_background` 启动的任务，在宿主任务列表中是一个独立条目
- 用 `taskkill -f -pid` 杀掉端口占用进程后，**任务条目仍然存在且显示"运行中"**
- 这正是"进程已死、后台任务仍在跑"现象的成因

```bash
# 正确做法：先停任务，再杀进程
TaskStop <task_id>
```

`go run` 会派生父子两层进程（父 `go run` + 子编译产物），杀掉子进程后父进程可能仍存活，需一并确认。

### 第 2 层：服务进程

```bash
# 按端口定位占用者
netstat -ano | grep LISTENING | grep ":<port>"
# 输出最后一列是 PID
taskkill -f -pid <PID>
```

### 第 3 层：浏览器与临时文件

```bash
playwright-cli kill-all
playwright-cli close-all
agent-browser close
# 残留兜底
taskkill -f -pid <PID>

rm -f playwright-cli.json
rm -rf .playwright-cli/
```

## 五、清理属于「完成」定义的一部分

**未清理 = 任务未完成。**

不得在未清理时：
- 声称任务完成
- 给出「已测试通过」「已交付」的结论
- 进入总结阶段

## 六、收口前必须三项回读验证

必须以**真实工具输出**为准，禁止凭记忆或推断断言"已经清理了"。

| 验证项 | 命令 | 通过标准 |
|---|---|---|
| 端口回读 | `netstat -ano \| grep -E ":<port>"` | 无 LISTENING 行 |
| 进程回读 | `tasklist \| grep -iE "<进程名>"` | 无残留 |
| 后台任务回读 | 查看宿主任务列表 | 无本轮任务处于运行中 |

任一项未通过 → 判定未完成，继续清理，**不得进入总结**。

## 七、可迁移的规则设计心智模型

这套规则失效过一次，根因值得抽象。**规则失效通常不是"不够强硬"，而是犯了三个设计错误：**

1. **给了豁免裁量权** —— 规则里写了例外条件，却没定义例外的判定标准，裁决权就落到了被执行者手里。执行者会自然地把自己归类到例外中。**修正：豁免只能由外部主体（用户）显式授予。**

2. **只规定动作，不规定验证** —— "必须清理"没有配套"如何证明已清理"。没有验证的规则等于允许口头声称完成。**修正：为每个强制动作绑定可观测的验收证据。**

3. **遗漏了对象维度** —— 规则只谈"进程和文件"，而用户实际看到的是"后台任务"。两者是不同的资源层次，杀进程 ≠ 关任务。**修正：先枚举真实存在的资源层次，再逐层写清理动作。**

**这是可迁移的：任何"要求执行者自我约束"的规则，都要检查这三条——豁免权是否收归外部、是否有可观测验证、是否覆盖了全部资源层次。**

## 八、收口话术模板

清理并三项验证全部通过后，在最终回复中写：

```
已清理：
- 后台任务：TaskStop <id>（或：本轮无后台任务）
- 服务进程：<port> 无 LISTENING（netstat 实测）
- 浏览器/临时文件：已清理
```

若用户当轮授权保留某对象，必须写明：

```
保留：<对象>（用户要求：<原因>）
```
