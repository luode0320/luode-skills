# 实施规划规则

只在来源对象（需求或 Bug）已经基本讲清、边界和目标可执行、当前准备进入编码，但实现路径仍然复杂，需要先把完成条件、异常边界、测试映射和执行步骤拆成清晰实施方案时使用这个 skill。
如果当前问题还是需求信息不全、边界不清或任务还没拆出当前优先闭环，请先转交相邻需求域 skill；但若用户本轮明确在索要计划，也必须先给出“受限计划 / 阻断计划”收口，不能表现成计划规则没有触发。

## Skill 作用与适用场景

- 若当前上下文处于 `Plan Mode`，本 skill 负责接住第一层计划路由，不允许把问题直接绕过去交给需求、Bug、测试或交付域；若当前问题仍存在需求前置缺口，应把它们显式 handoff 给相邻计划前置 skill，而不是直接跳到实施步骤。
- 若当前上下文处于 `Plan Mode`，必须按 `references/plan-question-coverage.md` 逐维度识别实现层不确定决策点并向用户弹窗多选；用户未选择即为“未决(待用户选择)”，禁止采纳推荐项或默认推进，覆盖不足或存在未决决策点时正式计划不放行。
- `implementation-planning-rules` 是 Plan Mode 的唯一计划 Owner：正式、受限和阻断计划均由本 Skill 负责，`reasoning-summary-structure-rules` 在 Plan Mode 下必须判定为 `NOT_APPLICABLE`，不得参与命中列表、模板读取或最终渲染。
- `RULE-PMW-001`：Plan Mode 决策提问进入 `WAITING_DECISION` 后，`request_user_input` 调用必须完全省略 `autoResolutionMs` 字段；该状态没有次数或时间上限，宿主返回空结果不构成取消、授权或完成。
- `RULE-PMW-001` 的上限约束：重发次数没有上限，等待时长没有上限，不得以宿主空答案次数达到某个阈值为由结束任务。
- `RULE-PMW-002`：`request_user_input` 返回 `answers:{}`、缺少答案、缺少预期问题 ID 或宿主隐式超时时，空答案后的下一动作只能是重新调用同一选择框（立即重新调用同一未决选择框）；重发保持原问题 ID、选项、推荐标记和冻结文案。部分答案必须保存并仅重发剩余问题，且旧调用返回后才创建下一次调用，始终只保留一个活动选择框。
- `RULE-PMW-003`：永久等待/重发循环期间禁止任何冻结集合内的可见输出（`commentary`、`limited_plan`、`pending_summary`、`proposed_plan`、`final`、`summary`、`final_answer`、`task_complete`、`result_and_conclusion`），也不得自动采用推荐项、创建 Goal、恢复任务投影或触发自动升级；上下文压缩时必须保留 `WAITING_DECISION`、未决问题 ID、选项和已选答案。
- `RULE-PMW-004`：只有用户完成全部选择、明确授权“你来定/按推荐”、明确要求停止，或工具明确不可恢复且无法再次调用时，才允许离开等待状态；工具故障仍须保持决策未决并报告宿主阻断，不得输出方案总结。
- 若当前上下文处于 `Plan Mode`，且运行环境要求最终计划放进 `<proposed_plan>` 或其他专用计划包裹中，包裹层不改变本 skill 的正文格式要求；外层是渲染协议，内层仍必须按本 skill 模板组织。
- Plan Mode 无未决决策时，唯一合法用户可见计划出口是一对完整的 `<proposed_plan>` 与 `</proposed_plan>` 标签；不得由总结 Skill 生成 `final_answer`、`# 📋 本轮总结` 或其它总结容器。
- 把已经确认的来源对象（需求或 Bug）或当前优先子项，转成编码前可执行的实施规划。
- 当新项目启动或项目初期同时存在多份需求、实施总览或实施周期时，先建立“需求与实施计划全量顺序实施方案”，统一排列需求 -> 实施总览 -> 实施周期 -> 周期内最小任务的全量执行顺序；每个实施计划内继续保留 `AC-*` 完成条件。
- “需求与实施计划全量顺序实施方案”是跨需求 / 跨来源对象的总调度表；它不替代单个来源对象的实施总览、实施周期和最小任务文档，只负责把这些文档串成一个可执行的项目级顺序。
- 实施规划阶段默认采用只读计划模式：禁止写代码、禁止直接改实现、禁止边计划边试做；只允许读仓库、定依赖、列风险、拆任务、写实施文档。
- 明确本轮要改哪些目录、文件、模块和职责边界，避免一边写代码一边临时漂移。
- 若计划包含新增文件，强制使用目录树（`text` 代码块）列出新增文件，并在树节点后标注用途说明。
- 若计划包含数据库新表或字段变更，强制给出可执行 SQL（`CREATE TABLE` / `ALTER TABLE`），禁止只写“需要改表”。
- 给出实施周期拆分、最小任务清单、任务顺序、依赖关系、最小闭环、真实测试安排（建议独立成章）和每一步的验证点。
- 实施计划正文开头必须先写“当前计划最终方案的简要说明”，用 1-3 句先交代推荐方案、主落点和为什么这么做；随后再写“agent 对当前问题的理解”，至少包含：agent 理解的问题 / 目标、本轮计划范围、不在范围、当前优先闭环、关键假设或待确认点；不得直接跳到阶段、任务或测试安排。
- 实施周期是项目第一期、第二期、第三期等大进度单位，也是实施顺序边界；实施文档必须显式写出周期序号、期次定位、周期目标、阶段划分、阶段产出、周期内最小任务清单、进入条件和收口条件。周期决定先做哪一期，最小任务决定当前周期内怎么执行。
- 执行顺序必须先按实施周期推进：当前周期未完成全部最小任务闭环前，不得跳到后续周期；同一周期内必须按最小任务逐个完成“实现 -> 真实测试 -> 6-review 风格回归”。禁止先连续实现多个最小任务再统一测试或统一风格回归。
- 实施计划必须先拆到最小可独立闭环任务粒度；每个最小任务都要单独写清产出、验证点、真实测试要求、任务完成条件、任务停止 / 结束条件、阻断条件和与前后任务的依赖关系。
- 最小任务默认优先按“依赖图 + 垂直切片”拆分，不按前端 / 后端 / 数据库等水平分层批量拆分；每个任务都应尽量形成端到端最小闭环。
- 单任务尽量单次专注完成，且默认应控制在约 5 个文件以内；若明显超过该粒度，优先继续拆小任务，而不是放宽任务边界。
- 实施计划必须显式写出任务完成条件、任务停止 / 结束条件和最大推进边界；长文本 / agent 执行模式下，缺少这些边界就不得进入实现或连续执行。
- 只要计划涉及生成代码、修改代码、重构代码或其他会改变可执行行为的实现变更，就必须显式写出真实测试安排（独立章节），至少包含测试入口、依赖环境、样本 / 数据来源和通过标准，并默认把“真实测试通过”写入完成定义。
- `build`、`lint`、静态检查、代码审查、人工阅读或口头说明都不算真实测试；若当前无法执行真实测试，必须在计划中记为阻断项或受限交接项，不得写成“后面再测”。
- 只有纯文档、纯注释、纯排版、纯静态资源改名 / 搬运、不会影响运行结果的配置说明整理等不改变可执行行为的场景，才允许显式标记“无需真实测试”并写明理由。
- 开发周期应尽量独立可切分；如果当前任务可以拆成多个更小的子任务周期，就不要把多个功能实现硬塞进同一个周期。
- 每个阶段默认只做一件事，只承载一个清晰目标；禁止把多个并列能力揉进同一步骤或同一阶段。
- 实施步骤必须显式归属到具体开发阶段，保证“阶段 -> 步骤 -> 验证点”链路清楚。
- 每个最小任务都必须单独闭环：实现完成后，必须先完成该任务自己的真实测试和 `6-review` 风格回归，再允许推进下一个最小任务；禁止先连续实现多个任务再统一检查。
- 复杂任务必须补图：至少 1 张 Mermaid 流程图，并按 `references/visualization-standard.md` 语义补齐时序 / 状态 / 数据 / 风险图（复杂任务判定与图形化硬门禁见 `references/plan-output-gate.md`）；简单任务可写 `图形化决策：N/A + 原因 + 证据`。
- 在技术路径存在多种合理实现时，先收敛 2-3 个方案，再锁定推荐路线。
- 保证计划中的每一步都可执行、可验证、可交接，不写空泛占位词。
- 正式计划必须满足 `references/cross-session-plan-execution-contract.md`：脱离当前会话后仍能独立执行，且不得依赖思考过程、悬浮窗或隐含工作目录。
- 只要引用其他项目的代码，必须建立 `EXT-*` 外部项目代码引用清单，写明可复现地址、版本/提交、项目根相对路径、文件/符号、引用用途、许可证/复制边界和验证回指；任一缺失都阻断正式计划。
- 将实施方案单独沉淀到 `artifact-storage-rules` 约定的实施总览/实施周期文档位置，作为后续编码、真实测试、`6-review` 和交付总结的阶段性依据。
- 当用户要求“补充需求、实施文档”或“完善实施文档”时，如果当前来源对象已经存在实施周期拆分，必须同步更新受影响的实施周期文档；不得只修改实施总览。若当前变更已经形成新的独立闭环但尚无对应周期文档，必须补建或补齐该周期文档。
- 降低“需求虽然清楚，但真正动代码时落点混乱、顺序错乱、验证遗漏”的风险。
- 对于“原需求已实现、当前只是原需求上的新增改动”的场景，必须在同一份实施总览下新增本次改动对应的实施周期，或在必要时补建新的实施总览；旧实施记录只能作为历史依据保留，不得直接伪装成当前闭环。
## 自动触发信号

- 当前上下文处于 `Plan Mode`。
- 来源对象、边界和完成条件已基本稳定，但任务仍涉及多个文件、多个模块、多个接口、多个步骤或多个验证点。
- `requirement-splitting-rules` 已拆出当前优先子项，但编码前还需要继续细化实施顺序和文件落点。
- 新项目开始、项目初期或大项目规划阶段已经出现多份需求文档、多份实施总览、多个实施周期，执行前需要先确定总执行顺序。
- 用户要求“实施顺序总表”“全量顺序实施方案”“需求与实施计划全量顺序实施方案”“新项目实施总顺序”“项目第一期/第二期整体排序”等跨需求执行索引。
- 用户明确要求先写开发计划、实施方案、落地步骤、任务清单或编码前执行方案。
- 用户明确提出计划型问题，例如“这件事怎么做”“这个需求怎么落地”“先给我一个计划”“先出方案和步骤”“这个怎么改最合适”。
- 用户明确表示“按建议执行 / 按方案执行 / 就按刚才那个建议做 / 按你说的做”，但当前只有聊天建议或方案结论，还没有正式实施计划。
- 用户要求“补充实施文档 / 补充需求、实施文档 / 完善需求与实施文档”，且目标是已有实施总览或实施周期文档。
- 当前实现路径存在多个合理技术方案，需要先比较后收口。
- 不先写计划就容易造成改动范围失控、顺序颠倒、验证遗漏或多人协作断层。
- 当前环境提供了专用计划输出协议（如 `<proposed_plan>`），但仓库仍要求计划正文遵守项目内 skill 模板，而不是退化成通用简版计划。
- 非 Plan Mode 下，任务预计触达 2-5 个文件、包含条件分支或多方案选择、或影响面不完全确定的中等改动（含非 Bug 域的一般性修复与小型调整），即使未达到“多文件 / 多模块 / 多接口”重量级门槛，也应命中本 skill 的 `minimum-plan-grading` 路由；来自 Bug 域的修复固定交给 `bug-fix-proposal-rules` 分级，不在此路由重复处理。

## 条件路由：plan-mode-and-cycle-contracts

本路由统一承接 Plan Mode、建议采纳后的正式计划闸门、全量顺序实施方案、实施总览、实施周期和最小任务闭环。它不改变本 skill 的自动触发条件，只把执行细则从入口文件拆到 reference。

命中后先读取 [plan-mode-and-cycle-contracts](references/plan-mode-and-cycle-contracts.md)，该文件承接本 owner 的阶段流程、边界、暂停条件、通过标准和归档契约；本入口只负责自动触发、主路由和职责裁决。

## 条件路由：minimum-plan-grading

本路由承接“非 Plan Mode 下按改动量分级的最小计划义务”，解决“计划规则只在 Plan Mode 或重量级多模块任务里生效，普通中等改动缺少显式计划环节”的缺口；它不改变本 skill 在 Plan Mode 下的既有流程，只在非 Plan Mode 场景新增一层轻量分级，且不接管 Bug 域已有的分级义务。

命中后先读取 [minimum-plan-grading](references/minimum-plan-grading.md)，该文件承接三级分级标准、“中等”分级最小计划的必填字段、Plan Mode 与非 Plan Mode 的执行边界差异，以及与 `bug-fix-proposal-rules` 的边界说明；本入口只负责自动触发和路由裁决。
