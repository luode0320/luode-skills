# 计划可行性探针

> 归属 owner：`implementation-planning-rules`。本文件负责"计划写完后、放行前，对计划里不可靠的关键假设做真实验证"，不产生独立自动触发入口。与 `plan-devils-advocate-review.md` 的分工：反方批判负责"假设是否值得怀疑"，本文件负责"被怀疑的假设是否真的成立"；批判给出候选，探针给出证据。

## 要解决的问题

计划文档结构完整、字段齐全、测试安排写得漂亮，不代表计划可执行。执行期才发现的问题通常来自计划里被当成事实的假设：

- 计划要复用的函数根本不存在，或签名与计划描述不一致。
- 计划依赖的库版本不提供该 API，或当前环境没有装。
- 计划要调用的外部接口实际不返回计划假设的字段。
- 计划给出的测试入口跑不起来，或测试框架没有计划假设的能力。
- 计划里的数据前提（表、字段、枚举值、配置项）在 local 环境并不存在。
- 计划设想的实现路径在真实运行时性能不达标、超时、内存爆掉。

前四类多数能靠只读手段确认；后两类，以及任何涉及"跑起来会怎样"的假设，必须真实执行才能确认。本文件把"确认假设"从执行期的运气，变成放行前的强制步骤，并明确真实执行的安全边界。

## 探针分级（两级，都算可行性验证）

可行性验证不等于只读。按假设性质选择级别，不要求一律只读。

| 级别 | 名称 | 适用假设 | 允许动作 |
| --- | --- | --- | --- |
| L1 | 只读探针 | 落点存在性、依赖是否安装及版本、配置项存在性、schema 结构、代码签名 | 读文件、查符号、跑版本命令、列目录、读配置、对 local 只读接口发一次请求、不改变状态的编译检查 |
| L2 | 隔离真实探针（spike） | 运行时行为、接口真实返回、依赖真实能力、迁移可行性、性能 / 超时 / 并发、端到端链路是否通 | 在 local 环境启动临时服务、写临时库表或临时数据、装依赖到临时环境、写一次性验证代码、真实执行一次迁移或调用、跑真实压测或超时测试 |

L2 是正式的可行性验证手段，不是越权行为。凡是"只有真跑一次才知道"的假设，必须用 L2，不能降级成 L1 后宣称已验证。

## L2 隔离真实探针的安全边界（强制）

真实执行必须受控，边界如下，缺任一项不得执行：

1. **环境**：只允许 `local` 环境，判定标准沿用仓库的 local 连接红线（连接信息来自 `config_local*`、`.env.local`、`.env.development` 等本地开发配置）。禁止使用 `test` / `prod` / `staging` / `pre` / `release` 配置，即使用户临时提供连接串也不得使用。
2. **资源隔离**：使用临时数据库 / 临时 schema / 临时表 / 临时目录 / 临时端口 / 临时虚拟环境 / 临时容器。不得复用主开发库的既有业务数据，不得在共享开发库中创建与真实业务同名的表。
3. **代码隔离**：一次性验证代码放在仓库外的临时目录，或仓库内明确命名的临时路径；不得改动生产代码主路径，不得把 spike 代码提交为交付物。spike 验证成功后，正式实现仍按计划重写，不直接把 spike 转正，除非计划已明确"复用该 spike"并把它纳入正式任务。
4. **可回滚**：执行前必须写明清理与回滚方案（删临时表 / 删临时数据 / 停临时服务 / 删临时目录 / 卸载临时依赖 / 恢复临时配置），执行后必须真实执行清理并回读验证。
5. **无外部副作用**：不得部署、不得改生产或共享配置、不得调用会改变外部系统状态的接口（发消息、下单、发布、扣款等）、不得写入任何非 local 目标。
6. **进程与产物**：临时服务、后台进程、临时文件按 `runtime-process-cleanup-rules` 在收口前清理并回读验证，不得污染仓库工作树和宿主任务列表。
7. **凭据**：探针输出、日志、计划文档中不得回显凭据原值。

## 与"禁止边计划边试做"的边界

规划阶段的默认姿态仍是只读规划：不写业务代码、不实现功能、不推进交付物。L2 探针是这条规则的**受控例外**，区分标准是目的与产物：

- L2 探针的**目的**只是取证——回答"这个假设是否成立"，不产出交付功能。
- L2 探针的**产物**是一次性的、不进入交付链、执行完即清理；正式实现仍从计划重新开始。
- 如果探针代码开始承载真实业务逻辑、被计划直接引用为交付物、或需要长期保留，它就不再是探针，应立即停止并转回正式计划与实施流程。

换句话说：允许为了"确认可行"真跑一次，不允许为了"省事"把实现提前做掉。

## 关键假设清单（`FEAS-*`）

正式计划放行前，必须从计划正文中提取全部"如果不成立，计划就要改路线"的假设，逐条登记为 `FEAS-*`：

| 字段 | 要求 |
| --- | --- |
| `FEAS-*` | 唯一编号，能被 `TASK-*` 和 `EVIDENCE-*` 回指 |
| 假设内容 | 一句话写清"计划认为什么是真的"，不写模糊的"环境可用" |
| 影响面 | 该假设不成立时，计划要改哪些 `TASK-*` / 哪条路线 |
| 验证方式 | 具体的命令、请求、临时服务或 spike 步骤；写明 L1 还是 L2 |
| 探针级别 | `L1 只读` / `L2 真实` |
| 结论 | `已探针验证` / `只读证据` / `未验证` / `不适用` |
| 证据 | 命令与真实输出摘要、文件路径与行号、符号位置、真实运行结果；不得只写"已确认" |

必须纳入清单的假设类型，以及建议的探针级别：

1. **落点存在性**：计划要修改或复用的文件、目录、类、函数、字段、路由、配置键、数据库表与列是否真实存在，签名是否一致。通常 L1。
2. **依赖可用性**：计划依赖的库、版本、工具链、编译器、测试框架、运行时能力是否已安装且版本满足。查已安装用 L1；验证"装上后真能用"用 L2。
3. **外部接口契约**：计划调用的上游或第三方接口是否真实返回计划假设的字段、状态码和错误语义。读文档用 L1；真实返回必须 L2（可用 mock 或 local 上游）。
4. **环境能力**：计划假设的 local 环境是否具备所需服务、端口、权限、数据量级和配置项。配置存在性用 L1；服务真能起来、权限真够用需要 L2。
5. **数据前提**：计划假设的枚举值、状态取值、数据格式、存量数据规模是否真实存在。查 schema 用 L1；查存量数据规模与分布需要 L2 查询。
6. **测试可执行性**：计划写出的测试入口、fixture、断言手段是否真的能跑，测试框架是否支持计划假设的断言形式。必须 L2——测试跑不起来是典型的"纸面计划"。
7. **运行时行为**：性能、超时、并发、内存、端到端链路是否满足计划假设。必须 L2。

## 结论分级与放行规则

- `已探针验证`：有真实执行输出支撑（L1 命令输出或 L2 真实运行结果）。可直接放行。
- `只读证据`：通过读代码、读配置、读文档确认，未执行。只适用于本质静态的假设；涉及运行时行为的假设不得用此结论。
- `未验证`：没有任何当场证据。
- `不适用`：该假设在本次计划中不存在，写 `N/A + 原因 + 证据`。

放行规则：

- 影响面为**方向级**（不成立就要换技术路线、换落点、换数据模型）的假设，结论必须是 `已探针验证`；涉及运行时行为的，必须是 L2 真实执行结果。`未验证` 或仅有 `只读证据` 时，不得输出正式实施计划，只能输出受限计划并登记 `GAP-*`。
- 影响面为**任务级**（只影响某个 `TASK-*` 的实现细节，不改路线）的假设，允许 `未验证`，但必须在对应 `TASK-*` 的前置条件里写明"执行期第一动作是先验证该假设，不成立则停止并回写计划"。
- 影响面为**无关级**的假设不登记，避免清单膨胀。
- 探针失败不是"计划作废"，而是**证据**：要么改计划路线，要么把失败原因写成阻断项；禁止探针失败后仍然按原假设放行。

## 与其他环节的衔接

- 反方批判（`plan-devils-advocate-review.md`）产出的"无证据假设"必须先落到 `FEAS-*`，再由本文件判定能否放行；批判环节不再单独判定"有证据"。
- 计划自审（`plan-review-checklist.md`）只检查 `FEAS-*` 清单是否完整、结论是否与证据一致、L2 边界是否守住，不重复定义探针方法。
- 跨会话执行契约（`cross-session-plan-execution-contract.md`）里"新会话核验落点与依赖"的步骤，只覆盖 `FEAS-*` 中登记为 `未验证` 的剩余项；已被探针验证的假设不再要求新会话重复验证，避免执行期重复劳动。
- 真实测试安排章节写的是"交付后怎么验证功能"，探针写的是"计划假设是否成立"；两者不得互相替代——探针通过不代表功能正确，测试计划也不能证明假设成立。
- 探针发现计划与代码不一致时，回到计划正文修正，不允许在探针里临时改实现或改代码去迁就计划。
- L2 探针与 `local` 连接红线、`runtime-process-cleanup-rules`、`test-strategy-rules` 的测试资产治理并行生效；探针不是测试资产，不写入根 `test/`，不留档为可执行测试。

## 执行要求

- 探针在反方批判之后、正式计划放行之前执行。
- 先做 L1 全量筛查，再对 L1 无法确认、且影响面为方向级的假设升级到 L2。不要一上来就对所有假设跑 L2，也不要用 L1 结论冒充运行时验证。
- `FEAS-*` 清单与结论写进计划正文的独立小节（建议放在"风险与阻断项"之前），不得只留在对话里。
- 探针命令、真实输出摘要、清理结果写入计划的执行附录或 `EVIDENCE-*`，供执行期和审查回看。
- L2 探针执行前必须在计划或执行记录里先写出清理与回滚方案，执行后回读验证并记录结果；未清理视为探针未完成。
- 探针本身失败（命令不存在、环境不可达、权限不足、依赖装不上）时，如实记录失败输出，按"探针失败"处理，不得把失败包装成 `已探针验证`。
- 纯文档、纯注释、纯排版、纯静态资源改名 / 搬运等无运行时假设的计划，可整体写 `FEAS: N/A + 原因 + 证据`，不逐条造假设。
