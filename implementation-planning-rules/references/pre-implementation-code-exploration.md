# 实施前代码库探索

> 本参考吸收 WorkBuddy 官方 `requirements-pilot` 与 `feature-dev` 的“先理解代码库再实施”原则，但不复制扫描脚本或 `.codebuddy/specs/` 落盘流程。

## 探索义务

正式编码前，只要来源对象（需求或 Bug）边界稳定并准备规划实施，必须先做一次只读代码库探索，并形成发现摘要：

1. 扫描项目结构：项目类型、语言、框架、目录与模块组织。
2. 识别技术栈：包管理器、依赖、构建工具、测试框架与配置。
3. 梳理代码模式：命名、分层、组件组织、API 结构与既有约定。
4. 阅读文档：README、API 文档、贡献指南、既有规格与项目规则。
5. 盘点开发工作流：Git 分支策略、CI/CD、测试策略、部署配置与既有 skill 规则。

## 发现摘要

- 探索结果必须写成可交接的发现摘要，包含：项目类型与用途、技术栈摘要、代码组织模式、既有约定、新功能/修复的集成点、潜在约束。
- 摘要只记录真实读取的事实，不猜测文件内容；引用关键文件时保留路径与证据。
- 探索发现摘要不替代实施总览/周期文档，只作为实施规划的输入。

## 批准闸门

- 用户未显式批准探索摘要前，不得进入正式编码。
- 探索失败、基线漂移或关键文件不可读时停止，回写 `GAP-*` 并回流实施规划。
- 批准只需确认“探索摘要与方向一致”，不要求逐条批准每个文件。
