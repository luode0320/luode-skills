# Plan Mode 决策维度提问与无选择处理协议

> 归属 owner：`implementation-planning-rules`。本文件是条件路由细则，不产生独立自动触发入口。用于 Plan Mode 下按维度识别实现层不确定决策点、向用户多选提问，并在用户未选择时保持未决而绝不默认推进。

## 适用场景

- 当前处于 Plan Mode，且已进入实施规划阶段（需求、边界、验收前置已基本稳定）。
- 需要在正式 `<proposed_plan>` 之前，把实现层所有真实不确定的技术决策点交给用户选择。
- 与需求 / 边界 / 验收前置缺口无关、纯属实现层的技术取舍，集中在本协议处理。

## 决策维度清单

按语义遍历以下维度，判断每个维度当前是否存在“需要用户拍板”的取舍（维度不限于此表，可按任务补充）：

1. 架构 / 技术路线
2. 代码落点（目录 / 包 / 文件位置）
3. 实现方式（存在 2-3 个都合理的方案时的比选）
4. 命名（变量 / 函数 / 类型 / 接口 / 字段口径）
5. 注释（粒度 / 语言 / 风格）
6. 日志（埋点位置 / 级别 / 字段 / 格式）
7. 错误处理与异常策略
8. 数据模型 / 表结构 / 字段
9. 接口契约（请求参数 / 响应结构 / 分页 / 错误码）
10. 依赖与库（复用现有 vs 新增第三方）
11. 测试策略 / 范围 / 样本来源
12. 配置 / 开关 / 环境差异
13. 兼容性 / 迁移 / 版本
14. 性能 / 并发取舍
15. 安全 / 权限
16. 回滚 / 灰度 / 发布方式

## 三态分类

对每个维度先做只读探索，再归入一种状态：

- `已确定`：仓库已有明确约定、既有实现或需求已冻结，可直接采用；必须写出依据（文件 / 约定 / 需求条目），不向用户提问。
- `真实不确定且影响大`：存在多个都合理但影响明显不同的取舍，且无法由探索得出唯一答案；必须向用户弹窗多选。
- `不适用`：本任务不涉及该维度；记 `N/A + 原因`。

禁止就“可由探索得到的事实”提问（如某结构在哪、用了什么框架）；这类先探索，不占用用户决策名额。

## 多选提问协议

- 一律使用 `request_user_input`，禁止在正文里写多选题让用户“回文本选”。
- 每个问题给 2-4 个互斥选项，推荐项置于首位并在标签后标注“(推荐)”；禁止填充明显错误或无意义的凑数选项。
- `AC-PMW-001`：决策型提问一律阻塞，调用 `request_user_input` 时必须完全省略 `autoResolutionMs`；`autoResolutionMs: 60000`、`null`、`0` 等任何显式值都判定为违规。该字段只可用于纯信息性、非决策的可选补充，不能出现在本协议的决策调用中。
- 每次调用最多 3 问；可以登记多个未决决策点，但选择框调用必须串行，任一时刻只保留一个活动选择框，用户完成当前活动框后再进入下一个决策点。
- 多轮迭代提问，直到所有 `真实不确定` 维度都被用户明确选定；重发次数、等待时长和宿主空返回次数均无上限。
- 广度策略为“维度清单驱动”：凡真实不确定的维度都要逐一弹窗，不设硬性数量上限，也不为凑数而问。

## 无选择 = 未决协议（核心，强制）

当已就某决策点向用户弹窗、但用户未做出选择时：

- `AC-PMW-002`：将状态保持为 `WAITING_DECISION`，并将 `answers:{}`、答案缺失、缺少预期问题 ID、`null`/空返回以及宿主隐式超时一律视为“未决”，不是取消、授权、默认选择或任务完成；旧调用返回后，下一动作只能立即再次调用 `request_user_input`。
- `AC-PMW-003`：重发必须沿用相同的问题 ID、选项、推荐标记和冻结文案；若本轮只回答部分问题，先合并保存已选答案，再只发送剩余未决问题，不得丢失已选内容。
- `AC-PMW-004`：重发没有次数或时间上限，禁止设置最大等待时间、重试计数或后台定时器；每次仅在上一调用返回后创建下一次调用，循环中始终只保留一个活动选择框。
- `AC-PMW-005`：循环期间严禁输出冻结集合内的任何可见内容（`commentary`、`limited_plan`、`pending_summary`、正式 `<proposed_plan>`、`proposed_plan`、`final`、`summary`、最终总结、`final_answer`、`task_complete`、`result_and_conclusion`），也不得采纳推荐项或把文本总结当作选择框替代品；所有依赖决策的计划分支保持挂起，不创建 Goal、不恢复任务投影、不触发自动升级。
- `AC-PMW-006`：上下文压缩或会话恢复时必须保留 `WAITING_DECISION`、未决问题 ID、完整选项、推荐标记、冻结文案和已选答案，恢复后继续同一重发循环。
- `AC-PMW-007`：只有用户完成全部选择、明确表达“你来定 / 按推荐 / 随便”等代选授权、明确要求停止，或工具明确不可恢复且无法再次调用时才可终止循环；工具故障须保持未决并报告宿主阻断，不输出方案总结。
- 严禁采纳推荐项，严禁把推荐项写成“默认假设”后继续，严禁以“用户没选就按最优先项推进”为由推进。
- 将该决策点标记为 `未决(待用户选择)`，并列入“待用户选择清单”；只要清单非空，正式 `<proposed_plan>` 和所有依赖分支均不得放行。
- 用户回到任务后，只需在当前活动选择框中完成选择；不要求另发文本唤醒消息。

## 决策维度覆盖表 + 待用户选择清单

在计划正文中维护一张覆盖表，逐维度登记状态：

| 维度 | 状态 | 结论 / 依据 |
| --- | --- | --- |
| 架构 | 已确定 / 已弹窗且用户已选 / 未决待选 / N/A | 写依据、用户所选项，或未决原因 |
| ...（其余相关维度） | ... | ... |

- `已确定`：写明依据来源。
- `已弹窗且用户已选`：写明用户所选项。
- `未决待选`：同时登记到“待用户选择清单”，并说明它挂起了哪些下游内容。
- `N/A`：写原因。

“待用户选择清单”单独成节，列出所有 `未决待选` 决策点、各自选项、以及被挂起的下游内容；只要该清单非空，正式计划一律不放行。

## 相邻域边界

- 需求语义缺口、业务规则、输入输出定义 -> `requirement-intake-rules` / `requirement-change-rules`。
- 是否属于本次范围、兼容边界 -> `requirement-boundary-rules`。
- 拆分优先级 -> `requirement-splitting-rules`。
- 完成标准口径 -> `implementation-planning-rules`。
- 本协议只覆盖“进入实施规划后、实现层面的技术决策点”，不替代上述需求 / 边界 / 验收前置域。
