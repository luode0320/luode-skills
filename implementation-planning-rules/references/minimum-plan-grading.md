# 非 Plan Mode 最小计划分级

> 归属 owner：`implementation-planning-rules`。本文件是条件路由 `minimum-plan-grading` 的细则承载，只在非 Plan Mode 场景补一层轻量分级，不改变本 skill 在 Plan Mode 下的既有流程。

## 要解决的缺口

本 skill 原有自动触发信号只覆盖两类场景：`Plan Mode`，以及非 Plan Mode 下"多文件 / 多模块 / 多接口 / 多步骤"的重量级任务。介于两者之间——非 Plan Mode 下的中等改动（例如涉及 2-5 个文件、存在分支或方案选择，但够不上重量级门槛）——此前只能靠 CLAUDE.md 的 Karpathy 硬闸门做内部隐性收敛，不要求向用户输出任何可见计划。本文件把"计划任何时候都需要，只是确认方式不同"落地为可执行分级：

- Plan Mode：先出计划，等用户明确确认后再执行。
- 非 Plan Mode：先出最小计划，默认直接执行，不必等待逐条确认。

## 与相邻 skill 的边界（先判断归属，不要重复分级）

- 若当前任务来自 Bug 域（问题已定位，准备从"定位"转到"怎么改"），分级和是否需要确认统一交给 `bug-fix-proposal-rules` 及其 `references/confirm-before-coding.md`；本文件不重复介入，避免同一次修复被两套分级规则同时套用。
- 若当前任务命中本 skill 原有重量级触发信号（多文件 / 多模块 / 多接口 / 多步骤 / 多验证点），或当前处于 Plan Mode，继续走完整的实施总览 / 实施周期 / Plan Mode 流程；本分级只处理"够不着重量级门槛，但也不该被 Karpathy 隐性收敛完全代替"的中间地带。
- 纯文档、纯注释、纯排版、确定性的单文件小改动，保留 Karpathy 硬闸门原状，不强制本文件的最小计划文本，避免仪式化开销。

## 三级分级标准（按改动量判定，不按任务来源域判定）

| 分级 | 判定特征 | 计划义务 | 执行方式 |
| --- | --- | --- | --- |
| 微小 | 预计触达 1 个文件、改动约在数行以内、没有分支或方案选择、成功标准显而易见 | 沿用 Karpathy 硬闸门的隐性收敛，内部想清楚假设和成功标准即可 | 直接执行，不强制输出独立计划文本 |
| 中等 | 预计触达 2-5 个文件，或存在条件分支 / 多种实现方式 / 影响面不完全确定，但未达到"多模块 / 多接口"量级 | 编码前必须先输出一段对话内可见的"最小计划"（不必落为 `artifact-storage-rules` 正式文档） | 输出最小计划后默认直接执行，不等待用户逐条确认 |
| 重量级 | 命中本 skill 原有自动触发信号（多文件 / 多模块 / 多接口 / 多步骤 / 多验证点），或当前处于 Plan Mode | 沿用本 skill 现有完整实施总览 / 实施周期 / Plan Mode 流程 | Plan Mode 下必须等待用户明确"开始实施"；非 Plan Mode 下仍需完整实施文档 |

## "中等"分级最小计划的必填字段

不需要固定标题模板，可以是回复正文里的一段结构化文字，但必须包含：

1. **改动目标**：这次要解决或实现什么。
2. **方案**：打算怎么改，涉及哪些文件 / 函数（点出关键落点即可，不需要完整目录树）。
3. **影响范围**：会不会碰公共方法、共享逻辑或外部契约；如果会，说明为什么仍判定为"中等"而不是"重量级"。
4. **验证方式**：改完后怎么验证，真实测试优先；纯文档 / 纯注释类可写"无需真实测试"并给理由。

## Plan Mode 与非 Plan Mode 的执行边界差异

- **Plan Mode**：不论分级是微小、中等还是重量级，只要当前处于 Plan Mode，一律按本 skill 现有 Plan Mode 全流程处理（决策点弹窗、`<proposed_plan>` 输出、等待用户明确"开始实施"才能进入编码）；分级只影响非 Plan Mode 的执行节奏，不降低 Plan Mode 的确认要求。
- **非 Plan Mode 且分级为"中等"**：最小计划输出后默认视为已获得继续执行的授权，可直接进入实现，不需要额外等待用户逐条确认；但若最小计划本身暴露出"必须先确认"的信号（会改公共模块、共享逻辑、对外契约，或存在两个以上代价明显不同的方案），仍必须停下来等用户确认，不得默认执行——这一判断口径与 `bug-fix-proposal-rules/references/confirm-before-coding.md` 的"必须先确认"清单保持一致。

## 触发时机与再评估

- 一旦判定当前非 Plan Mode 任务属于"中等"及以上分级，最小计划必须在正式开始编码前的第一次回复中给出，不得先动手改代码再补计划。
- 若执行过程中发现实际改动量超出最初判断（例如中途发现要碰的文件明显超过 5 个，或触及了公共模块），必须停下来重新评估分级，必要时升级为重量级并转入本 skill 完整实施规划流程。

## 与归档的关系

- "中等"分级的最小计划默认不需要写入 `artifact-storage-rules` 的正式实施文档；如果该任务本身已归属某个既有需求或 Bug 主文档，可以顺带在其记录里补一句最小计划摘要，但不为此单独建档。
- 若后续判断需要升级为重量级，再按本 skill 主流程的归档要求建实施总览 / 实施周期文档。
