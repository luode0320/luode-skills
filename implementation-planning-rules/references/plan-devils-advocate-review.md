# 方案反方批判（吸收自 grill-me 魔鬼代言人）

> 归属 owner：`implementation-planning-rules`。本文件是正式计划放行前的方案内容挑战环节，不产生独立自动触发入口。吸收来源：`softspark-ai-toolkit-grill-me`（LobeHub，v1.0.1）。与 `plan-review-checklist.md` 的分工：自审清单负责"结构完整性"（字段、覆盖度、占位词、可执行性），本文件负责"内容反方批判"（方案假设是否成立、推荐路线是否会被现实打脸）。两者都要做，先结构自审，再反方批判。

## 适用场景

- 技术路径已收敛出推荐方案（推荐路线、推荐落点、推荐实现方式）后、正式计划放行前。
- 用户坚持某个方案但方案有明显风险假设，或方案里存在"应该没问题""一般就是这样"类含糊依据时。
- 多方案比选已给出推荐项，但推荐项的关键取舍尚未被挑战时。
- 不适用：纯文档、纯注释、纯静态资源搬运等无方案取舍的场景，写 `N/A + 原因 + 证据` 即可。

## 核心姿态：目的不是通过，是找出漏洞

- 对推荐方案默认先问"如果它最可能失败，会败在哪里"，而不是先写"方案可行"。
- 反方批判产出一个明确的**反方结论**：`方案假设是否成立 / 推荐路线是否仍成立 / 需要补什么再放行`，三种结论必选其一。
- 批判只针对方案内容与假设，不针对决策者；控制在 3 条以内按严重度排序，避免无限抬杠。

## 批判维度（按任务裁剪，不适用写 N/A）

1. **假设挑战**：方案依赖的关键假设（技术可行性、依赖可用性、数据前提、上下游接口、环境能力）是否有证据支撑；无证据的假设是否已被标记为待确认或阻断项。
2. **依赖与顺序**：推荐路线是否隐含了未验证的依赖顺序；先做 A 再 B 的依据是否真实，还是口头顺序。
3. **取舍反方**：推荐方案相对被否方案的优势是否真实成立；被否方案是否有被低估的收益（如维护成本、兼容性、回滚难度）。
4. **边界与异常**：方案是否只覆盖了主路径，边缘案例（空数据、并发、超时、权限、迁移中断）被假设成"不会发生"。
5. **可验证性**：方案的完成标准是否真的可测；如果反方无法设计出验证方式，该方案不可放行。
6. **回滚与失败代价**：方案失败时回滚成本是否可接受；有没有"一旦上线就下不来"的单向门。
7. **跨会话可执行性**：交给新会话执行时，方案里的隐含上下文是否足以独立推进；依赖"思考过程/悬浮窗/上一轮输出"的部分视为反方缺口。

## 执行要求

- 反方批判在方案收敛后、正式 `<proposed_plan>` 放行前执行；批判结论写进计划正文"主要风险"区，不得只在对话里提一句。
- 反方批判发现的新阻断项（如某假设无证据且方向级），必须登记为计划级 `GAP-*` 或升级为阻断计划，不进入正式计划。
- 反方批判不通过的方案回到方案比选或补充证据，不允许"先放行，实现时再看"。
- 用户明确知晓反方风险仍坚持原方案时，不反复纠缠；记录"已知晓反方风险仍坚持"，把风险写入计划风险区由实施周期消化。

## 与现有规则的边界

- 结构自审、字段矩阵、占位词检查：以 `plan-review-checklist.md` 与 `plan-output-gate.md` 为准，本文件不改变其必填项。
- Plan Mode 决策提问与未决协议：以 `plan-question-coverage.md` 为准，本文件不新增提问渠道、不改变 `WAITING_DECISION` 语义。
- 只读规划模式：本文件仍属规划阶段，禁止边批判边写实现代码。
