# TDD 工作流（红→绿→重构，吸收自外部 tdd skill）

> 归属 owner：`implementation-planning-rules`。本文件是最小任务内的测试驱动实现节奏，不产生独立自动触发入口。吸收来源：`skillmd.ai/tdd`（SkillMD 生态，Kent Beck / Michael Feathers / Fowler 方法 + Ousterhout 反方）。与本地规则关系：`test-strategy-rules` 的隔离红线（禁止污染生产代码）、`test-program-rules` 的根 `test/` ASCII 镜像落点、`functional-validation-rules` 的真实运行验证全部保留；本文件只补"测试先行"的实现节奏，不改变任何既有红线。

## 适用场景

- 实现新功能、修复缺陷、重构存量代码，且行为可被自动化测试描述时，默认走 TDD 节奏。
- 需求/缺陷的完成条件已冻结为 `AC-*` 且可映射为测试断言时。
- 最小任务执行到"实现"环节时，优先先写失败测试（红），再最小实现（绿），再重构。
- 不适用或允许跳过：探索性 spike（保留代码则补测）、紧急 hotfix（事后立即补测）、纯 UI/样式改动、一次性脚本、一次性原型（见"使用/跳过时机"）。

## 核心节奏：红 → 绿 → 重构

1. **红（RED）**：先写一个失败的测试，描述期望行为，而不是实现。
   - 测试必须能独立运行且可断言失败；运行一次确认它确实失败（避免"永不失败的测试"）。
   - 测试放在根 `test/` 的 ASCII 源码镜像目录（遵守 `test-program-rules`），禁止在源码目录落 `*_test.go`。
2. **绿（GREEN）**：写**最小**代码让测试通过。
   - 只为实现该断言，不加额外逻辑、不做优化、不提前处理边缘案例。
   - 可"faking it"（先硬编码值让测试通过，再逐步泛化）。
   - 运行测试确认通过。
3. **重构（REFACTOR）**：保持测试全绿的前提下清理实现。
   - 提取 helper、重命名变量、消除重复；每步重构后跑全量相关测试。
   - 重构不得改变外部行为；行为变化必须先回到红阶段。

## 强制规则

- **没有失败测试，不写生产代码**：进入实现环节前必须先有红测试；禁止"先写实现，测试后补"作为默认顺序（本地"实现→真实测试"闭环只作为 TDD 不适用场景的降级路径，且仍需真实测试）。
- **一次一个行为**：每个测试只描述一个行为；测试名出现 "and" 或并列语义时拆成多个测试。
- **小步推进**：每次只走一小步（一个断言/一个最小改动），不跨多个行为批量实现。
- **测试快速且隔离**：单测不依赖真实网络/数据库（用 mock/stub/fake，按 `test-program-rules` 落点）；慢的外部依赖留给集成/联调层（`functional-validation-rules`）。
- **绿后提交**：每个"绿 + 重构"完成的小循环提交一次；提交信息引用对应 `AC-*` / 测试文件。

## 行为驱动要点

- 测试断言的是**行为**（输入→输出、状态变化、副作用），不是内部实现细节。
- 不把测试写成实现的白盒镜像（不因重构被迫改测试，除非行为确实变了）。
- 先写断言（期望结果），再倒推输入与调用，再实现。

## 三个 TDD Pattern

1. **从断言开始（Start with the Assertion）**：先写 `expect(result).toBe(42)`，再补 `const result = calculate(input)`，再补 `input`。
2. **三角测量（Triangulation）**：用多个示例驱动泛化——`double(2)=4` 与 `double(3)=6` 同时成立时才必须实现通用解，避免用硬编码糊弄。
3. **直接实现（Obvious Implementation）**：解法显而易见时直接写实现让测试通过，不必刻意绕路。

## 使用 / 跳过时机

| 场景 | 是否走 TDD | 说明 |
| --- | --- | --- |
| 新功能，需求明确 | ✅ | 测试即设计，先定义行为 |
| 缺陷修复 | ✅ | 先写复现缺陷的失败测试，再修复 |
| 存量代码重构 | ✅ | 先补特征化测试（characterization）兜底行为，再重构 |
| API / 接口设计 | ✅ | 测试能暴露接口易用性问题 |
| 长期维护的代码 | ✅ | 测试是安全网 |
| 探索性 spike | ⚠️ 跳过 | 保留代码则事后补测 |
| 紧急 hotfix | ⚠️ 跳过 | 事后立即补测 |
| 纯 UI / 样式 | ❌ | 无行为断言价值（页面交互仍走 `functional-validation-rules` 真实验证） |
| 一次性脚本 / 原型 | ❌ | 不保留则不测 |

## Ousterhout 反方（平衡，防教条）

> "TDD 的问题在于把注意力集中在让特定功能工作，而不是找到最佳设计。" —— John Ousterhout

- 探索性 / 架构性工作：先设计、再补测试；不要让测试把设计逼进角落。
- 警惕"战术编程"：测试驱动可能产出"易测但难懂"的代码；每轮重构后回看整体设计。
- 避免过度测试实现细节（把内部函数当公共 API 测）；行为测试为主，实现细节测试为辅。

## 与本地规则的边界

- 隔离红线（禁止为测试污染生产代码）：完全保留，TDD 的红测试也必须在 `test/` 侧实现，不得为可测性改生产代码（`test-strategy-rules/references/production-test-pollution.md`）。
- 根 `test/` ASCII 镜像、Go 编译路径：完全保留（`test-program-rules`《Go 测试编译路径（强制）》）。
- 真实运行验证：TDD 的单测绿不代表功能验证通过；联调/接口层仍按 `functional-validation-rules` 走真实运行验证。
- 最小任务闭环：TDD 节奏在最小任务内部执行，任务收口仍按"实现 → 真实测试 → 6-review 风格回归"完成闭环，不因 TDD 免除收口测试。
- 测试策略：何种测试类型、优先级、样本分布仍由 `test-strategy-rules` 裁决，本文件不改变测试策略域。
