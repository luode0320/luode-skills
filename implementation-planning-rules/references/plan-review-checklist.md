# 实施规划自审清单

## 任务表体检（吸收自外部任务拆解 skill）

> 结构自审前先做任务表体检：检查重复任务、依赖环、无人负责事项与顺序冲突；与反方批判（方案假设挑战）互补，本节省结构性错误。

- 是否存在**重复任务**：两个或多个最小任务目标语义相同、落点相同、验收相同，却各自立卡；发现后合并或删除，不保留并行重复项。
- 是否存在**依赖环**：任务 A 依赖 B、B 又直接或间接依赖 A；按 `task-granularity-and-order.md` 的依赖图检查，发现环必须拆解或调整顺序，禁止带环放行。
- 是否存在**无人负责事项**：最小任务/阶段/周期无归属、无 `TASK-*`、无 owner、无周期内顺序，或验收/测试/回滚字段空缺；补齐归属与字段后再放行。
- 是否存在**顺序冲突**：任务起止与前置依赖矛盾（依赖未完成却排期在前）、里程碑与周期收口不一致；本地以依赖顺序为准，冲突即阻断。
- 是否存在**孤儿任务**：任务不归属任何 `CYCLE-*`，或周期无进入/收口条件；按周期契约归位。
- 是否**承诺了无法兑现的工期或负责人**：不得在缺少人员与产能信息时凭空指定负责人或精确排期，也不得替用户承诺工期；写 `N/A + 原因 + 证据` 或标记待确认。

## 反方批判检查（吸收自 grill-me 魔鬼代言人）

> 结构自审覆盖度、占位词、密度、可执行性之前，先对推荐方案做内容反方批判；两者都要做，批判细则见 `plan-devils-advocate-review.md`。

- 推荐方案的关键假设（技术可行性、依赖可用性、数据前提、上下游接口、环境能力）是否都有证据支撑；无证据假设是否已标记待确认或阻断。
- 推荐路线是否隐含未验证的依赖顺序；"先 A 后 B"的依据是否真实，还是口头顺序。
- 推荐方案相对被否方案的优势是否真实成立；被否方案是否有被低估的收益（维护成本、兼容性、回滚难度）。
- 方案是否只覆盖主路径，边缘案例（空数据、并发、超时、权限、迁移中断）是否被假设成"不会发生"。
- 方案的完成标准是否真的可测；反方若无法设计验证方式，该方案是否未放行。
- 方案失败时回滚成本是否可接受；是否存在"一旦上线就下不来"的单向门。
- 反方批判结论（方案假设成立 / 推荐路线仍成立 / 需补充再放行）是否已写进计划"主要风险"区，而不是只在对话里提一句。
- 反方批判发现的新阻断项是否已登记 `GAP-*` 或升级为阻断计划，而非"先放行，实现时再看"。
- 用户已知晓反方风险仍坚持原方案时，是否已记录"已知晓反方风险仍坚持"并写入风险区。

## 覆盖度检查

- 若当前处于 Plan Mode、最终回复使用 `<proposed_plan>`、或输出正式计划 / 受限计划 / 阻断计划，是否已执行 `references/plan-output-gate.md`。
- 当前计划类型是否已明确归类为正式实施计划、受限计划或阻断计划。
- 当前计划类型对应的必填字段矩阵是否全部通过。
- 正文开头是否先给出“当前计划最终方案的简要说明”，而不是直接进入基本信息。
- 当前计划最终方案简要说明是否已经讲清推荐方案、主落点和选择原因。
- 当前优先闭环是否清楚。
- 是否已经先写出 agent 当前理解的问题 / 目标，而不是直接跳到阶段或任务。
- 是否已经写出本轮计划范围、明确不在范围和关键假设 / 待确认点。
- 规划阶段是否保持只读，没有把“先试做一点”混进计划过程。
- 是否已写出实施周期总览。
- 若当前是新项目、项目初期或多来源对象场景，是否已写出或回指“需求与实施计划全量顺序实施方案”。
- 全量顺序总表是否能回指需求文档 / Bug 主记录、验收标准、实施总览、实施周期和周期内最小任务摘要。
- 是否已经有独立的真实测试安排章节，而不是只散落在最小任务字段、验证点或备注里。
- 实施周期是否被写成第一期、第二期、第三期等大进度单位，而不是普通分组标题。
- 是否已写清周期顺序、每个周期的期次定位、进入条件、收口条件和与前后周期的衔接关系。
- 是否已明确当前计划为何可以独立成一个实施周期。
- 若任务还能拆成多个更小的子任务周期，是否已继续拆分，而不是硬并到一个周期里。
- 是否已写出阶段清单，且每个阶段只有一个清晰目标。
- 是否已写出最小任务清单。
- 每个最小任务是否都归属且只归属一个实施周期。
- 每个最小任务是否都写清周期内顺序。
- 每个周期是否都列出本周期最小任务执行顺序。
- 每个最小任务是否只承载一个独立目标。
- 最小任务是否优先按“依赖图 + 垂直切片”组织，而不是按前端 / 后端 / 数据库水平分层堆叠。
- 每个最小任务是否已经标出预计触达文件数；若明显超过约 5 个文件，是否已继续拆分。
- 目录、模块、文件落点是否清楚。
- 若涉及新增文件，是否已使用目录树（`text` 代码块）列出新增文件，并在树节点后标注用途。
- 若涉及数据库新表或字段变更，是否已给出对应 SQL（`CREATE TABLE` / `ALTER TABLE`）。
- 是否已经写出任务顺序、依赖关系、周期/阶段归属和验证点。
- 是否已经为每个最小任务写出实现产出、计划完成条件、测试点和 `6-review` 风格回归点。
- 每个最小任务的计划完成条件和 `6-review` 规则来源是否已冻结本轮必须通过项，未冻结的通用质量项是否明确按模型默认自查、不在执行期临场新增计划外硬阻断。
- 若涉及代码生成、修改或重构，“现状与落点”是否已经给出代码落点目录树，而不是只列文件名、模块名或普通条目。
- 涉及代码变更的最小任务，是否已经写出真实测试是否必需、测试入口、依赖环境、样本 / 数据来源和通过标准。
- 若标记“无需真实测试”，是否明确属于纯文档、纯注释、纯排版、纯静态资源改名 / 搬运或不会影响运行结果的说明整理，并已写明理由。
- 是否已经分别写出任务完成条件、任务停止 / 结束条件和最大推进边界，而不是混成一句空话。
- 是否已经说明主要风险、阻断项和待确认点。
- 新会话脱离当前对话后，是否能根据计划识别主项目地址、仓库类型、代码基线、第一步、当前任务、local 环境、依赖入口和中断点核验顺序。
- 计划是否明确不依赖思考过程、悬浮窗、上一轮输出或隐含工作目录。
- 只要引用其他项目代码，是否逐个建立 `EXT-*`，并填写项目地址、版本/提交、项目根相对路径、文件/符号、用途、许可证/复制边界、可达性失败停止条件和 `TASK -> TEST/EVIDENCE` 回指。
- 没有外部项目代码引用时，是否写出 `N/A + 原因 + 证据`，而不是留空或写“按需”。
- 是否已明确任务完成以计划完成条件、真实测试和 `6-review` 结果为准。
- 若当前是受限计划 / 阻断计划，是否已经明确写出“受限计划不得作为实施授权”，以及升级为正式执行计划前禁止进入编码、改码、重构、测试实施或其他执行动作。

## 占位词检查

- 不允许保留 `TBD`、`TODO`、`后续补充`、`实现时再看`。
- 不允许用“若干文件”“相关逻辑”“对应模块”等模糊说法代替具体落点。
- 不允许用“优化一下”“处理一下”代替实际执行动作。
- 不允许用“本阶段顺手一起做”“这个周期把几个功能都做完”这类混合目标表述。
- 不允许用“这个最小任务顺手再做一点”“一起补掉”把多个目标混进同一个最小任务。
- 不允许出现“后端先全做完”“前端统一补”“数据库最后一起改”这类水平分层推进表述，除非已明确说明无法切成垂直闭环的原因。

## 内容密度检查


- 每个最小任务是否已填写完整的零决策字段：文件/符号、操作、禁止触碰区、精确测试命令、断言、清理、回滚、完成条件、停止条件？
- 最小任务字段中是否存在空字段、纯标题字段，或写有"见上文""后续再定""若干文件""对应模块""TBD""TODO""实现时再看"等占位/模糊表述？
- 正式实施计划的主章节是否仅包含章节标题（如"最小任务清单""实施周期总览"等），但各任务或周期内缺少可执行的具体字段内容？
- 宿主外层包裹（如 `<proposed_plan>`）是否以简洁为由删减了计划正文中的任务字段、细节或零决策事项？
- 计划正文中是否存在"见上文""后续再定""若干文件""对应模块""TBD""TODO""实现时再看""按需""后续补"等占位词或模糊表述，且未附 `N/A + 原因 + 证据`？
- 代码变更类计划中，最小任务是否只列出文件名清单，未给出代码落点目录树（`text` 代码块格式）？
- 正式实施计划中所有最小任务的字段集合（文件/符号、操作、禁止触碰、真实测试、断言、清理、回滚、完成条件、停止条件）是否齐全，是否存在空字段或纯标题字段？
- 是否已检查"思考中已形成的细节是否完整写入了计划正文，未做合并或省略"？
- 是否已检查"跨会话执行所需细节已完整落盘，交给新会话无需重新猜测"？

## 可执行性检查

- 是否存在 `Summary`、`Key Changes`、`Implementation Changes`、`Public Interfaces`、`Test Plan`、`Assumptions` 等通用工程计划壳；若存在，是否已判定为未通过并重写。
- 是否存在“基本信息先开头、没有当前计划最终方案简要说明”的旧结构；若存在，是否已判定为未通过并重写。
- 若当前是受限计划，是否明确写出禁止实施说明和升级为正式实施计划的条件。
- 若当前是阻断计划，是否明确写出阻断证据、恢复路径、不得执行事项和重新进入条件。
- 每一步是否能直接指导后续编码。
- 每一步完成后是否能形成可检查结果。
- 计划开头的问题理解是否足以约束后续阶段、任务和测试，不会出现“后面写得很细但前面理解错题”。
- 是否把 `build`、`lint`、静态检查、代码审查或人工阅读误当成真实测试。
- 每个实施周期结束后是否有明确的任务停止 / 结束条件，而不是依赖“下一步建议”继续扩散。
- 顺序是否符合依赖关系，而不是纯口头顺序。
- 是否存在一上来就把改动面铺太大的问题。
- 每个阶段是否真的只做一件事。
- 每个步骤是否已经标明所属开发周期与所属阶段。
- 每个步骤是否已经标明对应最小任务。
- 是否已经说明每个最小任务为什么能形成端到端最小闭环，而不是模块清单。
- 当前最小任务未满足实施计划完成条件、未完成实现、真实测试和 `6-review` 前，是否明确禁止进入下一最小任务。
- 当前实施周期未完成全部最小任务闭环前，是否明确禁止进入下一实施周期。
- 当前全量顺序总表所指向的来源对象 / 实施周期未收口前，是否明确禁止跳到后续来源对象或后续项目期次。
- 是否不存在“先连续实现多个最小任务，再统一真实测试 / `6-review`”的周期级批处理写法。
- 每个最小任务完成后是否都有可独立检查的闭环结果。
- 代码变更类计划是否已经把落点明确到目录树层级，而不是只写“改这里”“修一下”。
- 周期与阶段之间是否能独立交接，而不是必须依赖大段口头上下文。
- 新会话是否可以按计划的第一步和当前任务继续，不需要读取原会话历史才能理解执行边界。
- 外部项目代码引用是否可以按地址和版本复现，不需要执行者自行搜索或猜测项目位置。
- 命中文件新增或数据库变更场景时，缺目录树或缺 SQL 必须判定为未通过；若仍使用普通条目描述目录信息同样判定未通过。

## 图片资产与 Mermaid 边界检查

- 是否在实施总览、实施周期和每个涉及图片的最小任务中写明 `图片资产决策：需要`，或 `N/A + 原因 + 证据`？
- 需要图片时，是否冻结了真实 `imagegen` 输入、失败阻断、`doc/data/images/` 目标路径、命名版本和 `IMG-*`？
- Markdown 图片是否均为从当前文档位置计算的 `/` 分隔相对路径，alt 非空且含 `IMG-*`，无绝对/远程/Base64/HTML/越界/反斜杠/旧路径？
- 资产清单是否记录用途、来源、相对路径、版本、关联 `REQ/RULE`、`AC`、`CYCLE`、`TASK`、引用章节、敏感状态和版权状态，并能检查孤儿图片？
- 是否明确 Mermaid 继续负责流程、时序、状态、依赖和数据关系，图片未替代既有 Mermaid 图、任务依赖图或周期门禁？
- 判定为复杂任务的计划，是否含 >=1 Mermaid 流程图并按语义补齐时序 / 状态 / 数据 / 风险图？简单任务是否写了 `图形化决策：N/A + 原因 + 证据`？（复杂任务判定阈值见 `plan-output-gate.md`）
- 是否在真实测试安排中包含图片存在性、格式签名、引用一致性、决策一致性、非孤儿和 imagegen 可用性断言？

## 交接性检查

- 其他人接手时，是否能根据这份计划知道先改什么、改哪里、怎么验。
- 其他人接手时，是否能明确当前做到哪个周期、哪个阶段、哪个最小任务、下一步承接什么。
- 后续真实测试、`6-review` 和交付是否能引用这份计划收口。
- 如计划被需求变更推翻，是否容易在同一份文档里更新差异。
