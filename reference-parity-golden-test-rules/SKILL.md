# 参考实现一致性校验规则

只回答一个问题：**生产实现与参考实现在同一输入下，是否产出完全相同的输出。**
不是"差不多"，不是"趋势一致"，是同一组数字。

## 第一铁律：参考实现是唯一真值（强制）

- **绝对禁止**为了让测试通过、让 diff 变小、让代码"更合理"而修改参考实现。
- 若生产实现与参考实现不一致，**只能改生产实现**。
- 若生产实现看起来"更对"（参考实现有 bug），**停下来问用户**，不要自行裁决。参考实现即使有 bug，也是线上真值——因为线上跑的就是它。
- 向用户复述这条约束并确认，避免"顺手优化参考实现"。

## 自动触发信号

- "校验我们代码和 XX 的回测/原型/脚本一致吗"
- "把这份实现移植到 XX 语言" / "照抄 XX 的逻辑"
- 用户说"不能改参考实现，不然就不一致了"
- 发现两处实现同名函数但语义不同（如聚合式 vs 逐元素式）

## 执行流程

### 第 0 步：冻结参考语义（先跑，再看代码）

1. **先把参考实现跑起来**，拿到一组**精确基线数字**，而不是只读代码：
   ```
   <venv>/python reference/main.py   # 记录 stderr/stdout 全部关键量
   ```
2. 基线必须包含：终值（净值/余额，保留全部小数位）、事件计数（买 N 次/卖 N 次）、过程量（手续费、现金、持仓）、以及**中间态快照**（未平仓列表、当前锚点、游标位置）。
3. 把这些数字**逐字抄进文档/测试**，作为不可协商的期望值。禁止四舍五入成一两位小数——舍入会把"差 1 个原子单位"掩盖成"通过"。
4. 逐行读参考实现，产出「语义清单」：每个函数、每个分支、每个取整方向、每个费率、每个边界判断。写清 **谁先谁后**（动作顺序常常是差异根源）。

### 第 1 步：逐行比对，产出差异表

对每一个语义点，标注生产实现是"一致 / 不一致 / 缺失 / 多余"。
**特别注意这几类高频偏差：**

| 高频偏差 | 表现 |
|---|---|
| 聚合 vs 逐元素 | 参考实现按"每个批次独立判断"，生产实现按"整轮合计判断"——数学上不等价 |
| 取整方向 | `ceil` 用于买入数量（向上），`floor` 用于卖出对齐；方向反了会长期累积偏差 |
| 动作顺序 | 同一次 tick 内先"止盈判断"还是先"加仓判断"，结果完全不同 |
| 隐式费率 | 参考实现在成本/收益里内嵌了费率，生产实现漏算或双边算成单边 |
| 状态重置时机 | 平仓后何时重锚、锚点是固定值还是随批次变化 |
| 默认值/上限 | 参考实现没有的"最大格数""单格上限"等，生产实现擅自加了，等于改了策略 |

### 第 2 步：重写生产实现对齐

- 以参考实现的**函数粒度**为单位对齐，函数名可以不同，**语义必须一一对应**。
- 保留参考实现的**全部怪癖**（多余的 epsilon、奇怪的边界判断），并在代码注释里标注"对齐参考实现第 N 行"。
- 精度必须用定点/十进制类型（`shopspring/decimal`、`BigDecimal`），**决策路径禁止 float**。

### 第 3 步：分层黄金回归测试（核心交付物）

**单一层次的比对不足以证明一致。** 按下面的层次建测试，**每层都必须有，全部通过才算一致**：

| 层 | 断言对象 | 抓什么风险 | 单层失效模式 |
|---|---|---|---|
| 1 聚合 | 终值 + 事件计数 + 终态持仓 | 整体量级、方向 | 内部差异互相抵消 |
| 2 逐笔/逐事件 | 每一笔事件的字段流水 | 动作顺序、单笔金额、累计量漂移 | 需先有逐笔数据 |
| 3 组合/多参数 | 多标的、多参数组逐组比对 | 参数装配、步长/精度、数据覆盖差异 | 需先有组合口径基线 |

**为什么必须有第 2 层**：聚合断言存在**抵消盲区**——例如多买一笔又少卖一笔，终值可能仍落在容差内；手续费与持仓在数值上互补，也会互相掩盖。只有逐笔流水比对能消除这种可能。

**为什么必须有第 3 层**：单标的最优参数只覆盖一条路径。多标的/多参数组能同时覆盖：不同本金口径（如组合跑法下每标的 principal = 总额 × 权重，而非总额本身）、不同精度步长（跨数量级的 lot/stepSize）、不同数据覆盖区间（有的标的缺月、有效行数不同）。

各层的公共要求：

1. **喂真实数据**：读取参考实现**实际使用过的同一份数据源**（缓存/导出/固定 fixture），不要另造数据。数据路径用环境变量覆盖 + 默认值兜底：
   ```
   BINANCE_BACKTEST_CACHE（或对应项目变量），缺省回退参考实现的缓存目录
   ```
2. **走生产代码的真实入口**（同一个决策函数），不要为测试复制一份逻辑。
3. **断言精确值**：把参考实现的完整小数位原样写入期望值。差异判定见下节「容差规则」。
4. **同时断言中间态**：未平仓批次的价格/数量逐个比对，锚点值比对。
5. **逐笔层必须断言过程量**：每一笔之后的现金、持仓、累计手续费都要比对——只断言"这笔卖价对不对"会漏掉记账错误。
6. 测试失败时打印完整的生产 vs 参考对照（每一项差多少），让下一次排查能直接定位。**日志纪律：把不一致计数放在 `bad` 计数器里，只有 `bad == 0` 才打印"通过"**——否则失败时也会打印"通过"，日志会误导后来人。
7. 数据缺失时 `t.Skip` 并说明如何获取，**不要伪造数据让它绿**。

### 第 3.5 步：变异校验（证明测试真的在守）

黄金数据是**人工抄进来的**，因此必须反向验证一次：**故意把期望值改错一个字段，确认测试 FAIL 且错误定位到该字段**，然后改回。

- 每次新增/修改黄金测试后做一次，尤其是本次刚注入的数据。
- 选一个**真实业务字段**（价格、数量、计数），改动量略大于容差即可。
- 若改错了却仍然 PASS → 断言写错了（字段没被真正比较、比较对象搞反、容差过宽），必须修好再继续。
- 校验完立刻还原，并用 grep 确认还原（避免把注入的错误值留在仓库里）。

### 第 4 步：参数漂移守卫

参数常被改在配置文件里，脱离代码审查视野。补一个独立测试，把生产配置（yaml/env/常量）与参考实现里的参数表**逐字段比对**，任何一项不等即失败：

```
order_pct / grid_gap / target_ratio / trail_drawdown / lot / weight / fee_rate
```

再加一条：同一份配置在不同环境档之间也不允许漂移（若项目已废弃某档环境，就断言该档不再存在，而不是继续拿它比对）。

### 第 5 步：判定与留痕

- 输出对照表：`参考值 | 生产值 | 是否一致`，一行一个指标；多层测试就分多张表。
- 一致性结论必须基于**黄金测试实跑结果**，不是基于代码阅读。
- 把「语义清单 + 差异表 + 基线数字 + 回归测试路径」写回项目文档，作为后续任何人改动此模块的护栏。
- 把期望值来源写清（哪一天、用什么脚本、耗时多久跑的参考实现），方便日后重跑复现。

### 第 6 步：把被门控的集成测试真正跑起来

**离线测试全绿 ≠ 一致。** 凡是靠环境变量/外部依赖门控而跳过（`t.Skip`、DB 不可达、服务未启动）的测试，**等于从未验证过**。它们里面同时藏着两类问题，必须跑一次才能分开：

- **测试装配缺陷**（测试自己的错）：同步点、阈值、时钟假设。
- **真实产品缺陷**（必须在这次修掉）：状态机、唯一键、状态迁移、错误处理。

跑起来之后按下面的清单判读。

## 容差规则（精确判定的正确做法）

红线是"**禁止用松容差掩盖真实差异**"，不是"禁止一切容差"。两种语言/两套数值类型之间，浮点表示噪声是客观存在的，要区分**噪声**与**漂移**：

- 参考实现用 `float64`、生产实现用定点十进制时，**必须用相对偏差**（`|got-want| / max(|want|,1)`），绝对偏差在大数值上会失效。
- 容差要取在**表示噪声之上、业务漂移之下**：典型 **1e-12 ~ 1e-9（相对）**。
  - 计数类（买次/卖次/未平层数/有效行数）一律**精确相等**，不给容差。
  - 整数量型（如 lot 步长能整除的数量）可收紧到 1e-12。
  - 金额（权益/现金/手续费）1e-9。
- **必须在测试里打印实测最大偏差**（如 `2.3e-15 @ event[6].cash`）。若实测值离容差只有几倍余量，说明容差压不住问题；若实测值比容差小 3 个数量级以上（如 2.3e-15 vs 1e-12），说明容差只吸收了噪声。
- 禁止的写法：`abs(diff) < 0.01`、`abs(diff) < 0.001` 这类与数值量级无关的绝对容差；也禁止用"四舍五入到 2 位小数后比较"。

## 参考值提取手法（不修改参考实现）

需要逐笔/逐字段的基线，但参考实现只打印汇总时：

1. **以模块方式导入参考实现，再 monkey-patch 采集函数**——前提是它有 `if __name__ == "__main__"` 守卫（否则导入会直接触发主流程）。若没有守卫，把主流程函数单独调用，而不是执行整个脚本。
2. 采集点选在**记账完成的最后一步**（如 `place_sell` 返回后读 `completed_trades[-1]`），这样拿到的是真实落账值，而不是调用前推演的值。
3. **包装器签名必须与调用点逐字一致**。先 grep 调用点确认是按位置还是按关键字传参：
   ```
   grep -n "place_sell(" reference.py     # 看到 place_sell(t, order, sell_price=price) → 包装器必须收 sell_price 关键字
   ```
   签名不匹配会直接 `TypeError`，别凭函数定义猜。
4. 把结果以 `repr(float)` 精度落盘 JSON（或制表符分隔文本），再注入测试。**不要中途 `.2f` 格式化**。
5. 采集脚本本身**不改参考实现一个字符**——这是第一铁律在采集阶段的体现。

## 排查手册：区分测试装配缺陷与产品缺陷

### 症状 A：事件被"丢弃"、条件永远不满足

先看门控/阈值类配置。**测试装配里的超时阈值必须大于被测组件的启动开销**：
组件常常在"就绪信号"之后仍要做 DB 往返（建配置、恢复状态、取锁），期间事件停在缓冲通道里。
若 `MaxPriceAge` 之类的阈值比启动耗时还小，首个合成事件会被判为过期而丢弃。
判定方法：打印实际 Δ 与阈值对比（如 `Δ=262ms` vs 阈值 `100ms` → 装配过紧，不是产品 bug）。
修法：测试阈值放宽到启动开销的 20 倍以上；"过期路径"用一条**专门**的旧事件测试覆盖，不要靠调小全局阈值。

### 症状 B：DB 显示已完成，内存/返回值还没变

这是最常见的**误判产品 bug**。当代码是「先落库、再结算、再登记内存」时，从外部观察会落在窗口里。
判定方法：确认这几步是否在**同一个同步调用链**内完成。若是（例如事件循环同步串行，不返回就不处理下一个 tick），则产品侧没有时序问题，**只有测试的同步点太弱**。
修法：断言改为等待**组件最终可达的状态**（内存态、可对外的完成信号），或对终态字段轮询；不要拿中间态（DB 已写、内存未登记）当同步点。
反例（本类误判的经典写法）：
```
requireEventually(round.status == ACTIVE)   // 这是 DB 中间态，早于内存登记
st := component.State()                     // 立刻读内存 → 大概率读到旧值
```
正例：`requireEventually(state.Find(batch) >= 0)`，即同步点落在**该步骤真正完成的那个状态**上。

### 症状 C：唯一键冲突 / 重复写入

先怀疑**标识符生成缺少单调递增**。若订单号、批次号、幂等键由序号派生，而序号只在"某一条"路径上自增（例如只在重启恢复路径自增、正常路径忘了自增），则第二次业务动作就会复用同一标识。
两个必查点：
1. **正常路径与恢复路径都要能推进序号**，且基线要取"历史上用过的最大值"（**含已终结的行**），不能只看当前活跃行。
2. 唯一键若包含软删标记（如 `(client_order_id, is_deleted)`），则**终态行仍会阻塞复用**——转终态不等于释放标识。若确实需要复用，必须在设计上单列方案。
排查提示：MySQL 对复合唯一键的冲突报错会把多列用 `-` 拼接展示（`'sg-12-1-b1-0'` 实为 `client_order_id='sg-12-1-b1'` + `is_deleted=0`），别被误导成"多了一个后缀"。

### 症状 D：错误被静默吞掉

见到 `_ = someCall()` 且该调用会改变持久状态（资金、库存、状态机）时，一律视为缺陷：失败后状态永远停在中间态且无人知晓。改为至少告警/上报。

### 症状 E：测试恒绿，改什么都不 FAIL

黄金数据被写错、比较对象搞反、容差过宽、字段根本没被比较——都会表现为"测试永远是绿的"。
**判定方法只有一个：做一次变异校验**（第 3.5 步），改错一个期望值看它是否 FAIL。不 FAIL 就是测试本身的问题，不是实现的问题。

### 调试纪律

**先取证，再改码。** 临时打印"DB 行 + 内存态"的对照输出，比反复读代码推测快一个数量级；诊断代码在收尾时必须全部撤除，并用 grep 确认无残留。


## 红线

- **禁止修改参考实现**（第一铁律）——包括为了"方便采集"而改动它。
- **禁止把"测试被门控跳过"当作验证通过**——未真正执行的测试等于没有测试。
- **禁止用松容差掩盖差异**：`abs(diff) < 0.01` / `< 0.001` 这类与量级无关的绝对容差一律驳回；跨数值类型时用相对偏差且容差取在表示噪声量级（1e-12 ~ 1e-9），并在测试里打印实测最大偏差自证。
- **禁止只做聚合级比对就宣布一致**——必须补齐逐笔（逐事件）层与组合（多参数）层，否则存在抵消盲区。
- **禁止跳过变异校验**——人工注入的期望值必须反向验证能 FAIL 一次。
- **禁止为测试污染生产代码**（加测试专用分支/字段/开关）。
- **禁止用近似数据**（自己重采样、自己造 fixture）替代参考实现的真实输入。
- **禁止只跑单点样本**：至少覆盖一段足够长的真实历史（多年、多行情形态），否则"逐元素 vs 聚合"这类偏差不会暴露。

## 权责边界

- 不负责"新功能设计是否正确" → `functional-validation-rules`
- 不负责"改动有没有带坏旧能力" → `test-regression-rules`
- 不负责测试资产落点与命名 → `artifact-storage-rules` / `test-strategy-rules`
- 若参考实现本身无法运行（依赖缺失、数据丢失），先阻断并报告，不要凭代码阅读下"一致"结论
