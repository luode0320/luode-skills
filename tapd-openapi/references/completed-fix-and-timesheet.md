# 已完成修复的补录与工时登记

适用于用户要求把本会话已经完成的修复记录到 TAPD，并登记明确工时的场景。目标是留下可核验的修复记录，不重新实现代码、发布通知或启动自动清任务流程。

## 创建前确认对象与项目

1. 沿用用户已明确给出的项目和实体范围；创建 Bug 使用 `/bugs`，创建 Task 使用任务接口。口语里的“任务”不能单独作为 Task 类型的证据。当前上下文足以确定是缺陷时创建 Bug；仍有多个合理对象或项目候选时只询问这一处缺口。
2. 多个 `TAPD_WORKSPACE_IDS` 不代表可以使用列表第一项。用 `workspaces/get_workspace_info` 核对候选项目名称，再结合已确认的仓库、业务及同类条目选择。`open_user_app/workspace_list` 返回空数组时仍可按已配置项目 ID 直查，不把它判为无权限，不反复获取 Token。
3. 按主入口的环境预检与真实创建人规则获取身份；Bug 显式传 `reporter`，Task/Story 显式传 `creator`。不要把本次实际姓名、项目 ID 或顺序固化为所有任务的默认值。
4. 查询目标项目是否已有同一修复记录，结合标题、业务对象、修复日期和提交记录判断重复；仅有关键词相似不能认定重复。默认补充已有同一记录；用户明确要求另建或归属仍不清时按其范围处理。
5. 新建 Bug 前按 [Bug 版本与当前迭代](bug-version-and-current-iteration.md) 实时查询其项目当前迭代和版本候选值，默认填所属迭代及发现版本；版本已明确时保留用户选择。本文不另设固定版本或重叠迭代回退规则。

## 记录内容与状态

- `description` 使用 HTML，包含现象及影响、直接根因、修复落点、验证结果、提交记录和剩余验证边界。只引用本会话已经取得的证据；多个补丁属于同一故障时在同一单中列出全部相关提交。
- 区分已验证代码路径、已经运行的新服务和正式接口验收。代码级回归通过不能写成部署完成或接口验收通过；未恢复的上游数据问题单独说明。
- 创建接口通常先返回初始状态。需将补录单标为已解决时，先查询 `workflows/status_map`（Bug 的 `system=bug`），再用实际存在的状态更新为已解决、`resolution=fixed`；不要直接猜测自定义状态值。未正式验收时不标为已验证或已关闭。
- 仅补录修复不自动发送评论、通知、重新指派测试人员或启动代码执行；用户另有明确要求时按对应 Owner 执行。
- 保存创建返回的完整实体 ID；确认创建成功后才做依赖该 ID 的状态更新和工时登记。

## 实际工时与预估工时

| 用户诉求 | 写入位置 | 边界 |
| --- | --- | --- |
| 已完成修复“工时填 1 小时” | `/timesheets` 的 `timespent=1` | 作为实际投入；不能只在描述或实体 `effort` 写 1 |
| 明确要求预估 1 小时 | 实体的 `effort=1` | 不是实际工时记录；不据此另写 timesheet |
| 明确要求两者都填 | 分别写 `effort` 和 timesheet | 最终分别报告，不能合计成 2 小时 |

1. `entity_type` 与实体真实类型一致，`entity_id` 使用创建回读确认的完整 ID；`owner` 使用已确认的实际工作人。日期按用户指定日期；未指定时使用用户时区的修复日期，不用宿主 UTC 日期替代。
2. 按 `entity_type + entity_id + spentdate + owner` 查询现有工时，客户端再核对这四项完全一致。已有记录且数值符合要求则复用；需要按用户要求纠正时按已有 timesheet ID 更新，不再新建。
3. 写入后回读核对记录数量、实际工时、日期和工作人，确认唯一且符合要求。`timeremain=0` 只在确实没有剩余工作时填写；代码已修复但仍有约定验收任务时不要自行推断剩余工时。

## 写入失败与最终回读

- Shell/脚本在 API 调用前失败：先确认没有请求发出，再换成可验证的运行方式；Windows 到 WSL 的安全调用见 `tapd-cli` 的运行说明。
- API 超时、连接中断或结果不明确：先 GET 查询实体或工时，确认是否已经落库。能够明确识别已有记录则继续后续步骤；无法排除已创建或无法唯一匹配时保留中断点，不盲目重复 POST。
- 中途失败时分别保留“实体已创建、状态是否更新、工时是否登记”的事实。恢复从未完成步骤开始，不把整个创建流程重跑一遍。
- 成功条件：实体 ID、真实创建人、状态及修复描述回读一致；指定日期的工时唯一且数值正确。HTTP 成功或 `status=1` 本身不代替字段核验。
- 最终给出标题详情链接、完整 ID、项目、状态、负责人、实际工时和日期；预估工时只有实际填写时另外报告。不给用户回显凭据或完整鉴权信息。
