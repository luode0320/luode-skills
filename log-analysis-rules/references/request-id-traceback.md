# 按 request-id / trace-id 反查一次请求全链路

## 适用场景

- 接口调用失败、响应体无法定位，需要从服务端日志还原这一次请求经过的全部步骤。
- 跨服务调用需要合并多个服务的日志片段。

## 前置条件

- 日志必须含可反查稳定标识（request-id / trace-id / 订单号），命名与 `logging-trace-rules` 的 trace-propagation 约定一致。
- 若无标识，无法拼接全链路，记录为 gap 并转交写侧补字段（`logging-trace-rules`），不得硬编。

## 操作步骤

1. **取标识**：从失败响应头、响应体、调用方日志或网关 trace 中取出 request-id / trace-id。
2. **定位文件**：按 `log-file-location.md` 定位当日日志文件。
3. **全文件 grep**：
   ```bash
   grep "<request-id>" <当日日志文件>
   ```
4. **时间窗收窄**：以请求发起时间为中心，先取 ±5 分钟确认边界，再收窄到 ±1 分钟内，避免误命中其它请求。
5. **按时间排序拼链路**：把命中行按时间戳升序排列，标记每个步骤（入口 → 中间件 → 业务 → DB → 出口）；缺失段说明该段无日志或未透传。
6. **跨服务合并**：各服务日志分别按同一标识 grep，再按时间戳合并排序；多文件合并用 `sort` 按时间列。
7. **输出取证片段**：每条带文件路径、行号、时间戳与原始行；片段回贴 bug 主文档或测试主文档。

## 判定要点

- 命中为空：确认标识是否正确、是否查错文件/时间窗，再判定"该段无日志"或"标识未透传"。
- 命中多条：按时间窗与业务键排除其它请求的噪声。
- 半截链路：首段或尾段缺失，优先查入口网关与出口响应日志。

## 禁止事项

- 只凭响应体猜测链路顺序。
- 无标识时强行拼接全链路。
- 改写或截断原文证据（脱敏字段按既有规则处理）。
