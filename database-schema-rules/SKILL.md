# 数据库结构规则

只在"表结构怎么变、迁移怎么写、回滚和兼容性怎么保证"这个问题上使用这个 skill。
如果当前问题是 SQL 查询、事务、锁、分页或批量 CRUD，请转交 `database-query-rules`。

## Skill 作用与适用场景

- 统一表、字段、索引、唯一约束、外键、迁移脚本和 DDL 的结构变更规则。
- **铁律 0：若项目采用启动时自动创建数据库或自动迁移表结构，则必须同步实现自动检查并创建缺失索引；库、表、索引必须作为同一条数据库初始化链路收口（建库 -> 建表 -> 建索引）。失败处理按场景分流：建库失败必须阻断启动（库不存在则后续连接必然失败，早失败早暴露，继续只会让真实错误被后续连接错误掩盖）；建表 / 补列 / 补索引失败只记错误不阻断（单张表的问题不该把不相关的存量业务一起拖下线）。无论哪一档都必须打出可定位的错误日志并在汇总行给出计数。**
- **铁律 0.1：数据库模型文件必须按“一张表一个文件”组织；自动建表/迁移逻辑必须单独文件存放；自动建索引定义、检查和创建逻辑也必须单独文件存放，禁止把多张表模型、迁移和索引混在同一个大文件中。**
- **铁律 0.2（自动迁移只做加法）：自动迁移的边界是「新表全自动，存量列只读」——表不存在则整表建出，列缺失则补列，索引缺失则幂等补建；已存在的列一律不碰（不改类型、长度、默认值、可空、注释、字符集），主键不改。因此禁止用 GORM `AutoMigrate` 这类"让库结构与模型完全一致"的 API 管理存量表：它会为了对齐注释这类纯元数据差异对大表执行 `MODIFY COLUMN`，进而锁表、超时、每次启动重复。存量列该不该改必须人工评估后走 DDL 脚本，不由一次服务重启决定；迁移超时也不得靠加大连接 `readTimeout` 掩盖。操作步骤、陷阱清单与验证矩阵见 `references/orm-auto-migration.md`。**
- **铁律 1：数据库的字段必须要定义数据类型、默认值、是否需要索引、字段 CHARSET=utf8mb4、ENGINE=InnoDB、注释说明等写清楚，不要遗漏，否则会导致自动创建表出现不可控的因素。其中"注释说明"的载体是 ORM 的 `comment:` tag 与 DDL 的 `COMMENT`（会落进数据库列注释）；模型字段行尾的 `//` 注释不算满足本项，也不得用来重抄 `comment:` 的内容，重复副本的治理归 `comment-rules`。**
- **铁律 1.1：SQL 标识符（表名、字段名、索引名）统一使用反引号包裹，养成固定习惯；例如 enabled 必须写成 `enabled`。**
- **铁律 1.2（表名单一定义源）：表名字面量在整个仓库只允许出现在两处——该表的模型文件（ORM 的 `TableName()` / `table` 元数据）与 DDL / 迁移脚本；每个表模型都必须显式实现返回表名的方法，禁止依赖 ORM 的复数化或结构体名推导。仓储层、查询层、迁移登记、脚本与测试要用表名时一律引用模型暴露的表名方法（如 Go GORM 的 `model.X{}.TableName()`），禁止再写一次字符串字面量。表名是 schema 的属性，属于本 skill 的定义权威；访问层如何引用它的执行细则见 `database-query-rules`。**
- **铁律 2：所有金额相关的要强制使用字符串，避免任何出现精度问题的情况。**
- **铁律 3：所有表必须包含 created_at 和 updated_at 字段，且必须自动维护——不允许靠业务代码逐处手写赋值。「自动」的实现方可以是数据库（`DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP`）也可以是 ORM（如 GORM 的 autoCreateTime / autoUpdateTime）；非 ORM 项目走数据库层，ORM 项目二者择一即可，但同一个项目内要统一。tag 写法见 `references/schema-examples.md` 的 GORM tag 小节。**
- **铁律 4：必须冗余一个毫秒级时间戳的创建时间，避免数据库的时区问题影响不同的时间格式。**
- **铁律 5：所有表必须包含逻辑删除字段，1 的状态标识删除，不是 1 代表正常非删除状态，默认 0=非删除。**
- **铁律 6：禁止物理外键约束（`FOREIGN KEY`），一律使用逻辑外键，外键列必须建索引。**
- 区分结构变更、数据修复、查询实现和业务逻辑的职责边界。
- 约束迁移安全、回滚策略、兼容性处理和上线风险说明。
- 防止把危险结构变更、不可回滚迁移和破坏兼容的 DDL 直接推进到后续环节。

## 自动触发信号

- 新增或修改数据库、表、字段、索引、唯一约束、外键、迁移脚本、DDL、实体结构、schema 定义。
- 新增或修改自动建库、自动建表、AutoMigrate、自动建索引、启动初始化数据库结构的逻辑。
- 要把已经有数据的存量表纳入 ORM 启动期自动迁移，或调整既有迁移的收录范围。
- 迁移在启动时报超时、`invalid connection`、`Duplicate key name`，或每次启动都重复执行同一条 `ALTER`。
- 发现多个数据库表模型、自动建表/迁移逻辑和自动建索引逻辑混放在同一个文件中。
- 需要判断字段类型、空值策略、默认值、约束、索引方案是否合理。
- 需要拆分"结构变更"和"数据迁移 / 数据修复"时。
- 需要确认迁移是否安全、是否可回滚、是否会影响旧版本兼容时。
- DDL 定义中缺少数据类型、默认值、索引、CHARSET=utf8mb4、ENGINE=InnoDB、注释说明等。
- 金额字段使用 DECIMAL、DOUBLE、FLOAT、INT 等数值类型。
- 缺少 created_at 和 updated_at 字段，或定义不正确。
- 缺少冗余毫秒级时间戳的创建时间字段。
- 缺少逻辑删除字段，或定义不正确。

## 进入后先做什么

1. 先识别当前变更是结构定义、迁移脚本、数据修复脚本还是查询实现。
2. **逐条核对上方铁律 1、1.1、1.2、2~6（DDL 定义完整、反引号、表名单一定义源、金额用字符串、时间字段与毫秒戳、逻辑删除、禁物理外键）**；判定细则与正反例见 `references/schema-boundaries.md`，不在此处重复展开。其中表名一项要顺带扫一遍访问侧：**发现仓储层、查询层或脚本重复硬编码同一表名时，先把它改成引用模型的表名方法再继续**。
3. **确认自动初始化链路是否同时覆盖自动建库、自动建表和自动建索引；若已有自动建库/建表但没有显式索引补建，必须补齐。**
4. **确认自动建索引具备幂等检查（先查后建，不重复创建同名索引），且有独立的显式补建步骤——不得依赖"表已存在时建表 API 一定会补齐所有索引"这种不确定的实现行为；失败处理按铁律 0 的场景分流口径（建索引失败只记错误不阻断）。**
5. **确认表模型、迁移、索引的文件组织是否符合“一张表一个模型文件、迁移独立文件、索引独立文件”；不符合时必须先拆分职责再继续结构变更。**
6. **若本轮是把已有数据的存量表纳入自动迁移，先按铁律 0.2 确认迁移实现不会改动已存在的列，再读 `references/orm-auto-migration.md` 走操作步骤与验证矩阵。**
7. 明确本轮只处理 schema 和迁移边界，不提前扩展到查询逻辑。
8. 判断当前变更会不会影响现有数据、现有接口契约或旧版本兼容。
9. 确认当前配置和环境差异规则已经稳定，避免把环境问题混进 schema 变更。
10. **确认 GORM tag 写 timestamp 字段时，`ON UPDATE CURRENT_TIMESTAMP` 不得放进 `default:`，须并入 `type:`，或直接依赖 GORM autoUpdateTime 不写 DB 层 ON UPDATE**；成因（`MigrateColumn` 默认值比对）与正反例见 `references/schema-examples.md` 的 GORM tag 小节。

## 默认执行流程

1. 默认先读 `references/schema-boundaries.md`，判断表、字段、索引、约束和数据变更的边界。
2. 如果涉及迁移执行、安全上线和回滚，再读 `references/migration-safety-and-rollback.md`。
3. 如果需要对照正反例或判断兼容性风险，再读 `references/schema-examples.md`。
4. 如果涉及新表设计、表结构评审、命名、类型选型、索引设计、关系映射或约束设计，再读 `references/table-design-standards.md`。
5. 如果涉及把存量表纳入 ORM 自动迁移，再读 `references/orm-auto-migration.md`（操作步骤、tag 陷阱、五段等价性验证）。
6. 输出结构变更结论、迁移顺序、兼容风险、回滚策略和不应一起混入的改动。
7. schema 方案未稳定前，不继续进入 `database-query-rules`。

> 本节只管「读哪些 reference、输出什么」。自动初始化的顺序与失败分流看铁律 0，只做加法看铁律 0.2，
> 文件组织看铁律 0.1，字段级要求看铁律 1~6 与 `references/schema-boundaries.md`——这些都不在本节重复罗列。

## 权责边界与不负责事项

- 只负责数据库结构、迁移和回滚边界，不负责 SQL 查询写法、事务、锁和分页，那属于 `database-query-rules`。
- 不负责环境变量、连接串、数据库开关和配置来源，那属于项目配置约束。
- 不负责发布窗口、灰度、线上发布回滚执行，那属于交付域或发布类 skill。
- 不把业务逻辑调整伪装成字段含义变化或默认值变化；这种情况应回流需求域或对应实现位点。
- 不默认所有结构变更都能在一次迁移里安全完成，必要时应拆分多步迁移。
- **必须确保自动建库、自动建表、自动建索引三类初始化能力边界清晰，不能只自动建库建表却遗漏索引。**
- **必须确保表模型、自动建表/迁移、自动建索引的文件边界清晰，不能把多张表、迁移和索引混放在同一个文件里。**
- **必须确保 DDL 定义中包含数据类型、默认值、是否需要索引、CHARSET=utf8mb4、ENGINE=InnoDB、注释说明等，不要遗漏**。
- **必须确保 SQL 标识符（表名、字段名、索引名）统一使用反引号包裹，避免裸写；例如 `enabled`。**
- **必须确保表名只有一个定义源（模型的表名方法 + DDL / 迁移脚本），本 skill 负责定义侧；访问层实际怎么引用该方法由 `database-query-rules` 检查，两边不重复定义规则。**
- **必须确保所有金额字段使用 VARCHAR 或 CHAR 字符串类型**。
- **必须确保所有表包含 created_at 和 updated_at 字段**。
- **必须确保包含冗余毫秒级时间戳的创建时间字段**。
- **必须确保包含逻辑删除字段**。
- **必须确保未使用物理外键约束（FOREIGN KEY），逻辑外键列已建索引**。

## 需要暂停并确认的条件

- 当前 DDL 会删除字段、缩窄类型、修改主键或直接重写大表结构，兼容风险高。
- 当前迁移同时承担结构变更、数据修复和业务开关切换，多重职责混杂。
- 回滚方案不清，或回滚后会造成数据不可逆丢失。
- 结构变更会影响旧版本代码、历史接口或上下游系统，但兼容窗口尚未确认。
- DDL 定义中缺少数据类型、默认值、索引、CHARSET=utf8mb4、ENGINE=InnoDB、注释说明等。
- 已有自动建库或自动建表逻辑，但缺少自动检查并创建索引的实现。
- 自动建索引不是幂等逻辑，可能重复创建同名索引或无法解释失败后的启动行为。
- 自动迁移会改动已存在列（尤其大表），或打算通过加大连接超时让这类 `ALTER` "跑完"。
- 要把存量表纳入自动迁移，但拿不到目标环境的真实结构（无法做等价性验证的段 1 与段 5）。
- 多张表模型、自动建表/迁移逻辑、自动建索引逻辑混在同一个文件中，职责边界不清。
- SQL 标识符存在裸写（如 enabled 未写成 `enabled`）。
- 表模型没有实现表名方法，或同一个表名字面量在模型之外被重复硬编码（仓储、查询、迁移登记、脚本、测试）。
- 金额字段使用 DECIMAL、DOUBLE、FLOAT、INT 等数值类型。
- 缺少 created_at 和 updated_at 字段，或定义不正确。
- 缺少冗余毫秒级时间戳的创建时间字段。
- 缺少逻辑删除字段，或定义不正确。
- 出现物理外键约束（FOREIGN KEY），或逻辑外键列未建索引。

## 执行通过 / 驳回标准

- 通过：结构变更边界清楚，迁移顺序合理，兼容与回滚策略可解释，且没有把查询实现或业务逻辑混入 schema 层；自动初始化链路覆盖建库、建表、建索引，按顺序幂等执行且失败处理符合铁律 0 的场景分流；自动迁移只做加法、不改动已存在列，存量表纳入时已按 `references/orm-auto-migration.md` 跑完五段等价性验证（含用真实环境结构 dump 的段 5）；表模型按一张表一个文件存放，自动建表/迁移和自动建索引逻辑分别独立文件存放；DDL 定义中包含数据类型、默认值、是否需要索引、CHARSET=utf8mb4、ENGINE=InnoDB、注释说明等，没有遗漏；SQL 标识符统一使用反引号包裹（如 `enabled`）；每个表模型都显式实现了表名方法，表名字面量只存在于模型文件与 DDL / 迁移脚本；所有金额字段使用 VARCHAR 或 CHAR 字符串类型；所有表包含 created_at 和 updated_at 字段；包含冗余毫秒级时间戳的创建时间字段；包含逻辑删除字段；未使用物理外键约束（FOREIGN KEY），逻辑外键列已建索引。
- 驳回：危险 DDL 无兼容保护、回滚不可解释、结构变更与数据逻辑混杂，或直接引入高风险不可逆变更；已有自动建库/建表但没有自动建索引，或自动建索引不幂等；建库失败不阻断启动；自动迁移会改动已存在列，或用加大连接超时的方式让这类 `ALTER` 跑完；存量表纳入自动迁移但只验证了标准结构、没跑真实环境结构的漂移验证；多张表模型、自动建表/迁移、自动建索引混在同一个文件；DDL 定义中缺少数据类型、默认值、索引、CHARSET=utf8mb4、ENGINE=InnoDB、注释说明等，会导致自动创建表出现不可控的因素；SQL 标识符裸写（例如 `enabled` 未加反引号）；表模型缺少表名方法，或表名字面量在模型之外被重复硬编码；金额字段使用数值类型；缺少 created_at、updated_at、冗余毫秒级时间戳或逻辑删除字段；出现物理外键约束（FOREIGN KEY）或逻辑外键列未建索引。

## 执行结果归档要求

- 将 schema 变更结论记录到迁移说明、任务记录、评审记录或部署说明中。
- 归档内容至少包含变更对象、迁移顺序、兼容策略、回滚方式、影响范围和风险说明。
- 如果涉及不可逆或高风险迁移，必须明确标记执行前提、观察点和人工确认条件。
- 确保 DDL 定义的完整说明已记录，包括数据类型、默认值、索引、CHARSET=utf8mb4、ENGINE=InnoDB、注释说明等。
- 确保表模型、迁移和索引文件边界已记录并执行：一张表一个模型文件，自动建表/迁移独立文件，自动建索引独立文件。
- 确保 SQL 标识符反引号规范已记录并执行（表名、字段名、索引名统一反引号包裹）。
- 确保金额字段、时间字段、逻辑删除字段的使用规范已记录。
- 确保未使用物理外键约束（FOREIGN KEY），逻辑外键列已建索引，且该红线已记录。
