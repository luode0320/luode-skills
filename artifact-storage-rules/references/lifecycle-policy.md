# 过程产物生命周期与退场策略

本文件是研发产物「时间维度」的唯一策略载体，与 `path-map.yaml` 的 `process_doc_*` 策略键、`update-policy.md` 的复用策略共同构成存储单一真相源。
它只管「过程产物的结论被萃取之后，原文档何时、以什么条件、用什么动作退场」，不管文档该放哪、叫什么、是否复用。

## 为什么需要这条策略

`update-policy.md` 已有的清理条款全部是**事件驱动**的：图片旧版本无引用才可删、`.gap.md` 缺口关闭后必须删除、目录迁移后删除旧目录、`test/{skill}/temp/` 收口时清理。
事件驱动意味着「事情发生时顺手清」，而「事情结束后渐渐没人看」的存量过程文档没有任何机制触发清理，只会随时间单调累积。
本策略补的就是这个缺口：把清理从「事件触发」扩展为「时间巡检 + 沉淀核验」，与知识库侧 `knowledge-flow/references/conflict-staleness.md` 的退场机制形成对称。

## 一、两类产物的生命周期定位

### 长期资产（不适用时间退场）

| 根目录 | 定位 |
|---|---|
| `doc/1-架构/` | 当前项目的稳定架构真相源，只按内容变化更新 |
| `doc/2-需求/` | 需求主文档，是实施与 6-review 的来源对象，长期有效 |
| `doc/5-tests/基线/` | 跨轮复用的机器可读接口基线数据资产 |
| `doc/6-审查/` | 历史只读归档 |
| `doc/7-验收/` | 历史只读归档 |
| 根目录 `项目设计.md` | 项目级设计主入口 |

这些根目录下的文档**不因时间流逝退场**。删改它们属于内容治理，不属于生命周期治理。

### 过程产物（可作为退场对象）

| 根目录 | 定位 |
|---|---|
| `doc/3-实施/` | 实施总览、实施周期、全量顺序实施方案 |
| `doc/4-bugs/` | Bug 主文档（限已闭环） |
| `doc/5-tests/` | 扁平测试主文档（不含 `基线/`） |
| `doc/6-review/` | 风格回归记录 |

过程产物的价值在收口时已转移到代码、知识库笔记或规则资产；原文档是**一次性推进过程的记录**，属于可退场对象。

## 二、时间判据

- 过程产物最后修改时间早于当前日期 **15 天**（半个月）即进入退场**候选**。
- 阈值唯一来源是 `path-map.yaml` 的 `process_doc_retire_after_days`；下游 skill 不得另设阈值。
- 筛出候选的参考命令（只读）：

```bash
# 按最后修改时间筛出候选（超过 15 天）
find doc/3-实施 doc/5-tests doc/6-review doc/4-bugs -maxdepth 1 -type f -name "*.md" -mtime +15
```

- **时间只用于缩小范围，不构成退场理由。** 是否退场完全由下节四道守卫决定；只满足时间的候选必须逐条走完守卫。

## 三、四道前置守卫（必须全部满足）

### 1. 沉淀守卫

该文档的可复用结论必须已真实进入知识库（`D:\谷歌云盘\知识库\`）笔记，且笔记可被检索到。

- 判定与写入由 `knowledge-flow` 负责，本 skill 只消费其结论。
- 「看起来已经过期」「应该没用了」「内容显然已被代码取代」**都不构成沉淀证据**。
- 找不到对应笔记时，不得删除，应先按 `knowledge-flow` 补齐沉淀，或在清单中标记为「待沉淀」并移出本批次。

### 2. 引用守卫

全仓库检索该文档文件名，引用数必须为 0。

```bash
# 以文档主干的稳定片段做引用扫描，命中任何引用即不得退场
grep -rn "<文档名稳定片段>" --include="*.md" --include="*.yaml" --include="*.json" .
```

- 存在任何引用（Markdown 链接、清单登记、索引、追踪矩阵）时一律不得退场。
- 正确处理顺序是：先清理引用或把引用改指向替代文档，引用归零后才重新进入候选。
- 该守卫与 `update-policy.md` 中图片资产「任何删除动作必须先检索全部 Markdown 引用」的口径一致，属于同一条原则在文档层面的延伸。

### 3. 闭环守卫

其来源对象必须已真实闭环：

- 需求：已实施完成，无进行中的实施周期；
- Bug：已验证修复，无未决 P0/P1；
- 测试：该测试轮次已收口；
- 且不存在未关闭的 gap、未裁决的 `conflicted` 结论或阻断级未决项。

### 4. 可恢复守卫

目标文件必须已被 Git 跟踪且历史提交存在：

```bash
git ls-files --error-unmatch <path>
```

- 未跟踪、被 `.gitignore` 忽略或仅有工作区改动的文件**不得退场**；这类文件删除后不可恢复。
- 若仓库未推送到远端，必须在清单中显式标注「仅本地历史可恢复」，由用户决定是否接受。

## 四、退场清单格式（执行前必须产出）

退场前必须输出清单，取得用户**明确确认**后才执行。清单至少包含：

| 字段 | 说明 |
|---|---|
| 路径 | 相对仓库根的完整路径 |
| 最后修改时间 | 用于核验是否超过阈值 |
| 沉淀证据 | 对应知识库笔记的相对路径；无则标注「待沉淀」 |
| 引用检查 | 检索引擎与命中结果（须为 0） |
| 闭环状态 | 来源对象及其闭环依据 |
| 可恢复性 | 是否已提交、是否已推送远端 |

## 五、执行与批次

- 退场动作固定为 `git rm`（`path-map.yaml` 的 `process_doc_retire_action`），不保留并行归档副本、不建归档目录。
- 单批次默认不超过 **10 个文件**（`process_doc_retire_batch_limit`）；每批次执行后复核工作树状态，出现异常立即停止。
- 若用户要求保留可追溯副本，则本策略不适用，改走 `update-policy.md` 的迁移/归档路径，不混用。

## 六、与相邻规则的边界

- **`knowledge-flow`**：负责沉淀判定与写入，是本策略沉淀守卫的唯一 owner。本 skill 不判断「什么值得沉淀」。
- **`update-policy.md`**：负责「同一任务复用旧文档还是新建」以及事件驱动的清理（gap 文档、图片旧版本、迁移后旧目录）。本策略只补时间驱动的退场，不重复这些条款。
- **`project-memory-rules` / `project-local-skills-rules`**：退场前若发现有稳定规则尚未固化，应先固化到项目记忆或项目本地 skill，再退场。
- **`git-collaboration-rules`**：`git rm` 属于写 Git 工作树与历史，必须遵守其提交授权边界；退场批次不自动构成提交授权。

## 七、禁止事项

- 禁止为了「目录整洁」批量删除。
- 禁止跳过沉淀守卫，仅凭时间阈值删除。
- 禁止删除仍被引用的文档。
- 禁止把退场动作扩大到 `doc/1-架构/`、`doc/2-需求/`、`doc/5-tests/基线/`、`doc/6-审查/`、`doc/7-验收/`。
- 禁止用「归档到别处」替代本策略的判定流程来回避四道守卫。
