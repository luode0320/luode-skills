# 静态定位路径

## 用途

用于在不进入运行时调试的前提下，沿代码和证据链逐步定位 Bug 根因。

## 默认路径

1. 从异常现象对应的入口开始。
2. 看错误日志、trace 或报错位置。
3. 顺着调用链往内收窄。
4. 对照关键状态、关键分支、关键数据转换。
5. 找到最接近异常产生的位置。

## 常用证据

- 报错堆栈
- 接口日志
- trace 链路
- 调用链关系
- 上下游输入输出差异

## 堆栈阅读纪律

- 读完整堆栈，从下往上读：根因通常在**最深的应用帧**，而不是顶层异常。
- 框架帧可跳过，但应用自身的帧应按序读完。
- 报错位置只是起点，先看它从哪里被调用进来。

## 快速路径：先查最近变更

Bug 出现在某次部署或提交之后时，**先查最近变更**常是最快路径：

- `git log` / `git diff` 最近改动，优先怀疑改动的调用链、状态、数据结构。
- 已知两个 commit 之间引入时，用二分 harness 配 `git bisect run` 自动定位引入 commit。

## 隔离战术（大范围 / 长链路）

静态阅读无法收窄时，用排除法机械缩小范围：

- **stub / bypass 排除**：把可疑组件桩化或绕过，检查 Bug 是否仍出现——不出现则该组件脱嫌。
- **禁用一半系统**：大代码库中禁用一半功能 / 组件，检查 Bug 是否仍出现，再对保留侧折半重复，直到收敛到最小嫌疑集。

## 原则

- 先沿事实走，不先沿猜测走。
- 每收缩一步，都要能说明依据是什么。
- 每收缩一步的关键判断和证据来源，都应写回当前 Bug 主文档。
