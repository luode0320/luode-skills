# 自主连续执行规则

## 目标

本 Skill 是自主连续执行的唯一自动触发入口，只负责决定“能否继续、何时暂停、何时交接、何时结束”。领域实现、测试、审查、验收、安全审批和最终用户渲染仍由对应 Owner 负责。

详细契约按职责下沉：

- 执行授权与计划边界：`references/execution-authorization-and-plan-boundary.md`
- 继续、暂停与高风险边界：`references/continuation-and-pause.md`
- 阻断状态收口与事实交接：`references/blocker-handoff.md`
- 用户结束、无下一步与防循环：`references/termination-loop-prevention.md`
- 落盘持久化与任务拆分（有损压缩前提）：`references/state-persistence-and-task-granularity.md`

## 落盘持久化与任务拆分铁律（最高优先级，强制）

前提：**上下文压缩是有损的，必然丢失细节**，且压缩发生时机不可精确预测。因此连续推进必须建立在“状态随时可从磁盘恢复”之上，执行节奏必须保证：任一时刻被压缩，最大损失不超过当前单个最小任务的未落盘增量。详细契约见 `references/state-persistence-and-task-granularity.md`。

**铁律 1：任务与执行状态必须落盘持久化**

- 所有任务清单、执行状态、关键决策、偏差、验证证据和“下一动作”指针，必须写入项目 `doc/` 目录（落点与命名按 `../artifact-storage-rules/references/path-map.yaml`）或知识库（仅跨项目可复用事实，经 `knowledge-flow` 三态判定），禁止仅停留在上下文会话、聊天输出、思考过程、宿主任务列表/悬浮窗或临时文件中。
- 写透（write-through）节奏强制：最小任务开始前先落盘 `in_progress`；状态迁移、关键决策、偏差发生、每步验证完成后立即落盘；准备结束回合、暂停或请求用户决策前必须先落盘。禁止“先做完再补写”。
- 任务完成的唯一判定依据是磁盘状态字段与已落盘证据；对话宣称、思考确认、UI 列表状态、投影状态均不构成完成判定。

**铁律 2：任务拆分必须足够小且相互隔离（最小恢复偏移）**

- 每个最小任务必须是可独立恢复的执行单元：单一目标、单一完成条件（AC）、预计可在一次连续执行内完成“实现 -> 真实测试 -> 6-review”闭环；预计无法一次闭环的必须继续拆分。
- 隔离性：任务之间只通过落盘产物（文件、测试结果、文档状态）交接，禁止依赖上一任务的会话记忆；后继任务的计划文档必须显式声明其依赖的前置落盘产物路径，前置产物缺失即阻断，不得凭记忆补齐。
- 恢复偏移度量：恢复任一任务所需读取的持久化文件不超过 2 个（该任务自身计划文档 + 其显式声明的关键输入）；超出即判定拆分失败，必须重新拆分。

**铁律 3：每个后续任务一份按执行顺序命名的独立任务计划文档**

- 每个最小任务必须配备独立 md 任务计划文档，按执行顺序编号命名，落点与命名基准引用 `../artifact-storage-rules/references/path-map.yaml` 的 `implementation_task_plan_doc`；文档必须包含：任务 ID 与序号、来源、目标、前置依赖（落盘产物路径）、输入文件、执行步骤、完成条件（AC）、状态字段（pending/in_progress/done/blocked/failed + UTC 时间戳）、追加式执行记录（决策/偏差/证据）和“下一动作”恢复指引。
- **严禁将上下文中的计划输出视为已完成**：未落盘的计划视为不存在，未更新状态字段的完成视为未完成；“计划已写进对话 / 已展示给用户 / 已生成悬浮任务列表”不产生任何完成事实。
- 投影层（`PROJECT_CURRENT.md` registry、宿主任务列表）只是任务计划文档的紧凑投影，不是事实源；两者不一致时以磁盘任务计划文档为准，并在下一检查点修正投影。

## 执行许可状态（新增）

只维护三态：`confirmed`、`unknown`、`revoked`。进入首次编码、上下文压缩恢复或用户改变边界时，必须按执行授权契约刷新状态；不得把聊天建议、口头方向或开工短句直接视为无边界执行许可。

完整状态转换、计划必填项和采纳建议场景见 `references/execution-authorization-and-plan-boundary.md`。

## 触发信号

- 自动触发：多步骤任务尚未闭环，且存在原执行计划内、完成原始目标所必需、当前可安全执行的下一步。
- 不触发或立即停止：用户明确结束、原始目标已完成、仅剩可选优化、执行许可不足、计划边界缺失、上下文压缩后编码许可未确认，或已进入关键/高风险节点。
- 自动触发不依赖用户再次说“继续”，也不得把“可继续优化”升级成新目标。

触发与排除样例见 `references/continuation-and-pause.md` 和 `references/termination-loop-prevention.md`。

## 默认执行策略

1. 先确认有效计划、完成定义、停止条件、最大推进边界和验证点。
2. 获得 `confirmed` 后，按当前计划连续推进，不在普通步骤重复询问；无论任务大小，首次领域动作前都先由 `task-plan-rehydration-rules` 为当前 `session_id` 持久化 `active` 或 `blocked` projection，持久化成功后的下一动作必须立即调用 `update_plan`；仅投影持久化失败、会话归属冲突/不确定或执行状态不明时硬阻断领域动作，单纯 UI 同步不可用（磁盘投影已成功且归属明确）时保留磁盘投影并继续领域执行，下一检查点重试 UI。
3. 每个最小任务必须独立满足实施计划完成条件，并完成“实现 -> 真实测试 -> 6-review”，不得批量实现后统一验证；任务开始前先创建或更新该任务的独立 md 任务计划文档并落盘 `in_progress`（铁律 3），状态迁移、决策、偏差与验证证据先落盘任务计划文档，再原子更新当前 session projection，再立即刷新悬浮任务列表；仅投影持久化失败、会话归属冲突/不确定或执行状态不明时硬阻断，单纯 UI 刷新失败进入 `UI_SYNC_BLOCKED` 降级继续：保留磁盘 projection + 继续领域执行，下一检查点重试 UI，不得声称 UI 已刷新。
4. 当前周期未收口不得跳到后续周期；当前周期收口且仍有计划内必需周期时自动继续。当前投影全部完成后先写为 `inactive`，后续回合不得重放。
5. 中间进度只说明已完成与正在推进的必需动作，不交还非关键执行权；`update_plan` 成功后才可声称 UI 已刷新；不可用或失败但磁盘投影已成功且归属明确时进入 `UI_SYNC_BLOCKED` 降级继续，如实说明磁盘 projection 已保存并继续领域执行，下一检查点优先重试 UI，不得声称 UI 已恢复。
5.1 十分钟只作缺失 projection 的异常修复闸门：任务已真实执行但当前 session 仍无活动或阻断 projection，且扣除 Plan Mode、等待用户、`blocked` 和 `manual_handoff` 后严格超过 600 秒时，先把资格交给 `task-plan-rehydration-rules` 的只读 `probe-timeout`，随后补建当前 session projection 并立即调用 `update_plan`；不得把 600 秒作为正常任务首次显示悬浮窗的入口。仅 `goal_check_required` 时由当前主 Agent 先 `get_goal`，复用明确匹配的活动 Goal，或在无活动 Goal 时使用脱敏摘要调用一次 `create_goal`；不匹配、不可用、失败或结果不明确时禁止重复创建并降级原 `ensure-timeout` 普通投影。任何 projection 成功持久化后才能调用 `update_plan`。
6. 遇到关键节点、高风险、越界、冲突或授权不足时立即暂停。
7. 真实 `blocked/manual_handoff` 先收口运行时状态，再交接结构化事实。
8. 原始目标完成后只允许三类合法后续；无合法后续时直接结束。
9. 准备输出最终回复前执行收口前任务状态检查（联动 `reasoning-summary-structure-rules` 的 `SUMMARY-GATE-PMW-002`）：若宿主任务列表仍存在 pending / in_progress 任务，或当前 session projection 存在未完成必需 step，且执行授权为 `confirmed`、无真实阻断 → 必须先继续执行，不得输出“已完成”式总结；因平台硬限制（上下文/token 上限、单回合步数上限、超时、额度、非交互模式进程退出）或真实阻断无法继续时 → 输出显式中断点（已完成清单 + 剩余任务清单 + 下一动作 + 重入入口/投影 ID），禁止“已完成”式收口。

完整执行节奏见 `references/continuation-and-pause.md`。

## Goal 生命周期交接

- `create_goal` 成功只表示 Goal 运行时已创建；用户已对“严格超过 600 秒且资格探测通过后自动创建一次 Goal”给出 standing authorization，但该授权只覆盖当前主 Agent 的 Goal 生命周期调用，不授予新的编码、文件写入、外部副作用或 Git 权限。创建后把事件交给 `task-plan-rehydration-rules` 创建安全三步投影，且不因此自动取得任何实现授权。
- `get_goal` 证明活动 Goal 仍存在时，可交给投影 Owner 恢复已有活动 Goal 悬浮列表；恢复 UI 前仍需核验中断点，且不得自动重放未知幂等写操作。若创建时已保留活动正式计划，Owner 返回 `preserved_formal` 且不重写、不刷新，正式计划仍走自身恢复路径。
- `update_goal` 进入 `blocked` 时，交给投影 Owner 持久化无进行中步骤的观察列表；不得把 blocked payload 解释为可以继续执行。`update_goal` 进入 `complete` 时，交给 Owner 失活 Goal 安全投影，随后真实收口 Goal；若结果为 `preserved_formal`，不得失活、改写或刷新独立的正式计划。
- Plan Mode、无活动 Goal、来源不匹配、损坏投影或工具失败时退出 Goal 投影路径；投影和 `update_plan` 从不改变本 Skill 的授权状态。

## 异步任务任务列表登记（强制）

- 启动后台异步任务（`run_in_background` 轮询、CI 等待、异步下载 / 发布 / 构建、异步子会话 / 后台 agent 等）时，必须先通过宿主任务列表登记为可追踪条目：`TaskCreate` 条目描述统一按「做什么 + 任务标识（任务 ID / CI run 编号 / 进程名）+ 何时查看（轮询节奏或完成信号）」三段式，让用户在任务列表 UI 上即可看到“在干什么、进度到哪、什么时候回来看”。
- 『启动异步任务』『等待 / 轮询结果』『回收并汇报结果』三个阶段必须用 `TaskCreate` / `TaskUpdate` 推进状态（pending → in_progress → completed），禁止把裸 `run_in_background` 后台进程当作唯一进度可见手段；异步任务启动即登记，不得等收口时才补。
- 收口时由 `reasoning-summary-structure-rules` 渲染「🔄 后台异步任务」分流小节并校验登记发生；未登记的异步任务视为进度不可见，需补登记后再收口。
- 登记只表示任务可见与可追踪，不改变本 Skill 的执行授权边界，也不授予任何额外的写入或外部副作用权限。

## 必须暂停确认的关键节点

- 首次从需求、Bug 分析或方案进入编码，且许可不是 `confirmed`。
- 开工指令缺少正式计划或停止边界；采纳建议但建议尚未转成执行计划。
- 上下文压缩后准备开始或继续编码，且编码许可未重新确认。
- 进入提交、推送或 PR 等 Git 动作，但当前轮没有明确 Git 授权。
- 方案越界、高风险或不可逆操作、成本显著上升、证据冲突无法收敛。
- 用户明确结束、无合法后续、运行时状态尚未真实收口或已满足真实阻断条件。

逐项处理见 `references/continuation-and-pause.md`、`references/blocker-handoff.md` 与 `references/termination-loop-prevention.md`。

## 关键节点提问格式（强制）

仅在确需用户决策时，简要说明当前阶段和节点类型，给出 2-3 个互斥可执行选项，推荐项置首；禁止默认开放式追问“接下来做什么”。用户已明确 Git 动作时直接让路给 `git-collaboration-rules`，不得重复询问是否提交。

## 与其他 Skill 的协作

- `git-collaboration-rules`：独占当前轮 Git 授权、提交和推送边界。
- `skill-execution-compliance-gate-rules` / `code-change-finalization-gate-rules`：独占执行合规与代码最终收口；自主执行不得跳过。
- `context-compression-rules`：提供压缩恢复事实；恢复偏移由任务计划文档状态字段确定；编码许可仍按本 Skill 的授权契约复核。
- `task-plan-rehydration-rules`：独占任务投影持久化、校验、失活、Goal 安全三步和 `update_plan` payload；UI 重建不恢复本 Skill 的执行许可；投影是任务计划文档的紧凑投影，不是事实源。
- `artifact-storage-rules`：任务计划文档与执行证据的落点、命名唯一真相源。
- 需求、Bug、实施、测试、审查、验收 Skill：保留领域决策和阶段门禁，本 Skill 只控制推进节奏。
- `reasoning-summary-structure-rules`：唯一负责面向用户渲染阻断与最终状态；本 Skill 只交接结构化事实。

## 禁止事项

- 不得绕过系统安全限制、权限审批、外部副作用确认或高风险防护。
- 不得以连续执行为由跳过正式计划、真实验证、审查、验收或证据。
- 不得继承上下文压缩前无法证明的编码许可。
- 不得在用户结束或无合法后续后继续工具调用、建议或占位输出。
- 不得把仅存在于上下文、对话输出、临时文件或 UI 列表中的计划、状态或证据当作已完成事实；未落盘的计划视为不存在。
- 不得执行没有落盘任务计划文档的最小任务，也不得以任务过大为由批量执行后统一补写落盘。

## 通过 / 驳回标准

通过：单入口自动触发；授权状态正确；计划内必需动作连续推进；每个最小任务独立闭环；任务与执行状态全程落盘可恢复，任一任务被压缩后可凭自身计划文档以最小偏移恢复；关键节点准确暂停；阻断事实完整交接；用户结束和无下一步语义生效；安全审批未被绕过。

驳回：重复询问普通步骤；无计划直接实施；压缩后直接编码；跨任务批量验证；状态只留会话、聊天、临时文件或 UI 列表；计划未落盘即宣称已完成；单个任务粒度过大或依赖会话记忆交接；越界或高风险静默继续；伪造运行时收口；自行渲染重复阻断；任务完成后继续扩散。

## 快速示例

- “开始执行”但没有执行计划：先形成受限计划并停在计划收口，不进入编码。
- 计划只输出在对话中、任务计划文档未落盘：视为计划不存在，先落盘任务计划文档再执行。
- 当前最小任务实现完成且测试、审查、验收尚未完成：继续完成该任务闭环，不询问是否继续。
- 用户说“结束”：立即停止自动继续和扩散，只做必要的真实状态收口与最小结论。
- 原始目标完成且无三类合法后续：直接结束，不输出等待、无需动作或下一步占位文案。
