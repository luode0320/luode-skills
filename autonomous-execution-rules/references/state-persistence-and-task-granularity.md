# 落盘持久化与任务拆分契约（有损压缩前提下的执行状态铁律）

本文件是 `autonomous-execution-rules` 的落盘持久化与任务拆分唯一细则；`context-compression-rules` 与 `task-plan-rehydration-rules` 引用本契约，不另建平行口径。

## 0. 前提与设计目标

- 前提：**上下文压缩是有损的，必然丢失细节**，且压缩发生时机不可精确预测。任何未落盘的计划、状态、决策、偏差、证据，在压缩后一律视为已经丢失。
- 设计目标一（损失上界）：执行全程保持 write-through 节奏，任一时刻被压缩，最大损失不超过当前单个最小任务的未落盘增量。
- 设计目标二（恢复偏移最小）：恢复任一最小任务，只需读取不超过 2 个持久化文件（该任务自身计划文档 + 其显式声明的关键输入），不回读会话历史、其他任务的执行过程或其他任务计划文档全文。

## 1. 三层状态架构

| 层 | 载体 | 保真度 | 角色 |
| --- | --- | --- | --- |
| L1 持久层 | `doc/3-实施/` 按序任务计划文档、实施总览/周期文档、`doc/5-tests/` 测试主文档、`doc/6-review/` 回归记录、知识库笔记 | 全保真 | 唯一事实源 |
| L2 投影层 | `PROJECT_CURRENT.md` registry（最多 20 条，仅任务 ID / 文案 / 三态）、宿主任务列表与悬浮窗 | 紧凑投影 | UI 呈现与跨会话再水化索引 |
| L3 会话层 | 对话输出、思考过程、临时文件、内存变量 | 易失 | 仅工作缓冲，禁止作为事实源 |

- 固定顺序：先 L1 后 L2；L3 不产生任何事实。
- 三层不一致时，以 L1 磁盘任务计划文档为准，并在下一检查点把 L2 修正为与事实源一致。
- L2 的任何写入（含 `update_plan`、宿主任务列表登记）不得替代或推迟 L1 落盘。

## 2. 铁律 1：任务与执行状态必须落盘持久化

### 2.1 必须落盘的内容

- 任务清单与拆分结果（SLICE / CYCLE / TASK 标识及执行顺序）。
- 每个最小任务的执行状态与状态迁移时间戳。
- 关键决策及理由，含被否决的备选方案。
- 执行偏差（计划外改动、范围变化、环境差异）及处理结果。
- 验证证据（命令、关键输出摘要、结论）；证据正文按域落 `doc/5-tests/`、`doc/6-review/` 等对应文档。
- “下一动作”指针（下一步做什么、从哪个文件继续）。

### 2.2 落点路由

- 项目内任务与执行状态 → 项目 `doc/` 目录；落点与命名以 `../../artifact-storage-rules/references/path-map.yaml` 为唯一真相源。
- 跨项目可复用的事实、流程、定义、调试经验 → 知识库（经 `knowledge-flow` 三态判定与查重后沉淀）。
- 禁止落点：仅会话上下文、聊天输出、思考过程、`/tmp` 等临时目录、内存变量、仅 UI 任务列表/悬浮窗。这些载体中的内容一律视为易失，不构成完成或状态事实。

### 2.3 写透检查点（强制时机）

以下时机必须先落盘、再继续执行；禁止“先做完再补写”：

1. 最小任务开始执行前：任务计划文档落盘 `in_progress`。
2. 任一状态迁移前：先落盘目标状态与依据。
3. 关键决策作出后：决策、理由、被否决备选立即落盘。
4. 偏差发生后：偏差描述与处理方案立即落盘。
5. 每步真实测试或验证完成后：证据与结论立即落盘。
6. 准备结束回合、暂停、交接或请求用户决策前：全量状态落盘。
7. 检测到上下文刚被压缩后：先按第 5 节恢复流程从任务计划文档重建状态，再继续。

### 2.4 完成判定

- 任务完成的唯一判定 = 磁盘任务计划文档状态字段为 `done` 且证据已落盘。
- 对话宣称、思考确认、UI 列表状态、投影状态均不构成完成判定。

## 3. 铁律 2：任务拆分必须足够小且相互隔离

### 3.1 最小任务粒度判定清单（全部满足才合格）

1. 单一目标：只对应一个可独立验证的完成条件（AC）。
2. 单轮闭环：预计可在一次连续执行内完成“实现 -> 真实测试 -> 6-review”闭环；预计无法一次闭环的必须继续拆分。
3. 上下文自足：恢复该任务只需要其自身计划文档 + 显式声明的输入文件，不需要回读会话历史、其他任务的执行过程或其他任务计划文档全文。
4. 状态自描述：文档内含状态字段与“下一动作”指针，任何接手者（包括被压缩后的自己）按文档即可继续。
5. 写集明确：声明将触碰的文件集合；与并行任务写集互斥。

粒度反例（判定失败，必须重新拆分）：批量实现多个功能后统一验证；一个任务横跨多个 AC；依赖“上一个任务的对话记忆”推进；任务描述无法在不读会话历史的情况下独立执行。

### 3.2 隔离性要求

- 任务之间只通过落盘产物交接（文件、测试结果、文档状态），禁止通过会话记忆传递信息。
- 后继任务的计划文档必须显式声明其依赖的前置落盘产物路径；前置产物缺失即阻断，不得凭记忆补齐。
- 恢复偏移度量：恢复任一任务所需读取的持久化文件 ≤ 2 个；超出即判定隔离失败，重新拆分或补齐产物指针。

### 3.3 与上游拆分 Owner 的分工

- 业务切片（SLICE）、实施周期划分、文件/符号落点、AC 定义仍由 `requirement-splitting-rules`、`implementation-planning-rules` 负责；本契约只约束执行层的最小任务粒度、隔离与落盘，不改变上游职责。

## 4. 铁律 3：按执行顺序命名的独立任务计划文档

### 4.1 落点与命名

- 每个最小任务一份独立 md 文档，落 `doc/3-实施/`；命名引用 `../../artifact-storage-rules/references/path-map.yaml` 的 `implementation_task_plan_doc`。
- 文件名内嵌三位零填充执行序号 `task_seq`：在来源对象实施范围内从 001 起全局递增，跨周期不重置、不复用、不因会话或压缩重排；执行顺序以序号为权威。
- 时间戳前缀仅记录文档创建时刻，不参与排序。

### 4.2 文档最小字段集（模板）

```markdown
# 任务{task_seq:03d}：{中文主题}

- 任务 ID：TASK-xxx（沿用实施周期文档的任务编号；与文件名 task_seq 的映射在此声明）
- 来源：{实施周期文档相对路径}
- 状态：pending | in_progress | done | blocked | failed（附 UTC 时间戳）
- 目标：{一句话，对应唯一 AC}
- 前置依赖：{前置任务落盘产物路径列表}
- 输入文件：{路径列表}
- 执行步骤：1..n
- 完成条件（AC）：{可测试断言}
- 执行记录（追加式）：每条含时间戳，记录决策 / 偏差 / 证据
- 下一动作：{指针：下一步做什么、从哪继续}
```

### 4.3 状态机与更新时机

- `pending -> in_progress`：开始执行前先落盘。
- `in_progress -> done | failed | blocked`：迁移前先落盘证据与依据。
- `blocked -> in_progress`：解除阻断的授权或事实先落盘。
- 执行记录只追加、不改写；纠错用新条目注明更正关系。

### 4.4 禁止事项

- 严禁将上下文中的计划输出视为已完成：未落盘的计划视为不存在，未更新状态字段的完成视为未完成。
- 严禁用 L2 投影写入（registry / 宿主任务列表）替代 L1 任务计划文档落盘。
- 严禁把多个最小任务塞进同一份任务计划文档；实施周期文档中的 TASK 清单与每任务独立计划文档并存、互不替代。

## 5. 压缩后恢复流程（与 context-compression-rules 对接）

1. 读取当前任务的计划文档状态字段，确认任务状态。
2. 读取“下一动作”指针与前置产物路径，确定恢复偏移。
3. 核验中断点：磁盘文件、测试结果、外部状态与文档记录一致后才继续；未知或非幂等写操作只查询、不重放。
4. 在执行记录追加一条“压缩恢复于 {UTC 时间}，恢复偏移 = {读取的文件列表}”。
5. 继续执行，并维持写透检查点节奏。

禁止：凭对话记忆或压缩摘要续做；跳过中断点核验直接重放写操作。

## 6. 通过 / 驳回标准

- 通过：状态与证据全程 L1 落盘且写透时机无遗漏；每个最小任务满足粒度清单且通过落盘产物交接；每任务一份按序独立计划文档且字段齐全；任一任务被压缩后可按第 5 节以最小偏移恢复。
- 驳回：状态只留会话、聊天、临时文件或 UI 列表；未落盘即宣称完成；单任务跨多个 AC 或依赖会话记忆交接；恢复需回读大量会话历史；用投影写入替代事实源落盘。
