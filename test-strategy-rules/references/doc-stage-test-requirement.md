# 文档阶段测试要求预埋（强制）

> 本节是「文档阶段测试要求预埋」的单一权威来源（历史别名：文档阶段接口测试要求预埋）。写需求主文档、实施总览 / 实施周期 / 最小任务、Bug 主文档时，必须在文档的测试要求 / 测试映射 / 真实测试安排章节显式预埋本节要求；`requirement-intake-rules`、`implementation-planning-rules`、`bug-intake-rules` 直接引用本节，不重复定义。补于 2026-09-14：原节只预埋「本地单测 + apifox 用例」两层，前端页面自动化点击测试层缺失，文档阶段就没有第三层的落点，执行阶段必然漏做；现已补齐为三层。

### 判定本轮适用哪几层

- **代码级（本地 `test/` 单元测试）**：本轮改动落在函数 / 模块 / 纯逻辑即适用。
- **接口级（apifox API 用例）**：来源对象存在「有 method + path、经 HTTP 协议调用」的接口，且本轮需要做接口功能验证、回归或上线门禁的接口部分即适用。
- **页面前端级（自动化点击与交互）**：命中《页面/UI 级测试执行通道（强制）》触发判定任一条即适用——前端改动面、**被前端调用的接口改动（前端代码零改动同样触发）**、影响前端可见行为的其他后端变更；判定细则见该节。**纯前端项目（无后端）不改变该判定**，无后端时本层仍为强制项，只把 Network 断言与进程收口切换到无后端分支。
- 仅改函数 / 模块 / 纯逻辑且无前端改动面 → 只要求本地 `test/` 单元测试，不强制 apifox、不强制浏览器点击测试。
- 纯文档 / 注释 / 排版等不改变可执行行为的改动 → 按 `implementation-planning-rules` 的「无需真实测试」豁免，写 `N/A + 原因 + 证据`。

### 预埋要求（最多三层，按序缺一不可）

文档测试安排必须显式写出本轮适用的每一层要求，并保持先后顺序：

1. **本地 `test/` 单元测试（代码级）**：走根 `test/` 的 `go test` / pytest，覆盖函数、模块、纯逻辑；落点按 `test-program-rules` 的 ASCII 源码镜像目录。
2. **完善 apifox API 接口用例（接口级）**：走《接口测试执行通道（强制）》，用例真实运行并落地保存到 apifox「AI 团队」对应项目。
3. **前端页面自动化点击测试（页面前端级）**：走《页面/UI 级测试执行通道（强制）》，用 agent 内置浏览器（优先）或系统默认浏览器（兜底）对页面执行真实点击与交互，断言结果并保留证据；写 `N/A` 时**必须同时满足三条件**（纯后端改动 + 不影响前端可见行为 + 不涉及前端调用的接口）并附**前端调用面检索结论**——只写「本轮为纯后端改动，前端代码零改动」**不构成有效豁免理由**。**纯前端项目（无后端）本层同样必填**，并在文档中写明数据来源类型（本地 mock / 静态 JSON / 浏览器存储 / 第三方公网接口）与对应的 Network 断言分支。

- **顺序约束**：先本地 `test/` 单元测试，后完善 apifox 接口用例，最后执行前端页面点击测试；不得只写单测漏 apifox 用例，也不得以「本地 curl 验证过」替代 apifox 落地，更不得以「接口已验证」替代前端点击测试。
- **完成标准**：apifox 接口用例「完善」= 用例已创建、已真实运行、结论写回 `doc/5-tests/` 测试主文档（内联 caseId / 报告链接）并通过；前端点击测试「完善」= 在真实浏览器中完成关键交互路径，动作序列、断言明细与观测证据写回同一测试主文档并通过；「已测试」无凭据不算完善。
- **豁免口径**：任一层不适用或受限时，必须在文档内写明层级名 + 状态（`not_applicable` / `limited`）+ 原因 + 依据 + 替代验证 + 人工补验入口，禁止整节留空或以一句话笼统概括三层。
