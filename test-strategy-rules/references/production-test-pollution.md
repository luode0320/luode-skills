# 生产代码测试污染判定与治理

## 什么是测试污染

为了让测试跑起来，往生产代码里新增只有测试会用到的函数、数据、字段、分支或构造器，就是测试污染。

测试只能验证生产代码本来就有、生产路径本来就在用的能力。测试需要的静态样本、种子数据、假依赖和构造逻辑，一律放在根 `test/` 的镜像目录里，不进生产源码。

## 主判据：引用面判据

判定不看写代码时的意图，只看引用面事实：

> 生产目录中的符号，若其全部非定义引用都来自 `test/`，且生产路径引用数为 0，判定为测试污染。

意图判据（“这段代码将来生产也会用”“这是通用初始化能力”）不成立，不接受作为放行理由。将来会用的能力等到生产真的接线时再写。

引用面证据可以用三种方式取得，结论一致即可：

- `test-strategy-rules/scripts/scan_test_pollution.py` 扫描（推荐，机器可核验）
- CodeGraph 的符号引用面板（看引用列表里是否只有 `test/` 路径）
- `rg -w '<符号名>'` 手工分桶统计

## 五类污染模式

### P1 测试专用函数 / 方法

生产文件里的函数或方法，生产调用方为 0，只有 `test/` 在调。

反例：

```go
// database/repository/blacklist/repo.go —— 生产文件
// EnsureSeed 在单个统计库事务内幂等 seed 原 13 个地址 + 3 个合约。
func (r *Repository) EnsureSeed(ctx context.Context) error {
    // ... 只有 test/database/repository/blacklist/seed_probe 等测试在调用
}
```

正例：测试需要黑名单里有数据，就在测试侧自己准备：

```go
// test/database/repository/blacklist/blacklist_fixture.go —— 测试文件
// seedBlacklist 在测试开始前写入本轮所需黑名单样本，测试结束回滚。
func seedBlacklist(ctx context.Context, db *gorm.DB) error {
    // 测试侧直接用生产已导出的写入 API 落样本
}
```

### P2 测试专用静态数据

生产目录里的常量数组、切片或 map，内容是固定测试样本，只被测试消费。

反例：

```go
// database/repository/blacklist/constant.go —— 生产文件
var seedAddressBlacklist = []string{ /* 13 个固定测试地址 */ }
var seedContractBlacklist = []string{ /* 3 个固定测试合约 */ }
```

正例：同样的数组放测试侧的 fixture 文件，与被测源码保持同一镜像路径。

判断口径：这批数据如果生产启动、生产业务流程都不读，它就是测试 fixture，不是生产配置。生产真正需要的初始化数据走迁移脚本、配置文件或运维流程，不靠一个没人调的函数。

### P3 测试专用结构体字段

结构体字段只在测试里写入或读取，生产逻辑完全不消费。典型形态是给结构体加一个 `LastCalledAt`、`CallCount`、`InjectedNow` 之类只为断言存在的字段。

替代做法：断言改为观察生产可见结果（返回值、DB 状态、HTTP 响应、日志），不在生产结构体上挂探针。

### P4 运行时测试分支

生产执行路径里出现仅测试可达的分支：

```go
if os.Getenv("APP_TEST") == "1" { ... }
if cfg.Env == "test" { ... }
if isTest { ... }
```

这类分支把测试决策带进生产运行路径，增加线上行为的不确定性，一律驳回。

`local` 与 `prod` 的正常环境差异化配置不属于本条——判断标准是这个分支生产环境是否真实会走。只有测试会走的，才是污染。

### P5 测试专用构造器 / 重载

与生产构造器功能重复、只供测试调用的第二入口，例如生产用 `NewRepository(db)`，另外加一个只有测试调的 `NewRepositoryForTest(db, clock)`。

替代做法：测试直接用生产构造器；生产构造器缺参数时按下节的替代出路处理。

## 白盒测不到时怎么办

禁止为测试改动生产代码后，遇到“内部状态测不到”按优先级选出路，不允许回头造测试专用代码：

1. **黑盒验证**：只用生产已导出的 API 组合完成验证。绝大多数场景到这一步就够。
2. **端到端行为断言**：通过 local 真实环境的可观测结果间接断言内部行为——数据库落库状态、HTTP 响应体、消息队列投递、日志输出。
3. **判定当前不可测**：把它写成“待补测风险”记入 `doc/5-tests/` 当轮测试主文档，说明测不到的原因和补测条件，然后放过。不测比造污染代码好。

### 生产代码重构的合法条件

依赖注入、接口抽象、拆函数这类重构**允许做**，但只能以生产价值立项，走正常需求 / 实施流程。放行要同时满足四条：

- 改动理由能独立成立：即使没有任何测试需求，这个改动本身也应该做；
- 生产 wiring 真实使用新结构，不是只有测试在用；
- 生产行为不变，或变化已被需求确认；
- 改完不存在仅测试可达的入口、分支或字段。

以“为了能测”为唯一理由的改动一律驳回。四条里缺任一条，都退回上面的三级替代出路。

## 合法豁免与登记

引用面判据对以下情况会误报，需要显式登记后才放行：

- 反射调用、注解 / 标签驱动调用
- 配置表、路由表、任务表驱动注册的处理器
- 对外导出的 SDK / 库 API，调用方在本仓库之外
- 尚未接线的新功能（必须写关联需求 ID 和预计接线节点）
- 跨包同名符号造成的引用归属错判

登记文件为项目根 `.test-pollution-allowlist`，UTF-8，每行一条：

```
<相对路径>::<符号名>  # <豁免理由>
```

示例：

```
internal/handler/registry.go::HandleRefund  # 路由表驱动注册，无静态调用点
pkg/sdk/client.go::NewClient  # 对外导出 SDK，调用方在仓库外
internal/service/settle.go::SettleBatch  # REQ-SETTLE-011 待接线，预计本周期 03 接入
```

登记只是承认这条是误报或已知例外，不是污染的免罪牌。豁免项仍会在扫描报告中列出，`6-review` 时应复核理由是否还成立；理由失效的条目必须删除或整改。

## 存量污染治理四步

发现存量污染后按顺序处理，不跳步：

1. **判定性质**：逐个符号确认属于 P1–P5 哪一类，还是属于合法豁免。拿不准的先按污染处理并向用户确认，不自行放行。
2. **迁移落点**：污染符号整体搬到 `test/` 下与被测源码同路径的镜像目录。函数变成测试包内的 helper，静态数据变成 fixture，字段和分支直接删除。搬迁不改变测试断言的业务含义。
3. **验证生产不受影响**：跑生产构建（Go 为 `go build ./...`）确认编译通过，再跑受影响的测试确认仍然通过。生产行为必须零变化。
4. **归档**：把治理清单、迁移前后落点和验证证据写入 `doc/5-tests/` 当轮测试主文档，并在 `doc/6-review/` 的风格回归里记录目录归位结论。

## 通过 / 驳回标准

- 通过：本轮新增或修改的生产符号都有真实生产调用方；测试所需的样本、种子数据、假依赖全部在根 `test/` 镜像目录；生产路径无仅测试可达的分支、字段和入口；扫描输出 `POLLUTION: PASS`，或全部命中项已在 `.test-pollution-allowlist` 登记且理由成立。
- 驳回：为测试在生产代码新增函数、常量、字段、分支或第二构造器；用“将来生产也会用”“这是通用能力”作为放行理由；扫描 FAIL 却未整改也未登记豁免；把测试 fixture 伪装成生产初始化数据。
