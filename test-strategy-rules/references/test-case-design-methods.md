# 用例设计方法（测试域单一权威）

> 归属 owner：`test-strategy-rules`。吸收自 `comprehensive-test-case-writer`（skillhub 安装源，2026-08-30）。
> **本节是测试域「测几个维度、用什么方法设计用例、用例质量怎么判」的唯一定义处**。功能验证、回归、测试程序、Bug 验证等测试 skill 需要用例设计方法时统一以本节为准，不再各立一套。
> **接口级落地细节不在此处**：测试对象为 HTTP 接口时，用例字段模板、RTM 追溯、P0/P1/P2 风险赋值统一以 `apifox-cli__skillhub/modules/test-case-from-requirement.md` 为准；本文件只给方法与维度定义，避免两套模板。

## 何时读取

- 需要回答"这次要覆盖哪些维度""用什么方法设计用例""用例写得到底合不合格"。
- 用户提到测试用例设计、测试设计、测试点分析、边界值、等价类、决策表、状态转换、场景法、覆盖度评审。
- 非接口测试对象（纯逻辑、前端页面、脚本、游戏玩法）找不到用例设计依据时——接口侧已有 apifox 模块承接，本文件补齐非接口场景。

## 一、质量维度全景（8 维）

测试策略必须显式回答"覆盖哪几个维度"，不能默认只测功能。下表是维度清单，**不是每轮必测全表**，裁剪规则见第三节。

| 维度 | 要回答的问题 | 典型判据 | 执行通道 |
|------|-------------|----------|----------|
| 功能 | 是否按需求/规则正确工作 | 正常路径、业务规则、数据落库一致性 | 接口→apifox；其他→本地真实运行 |
| 异常健壮性 | 出错时是否优雅 | 无效输入、依赖超时、并发冲突、故障恢复、资源耗尽 | 接口→apifox；其他→本地真实运行 |
| 安全 | 是否可被绕过/泄露 | 认证鉴权、越权、注入、敏感信息回显、会话失效 | 接口→apifox（9 类 payload 见 `apifox-cli__skillhub/modules/testing-pitfalls.md`） |
| 性能 | 负载下是否还可用 | 响应时间、吞吐、并发、资源占用、长时稳定性 | 接口→`apifox-cli__skillhub/modules/test-performance.md` |
| 界面 UI | 是否符合设计规范 | 布局、颜色字体、响应式、空/满/错误态、图标文案 | **不进 apifox** → 浏览器链路或人工 |
| 易用性 | 用户能否无师自通 | 操作路径长度、错误提示可理解性、可恢复性 | **不进 apifox** → 人工/探索式 |
| 兼容性 | 换环境是否还工作 | 浏览器/OS/设备/分辨率、版本升级前后、数据格式兼容 | 接口兼容→apifox；客户端兼容→`test-regression-rules` + 真机/浏览器 |
| 领域专项 | 领域特有风险是否覆盖 | 见第五节（游戏）；其他领域按项目约定补充 | 按领域定 |

**通道判据**：只有"测试对象是 HTTP 接口（有 method+path）"的维度才进 apifox；UI / 易用性 / 客户端兼容性 / 游戏体验这类非 HTTP 维度写不进 apifox 用例，不得为了凑覆盖而伪造接口用例（接口维度边界表见 `apifox-cli__skillhub/modules/test-case-from-requirement.md` 的 Step 3.5）。

## 二、黑盒用例设计五法

按被测对象特征选方法，**不机械铺满**；接口级用例的字段模板与命名以 apifox 模块为准。

| 方法 | 适用信号 | 取值/覆盖要点 | 用例下限 |
|------|----------|--------------|----------|
| 等价类划分 | 输入有明确合法域 | 有效类、无效类各至少一例；每类取代表性值而非随机值 | 有效 ≥1，无效 ≥1 |
| 边界值分析 | 输入有范围/长度/数量/时间限制 | `min-1 / min / min+1 / max-1 / max / max+1`，另加 0、空、超长、空数组、单元素 | 每个边界字段 ≥5 |
| 决策表 | 多条件组合决定结果（规则多、条件交叉） | 条件桩+动作桩按**规则行**覆盖，按风险裁剪组合，禁止全组合爆炸 | 每条规则行 ≥1 |
| 状态转换 | 业务对象有状态机 | 每个有效转换 ≥1；每个无效转换（应被拒绝）≥1；终止态无后续转换；跨会话状态持久化 | 有效+无效转换全覆盖 |
| 场景法 | 有业务流程（主流程/备选/异常流） | 基本流、每个备选流、每个异常流各 ≥1；串联跨接口/跨页面数据 | 基本流 1 + 备选/异常流各 ≥1 |

**组合原则**：单个需求命中多方法时，按"输入有域→等价类+边界值，规则交叉→决策表，有状态→状态转换，有流程→场景法"叠加，叠加后仍按风险裁剪，不以用例数量论覆盖。

## 三、按任务类型裁剪维度（默认最小集）

铺满 8 维属于策略失控，按下表给最小集，需要加维必须写出风险理由：

| 任务类型 | 最小维度集 | 可加维条件 |
|----------|-----------|-----------|
| 新需求（接口） | 功能 + 异常 + 安全（含鉴权） | 上线门禁加契约/性能；涉及资金加并发 |
| 新需求（页面） | 功能 + 异常 + 界面 UI | 面向 C 端加易用性；多端适配加兼容性 |
| 新需求（纯逻辑/脚本） | 功能 + 边界 + 异常 | 数据量大加性能 |
| Bug 修复 | 功能（复现路径）+ 回归相关维度 | 安全类 Bug 必加安全；线上事故加监控/告警验证 |
| 配置变更 | 功能 + 兼容性 | 灰度/开关类加异常（开关降级） |
| 公共模块/底层改动 | 功能 + 兼容性 + 性能 | 跨服务加契约 |

## 四、用例质量四性检查（收口前自查）

用例写完后按四性判定，任一不通过不得作为覆盖证据：

1. **正确性**：与需求/业务规则一致，输入输出明确，边界完整，异常处理完备。
2. **完整性**：需求条目全挂用例（无空需求），场景无缺口，维度按第三节裁剪到位，角色权限覆盖。
3. **可执行性**：步骤具体到可照做，测试数据是**真实具体值**（禁止 `[有效邮箱]` 占位符），环境可搭建，结果可验证（状态码/响应结构/页面表现/落库结果四选一可测）。
4. **一致性**：用例内部无矛盾、与需求口径一致、术语统一，同一对象不出现两套 ID 命名。

**常见反例（直接驳回）**：用例笼统无具体数据；预期结果写成"正常显示"不可验证；靠伪造数据并接受失败"符合预期"；未覆盖无效等价类；孤儿用例（无需求挂靠）；把 UI/易用性/兼容性硬写成接口用例充数。

**与接口级检查清单的分工**：接口级用例的覆盖验证清单（Step 5 的 11 项自查）以 `apifox-cli__skillhub/modules/test-case-from-requirement.md` 为准，本四性不重复那份清单；本四性用于**非接口场景的用例判定**以及**跨维度、跨用例集的总判**，接口用例只需按 apifox 清单执行，通过即视为满足本节的完整性与可执行性要求。

## 五、领域专项：游戏测试（命中游戏项目时加载）

**触发**：被测对象为游戏客户端、游戏服务端或玩法系统（引擎不限，Godot/Unity/自研均适用）。

**通道分离（强制）**：游戏**服务端 HTTP 接口**仍走「接口测试执行通道（强制）」，在 apifox 落地；玩法、数值、客户端表现、联机体验类维度**不属于 apifox 落地范围**，走本地真机/编辑器运行 + 人工/探索式，证据写回 `doc/5-tests/` 测试主文档。

| 专项 | 测试要点 |
|------|----------|
| 玩法流程 | 主流程贯通、任务/关卡可达、中断恢复、引导不卡死、失败可重试 |
| 数值平衡 | 角色属性、技能伤害公式、经济产出/消耗、成长曲线、掉落概率与保底（按大样本验分布，不靠单次手感） |
| 角色技能 / 道具 | 释放条件与冷却、异常状态叠加与免疫、道具堆叠上限、使用与消耗一致性、边界数量（0/满/溢出） |
| 多人联机 | 状态同步、延迟补偿与回滚、断线重连、房间创建/解散/踢人、匹配机制、跨端兼容 |
| 付费与内购 | 下单/发货/退款链路、重复支付与掉单、金额与档位一致性、未成年人/合规限制、日志可审计 |
| 本地化 | 多语言文案不截断不窜位、时区与货币、文化合规、字体缺字回退 |
| 更新兼容 | 版本升级后存档/配置兼容、热更资源完整性、旧版本强制更新提示、回滚可用 |
| 兼容性矩阵 | 设备（手机/PC/主机）× 操作系统 × 分辨率 × 网络环境（弱网/断网/切换）至少各覆盖一档 |

**游戏用例质量附加项**：除四性外，额外检查玩法可玩性（是否卡关/无解）、数值合理性（是否数值爆炸）、操作流畅性、视听表现，问题写实不写"体验不好"这类不可判定描述。
