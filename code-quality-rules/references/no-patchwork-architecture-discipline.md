# 严禁打补丁式改动与架构妥协准则（no-patchwork-architecture-discipline）

## 1. 核心红线

**改动、改 Bug、改需求严禁用打补丁的方式实现。**

在任何代码修改、功能迭代或缺陷修复过程中，**严禁为了“不想改动太多”、“控制 diff 行数”、“避免修改已有调用”或“贪图省事”而选择打补丁**。
这种妥协式的打补丁实现不仅会严重破坏代码的可读性，还会导致系统原有设计被肢解、架构被严重破坏，使代码库迅速沦为充满特例、隐式分支与历史包袱的垃圾场。

---

## 2. 什么是“打补丁”（四大典型坏味道形态）

在日常工程中，必须坚决识别并阻断以下四大典型“打补丁”行为：

1. **外围堆砌特判 Flag / 开关分流**：
   - 面对新需求或新规则与旧逻辑的冲突，不重构原有逻辑，而是在数据表、DTO 或入参强行增加 `isLegacy`、`isNewVersion`、`strategyTypeV2` 等标志位。
   - 在核心流程、状态机或下游消费处到处增加 `if-else` 分流判断，把同一个业务链路割裂为多套互不兼容的平行逻辑。
2. **新老双轨并行兼容（逃避模型演进）**：
   - 当策略参数、业务规则或核心模型发生变更时，为了“保证老单/旧数据完全按老逻辑跑”，在同一业务引擎中硬塞进两套独立状态机或两套规则解析引擎。
   - 导致系统长期背负双轨债务，后续排查问题时必须在两套规则间反复确认，认知成本翻倍。
3. **套壳包装与胶水绕道**：
   - 原有方法职责不合理或缺少必要能力，开发人员不愿动原方法，而是在外围包装一个 `XxxWrapper`、`XxxHelper` 或临时前置/后置函数，在外面绕一道弯强行打补丁。
   - 导致原本清晰的调用链变得曲折晦涩，读者无法直观理解核心业务流向。
4. **下游吞异常与脏数据兜底**：
   - 产生问题的根本原因在上游或数据源头，但为了“少改上游代码”，在下游消费者、控制器或数据访问层加 `try-catch` 吞掉异常，或者对错误数据做强行类型转换、默认值伪装。
   - 表面上压住了症状，实际掩盖了系统数据一致性缺陷，同类问题在其他入口持续复发。

## 3. 正向准则：流程遗漏直接在主流程补齐

反对打补丁，**绝不意味着排斥正常的流程补齐与缺陷修复**。必须严格区分“流程补齐”与“妥协打补丁”的本质差异：

| 维度 | 正向准则：流程遗漏直接补齐（提倡） | 反向红线：为少改动打补丁（严禁） |
| --- | --- | --- |
| **发生场景** | 排查发现主流程确实遗漏了步骤（如缺少状态流转、缺少合法性校验、漏触发事件、未处理边界返回值）。 | 新需求或规则与旧设计冲突，开发人员为了控制改动范围不想大动旧代码。 |
| **修改位置** | **直接改在主干流程/核心状态机内部**，补齐缺失的环节，保持单一流水线。 | **改在外围、调用方或旁路**，增加绕道逻辑、外层包装或外挂检查。 |
| **结构影响** | 主流程更加健全自洽、线性透明，没有额外概念包袱与分支分流。 | 核心链路被打碎，到处堆砌 `if isXxx` 分支或双轨分流，可读性严重下降。 |
| **架构演进** | 符合统一架构模型，消灭未知边界盲区。 | 破坏既有架构设计，人为引入技术债与历史双轨负担。 |

**正向补齐的标准**：
- 如果主状态机漏掉了一个合法的状态流转，直接在主状态机中增加该状态转移分支，使其成为标准流转的一部分；
- 如果某个核心方法缺少前置校验，直接在该方法入口补齐校验逻辑，所有调用方一视同仁；
- 如果缺少某种事件通知，直接在业务完成动作时触发通知，绝不让外部调用方在每次调用后手动“打补丁补发”。

## 4. 架构优先与可读性优先原则

面临改动方案取舍时，必须坚守以下铁律：

1. **架构与设计优先于局部 diff 最小化**：
   - 最小改动原则（`code-quality-rules`）的初衷是“排除无关重构与过度抽象”，**绝对不是让“改动行数最少”凌驾于系统架构和代码可读性之上**！
   - 当改动涉及核心机制（如量化网格参数计算、撮合状态机、资金清算、权限控制）时，**宁可正向重写或统一演进核心主干，也绝不在外围堆叠补丁**。
2. **统一模型，拒绝双轨**：
   - 当新旧规则不一致时，优先考虑在数据入口或配置加载时完成统一归一化转换，使核心业务引擎始终只运行单一、干净的模型；
   - 若存量数据确实需要区分，应通过明确的版本迁移脚本（Migration）一次性升级，或者设计清晰、显式的策略接口替换，严禁在状态机内部随处打小补丁。
3. **可读性是可维护性的生命线**：
   - 任何改动完成后，新接手的开发人员顺着调用链向下阅读时，主流程必须清晰自然、一目了然；
   - 凡是让人觉得“这里为什么莫名其妙冒出来一个特判”、“为什么新老逻辑混在一起跳来跳去”的代码，一律判定为违规补丁代码，必须重写。

## 5. 方案设计前自检（三问红线）

在实施规划（`implementation-planning-rules`）、Bug 修复提议（`bug-fix-proposal-rules`）和正式编码前，必须自检以下三问：

1. **我这个方案是不是为了“不想改动太多旧代码”而在外围做妥协？**
   - 如果是，立即停止！回到架构设计，思考如何在主流程中优雅实现。
2. **新写下的逻辑是在补齐流程漏洞，还是在给既有缺陷打掩护、做绕道？**
   - 补齐漏洞应该让主干更坚固；打掩护只会让系统更脆弱。
3. **改动完成后的主业务逻辑，是否像全新设计一样清晰自然？**
   - 如果读起来充斥着条件特判与历史包袱，说明架构已被破坏，方案必须推倒重来。
