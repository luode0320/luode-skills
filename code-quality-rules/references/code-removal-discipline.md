# 删除纪律（code-removal-discipline）

## 用途

当"删除某代码 / 功能 / 模块"是本轮明确目标时，定义删除动作的完整语义：删除 = 彻底移除（remove），不是废弃保留（deprecate）。删除后不应留下任何可被后续会话或文档重新引用的残留。

## 核心原则：remove 语义，不是 deprecate 语义

- 用户说"删除"，执行的是**移除**：目标代码从代码库中消失，而不是"保留一份 + 标记不可用"。
- 禁止创建 `xxxv2`、`xxx_old`、`xxx_removed`、`xxx_bak` 之类的"删除版本 / 备份版本"残留旧实现。删除决定本身已由 git 历史兜底，不需要文件级备份。
- 删除是单向不可逆动作：本轮删除后，旧实现不再以任何名称存在于当前工作树、配置、测试或文档中。

## 全链路清理清单（删除 = 一处不留）

当删除目标确定后，必须同步清理以下所有关联，缺一即为删除未完成：

1. **源码本体**：目标文件 / 函数 / 类 / 组件 / 路由 / 接口定义本身。
2. **调用点与引用**：所有 import、调用、引用、类型依赖、配置注册、路由挂载点；删除后代码库必须可编译、可启动。
3. **测试资产**：针对该目标的单元测试、集成测试、测试夹具、mock 定义；测试目录中不留指向已删除符号的用例。
4. **配置与产物引用**：环境变量、配置文件、依赖声明（如 go.mod / package.json）、构建脚本、CI 步骤中对该目标的引用。
5. **文档提及**：需求文档、实施文档、设计文档、README、注释中对该功能的描述；禁止用"已删除 / 已废弃 / 禁止使用 / 保留不用"的占位文字替代真实删除。
6. **记忆与知识残留**：`PROJECT_MEMORY.md`、`PROJECT_CURRENT.md`、`PROJECT_HISTORY.md`、知识库笔记、风格库中与该目标绑定的实体条目；删除后**禁止写入"xx 已被强制删除、不能使用"类警示描述**——代码物理上已不存在，天然不可用，无需再用文字"禁用"它；记忆侧清理细则由 `project-memory-rules` 落地，本文件为权威定义。

## 与最小改动的关系（防多删 vs 防少删）

- 最小改动主线约束**"没被要求删的别删"**：阻断顺手清理大段旧代码、无关重构、无关风格统一。
- 删除纪律约束**"被要求删的要删干净"**：明确要求删除的目标必须全链路移除，不允许"保守只删一半、留备份、留警示"。
- 两者互补，冲突时的判断标准：**以"本轮删除目标是否明确"为界**——目标明确（用户点名删除 / 需求删除 / 功能下线）→ 按本文件执行彻底删除；目标不明确（只是顺手看到旧代码）→ 归最小改动越界，不删。

## 边界与例外（需要暂停确认）

- 用户明确要求"保留旧版本 / 归档 / 仅停用不删除"时，按 deprecate 语义执行，但必须与用户确认保留方式（归档目录、git 分支、tag），不得自行选择"xxxv2"式命名。
- 删除涉及跨项目文件、他人维护模块或用户手改内容时，先确认影响范围再删。
- 删除后无法验证可编译 / 可启动（依赖链不清）时，先列清理清单再动手，禁止"删完再补"。
- 判断失误需要回退时，用 git 恢复，不依赖文件级备份；若删除已提交且被推送，按 `git-collaboration-rules` 处理回退边界。

## 执行验证

- 删除完成后用真实构建 / 测试 / 启动验证目标符号已完全消失：grep 目标名（含大小写变体）在源码、测试、配置、文档中 0 命中（历史 git 记录除外）。
- 若命中残留，继续清理直到 0 命中，再进入收口闸门。
