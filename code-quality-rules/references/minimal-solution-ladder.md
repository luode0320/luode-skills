# 极简解法阶梯与过度设计审查规则

> 归属 owner：`code-quality-rules`（最小改动主线权威支撑）。
> 核心哲学：**最好的代码，是从未写过的代码。** 在动手写代码前，必须依序经历阶梯反射，在第一个站得住的台阶停下；绝不以砍掉输入校验、错误处理、安全防护与可访问性为代价。

---

## 1. 七级极简解法阶梯（The Seven-Step Minimal Ladder）

在真正看懂问题与改动范围后，按以下顺序由高到低依次排查，**在第一个站得住的台阶上停下来**：

```
[第 1 阶] 这件事需要存在吗？(YAGNI) ─── 投机性需求直接跳过
   │ (不成立)
[第 2 阶] 代码库里已经有了吗？ ───────── 复用已有 helper/util/类型/结构
   │ (不成立)
[第 3 阶] 标准库能做吗？ ─────────────── 优先使用语言标准库，不自己造轮子
   │ (不成立)
[第 4 阶] 平台原生能力覆盖了吗？ ─────── 查阅 platform-native，平台原生优先于依赖
   │ (不成立)
[第 5 阶] 已安装的依赖能解决吗？ ─────── 绝不为几行代码就能搞定的事新增依赖
   │ (不成立)
[第 6 阶] 能写成内联一行吗？ ─────────── 保持直写，不为一次性逻辑封装多层函数
   │ (不成立)
[第 7 阶] 编写最小可运行实现 ─────────── 仅实现当前必需，非平凡逻辑保留最小自检
```

### 台阶详解

1. **第一阶：这件事需要存在吗？（YAGNI）**
   - 投机性的需求、未被用户明确要求的配置开关、为“未来可能用到”而准备的分支，一律跳过。
   - 用最精炼的一句话说明为什么当前阶段不需要它。

2. **第二阶：代码库里已经有了吗？**
   - 动手前先全局搜索项目中已有的 helper、工具函数、常量、类型和公共组件。
   - 重新发明隔几个文件就已存在的同类逻辑，是代码库腐化的最大来源。发现已有实现时优先复用。

3. **第三阶：标准库能做吗？**
   - 优先查阅当前语言的标准库能力（例如 Go 的 `slices`/`maps`/`strings`，Python 的 `functools`/`itertools`/`dataclasses`，Node/JS 的内置全局对象）。
   - 标准库由专业团队长期维护且无额外依赖包体积，永远优先于手写工具函数。

4. **第四阶：平台原生能力覆盖了吗？**
   - 优先核对宿主平台、运行环境或 Web 规范的原生能力（详见 `platform-native-substitutes.md`）。
   - 原生 HTML 元素胜过自定义控件库，现代 CSS 胜过手写 JS 脚本，数据库层约束胜过应用层多层冗余检查。

5. **第五阶：已安装的依赖能解决吗？**
   - 如果项目中已经引入了被广泛使用的成熟基础库，且该库提供了可靠实现，直接复用既有依赖。
   - **绝不为“几行代码或标准库就能搞定的事”在 `package.json`、`go.mod` 或 `requirements.txt` 中新增第三方依赖**。

6. **第六阶：能写成内联一行吗？**
   - 一次性、无复用需求、逻辑直观的赋值、映射或局部判断，直接就地内联表达。
   - 不要为了所谓的“美观”将 1-3 行自明代码包装进独立的小函数或浅层类中。

7. **第七阶：编写最小可运行实现**
   - 只有前面六级全部确认无法满足时，才动手编写具体的新增实现。
   - 实现必须保持最短路径，不做多余的封装或提前抽象。
   - **非平凡逻辑的自检底线**：涉及分支、循环、数据解析、金额或鉴权的非平凡逻辑，必须保留一个能跑的最小验证（如基于 `assert` 的单测或自检用例），不能把无检查的草率代码当成极简。

### 阶梯执行纪律

- **阶梯是反射，不是代替阅读的借口**：阶梯缩短的是“方案”，绝不是“对问题的理解”。必须先完整阅读任务涉及的上下文与调用链路，端到端走通真实逻辑，再爬阶梯。
- **高台阶优先**：若同时有两个台阶看似成立，永远取更高层级的那个。
- **不可突破的安全底线**：极简绝不以牺牲安全性为代价。**永远不要为了简化而砍掉：信任边界上的输入校验、防止数据丢失的错误处理、核心安全鉴权防护、无障碍可访问性要求，以及用户明确指定的任何要求。**

## 2. 有意折中技术债规范（Tradeoff Annotation）

在研发过程中，为保持最小改动或快速闭环，有时会做出有意识的极简折中（例如采用粗粒度互斥锁代替分段锁、O(n) 全表/全内存扫描代替复杂索引树、朴素轮询代替复杂的事件长连接等）。

为了防止“以后再说”悄悄演变为“永远不做”，所有此类有天花板的有意折中，必须显式附加统一的技术债注释：

### 注释规范格式

```text
# tradeoff: <当前天花板/局限>, <升级重构的触发条件>
// tradeoff: <当前天花板/局限>, <升级重构的触发条件>
```

### 示例

```go
// 正确示例：明确标示了局限与触发重构的阈值
// tradeoff: 单机内存 map 缓存，多实例水平扩容或数据量超 10 万条时需切换为 Redis
var localCache = make(map[string]interface{})

// 正确示例：标明算法局限与升级指标
// tradeoff: 朴素 O(n) 内存过滤，列表单次返回超过 500 条且出现延迟毛刺时补联合索引
func filterItems(items []Item) []Item { ... }

// 错误反例：未写升级条件，属于会悄悄腐烂的代码
// tradeoff: 临时全局锁
```

- 任何没有注明升级路径或触发条件的折中注释，均被视为不合规的技术债隐患。

## 3. 过度设计专项审查五标签（Review Tags）

在对代码改动（diff）或已有代码做过度设计审查时，统一使用以下五个精简标签，指出可以删减或内联的冗余设计：

| 标签 | 核心含义 | 处置要求 |
|---|---|---|
| `delete:` | 死代码、无人使用的灵活性、投机性配置项与分支 | **直接删除**，不需要任何替代实现。 |
| `stdlib:` | 手写的自造轮子，而当前语言标准库原生具备该能力 | **点名具体的标准库函数/类型**并直接替换。 |
| `native:` | 引入第三方库或手写大段代码，而平台底层原生已支持 | **点名具体的平台原生能力**（对照 `platform-native-substitutes.md`）替代。 |
| `yagni:` | 只有一个实现的接口、单产品的工厂、只有单个调用方的包装层 | **就地内联**，等待出现真实的第二调用方或第二实现再抽象。 |
| `shrink:` | 业务逻辑正确，但代码行数过多、写法啰嗦，可用更紧凑的语法实现 | **给出更短、可读性更高的等价写法**。 |

### 审查示例

```text
auth.go:L42: yagni: TokenValidator 接口当前仅有 JwtValidator 一个实现。直接内联使用具体结构体，等出现真实第二个验证方式再提炼接口。
util.js:L15: stdlib: 手写 25 行深拷贝函数。直接用原生 structuredClone(data) 替代。
styles.css:L80: native: 引入第三方 JS 监听窗口尺寸计算弹窗位置。改用原生 CSS anchor positioning 或 position: fixed + translate。
retry.py:L10-28: delete: 在幂等的单机只读查库外层套用了 3 层的指数退避重试包装。直接删除包装层，直调数据库驱动。
parser.go:L55: shrink: 手写 15 行嵌套循环解析键值对。改用一行 strings.Split / map 字面量初始化。
```
