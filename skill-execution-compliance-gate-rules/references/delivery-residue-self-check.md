# 交付残留自查（收口前横切检查）

## 目标

在收口前以「本轮真实变更集」为输入、以「独立读者视角」重读本轮全部产物，找出**计划外产生的残留**：任务本身已宣布完成，但交付物仍不干净、不完整或不同步的问题。

解决的实际问题是「任务收口后，用户再问一次仍能发现该任务的新问题」——残留不是在收口对账环节产生的，而是在现有收口链**无人覆盖的空白区**产生的。

## 与既有 owner 的边界（强制）

- `applicability-and-gap-check.md` 从「本轮命中的 skill 声明」**正向**抽取规则，判定「可执行但未执行」的缺口；本文件从「磁盘上的真实变更集」**反向**推导残留，判定「计划内已完成之外仍存在的问题」。两者输入方向相反、判定对象不同，互补不重复。
- 本文件不判断代码风格（归 `code-style-consistency-rules` 的 `6-review`）、不判断业务正确性（归真实测试与 `functional-validation-rules` / `test-regression-rules` / `bug-validation-rules`）、不复制任何 owner 的判据、命令或字段细则。
- 本文件不拥有用户可见渲染权：只产出「残留清单 + 处置状态」，阻断区块与最终结构归 `reasoning-summary-structure-rules` 唯一所有。
- 本文件不能替代 `6-review`、真实测试或任何验证 owner；维度重叠处判据不同，不得互相顶替。

## 触发时机

| 检查点 | 范围 | 强制 / 条件 |
|---|---|---|
| `中段改码` | 轻量版：仅维度 1、4 | 条件：本轮首次发生代码或规则资产改动后 |
| `收口前` | 完整 6 维 | 强制：本轮存在代码 / 文档 / 规则 / 测试资产改动，或产生交付结论 |
| `失败时` | 并入影响面判定 | 条件：命中 `execution-failure-learning-rules` 时，把失败案例的受影响范围并入维度 2 |

- 谓词判定以 `git status --porcelain` / `git diff --name-only` 的真实输出为准，不得以「我记得只改了 X」代替。
- 负向：Plan Mode 不触发；纯问答、单次只读查看不触发。

## 检查维度（6 项，全部强制）

### 维度 1 需求覆盖对账

- 动作：逐条列出用户原始诉求与冻结的验收条件（`AC-*` / 需求条目），每条回指具体文件 + 符号或文档章节。
- 证据：条目 → 落点的映射；无落点的条目必须显式标注「未覆盖」。
- 驳回：存在未覆盖条目却未标注；或用「已实现相关功能」这类无法回指具体落点的表述。

### 维度 2 影响面 / 消费方对账

- 动作：对每个被修改的**契约面**扫描全部消费方，确认同步或显式声明「无需同步 + 理由」。
- 契约面清单：数据结构形态与字段、函数与方法签名、配置键、文件路径与目录约定、常量与枚举值、对外输出格式、接口契约、注册表与索引。
- 扫描要求：对每个改名或改形态的符号执行全仓引用扫描，命中数必须为 0，或已登记同步项；只改实现内部且不跨越契约面的改动，写 `N/A + 不涉及契约面`。
- 驳回：改了契约面却未做消费方扫描；或扫描命中存在未处置的调用方。
- 实证来源：来源映射 v1→v2 升级后，监督侧读取方仍按 v1 形态解析，静默降级为 P1 且测试全绿（`doc/6-review/2026-09-11_172500_…` 问题三）。

### 维度 3 残留物清扫

- 动作：枚举本轮产生但不应交付的中间物。
- 清单：临时脚本与一次性文件、debug 打印与调试开关、被注释掉的代码、新增后未使用的导入 / 变量 / 函数、孤儿文件、缓存目录、临时目录、本轮启动且未关闭的后台进程。
- 判定：以 `git status --porcelain` 逐项归类；测试与服务进程按 `test-strategy-rules`《测试进程生命周期（强制）》核验已关闭。
- 驳回：临时产物仍留在仓库；本轮启动的服务或进程未关闭且无说明。

### 维度 4 文档与引用一致性

- 动作：本轮新建 / 改名 / 删除的文件逐项核对引用方向，且必须双向核对——「文件出现在哪些文件里」与「路由 / 索引 / 总控文件引用了哪些子文件」。
- 驳回：被删文件仍存在引用；新建文件存在却零引用不可达；改名后索引未同步。
- 实证来源：夹具引用已删文档；`mock-factory-pattern.md` 与 `runtime-mock-pattern.md` 规则存在却零引用不可达（`doc/6-review/2026-09-11_172500_…` 问题二）。

### 维度 5 口径一致性

- 动作：抽取本轮全部涉及的数字、术语、版本号、命名与状态词，跨代码、配置、文档、测试、记忆五类载体比对。
- 驳回：同一事实在不同载体上数值或命名不一致，例如声明数量与实际数量不符、命令数与帮助文案不符、注册表条目与列表长度不符。
- 实证来源：模板注册表 `template_count` 22 与实际 21 不符；来源登记 28 与 22 不符；命令数 54 与 53 不符（`PROJECT_CURRENT.md` 与对应 `6-review` 记录）。

### 维度 6 验证有效性反审

- 动作：逐项反审自己用于证明「完成」的证据，判断是否可能假阳性。
- 反审清单：
  - 夹具 / 守卫是否与生产数据格式脱钩，导致双方各自自洽、测试全绿而缺陷不可见；
  - 断言是否恒真、下限化或只看退出码；
  - 是否把 `limited` / `not_applicable` / 「仅静态验证」当成通过；
  - 是否用 build、lint、静态搜索或读代码顶替真实运行验证（阻断口径归 `code-change-finalization-gate-rules` 与 `functional-validation-rules`，本项只做自查标记，不新建判据）；
  - 覆盖的是否恰是「被改的那一面」而非「容易测的那一面」。
- 驳回：证成本轮结论的判据本身未经验证；或用本轮证据自证本轮验证有效（自我指涉，必须有独立判据）。
- 实证来源：监督侧测试自带旧形态夹具，与生产数据格式脱钩，缺陷对测试套件不可见（`doc/6-review/2026-09-11_172500_…` 问题三）。

## 收口标准

- 通过：6 维逐项给出结论，每项带可核验证据（命令 + 命中数 / 文件路径 / 行号）；发现项按下表完成处置。

| 发现项处置 | 适用条件 |
|---|---|
| 已修复 | 修复动作与本轮主任务同范围、同主题 |
| 登记为显式遗留 | 影响可控且不在本轮边界内；必须写明原因 + 影响 + P2/P3 定级 + 后续入口 |
| 形成 `BLK-*` | 仅阻断级：影响本任务结论正确性且当前边界内无法解决 |

- 驳回：
  - 任一维度未执行，或结论只有「已检查」而无证据；
  - 改了契约面却跳过维度 2；
  - 发现项既不修复也不登记（静默丢弃）；
  - 用本轮的验证证据自证本轮验证有效；
  - 用本环节替代 `6-review`、真实测试或任一验证 owner。

## 防退化约束（强制）

1. **输入必须是磁盘事实**：变更集取自 `git status --porcelain` / `git diff --name-only` 等真实命令；消费方与引用扫描取自真实引用扫描。不接受记忆、声明或计划文本作为输入。
2. **发现项必须落盘**：残留清单写入本轮 `6-review` 记录或对应测试主文档的证据小节，落点按 `artifact-storage-rules/references/path-map.yaml`；不得只在回复中口述。
3. **二次发现即机制失效**：同一残留在本仓库第二次出现时，判定为机制失效，须回流 `execution-failure-learning-rules` 沉淀，而不是就地再修一遍。

## 结果归档

- 6 维结论与残留清单作为本轮 `6-review` 记录的证据小节落盘；`6-review` 自身仍只产出 `STYLE`，本环节不新增平行文档。
- 发现项涉及代码 / 测试改动归位时，回流 `code-change-finalization-gate-rules`；涉及文档落盘时回流 `artifact-delivery-gate-rules`；涉及需求未覆盖时回流需求域 owner。
