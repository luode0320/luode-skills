# 修复后复盘（Post-mortem）

> 归属 owner：`bug-validation-rules`。本文件吸收自 `mattpocock/skills` 的 `diagnose`（v1.0.0，2026-08-22 吸收）。负责在 Bug 修复验证通过后做一次轻量复盘，把「这次怎么没被拦住」沉淀为可执行改进，而不是停在"修好了"。

## 触发时机

修复验证已通过、Bug 具备关闭条件之后，关闭前做一次复盘。

## 复盘问题：什么能阻止这个 Bug？

修复完成后问一个问题：**如果重来一次，什么措施能在 Bug 进入线上之前拦住它？**

从三个方向找答案：

1. **测试接缝**：是否存在正确接缝能让回归测试在 Bug 产生时就失败？没有正确接缝本身就是架构发现（见 `test-regression-rules/references/correct-seam.md`）。
2. **调用方纠缠 / 隐藏耦合**：Bug 是否源于调用方过多、状态共享或隐藏耦合，导致单点测试锁不住？
3. **可验证性**：Bug 产生路径是否可测、可观测？不可测的路径下次还会漏。

## 架构建议在修复后提出

- 架构层面的改进建议**在修复完成后再提出**——修复后拥有的信息比开始时多，建议更准确。
- 不在修复过程中顺手重构（避免修复与重构混杂、风险不可控）；作为独立后续动作记录。
- 若答案是"需要架构调整"，将建议写入 Bug 主文档的后续动作 / 技术债区，标记责任方与完成判据。

## 归档要求

- 复盘结论（问题 + 三个方向的答案 + 是否触发架构建议）写入当前 Bug 主文档。
- 复盘发现的架构问题若值得跟踪，记录为独立后续项，不占用 Bug 关闭结论。
