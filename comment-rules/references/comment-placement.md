# 注释放置原则

- 注释应放在读者最需要停下来理解的地方，而不是机械堆在函数开头。
- 优先关注复杂分支入口、兼容逻辑、风险点和非直观约束。
- 字段定义处必须写字段含义（如"名称"、"类型"、"用户ID"等简短含义描述）；当字段名语义不足以表达意图时，在初始化、字段映射或字段使用位置补字段含义注释；字段名已语义自明时，不添加冗余重复注释。**禁止在字段位置添加改动说明类注释**（如"两个简称取括号外的纯简称"、"因xxx改为xxx"），字段含义注释描述"字段是什么"，改动说明记录在 `doc/` 文档中。
- **例外：字段含义已由同一行的结构化元数据承载时，不再写行尾注释重复一遍。** 典型载体是 ORM 的 `comment:` tag（GORM `gorm:"...;comment:网络类型"`、JPA `@Column(comment=)`）、schema 的 `description`、IDL 的字段说明。判据是语义重复即删，不要求逐字相同（`comment:网络类型` + `// 网络类型` 是重复，`comment:网络类型` + `// 网络类型标识` 也是重复）。
- 上一条的反向同样成立：**结构化元数据缺字段说明、只有行尾注释时，优先把说明补进元数据，再删掉行尾注释**。因为 ORM 的 `comment:` 会落进数据库列注释（DDL 的一部分，DBA、SQL 客户端、其他语言的调用方都能看到），行尾 `//` 只有读这个文件的人能看到，是弱载体。
- 结构化元数据放不下的信息仍写行尾注释，但只写元数据没说的部分，不重抄：单位与量纲（`// 单位：毫秒`）、枚举取值含义（`// 1=删除 0=正常`）、业务约束、与其他字段的关系、历史兼容与废弃说明。**不写"为什么这么设计"**——设计原因属于过程信息。
- 块注释用于说明整体意图；贴近代码的短注释用于说明局部边界、风险和字段含义。
- **一组连续同构语句已形成统一形态（统一的行尾短注释风格，或字段语义由 `comment:` tag 等结构化元数据承载、整组无行尾注释的裸行）时，禁止在其中某一行上方插入多行块注释。** 典型场景是注册列表、初始化列表、路由表、枚举常量、结构体字段这类逐行平行的代码：多行块注释会打断整组的对齐节奏，让读者误以为该行是特殊分支，同一处出现两种注释形态即判定风格不一致。正确做法是保持与同组一致的行尾短注释并按列对齐；确有必须记录的背景、上线顺序、耦合约束或风险权衡时，写进**模块文档或提交说明**，不在代码里留任何痕迹——同构语句组内既不插块注释，也不加"一行结论 + 文档锚点"的折中式注释；函数头只承载目的、`[参数]`、`[返回]` 与 `最近修改时间`。结构体字段组的裸行形态（语义已进 `comment:` tag、整组无行尾注释）同样受此约束：在字段上方挂多行机制/决策块注释即违规，字段含义一律走 tag，过程信息写模块文档或提交说明（写码前规避正反例见反例库 `STYLE-CASE-GO-006`）。
- 函数/方法体、闭包体和连续控制流代码块超过 5 行非空代码/注释行时，步骤注释必须进入对应代码块内部，并贴近步骤或控制流入口；只在函数头、块外或开头集中写总览不算满足。
- 每个超过 5 行的代码块独立判断；嵌套块超过阈值时，不能只借用外层编号，必要时使用 `1.1`、`1.2` 等层级编号。
- 当判断结果已经进入"改动位点必须补齐哪些注释、方法体步骤编号是否完整、函数头元信息是否缺失"时，应转交 `comment-rules` 补齐闸门分区。
- 旧注释若已与实现脱节，应优先清理或更新，不能让新注释叠在旧误导信息上。
