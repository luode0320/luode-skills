# 注释颗粒度

- 能靠好命名解决的，不靠注释重复解释。
- 注释优先说清这段代码"是做什么的"、边界在哪里，不解释"为什么这样、不这样会怎样"，也不逐行复述代码动作。
- 简单字段赋值、函数调用替换、变量重命名等语义自明的代码修改，默认不加改动说明注释；字段名含义不明显时可加简短含义注释（如"名称"、"类型"），禁止加改动方式或修改原因说明。
- 一条注释只解决一个理解问题，避免把多层背景、流程和术语塞进同一段大注释。
- **单条说明性注释默认占一行**（函数头元信息块与编号步骤注释不适用本条）。超出一行即判定为过程注释，**直接删除**，不做"压成一行"的缩短保留。
- **同构语句组内默认零注释**：注册列表、初始化列表、路由表、枚举常量、结构体字段等逐行平行的结构，禁止在其中插入多行块注释——它既打断整组的对齐节奏，又会让读者误以为被注释的那一行是特殊分支。确需记录上线顺序或耦合约束时，写进 `doc/` 或提交说明，不在代码里留任何形式的痕迹。
- **配置文件注释同等适用硬约束**：YAML/TOML/JSON 等配置文件的配置项上方注释同样严格遵守“只写目的，不写过程”。一个配置项注释只回答“它控制什么、范围是什么”，不回答“为什么加这个开关、曾经发生过什么事故、打开后内部如何分步校验、关掉后与老版本的差异”。事故编号（如“某日事故修复要件”）、内部流转机制（“先写待确认、10分钟复核后升级”）与开关关停对比一律删除，只保留单行核心作用说明。
- 注释写**当前状态的结论**，不写**得到该结论的过程**。代码注释只有一类合格形态：**目的注释**——一行说明这段代码"是做什么的"（`// 创建并注册交易所moonpay`）。以下内容一律不进代码注释，**不设例外**，直接删除：
  - 方案对比与选型理由（"为什么不用 A 而用 B""A 会导致…所以选了 B"）。
  - 实测数据、采样记录、性能数字（"实测 3 秒超时""采样 8 次有 2 次…"）。
  - 历史演进叙述（"原来是…后来改成…""既有实现是…本接口改为…"）。
  - 自辩式说明（"这样做是安全的因为…""判据为什么有区分力"）。
  - 因果与后果推演（"只注册不排除会…""顺序反了扣减就失效"）。即使"不写下来后人就会改错"的顾虑成立，也不用注释兜底——这类约束由工程手段保证（两处同批上线、封装成单一入口、加测试）或写进 `doc/` 与提交说明。
  - 反事实句式：`只…不…则…`、`只…不…会让…`、`如果不…就会…`、`否则会…`、`一旦…就…`、`之所以…是因为…`。
- **不设"压成一行 + 文档锚点"的折中形态**：过程信息不进代码就是**删掉**，不存在"缩短后保留"的中间态；把 4 行压成 1 行仍然是过程注释。
- **小改动不记录改动历史**：修改 Bug、调整需求、小逻辑调整、删除代码等任何改动，其说明写在 `doc/` 对应文档，不写入代码注释。特别禁止以下模式出现在注释中：
  - `// 修复了xxx问题`（改为在 Bug 主文档中记录修复方案）
  - `// 因xxx需求改为xxx`（改为在需求文档中记录变更）
  - `// 删除了旧的xxx逻辑`（改为在实施文档中记录删除范围）
  - `// 这里原来是xxx，现在改为xxx`（这是历史叙述，不是当前状态）
  这些是改动历史，应该写在提交信息或 `doc/` 文档中。
- 函数头注释的正常规模是 `1~3` 行说明 + `[参数]`/`[返回]`/`最近修改时间`。超出时先自问：多出来的是"读代码的人必须知道的结论"，还是"我推导时的思考过程"；属于后者一律删。
- 判断一段注释是否该留，用**换人视角**：一个不了解这次改动背景的同事读它，是更快看懂代码在做什么，还是被迫先理解一段与当前代码无关的往事。
- 超过 5 行的代码块至少要有一条块内顶层步骤注释；多个步骤按 `1.`、`2.`、`3.` 拆开说明意图，不要求每一行都写注释。
- 步骤注释应说清该段逻辑的意图与边界，不逐行翻译代码；代码块长度门槛约束的是“块内落点”，不是把注释堆成逐行复述。
- 若某段逻辑复杂到需要成片注释才能看懂，应先评估是否该回到命名或结构调整。
- **复杂逻辑归位专门功能文档**：若业务涉及多步骤状态机流转、多方依赖、复杂探测/升级机制、速率防线或异常防护兜底，绝不能试图用代码或配置中的多行注释把机制解释清楚，而**必须在 `doc/` 下建立专门的功能或业务链路文档记录**（如 `doc/1-架构/<序号>-业务链路-<业务名称>.md` 或 `doc/2-需求/` 规格文档）。代码与配置注释只说明"当前做什么/控什么"，复杂机制的设计全景、状态流转与时序交互一律归位于专门文档。
- 若读者已经能从上下文自然推断，不额外补“显而易见”的重复注释。
