# 配置持久化写入安全与配置故障定位

## Skill 作用与适用场景

- 配置类故障的共同点是：**代码没动、服务没升级，但配置「数据」被写坏了**，表现为服务起不来、关键路由 404、端口异常、功能集体失效，极易被误判为「某次发版/某个组件把系统搞坏了」。
- 本 skill 提供三件可迁移的能力：
  1. **格式契约意识**——先搞清楚「配置存储里到底该存什么形态」，再动手写；
  2. **症状 → 根因**的映射与判据（用可复制的命令取证，而不是猜）；
  3. **写入源追溯手法**——先定位「谁写的」，再修，否则修完会被再次写坏。
- 本 skill 是通用层：具体项目的路径、容器名、端口、拓扑写在各自的项目级 skill 里。

## 核心风险：配置的「二次序列化」损坏

最高频、最隐蔽的损坏模式：

> 读出配置（字符串）→ 用 JSON 序列化/反序列化处理一层（如 `json.dumps` / `JSON.stringify` / 模板渲染）→ 写回存储。

后果：**换行被转义为字面 `\n`（两字符），整篇配置塌缩成单行**（引号、制表符同理）。

- 对 YAML 尤其致命：整篇塌缩成一行后，若首字符是 `#`，整行被判为注释 → **解析结果为空配置** → 关键项（端口、密钥、开关）全部丢失。
- 常见来源：跨语言/跨进程传递时把配置当「JSON 字符串字段」处理、拼接 SQL/模板时未做原始写入、把配置经日志/消息队列中转后回写。

**铁律：写入前必须明确该存储的格式契约；不确定时，先读出一份「当前正常内容」作为对照基准，写完用哈希逐字节比对。**

## 症状识别（三条判据同时成立即可定性）

```bash
# 1) 关键监听端口是否漂移（应为显式配置值；异常时是随机端口或根本没监听）
ss -lntp | grep -E ':<EXPECTED_PORT>|<SERVICE_PROC_NAME>'

# 2) 关键路由是否 404（401/403 = 路由在、需鉴权 = 正常；404 = 路由未注册 = 配置为空）
for p in /health /<management_path>; do
  printf '%s -> ' "$p"; curl -s -o /dev/null -w '%{http_code}\n' "http://127.0.0.1:<PORT>$p"
done

# 3) 配置内容是否塌缩成单行（正常真实换行数 ≈ 行数；故障时 = 1）
#    以 MySQL 为例：
SELECT char_length(content),
       (char_length(content)-char_length(replace(content,char(10),''))) AS lf,
       md5(content)
FROM <db>.<config_table> WHERE id='<row_id>';
```

- 「端口漂移 + 路由 404」同时出现，几乎可以断定是**配置解析为空**，而不是网络/反代故障。
- 用 `md5` 把「存储中的内容」与「运行进程实际读到的文件」对比：若一致，说明进程是**原样**读取该存储，存储里就必须是最终形态（见下方「写入与恢复」）。

## 写入源定位手法（可迁移）

生产故障时**先定位写入源，再修**：

1. **容器/系统事件日志**，锁定故障时段谁在操作：
   ```bash
   docker events --since <ISO_T1> --until <ISO_T2> | head -40
   ```
   关注外部会话的 `exec`（读配置、直连数据库）等痕迹。
2. **按时间窗找被改文件**：
   ```bash
   find <candidate_dirs> -newermt '<T1>' ! -newermt '<T2>' -type f 2>/dev/null | grep -v '\.git/'
   ```
3. **指纹比对定案**：候选文件与目标文件 `md5sum` 相同，即为写入源证据。
4. **时间线交叉验证**：应用日志中的字段变化记录、存储的 `updated_at`、文件 mtime 三者应指向同一时刻。

**误判排除清单**：
- 不是「最近一次发版」——发版走正常接口，发版后关键接口通常仍正常；
- 不是「前端/静态资源升级」——那只是让报错文案指向新版本号；
- 不是「反代配置被改」——反代通常没动，是后端端口漂移后才报 502。

## 安全写入与恢复

**原则：先备份 → 再修复 → 每步回读校验 → 失败即回滚。**

```bash
# Step 1 备份（文件 + 存储，两个回滚点）
cp -a <config_file> <config_file>.broken.$(date +%Y%m%d_%H%M)
# 存储侧：CREATE TABLE <table>_bak_<ts> AS SELECT * FROM <table>;

# Step 2 用「无转义歧义」的方式写入
#   - 首选：走应用提供的配置写入 API（它自带正确序列化）
#   - 直写数据库时：hex 编码写入，彻底规避 shell/SQL 多层转义
#     UPDATE <table> SET content = CONVERT(UNHEX('<hex>') USING utf8mb4) WHERE id='<row_id>';

# Step 3 立即回读校验（长度 / 真实换行数 / md5 与预期一致），不一致就回滚，不要继续

# Step 4 重启服务，确认启动日志中关键项恢复（端口、路由注册）
#   注意：加载大量插件/依赖时启动可能需数十秒，勿误判为启动失败

# Step 5 双端验收：本地直连 + 对外入口，关键接口应为 200 或 401（非 404）
```

**回滚**：从备份表/备份文件恢复内容 → 重启服务。

**注意**：用 Python 等脚本做反转义时，注意脚本自身的转义层级（heredoc / shell / 语言字符串三层转义极易互相吃掉）。稳妥做法是用字符构造（如 `chr(92)+'n'` 表示字面反斜杠+n），或用 base64/hex 传输脚本与数据。

## 红线

1. **禁止**对生产配置做「读出 → 二次序列化 → 写回」；写操作一律走应用提供的配置写入 API。
2. 必须直写存储时：**hex 编码 + 写后 md5 回读校验**，缺一不可。
3. **关键项显式固定**（端口、密钥、开关），避免解析异常时静默回退到默认/随机值，让下游 502 掩盖真实故障。
4. **禁止多会话/多脚本并行改同一份生产配置**；改前确认没有其他写入方。
5. **凭据纪律**：`docker events`、进程列表、连接串等输出常带明文凭据，严禁回显到日志、报告、回复或提交信息。
6. 生产写操作（改库、重启服务）属**需确认级**：先声明目标、说明影响、取得确认，再执行。

## 权责边界与不负责事项

- 只负责「配置持久化写入安全」与「配置类故障定位/恢复」，不负责具体业务代码缺陷、发版流程、需求实现。
- 不含具体项目的路径、容器名、端口、拓扑——那部分由对应项目级 skill 承接。
- 不在未备份、未取得用户对生产写操作确认的情况下执行写入或重启。

## 执行通过 / 驳回标准

- 通过：定性有「端口 + 路由 + 内容格式」三重证据；写入源有「事件日志 + 时间窗文件 + md5 指纹」证据；恢复有回滚点且每步回读校验；验收覆盖本地与对外双端。
- 通过：写入采用无转义歧义方式（API 或 hex），并做了哈希回读。
- 驳回：未定位写入源就修复；未备份即写；用裸字符串替换做转义修复；仅凭外网 502 就断言「反代/某组件把系统搞坏了」；把凭据明文写入任何输出。
