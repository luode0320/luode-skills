# 发散范围、外扩判定与噪音上限

> 归属 owner：`verify-brainstorm-rules`。用途：让"发散"既放得开，又不失控。

## 1. 发散起点

发散**必须从一个确定的起点出发**，起点由三者共同定义：

| 要素 | 说明 |
|---|---|
| 改动点 | 本轮 diff 涉及的文件与符号（含配置、SQL、接口定义） |
| 来源对象 | 本轮对应的需求标识或 Bug 标识 |
| 版本基线 | 对比基线（分支 / commit），改动范围以此为准 |

起点无法确定时（无 diff、基线不清、来源对象缺失）→ 暂停并确认，不进入发散。

## 2. 允许外扩一层（用户已确认口径）

发散范围 = **改动点自身** ∪ **沿调用关系与数据流外扩一层**。

外扩的两种合法路径：

- **调用关系**：直接调用方（谁调用了改动点）、直接被调方（改动点调用了谁）。
- **数据流**：与改动点共享同一数据结构、同一表、同一接口契约、同一配置项的模块。

外扩**只走一层**。第二层及以外默认不扫；确有强证据表明影响会传导到第二层时，允许作为 `外扩·超一层` 单条登记，并注明传导理由。

### 正例（应当外扩）

- 改动了一个函数签名 → 扫它的所有直接调用点，确认新参数在各调用点都有正确取值。
- 修改了一个数据库字段的写入逻辑 → 扫读取该字段的模块，确认读侧对新值域仍成立。
- 调整了一个接口的响应结构 → 扫该接口的直接消费方（前端请求封装、下游服务调用）。

### 反例（不应外扩）

- "顺手看看同目录其他文件有没有类似问题" → 属于全项目巡检，超出本 skill。
- "这个模块和改动都在同一个业务域，一并扫了吧" → 业务域相邻不等于调用或数据相关。
- "既然改了支付，把整个支付链路全扫一遍" → 超出外扩一层，除非能给出逐跳传导证据。

## 3. 噪音上限与截断规则

- **单轮上限 15 条**。达到上限后停止新增，进入收敛。
- 超出上限时的保留顺序：`P0` → `P1` → 高置信 `P2`（能给出触发路径）→ 其余合并为"待观察"附注（只写维度与位置，不展开）。
- **去重优先于截断**：同一根因引发多条现象时先合并为一条，合并后仍超限才截断。
- **降级不删除**：因证据不足被降到 P2 的发现仍然保留在清单中并标注"未证实"，不得直接丢弃。

## 4. 停止条件

以下任一条件满足即收手并进入落盘：

- 13 个维度全部走完且外扩一层已完成；
- 达到 15 条噪音上限并完成优先级截断；
- 继续发散需要新增代码外的运行环境或数据（转人工验证，写清所需条件）；
- 发现 P0 级问题（资损、数据损坏、安全漏洞、崩溃风险）——立即提示用户，随后继续完成剩余维度的快速走查。

## 5. 边界判定速查

| 现象 | 判定 |
|---|---|
| 改动点的直接调用方有 3 处 | 全部纳入外扩 |
| 改动点所属包的兄弟文件 | 不纳入（同包 ≠ 相关） |
| 改动点写入的表被另外 2 个模块读取 | 纳入外扩（数据流） |
| 改动点被某个定时任务间接调用 | 单条登记为 `外扩·超一层`，注明传导路径 |
| 整个仓库的同类写法 | 不纳入（属体系级问题，转 `skill-audit-rules` 或专项重构） |
