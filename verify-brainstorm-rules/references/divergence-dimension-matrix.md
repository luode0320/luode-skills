# 发散维度矩阵（13 维追问清单）

> 归属 owner：`verify-brainstorm-rules`。用途：把"发散"变成可复现的扫描动作，避免随机联想漏项。

## 使用规则

- 13 个维度**逐个走完**，每个维度都要留下结论：`有问题（N 条）` 或 `无问题 + 依据`。
- 追问清单是**联想触发器**，不是勾选框：清单问题全部答"否"但仍想到别的，照样记录。
- 允许在矩阵之外追加发现，追加项标注 `矩阵外`。
- 同一根因命中多维度时，记在**最主要的那个维度**，其余维度写"见 X 维度 #编号"，不重复计数。

## 1. 安全

追问：
- 新增或变更的输入是否经过校验 / 白名单？是否可能拼进 SQL、命令、模板、路径、URL？
- 涉及资源 ID 的读写是否校验了归属（越权 / IDOR）？
- 密钥、token、凭证、个人敏感数据是否出现在日志、报错、响应体或埋点中？
- 权限判断是否落在服务端，而非仅前端隐藏入口？
- 新增依赖是否可信、是否锁定版本？

典型信号：字符串拼接查询、`fmt.Sprintf` 拼 SQL / 命令、`eval` / `exec`、用户输入直连 URL、日志打印完整请求体。

## 2. 性能

追问：
- 是否引入 N+1 查询，或在循环内发起 IO / 远程请求？
- 是否存在无索引查询、无分页的全量读取？
- 循环内是否重复计算或重复序列化？
- 数据量放大后内存是否可控（一次性加载全集 vs 流式）？
- 是否有阻塞主线程 / 事件循环的同步 IO？
- 缓存是否会击穿、雪崩，或缺失过期时间？

典型信号：`for` 内 `await` / `query`、`SELECT *` 无 `WHERE`、循环内 `json.Marshal`、一次性 `ReadAll`。

## 3. 逻辑正确性

追问：
- 分支是否穷尽？`switch` 是否有 `default`？
- 状态机是否允许非法跃迁？重复调用是否幂等？
- 布尔条件是否写反？边界比较是否用错（`<` 与 `<=`）？
- 计算口径是否与需求一致（含 / 不含、税前 / 税后、含 / 不含手续费）？
- 提前返回或异常路径是否跳过了必须执行的清理动作？

典型信号：缺失 `default`、取反条件、`&&` 与 `||` 混用无括号、多个 `return` 各自处理清理。

## 4. 边界与空值

追问：
- 空值、0、负数、超大值、整型极值输入会怎样？
- 空数组、空字符串、`nil` / `null` 是否会被解引用？
- 数组越界、切片边界、分页 offset 超范围？
- 请求缺字段、多字段、类型不符时如何处理？
- 首次运行（无历史数据）与"查不到数据"两条路径是否都能走通？

典型信号：直接取 `arr[0]`、用 `len - 1` 不判空、未判空即取属性、默认列表非空。

## 5. 并发与竞态

追问：
- 共享状态是否加锁或使用原子操作？
- 是否存在 check-then-act 的时序窗口（TOCTOU）？
- 多请求 / 多实例同时操作同一资源（余额、库存、nonce、序号）会怎样？
- 锁顺序是否一致，是否有死锁风险？
- 重放场景是否有幂等键兜底？

典型信号：全局 map 无锁读写、先查后改、计数器非原子、无唯一约束的并发插入。

## 6. 异常与错误处理

追问：
- 是否吞掉异常（捕获后静默返回）？
- 错误是否向上传递并保留原始上下文（而不是被替换成笼统文案）？
- HTTP、数据库、缓存调用是否设置了超时？
- 重试是否有次数上限与退避？重试对象是否幂等？
- 失败路径是否释放资源？
- 是否存在可用的降级路径？

典型信号：空 `catch`、`_ = err`、无超时的客户端、无上限重试、`defer` 缺失。

## 7. 数据精度与类型

追问：
- 金额、数量是否使用浮点数参与计算？
- 单位换算是否一致（元 / 分、小数位、链上 decimals）？
- 时间是否以 UTC 存储、本地化展示？跨天与夏令时边界如何处理？
- 是否存在字符串与数字的隐式转换、大整数精度丢失？
- 编码、超长截断、序列化往返是否保持值不变？

典型信号：`float64` 存金额、`time.Now()` 未指定时区、忽略 `strconv` 的错误、JSON 数字精度丢失。

## 8. 资源与生命周期

追问：
- 连接、文件、句柄是否确保关闭（含异常路径）？
- 是否存在泄漏：goroutine、订阅、定时器、临时文件、锁文件？
- 大对象是否长期驻留内存？
- 进程退出或任务结束是否清理了遗留状态（端口、PID、临时目录）？

典型信号：未 `Close` 的响应体、未 `Cancel` 的 context、无退出条件的 goroutine、残留临时文件。

## 9. 兼容性

追问：
- 接口契约是否向后兼容（新增字段可空、删除字段是否破坏调用方）？
- 前后端字段名、类型、枚举取值是否一致？
- 旧数据在新逻辑下能否正确解析（是否需要默认值或迁移）？
- 升级与回滚是否双向兼容？
- 依赖的第三方 API 是否存在版本行为差异？

典型信号：重命名字段、删除字段、新增枚举值未处理默认分支、直接读取历史数据而无默认值。

## 10. 可观测性

追问：
- 关键路径是否有日志，且不包含敏感信息？
- 失败时是否有足够上下文定位（trace id、入参摘要、关键状态）？
- 新增的失败路径是否有指标或告警覆盖？
- 日志级别是否合适，是否会污染生产日志？

典型信号：关键分支无日志、错误日志缺少标识、日志中打印完整敏感数据、生产环境 DEBUG 全开。

## 11. 配置与依赖

追问：
- 新增配置项是否有默认值？缺失时的行为是否安全？
- 配置是否区分环境（local / test / prod），是否存在跨环境误用？
- 依赖版本是否锁定？是否有已知漏洞或停维护风险？
- 同一常量或配置是否在多处重复定义，存在漂移风险？

典型信号：硬编码值、缺配置直接崩溃、依赖未锁版本、同一阈值多处写死。

## 12. 业务与用户视角

追问：
- 高风险操作（删除、支付、转账、发布）是否有二次确认或防重复提交？
- 涉及资金、资产、额度的路径是否可能造成资损，是否有拦截？
- 权限边界是否符合业务预期（谁能做、谁不能做）？
- 关键操作是否可审计（谁在何时做了什么）？
- 报错后用户是否陷入死胡同（无法继续操作）？

典型信号：一键不可逆操作、无防抖的重复提交、无审计记录、报错后无恢复入口。

## 13. 代码格式与风格

> **判据归属声明**：本维度的判据权威归 `code-style-consistency-rules`（含 `code-generation-style-rules` 产出的本轮代码风格契约与 `PROJECT_STYLE.md` 约定）。本 skill 在本维度只做**偏离发现**——指出"这里与项目既有写法不一致"，不重新定义风格规则、不发起全仓统一格式化，也不替代其 `6-review` 的 `STYLE: PASS / FIX_REQUIRED` 判定。

追问：
- 新增代码的命名（变量、函数、常量、文件）是否与同目录既有写法一致？
- 缩进、换行、行尾符、引号、导入顺序、空行组织是否跟随项目既有格式化口径？
- 是否引入了项目未使用的格式风格（tab 与空格混用、与 `gofmt` / prettier 等既有格式化结果不一致）？
- 注释风格是否符合项目约定（默认无注释、必要处只写目的、不留改动历史）？
- 新文件、新目录的落点是否符合项目结构与归位约定（含测试资产归位）？
- **diff 中是否混入了与本轮无关的格式化改动**——无关行的缩进重排、引号批量替换、空白调整、导入重排？
- 既有文件的既有风格是否被无意改变（局部风格跳变、个人偏好写法侵入同一模块）？
- 是否复制了外部模板式的"优雅写法"，与当前项目现状割裂？

典型信号：仅有格式变化的 diff 行、格式化检查报出未格式化文件、同一文件内出现两种缩进风格、import 分组顺序被重排、注释里出现"修复了什么 / 改了什么"这类改动历史、新增文件落在与项目结构不符的位置。

严重度约定：

- 风格类发现**默认 P2（建议）**，且必须写明"判据归 `code-style-consistency-rules`"。
- 只有当它**直接导致构建、CI 或工具链失败**（如 `gofmt -l` 报错、行尾符导致脚本执行失败）时才升为 **P1**。
- 不因风格问题直接判 P0；风格也不构成"功能不可用"结论。

边界提醒：本维度不做全仓风格巡检、不主动清理历史格式债——那超出"本轮改动及其外扩一层"的发散边界。
