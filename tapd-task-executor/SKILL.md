# TAPD 任务执行

自动领取并完成当前用户的 TAPD 任务/缺陷：找活 → 分析 → 分流 → 执行/兜底。

## 触发与依赖

- 触发：用户提出三大核心意图之一（分析任务、完善任务、批量扫描清任务），或表达主动领取 TAPD 工作的意图（见 frontmatter description），无需 tapd.cn 链接。
- 依赖（复用，不重复实现）：
  - `tapd-env-bootstrap`：环境预检（TAPD_TOKEN / TAPD_API_ENDPOINT / TAPD_WORKSPACE_IDS）
  - `tapd-cli` / `tapd-openapi`：拉取任务与 bug、更新状态
  - `tapd-addcomment`：执行结果评论回写

## 三大核心操作意图与路由规范（强制铁律）

用户提出 TAPD 相关意图时，必须精准识别并路由到以下三类工作流之一，严禁越界或混淆行为边界：

### 1. 单任务分析意图（"看一下这个任务 / 看看任务"）

- **触发词**：`看一下这个任务`、`看看任务`、`分析这个任务`、`看下需求`、`看一下bug` 等；
- **核心定位**：**只做深度分析评估，不直接动手改代码**；
- **执行闭环**：
  1. 定位目标条目并拉取详情；
  2. 自动进行代码库只读侦察（查找涉及的文件、数据模型、API 入口、现有逻辑）；
  3. 核查清楚度（目标、范围、输入输出、验收标准）与可实现性（代码可达、依赖齐备、可验证）；
  4. **在 TAPD 对应条目下发布标准五要素【分析结论评论】**（分析结论、是否可以开始执行、是否缺失材料、是否缺少前置条件、是否需要人工补充缺失信息）；
  5. 评论发布后即完成该意图闭环，向用户清晰汇报分析要点，停留在分析就绪状态，等待用户进一步决策（如指示开工或指示完善）。

### 2. 任务描述完善意图（"完善这个任务 / 完善任务"）

- **触发词**：`完善这个任务`、`完善任务`、`补充这个任务`、`补充需求说明`、`完善需求内容` 等；
- **核心定位**：说明当前条目的**描述不清楚、信息缺失或背景模糊**，需要补充完善该需求/任务的具体内容；
- **执行闭环**：
  1. 读取原条目的已有描述、标题、评论及关联背景；
  2. 结合代码库现有实现、关联接口契约、历史提交或业务模型进行针对性调研；
  3. **补充完善需求内容**：
     - 通过 API（`update_story` / `update_task`）将整理出的结构化规格（业务背景、需求目标、涉及模块、详细参数/字段说明、数据/交互流程、验收条件 AC）更新补充到条目的描述（`description`）中；
     - 同时或备选：在 TAPD 下发表【需求内容完善与详细规格说明】评论，结构化列出补充内容，并 `@` 需求创建人确认；
  4. 若存在关键业务规则分歧或必须产品/测试明确的边界，在末尾明确列出待人工确认项。

### 3. 批量扫描与清任务流水线（"扫描tapd [xx], 清任务 / 开始做tapd[xx]任务 / 开始做tapd任务"）

- **触发词**：`扫描tapd [xx], 清任务`、`开始做tapd[xx]任务`、`开始做tapd任务`、`清任务`、`做tapd任务`、`找tapd的任务做` 等；
- **核心定位**：**全自动批量清理任务流水线**。扫描指定项目或当前迭代下的所有需求、任务与 Bug，严格按优先级从高到低逐个分析，**只要可做，立刻开工，走完完整实现与收口流程，闭环一个再推进下一个**；
- **执行闭环（严格串行推进状态机，严禁并发抢跑）**：
  1. **确定扫描范围**：
     - 若指定具体项目 `[xx]`（如“扫描tapd 兑换, 清任务”），则严格限定扫描该项目；
     - 若未指定具体项目，则扫描当前迭代/当前 workspace 的所有需求（Story，按叶子需求保护）、任务（Task）与缺陷（Bug）；
  2. **全局优先级严格排序**（统一权威排序）：
     - 缺陷优先于任务/需求；
     - 缺陷按严重度：致命/严重 > 一般 > 提示/建议；
     - 需求/任务按优先级：紧急/高 > 中 > 低；
     - 同档按创建时间早者优先；
  3. **逐个条目闭环流水线**：
     - **环节 A（分析与评论）**：对排在当前最高优先级的条目展开分析，在 TAPD 发布五要素分析评论，判断是否具备开工条件；
     - **环节 B（若可做，立刻开工走全套流程）**：
       ① **追加开工评论**：发布 `agent开始代码实现` 评论（@ 用户本人）；
       ② **代码实现**：在当前工作区定位文件，执行需求/Bug 代码修改；
       ③ **本地自测验证**：运行单元测试、接口测试或自测脚本；
       ④ **【铁律】代码完成即本地提交**：自测通过后严禁暂存更改在工作区，立即自动提交本地 Git（`git commit`，严禁自动 push 远端），**提交信息必须使用 `agent-` 前缀指明**（格式：`<type>: [agent-<模块>] <描述> [TAPD#<ID>]`，例如 `fix: [agent-兑换] 修复SWAPKIT报价解析异常 [TAPD#1162459836001003690]`），并获取本地 commit hash；
       ⑤ **实现完成总结评论**：发布分节总结评论（成果、方案、验证结果、本地 commit hash）；
       ⑥ **收口流转与测试指派**：将状态流转至“待版本验证”，处理人变更为测试人员（杨莹、李红、韩忠宝），并登记工时；
       ⑦ **闭环当前任务，自动进入清单中的下一个条目**；
     - **环节 C（若不可做，记录缺口并推进下一条）**：
       - 若分析结论为“待完善 / 缺少材料 / 缺少前置条件”，在分析评论中明确列出缺口，同时 `@` 触发用户本人和创建人；
       - 该条目跳过实现阶段，归入待完善清单，**立即继续推进清单中的下一个条目**，直到所有可执行任务全部清空。

## 自动化授权边界（强制，`tapd-openapi` 复用同一份，不重复定义）

TAPD 任务的目的是 agent 全自动调度执行，减少人工中间确认；但"全自动"只覆盖可自主判断的动作，不覆盖不可逆动作。两类动作边界如下：

- **默认已授权、不需要在对话里再次确认**：
  - 仓库只读侦察（Grep / Read / Glob / Explore agent 等）定位代码、确认现状、评估可实现性——这是分析阶段的必经动作，粘贴链接或表达委派意图本身就是授权，不需要再问"要不要我去仓库看看"。
  - 按本节以下规则推进分析 → 评论 → 执行 → 收口的既定流程。
  - 进度通知：默认通过 TAPD 评论回写（沿用四阶段模板），**不通过对话做"要不要继续""要不要执行"这类执行范围确认式提问**；对话侧只在阶段完成后给一句简要收口摘要，详细过程留在 TAPD 评论里，用户通过 TAPD 通知感知进度。
  - **`@` 名单分两档**（语法见 `tapd-openapi/references/comments/addcomment.md` 的 `@提及` 一节）：
    - **正常执行过程**（开始执行评论、实现完成总结评论、收口流转说明，以及分析评论判定为"材料齐全、可以开始做"）→ 只 `@` 触发用户本人（`data-userid` 取 `TAPD_USER_NAME`，缺失时取该条目 `current_owner` / `reporter` 的登录名）。
    - **材料不足 / 需求上下文不够**（分析评论五要素中"是否缺失材料""是否缺少前置条件""是否需要人工补充缺失信息"任一项判定为是，含归入"待完善"清单的条目）→ 同时 `@` 触发用户本人**和**该条目的创建人（`creator` 字段），让缺口第一时间回到提出需求的人手里，不要只 @ 自己。
    - **`creator` 取登录名的注意事项**：实体详情里的 `creator` 通常是显示名/昵称，不一定是 `data-userid` 要求的登录账号名；能查到登录名（如 `/users/info`、项目成员列表）就用登录名 @，查不到就在评论正文里用文字点名创建人昵称并说明"未能触发系统通知，请知悉"，不要因为查不到登录名就漏 @ 或用错账号强行 @。
- **仍需暂停等待人决策，不得自主判断**（红线不变，只是确认渠道优先改为 TAPD 评论 + `@`，用户若就在当前对话里，对话确认与评论确认二选一即可，不必两处都问）：
  - 疑似已完成的边界判定（第 5 步）；
  - 验证中发现的顺带缺陷是否修复/记遗留/另开单；
  - 跨项目写入、代码 push 远端等不可逆或越权动作——这类始终禁止，不是"确认后可以做"。

## 执行流程

### 1. 环境预检

按 `tapd-env-bootstrap` 核对 `TAPD_TOKEN` 已注入且非空（只判断有无，禁止回显 Token 明文）。缺失 → 阻断并输出配置指引。`TAPD_WORKSPACE_IDS` 为空 → 提示但不阻断。

### 2. 确定当前用户

- 优先取环境变量 `TAPD_USER_NAME` 或 `CURRENT_USER_NICK`；
- 否则调用 `tapd-cli user info` 取当前登录用户 nick。

### 3. 拉取我的任务 + bug

遍历 `TAPD_WORKSPACE_IDS`（逗号分隔），对每个 workspace_id 执行：

- **优先** `tapd-openapi/scripts/tapd_client_stdlib.py mine`（一条命令同时拉我名下的需求+缺陷，含当前迭代定位、状态过滤、优先级排序、父需求树）：
  ```bash
  python <skills>/tapd-openapi/scripts/tapd_client_stdlib.py mine --workspace-id <id> --iteration current --status active
  # 只看缺陷加 --bugs；只看需求加 --storys；状态 all 不过滤
  ```
  mine 输出为表格（含 19 位 id、状态、优先级、owner、标题、详情链接），直接解析为候选清单。
- **兜底**（mine 不可用或需精确字段时）——**按人筛选的字段两个实体不一样，用错会静默返回全项目数据**：

  ```bash
  tapd-cli bug   list workspaceid=<id> current_owner=<用户> status="<>closed" limit=50
  tapd-cli story list workspaceid=<id> developer=<用户> limit=200
  ```

  story 用 `current_owner` 不报错但过滤失效；`task` 实体通常为空，找活默认查 story + bug。详见 `references/cli-field-pitfalls.md`。

汇总候选清单：id、标题、描述、优先级/严重度、状态、链接（`$TAPD_SITE_URL/tapd_fe/<workspace_id>/<story|bug>/detail/<entity_id>`）。

拉完先抽查几条的 `developer` / `current_owner` 是否真含目标用户名——条数接近项目总量即说明过滤没生效。

**候选清单排序（强制）**：多 workspace 汇总后，按 `references/task-analysis-criteria.md` 第四节「候选清单处理顺序」统一排序，优先级高的排前面；`mine` 命令的单 workspace 内排序只是起点，跨 workspace 汇总后必须重新按同一套标准整体排序一次。该顺序贯穿后续归项目过滤、分析、执行——不是只用于兜底展示，逐条处理时严格按此顺序推进，不按拉取到的原始顺序或创建时间顺序处理。

### 4. 归项目过滤（只筛当前会话项目）

- 目标 = 当前会话工作区项目（如 luode-skills、ellipal_admin）。
- 判定：标题/描述中出现当前项目名、仓库名、模块名特征词，或可解析出明确项目标识 → 归入；否则忽略（不进兜底清单）。
- 无法判定归属 → 忽略并记录原因。
- 跨项目任务一律不写（红线，见下）。

### 4.1 Story / Bug / Task 分类处理工作流（强制）

对过滤出的当前项目条目，按实体类型执行差异化自动化处理（详见 `references/story-bug-task-workflow.md`）：

1. **Story（需求）处理规则**：
   - **识别目标（叶子保护）**：仅处理无子 Story 的叶子节点需求；若 Story 下包含子 Story（父级需求/Feature/Epic），**保持原样不予处理**。
   - **拆解任务触发**：当叶子 Story 处于“规划”或“实现中”，且名下无子 Task 时（**我们的完成，还有其他人未完成的不算**——若当前开发者名下无进行中子 Task 且有待实现范围，才触发拆解），自动分析该需求并拆分为可执行的子 Task。
   - **任务信息规范**：清晰编写每个子 Task 的标题与具体实现方案，将处理人/开发人员明确指派为当前开发者，并填写合理的预估工时（effort，单位小时）。
2. **Bug（缺陷）处理规则**：
   - Bug 由测试人员提交，**严禁修改原始描述**，也**无需创建新任务**。
   - 直接分析问题成因，并在该 Bug 的评论中清晰记录排查结果、解决方案及处理进度。
3. **Task（任务）处理规则**：
   - 现有的独立 Task（或已拆解分配的任务）可直接承接，按规划进入开发实现。

### 5. 描述清楚度 + 可实现性分析与分析评论回写

按 `references/task-analysis-criteria.md` 判定表逐条评估，输出四类：

- **可执行**：描述清楚（目标/范围/输入输出/验收，或复现步骤/预期实际）且可实现（代码可达、依赖可获取、无外部权限依赖、可本地验证）
- **疑似已完成**：查证确认功能已在仓库内落地，只是 TAPD 状态没同步
- **待完善**：仓库内查无痕迹且关键信息缺失 → 记录缺口
- **忽略**：描述基本为空或纯转发

**只有标题的老单必须先回仓库查现状再定性**：描述为空、无评论、创建日期较早的单，很可能早已实现只是没人回来改状态。直接判「待完善」会丢掉一个能立刻关掉的单，直接判「待执行」会重复造轮子。按标题里的名词在仓库搜实现与前端定义，再比对创建日期附近的提交记录。

**【强制自动化约束 1】分析完成自动添加分析评论**：
当会话确认已完成对某个任务、需求或 bug 的分析时，**必须自动在对应条目下添加一条分析评论**，留痕当前评估状态。评论内容必须严格包含以下五项要素（规范见 `references/task-analysis-criteria.md` §五）：
1. **分析结论**：说明清楚度、可实现性及具体判定结论；
2. **是否可以开始执行**：给出确定性结论（可以开始做 / 暂不可执行 / 待人工确认）；
3. **是否缺失材料**：说明是否有原型、文档、字段或设计材料缺失；
4. **是否缺少前置条件**：说明是否有环境、配置、前置接口或权限缺失；
5. **是否需要人工补充缺失信息**：说明是否需要人工或产品/测试补充具体信息。

### 6. 执行 / 兜底

可执行清单非空 → **按第 3 步排定的优先级顺序**逐条闭环，优先级高的先做完整闭环再推进下一条，不并发抢跑、不按创建时间或拉取原始顺序处理：

1. **领取与开始实现**：
   - 任务更新 `status=progressing`；缺陷按工作流置处理中（先读 `workflows/all_transitions` 拿合法下一跳与必填字段，确实读不到映射时才退回「仅评论说明开始处理」，不凭猜测硬改状态）。
   - **【强制自动化约束 2】开始执行追加评论**：当分析结论为可直接执行，且已在第 5 步添加包含“可以开始做”的分析评论、会话已实际开始执行该任务/需求/bug 后，**必须及时追加一条评论**（开头 `@` 触发用户本人），内容明确包含：
     ```text
     agent开始代码实现
     ```
2. **实现与本地 Git 提交**：
   - 按宿主仓库 AGENTS.md 与既有规则闭环（需求接入/实施拆解/编码/真实测试/验证，按需联动 requirement-intake-rules、implementation-planning-rules、bug-root-cause-rules 等）。
   - **【强制自动化约束：代码完成即提交本地】**：Agent 自行完成的代码实现，**严禁暂存在项目的未提交更改中，完成自测验证后必须立即自动提交到本地 Git 仓库（git commit）**。
     - **提交前缀与信息格式（强制）**：必须使用 `[agent-<模块>]` 前缀明确标识为 Agent 自动完成，严格遵循格式：`<type>: [agent-<模块/功能>] <改动说明> [TAPD#<ID>]`（例如 `fix: [agent-兑换] 修复SWAPKIT报价解析异常 [TAPD#1162459836001003690]`、`feat: [agent-Onramper] v2接口适配与用户IP透传支持 [TAPD#1162459836001003250]`），便于团队从 git 历史一眼识别 Agent 提交并关联单据；
     - 提交后获取本地 commit hash。
   - **红线安全边界**：仅自动提交到**本地（commit）**，**绝对禁止自动 push 到远端仓库**。
3. **实现完成评论回写**：
   - **【强制自动化约束 3】代码实现完成后自动添加总结评论**：代码实现完成并提交本地后，**自动添加一条评论说明实现已完成，并总结本次实现的内容**（开头 `@` 触发用户本人）。
   - 评论结构遵循「TAPD 回写规范」的分节骨架（结论、方案、验证方式与结果、验证边界、遗留风险、代码状态），总结本次实现改动的文件、功能逻辑与测试验证结果。
   - **代码状态**一律明确注明：`已提交到本地 Git（commit: <hash>，待推送远端）`。禁止平铺一整段，正文写进文件再读文件传参提交。
4. **收口（流转至“待版本验证”并变更为测试人员）**：
   - **【强制自动化约束 4】流转至“待版本验证”与测试人员指派**：
     实现完成评论发布后，**必须将该条目状态流转至“待版本验证”，并将处理人变更为测试人员**。
     - **目标状态**：流转至「待版本验证」（在具体需求/缺陷工作流中匹配对应状态，如 `待版本验证` 或开发终态 `resolved`，按工作流最短合法路径逐跳流转）。
     - **处理人变更**：将条目的处理人（`current_owner` / `developer`）变更为测试人员。
     - **测试人员名单持久化配置**：测试人员名单通过落盘配置（`config/qa-team.json`）与项目长期记忆（`PROJECT_MEMORY.md`）持久化保存：
       **杨莹、李红、韩忠宝**。
       指派策略与命令细节详见 `references/qa-assignment-rules.md`。
     - **双重核对**：每跳流转和处理人变更后，**必须回读实体核对** `status` 已变为待版本验证且 `current_owner` 已变为测试人员，未生效不得谎报。
5. **登记工时（强制）**：改完终态必须填工时，不填不算收口。先查再写——同一实体同一天同一人只能有一条记录，且**部分项目关单时会自动生成 `timespent=0` 占位记录**（项目级差异，不能假设）：

   ```bash
   tapd-cli timesheet list workspaceid=<id> entity_type=story entity_id=<19位id>
   # 查到 → timesheet update workspaceid=<id> id=<记录id> timespent=<小时> memo=<说明>
   # 没查到 → timesheet add workspaceid=<id> entity_type=story entity_id=<19位id> \
   #            timespent=<小时> owner=<中文名> spentdate=YYYY-MM-DD memo=<说明>
   ```

   单位小时、0.5 为最小粒度，按**实际投入**估不按任务重要性估：只读核查关单 0.5、小改动含测试 1、中等改动含测试闭环 2~3、跨模块或多轮返工 3 以上。`entity_type` 用单数（与评论的复数 `entry-type=stories` 不同）。详见 `references/cli-field-pitfalls.md`。

   **任务（task）要先登记工时才能流转为完成**：没有工时记录时 `status=done` 静默不生效（接口返回成功、回读仍是 progressing），所以 task 的顺序固定为「登记工时 → 改 done → 回读核对」，见 `references/cli-field-pitfalls.md` §九。

6. **交付给用户时必须给可点链接，不能只给裸 id**：格式 `$TAPD_SITE_URL/tapd_fe/<workspace_id>/<story|bug>/detail/<19位id>`。新建的单还要一并说明**所在项目**与**是否属于某个迭代**——多 workspace 场景下用户默认只看主项目，`iteration_id=0` 的单不进迭代看板，只给 id 会导致用户根本找不到（2026-08-28 真实发生过）。所以新建需求 / 任务默认就挂当前迭代，规则见 `references/story-bug-task-workflow.md` §3。

**疑似已完成**清单非空 → 先向用户确认需求字面目标的边界（例如「加到流水」是指展示列，还是要能按它筛选/聚合——边界不同工作量差一个数量级，这是用户的决定）。确认渠道优先发一条 `@` 触发用户本人的 TAPD 评论提问，用户就在当前对话里时也可直接对话确认，不必两处都问；确认后补跑真实验证出报告，再按上述 3~6 走完回写评论、改状态、登记工时与交付链接。**不要凭代码印象直接关单**；工时按补验证的实际投入填，不因「代码早就写好了」而省略。

验证过程中发现顺带缺陷时**停下来问用户**（修 / 记为遗留 / 另开缺陷单，渠道同上），不擅自扩大改动范围。

可执行与疑似已完成清单都为空 → **兜底**：从待完善清单按 `references/task-analysis-criteria.md` 第四节「候选清单处理顺序」排序，列 3 条高优先级任务/bug，逐条注明缺什么信息、由谁完善。

### 7. 改动找不到对应单时

手上已有改动但不确定挂哪个单时，**先证明真的没有**再问用户：拉全量需求与缺陷（`count` 确认总量 → 分页 `limit=200` → 本地关键词过滤，模糊查询语法不可用），两个 workspace 都扫。

确认无对应单后，把「建单 / 不建单」交给用户决定，不擅自建单。判断素材给足：这批改动是什么性质、有没有影响线上行为的策略变更、当前有哪些留痕（commit message、测试报告）。安全策略类变更零留痕的风险要明说。

## TAPD 全生命周期自动化行为与回写规范（强制）

从任务分析到执行收口，必须在 TAPD 上完整落地四个阶段的自动化行为约束，**缺任何一样都不算合规闭环**：

| 阶段 | 自动化行为 | 判定「真的做到了」的依据 |
|---|---|---|
| 1. 分析完成 | **分析评论**（含五要素） | 必须含结论、是否可开始、是否缺材料、是否缺前置条件、是否需人工补充 |
| 2. 开始执行 | **追加评论**「agent开始代码实现」 | 分析可执行且已发“可以开始做”评论、实际开始执行后及时追加 |
| 3. 实现完成 | **实现总结评论**（分节骨架） | 明确说明实现已完成，分节总结实现内容与验证结果 |
| 4. 收口流转 | **流转待版本验证 + 变更处理人为测试** | 状态变更为「待版本验证」，处理人变更为杨莹/李红/韩忠宝，并登记工时 |

### 1. 评论必须分节，禁止平铺一整段

一大段连续文字没人读得下去，关键信息（验证结果、遗留风险、代码是否已提交）会被埋掉。**用小标题分节 + 列表 + 表格**，让人扫一眼就能定位。

按下面的骨架写，没有的节直接省略，不要留空节：

```markdown
## 结论
一句话说清做了什么、当前处于什么状态。

## 根因
缺陷才写。现象 → 定位 → 为什么会这样。
若核查结果与原始描述不符，**在这里显式指出出入**，不要默默按自己的理解改。

## 修复方案 / 实现方案
改了什么、为什么这么改。有被否决的替代方案就写清否决理由。

## 验证方式与结果
用表格，一行一个检查项：

| 检查项 | 期望 | 实测 |
|---|---|---|
| ... | ... | ... |

## 验证边界
**如实写没验什么、为什么不验。** 不写这节会让人默认「全验过了」。

## 遗留风险
没有就写「无」，不要省略这节。

## 代码状态
已提交到本地 Git（commit: <hash>，待推送远端）
```

硬要求：

- **正文写进文件再读文件传参**，绝不在 shell 里内联拼接——Markdown 的 `---` 会被当命令、`|` 会被当管道，内容**静默截断后照常提交成功**（返回 ok，线上是残缺评论）
- 提交后**核对回显正文的字符数与结尾**，与本地一致才算数
- 结论与事实不符时补发更正评论，不留错误留痕（例如先写了「交人工」后又自动流转了）
- 敏感信息脱敏；Token 一律不回显

### 2. 工时：先查后写，更新优先于新增

同一实体 + 同一天 + 同一人**只允许一条记录**，直接 `add` 会撞唯一约束；部分项目关单时还会自动生成 `timespent=0` 占位记录。所以**固定先 list 再决定 update 还是 add**。

**同一天内**二次投入同一个单（例如同日换个会话补验证、返工重跑），走 **update 把工时累加上去**，不要新增第二条，`memo` 把两次做的事合并写清；**跨天**的二次投入才是新增一条（`spentdate` 不同，不冲突）。

按**实际投入**估，不按任务重要性估。分档与字段细节见 `references/cli-field-pitfalls.md`。

### 3. 状态与处理人：读工作流、流转至待版本验证、指派测试人员

不要假设能一步到终态。方法见上方第 6 节第 4 步与 `references/qa-assignment-rules.md`：
- 流转至「待版本验证」；
- 处理人变更为持久化配置的测试人员（杨莹、李红、韩忠宝）；
- 回读校验状态与处理人双生效。

## 红线（强制）

- 只处理能归到当前会话项目的任务/缺陷；其他项目代码只读，不产生任何写入（AGENTS.md 跨项目红线，用户口头授权也不放行）。
- TAPD Token 禁止回显；评论/描述中的敏感信息脱敏。
- **代码实现完成即自动提交本地 Git（严禁自动 push 远端）**：Agent 自行完成的代码实现，严禁暂存在项目的未提交更改中，完成真实测试验证后必须立即自动执行本地 `git commit` 留痕；但**绝对禁止自动 git push 到远端**，向远端推送仍需用户显式授权。
- **四大自动化行为约束强制执行**：
  1. 完成分析必发分析评论（含五要素）；
  2. 可执行并开始执行后必发「agent开始代码实现」评论；
  3. 代码实现完成必发实现完成总结评论（含本地 commit hash 说明）；
  4. 实现完成评论后必流转至「待版本验证」并变更处理人为测试人员（杨莹、李红、韩忠宝）。
- 单条任务实现必须走真实测试与验证，禁止只改代码不验证。
- 评论必须分节，禁止平铺一整段；每跳流转与处理人变更必须回读核验。
