# TAPD 待版本验证流转与测试人员指派规范

## 一、目标与触发时机

- **触发时机**：当任务/需求/bug 的代码实现已完成，且已成功发布「实现完成评论（含实现内容总结）」后，必须立即触发本流程。
- **核心动作**：
  1. 将该条目状态流转至「待版本验证」；
  2. 将该条目的处理人（`current_owner` 等）变更为测试人员。

## 二、测试人员名单与持久化配置

测试人员名单通过落盘配置与项目长期记忆双重持久化保存：

- **落盘配置文件**：`<skills>/tapd-task-executor/config/qa-team.json`
- **项目长期记忆**：`PROJECT_MEMORY.md` 稳定决策区
- **持久化测试人员名单**：
  1. **杨莹**
  2. **李红**
  3. **韩忠宝**

### 指派策略

1. **原指定测试优先**：若需求/缺陷已有原关联测试人员（如提单测试人或历史指派记录在上述 3 人之中），优先指派该测试人员。
2. **默认/轮询指派**：若未指定特定测试人员，按名单顺序（杨莹 -> 李红 -> 韩忠宝）轮询指派，或根据业务模块负责划分指派。
3. **严禁指派非测试角色**：开发完成后禁止将处理人留置为开发人员自身或留空。

## 三、流转至「待版本验证」与指派操作

### 1. 需求（Story）流转与指派

```bash
# 1) 获取当前工作流状态与流转参数
# 2) 更新状态为待版本验证，并变更处理人给测试人员
tapd-cli story update workspaceid=<id> id=<19位id> status="待版本验证" current_owner="<测试人员姓名>" current_user="<当前操作人>"
```

> **注意**：部分 TAPD 需求工作流中“待版本验证”对应的内部状态键名为 `resolved` 或 `status_X`，可先通过工作流接口或需求详情确认实际状态字典，确保状态与中文名称对应。

### 2. 缺陷（Bug）流转与指派

缺陷通常有严格的状态机跳转路径（例如 `in_progress` -> `resolved` / `待版本验证`），不能假设可直接一步跳跃：

```bash
# 1) 拉取工作流合法流转路径与必填字段
python <skills>/tapd-openapi/scripts/tapd_client_stdlib.py \
  get --endpoint workflows/all_transitions -p workspace_id=<id> -p system=bug

# 2) 逐跳流转，目标状态匹配「待版本验证」（或对应 resolved 状态）
# 3) 同步变更处理人为测试人员
tapd-cli bug update workspaceid=<id> id=<19位id> status="resolved" current_owner="<测试人员姓名>"
```

### 3. 双重核对校验（强制）

变更提交后，必须回读该条目，确保：
1. **状态校验**：`status` 字段真实流转至「待版本验证」（或对应的 `resolved`）；
2. **处理人校验**：`current_owner`（或相关负责人字段）真实变更为指定的测试人员姓名（杨莹、李红或韩忠宝）。
3. 若回读发现状态或处理人未改变，判定为流转失败，记录错误并向用户报告，严禁谎报已流转测试。
