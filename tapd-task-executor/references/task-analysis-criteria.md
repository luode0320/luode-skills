# 任务/缺陷可执行性判定标准

## 一、描述清楚度

### 任务（task）判定项

- 目标：一句话说清要交付什么
- 范围：涉及模块/文件/接口明确
- 输入输出：数据来源与产物格式
- 验收：如何判定完成（AC 或可验证行为）

### 缺陷（bug）判定项

- 复现步骤：可照做触发
- 预期 vs 实际：明确两个行为的差异
- 环境信息：版本/平台/数据上下文
- 影响范围：模块/接口/用户

### 分级

- 清楚：4 项全满足且无歧义
- 基本清楚：≥3 项，少量细节可自行查证
- 模糊：<3 项，关键信息缺失

### 只有标题的老单：先查现状，别急着判模糊

描述为空、无评论、创建日期较早的单，**不能直接归入「待完善」**。这类单很可能早就实现了，只是状态没人回来改。判成模糊会白白丢掉一个能立刻关掉的单，判成待执行又会重复造轮子。

正确顺序是**先回代码仓库查现状**：按标题里的名词（页面名、字段名、模块名）在仓库里搜实现与前端列定义，再比对创建日期附近的 git 提交记录。三种结果：

- **已实现**：功能在、状态没同步 → 走「疑似已完成」分流（见第三节）
- **部分实现**：主体在、边角缺 → 按缺口重新界定范围，向用户确认本轮做到哪
- **确实没做**：仓库里查不到任何痕迹 → 才归「待完善」，记录缺什么信息

判据示例：需求「地区需要增加到兑换流水」只有一句标题，仓库里 `client_display.go` 已有国家地区解析、前端已有该列、改动时间恰在需求创建当天——判定为已实现。

## 二、可实现性

- 代码可达：目标代码在当前会话项目内，或可从当前项目只读定位
- 依赖可获取：所需库/服务/凭据在本机或项目内可用
- 无外部权限依赖：不需要生产写权限、人工审批、跨项目写入
- 可验证：存在本地验证路径（测试/构建/日志/接口）

## 三、分流规则

- 可执行 = （清楚 或 基本清楚）+ 可实现 4 项全过
- **疑似已完成** = 查证确认功能已在仓库内落地，只是 TAPD 状态未同步
- 待完善 = 模糊且仓库内查无痕迹，或可实现有 1 项以上不满足
- 可执行但缺测试基线：描述清楚仍可执行，按宿主项目规则补测试

### 疑似已完成的处理

**不要直接改状态关单**，先补验证再关，否则等于凭代码印象宣布完成。顺序：

1. 向用户确认边界——需求字面目标是否等同于已实现的部分（例如「加到流水」是指展示列，还是要能按它筛选/聚合）。边界不同，工作量差一个数量级，这是用户的决定不是你的。
2. 用户确认「已完成」后，跑一轮真实验证补齐证据，出测试报告。
3. 验证通过再回写评论 + 改状态。

验证过程中发现顺带缺陷时，**停下来问用户**（修 / 不修记为遗留 / 另开缺陷单），不擅自扩大改动范围。

## 四、兜底优先级排序

1. 缺陷优先于任务
2. 缺陷按严重度：致命/严重 > 一般 > 轻微
3. 任务按优先级：紧急/高 > 中 > 低
4. 同档按创建时间早者优先

## 五、分析完成自动评论规范（强制）

当会话确认已完成对某个任务、需求或 bug 的分析时，**必须自动在 TAPD 上添加一条分析评论**，留痕当前评估状态。

### 1. 评论必含五大要素

1. **分析结论**：清晰阐明分析结果与判定依据（清楚度分级、可实现性判定、归属分析）；
2. **是否可以开始执行**：给出确定性结论（可以开始做 / 暂不可执行 / 待确认）；
3. **是否缺失材料**：说明是否有原型、设计稿、字段定义、文档或样本等材料缺失；
4. **是否缺少前置条件**：说明是否有环境、依赖服务、前置接口、权限或配置等前置条件缺失；
5. **是否需要人工补充缺失信息**：明确指出是否需要产品/测试/业务人员介入提供输入。

### 2. 标准评论结构模板

```markdown
## 📋 任务分析结论

[简述分析结论，如：经代码库与需求分析，该需求描述清晰，核心涉及 xxx 模块改动，本地代码可达且可验证，判定为可直接执行。]

## 🔍 执行就绪度核查

- **是否可以开始执行**：可以开始做（或：暂不可执行）
- **是否缺失材料**：无缺失（或：缺失 xxx 原型/字段契约）
- **是否缺少前置条件**：具备所有前置条件（或：缺少 xxx 服务部署与数据库表结构）
- **是否需要人工补充缺失信息**：无需人工补充（或：需要人工补充 xxx 具体信息）
```

> **硬约束**：分析评论发布后，若结论判定为「可以开始做/可直接执行」，且会话实际进入代码实现阶段，必须联动触发后续「agent开始代码实现」评论。
