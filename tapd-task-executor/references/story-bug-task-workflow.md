# TAPD 需求、缺陷与任务自动化处理工作流（Story / Bug / Task）

本规范定义系统中对 Story（需求）、Bug（缺陷）和 Task（任务）的分类识别、自动拆解、评论回写与流转约束。

---

## 一、Story（需求）处理规则

### 1. 识别目标：仅处理叶子节点需求

- **叶子节点判定**：通过 API 查询需求层级关系。仅处理无子 Story 的叶子需求（`has_children=false` 或子需求列表为空）。
- **父级需求保护（不处理）**：若 Story 名下包含子 Story（即父级需求 / Feature / Epic），**保持原样不予处理**，严禁在父需求下直接编码或强行流转，确保需求层级树完整。

### 2. 自动拆解任务触发条件

当且仅当满足以下条件时，自动触发子 Task 拆解：

1. **叶子 Story**：无子 Story；
2. **状态符合**：处于“规划”（planning）或“实现中”（in_progress / progressing）；
3. **名下无未完成子 Task**：
   - 若名下完全无子 Task，自动进行拆解；
   - 若名下已有子 Task：**当前开发者（我们）名下的 Task 已完成，但其他人名下还有未完成的，不算我们的未完成**；若当前开发者名下无进行中/未完成的子 Task，且仍有本开发者需承担的开发范围，则按需分析并拆分可执行子 Task；若我们负责的任务已全部完成，则不重复拆解。

### 3. 子 Task 任务信息与创建规范

拆解出的子 Task 必须满足以下要素：

- **标题明确**：采用“动词 + 宾语”清晰表达模块与目标（如：`[前端] 增加兑换流水地区筛选下拉框`、`[后端] 地区查询接口参数校验与缓存支持`）；
- **具体实现方案**：在 Task 描述（description）中详细记录技术方案、改动文件/模块清单、调用链路与自测用例；
- **处理人指派**：将处理人 / 开发人员（`developer` / `current_owner`）明确指派为**当前开发者**（当前登录用户，如“罗德”）；
- **合理预估工时**：根据任务复杂度填写合理的预估工时（`effort` / `estimate`），单位为小时，以 0.5 小时为最小粒度（常见小任务 1~2h，中等任务 2~4h）；
- **显式指定创建人（防占位符）**：必须显式传入 `creator` 为当前登录开发者姓名（如“罗德”），绝对禁止漏传或随便取名，避免被 TAPD 默认写入凭据名 `tapd_my_token`。
- **默认挂当前迭代**：新建的需求和子 Task 一律传 `iteration_id=<当前迭代id>`，不留 `0`（用户 2026-09-29 要求）。`0` 的单不进迭代看板，用户找不到。子 Task 跟随所属需求的迭代；需求本身没有迭代时，按当天日期取当前迭代，查法见 `cli-field-pitfalls.md` §十。只有用户明确指定其他迭代或要求不挂迭代时才例外。

```bash
# 创建子 Task 示例命令（必须带上 creator 与 iteration_id）
tapd-cli task add workspaceid=<id> story_id=<叶子需求ID> \
  name="<任务标题>" description="<实现方案与改动点>" \
  current_owner="<当前开发者>" creator="<当前开发者>" effort=<预估小时> \
  iteration_id=<当前迭代id>
```

## 二、Bug（缺陷）处理规则

### 0. 缺陷创建与代提交规范（若涉及 Agent 协助创建 Bug）

- **创建人显式传入（强制铁律）**：通过 API 创建 Bug 时，**必须显式传入 `reporter` 参数**，取值必须是当前登录员工真实姓名（如“罗德”，可从 `GET /users/info` 动态解析），**绝对禁止随便取名**（如随意填 `admin`、`agent`、`workbuddy`、`bot` 等虚拟名称）。
- **防 `tapd_my_token` 陷阱**：若漏传 `reporter`，TAPD 服务端将强制默认回退为凭据名 `tapd_my_token`，造成团队看板与责任人追溯失真。
- **审计只读不可修改机制**：TAPD 缺陷创建完成后，`reporter` 字段在服务端具备严格只读保护，后续调用 `update_bug` 无法修改。若创建时发生错误，只能关闭作废并重新创建正规单。

### 1. 角色分工与描述保护

- **来源定位**：Bug 通常由测试人员提交，其原始标题、缺陷描述、复现步骤与现场截图是第一手测试证据。
- **保护原则**：**严禁修改测试人员提交的原始描述**，也**无需创建子任务或新任务单**，保持缺陷单原貌。

### 2. 直接分析与评论回写闭环

在当前 Bug 上直接开展分析与排查，并通过 TAPD 评论清晰记录全流程：

1. **排查结果与成因分析**：
   - 直接分析问题成因并在评论中清晰记录排查结果（报错堆栈、问题定位到具体代码行、触发边界条件）。
   - 必须遵循「分析完成自动添加分析评论」五要素：分析结论、是否可以开始执行、是否缺失材料、是否缺少前置条件、是否需要人工补充缺失信息。
2. **开始执行追加**：
   - 确认可修复并实际开始编码时，追加评论：`agent开始代码实现`。
3. **修复方案与实现总结（含本地 Git 提交）**：
   - 代码修复完成并通过本地测试验证后，**不要暂存在项目的更改中，必须立即自动提交到本地 Git 仓库（git commit，严禁自动 push 远端）**。
   - **提交信息格式（强制）**：必须使用 `[agent-<模块>]` 前缀明确标识为 Agent 自动完成，严格遵循：`<type>: [agent-<模块/功能>] <改动说明> [TAPD#<ID>]`（例如 `fix: [agent-兑换] 修复SWAPKIT报价解析异常 [TAPD#1162459836001003690]`）。
   - 随后添加总结评论：说明实现已完成，附上本地 commit hash，总结本次改动代码、修复方案与本地验证结果。
4. **流转至待版本验证与测试指派**：
   - 修复完成后，将 Bug 状态按工作流流转至「待版本验证」（或对应 resolved 状态），并将处理人指派回测试人员（持久化名单：杨莹、李红、韩忠宝），等待测试验证。

## 三、Task（任务）处理规则

### 1. 独立 Task 直接承接

- 现有的独立 Task（未挂载在 Story 下或已拆解完成分配给当前开发者的 Task），无需二次拆解。
- 确认符合当前项目范围且可执行后，**直接承接**，按既定规划进入开发实现。

### 2. 执行与回写联动

- 领取后将 Task 状态置为进行中（`progressing`）；
- 实际开始代码实现追加评论：`agent开始代码实现`；
- 代码实现与测试验证完成后，**不要暂存在项目的更改中，立即提交到本地 Git 仓库（git commit，严禁自动 push）**，提交信息按 `<type>: [agent-<模块/功能>] <改动说明> [TAPD#<ID>]` 格式填写；
- 随后回写完成总结评论（含本地 commit hash），登记工时，并流转至开发完成/待版本验证。

## 四、三大核心操作意图与执行状态机规范（强制）

为杜绝人机协作时的意图模糊，系统确立三种典型操作意图与自动化执行标准：

### 1. 单任务分析意图（"看一下这个任务 / 看看任务"）

- **用户语义**：`看一下这个任务`、`看看任务`、`分析这个任务`、`看下需求` 等。
- **业务定位**：深度技术与可行性评估，**禁止直接开工修改代码**。
- **操作步骤**：
  1. 定位目标条目并拉取详情；
  2. 结合代码库执行只读侦察（梳理现有调用链、受影响文件与接口）；
  3. 核查清楚度（目标、范围、输入输出、验收标准）与可实现性（代码可达、依赖可用、可验证性）；
  4. 在 TAPD 上发表【标准五要素分析结论评论】（分析结论、是否可以开始执行、是否缺失材料、是否缺少前置条件、是否需要人工补充缺失信息）；
  5. 向用户输出结论摘要，停在分析就绪状态，等待明确开工或完善指令。

### 2. 任务描述完善意图（"完善这个任务 / 完善任务"）

- **用户语义**：`完善这个任务`、`完善任务`、`补充这个任务`、`补充需求内容` 等。
- **业务定位**：明确判定当前条目**描述不清楚、关键信息缺失或背景模糊**，需要补齐需求规格。
- **操作步骤**：
  1. 结合已有标题、上下文与代码仓库实现（查看表结构、API 定义、现有业务逻辑）进行补全；
  2. 整理出结构化的需求规格：
     - **业务背景与目标**：一句话说清为什么要做、达到什么业务目的；
     - **改动范围与涉及模块**：列出涉及的前后端模块与文件位点；
     - **详细输入与输出契约**：字段名、数据类型、必填性与校验规则；
     - **业务规则与异常分支**：各种边界条件的处理方式；
     - **验收标准（AC）**：可测试的具体行为与结果。
  3. **落地回写**：
     - 调用 API 更新条目的 `description`（追加结构化规格）；
     - 或在评论中发表【需求规格补充说明】，并 `@` 需求创建人核对；
  4. 若存在无法由代码反推的纯业务决策，以清单形式列出待产品人员确认项。

### 3. 批量扫描与清任务流水线（"扫描tapd [xx], 清任务 / 开始做tapd[xx]任务 / 开始做tapd任务"）

- **用户语义**：`扫描tapd [xx], 清任务`、`开始做tapd[xx]任务`、`开始做tapd任务`、`清任务`、`做tapd任务`、`找tapd的任务做` 等。
- **业务定位**：**全自动任务清理流水线**。扫描目标范围条目，严格按优先级排序逐个分析推进，**只要可做立刻开工完成闭环，完成一个再做下一个**。
- **状态机执行步骤**：
  1. **确定扫描范围**：
     - 指令带 `[xx]` 时，严格限定扫描指定项目；
     - 未指明时，默认扫描当前迭代/当前 workspace 绑定的未完成需求（叶子）、任务与缺陷；
  2. **统一优先级严格排序**：
     - 缺陷优先于任务/需求；
     - 缺陷按严重度排序（致命/严重 > 一般 > 提示/建议）；
     - 需求/任务按优先级排序（紧急/高 > 中 > 低）；
     - 同级按创建时间早者优先；
  3. **串行推进流水线（逐条闭环，严禁并发）**：
     - **第一步（分析与研判）**：拉取当前第一优先级的条目，发表五要素分析评论；
     - **第二步（分流判定）**：
       - **分支 A（可做 → 立即开工）**：
         1. 追加评论：`agent开始代码实现`（@ 用户本人）；
         2. 定位代码并完成编码修改；
         3. 运行本地测试自测验证；
         4. **【强制铁律】代码完成即本地提交**：立即执行 `git commit`（严禁自动 push 远端），提交前缀必须带 `[agent-<模块>]`（格式：`<type>: [agent-<模块/功能>] <改动说明> [TAPD#<ID>]`），获取本地 commit hash；
         5. 发表分节总结评论（成果、方案、验证结果、本地 commit hash）；
         6. 流转状态至「待版本验证」，处理人指派为测试人员（杨莹、李红、韩忠宝），登记工时；
         7. 本条闭环完成，自动取出队列中的下一条，循环执行第一步；
       - **分支 B（不可做 → 记录缺口并跳过）**：
         1. 在分析评论中明确指出材料/前置缺口，@ 创建人与用户；
         2. 标记该条为待完善，暂不阻塞流水线，**立刻继续推进队列中的下一条**。
  4. **收尾汇报**：所有条目扫描完毕后，汇总输出本次清任务的战果报告（已完成并流转测试的条目清单、待完善条目清单）。
