# `6-review` 风格回归契约

## 入口与结果

- 入口：真实测试全部完成后执行一次，活动记录写入 `doc/6-review/`。
- 结果：只能是 `STYLE: PASS` 或 `STYLE: FIX_REQUIRED`。
- 前置：测试失败时不得用 `6-review` 代替测试；应先修复或记录测试阻断。
- 历史：`doc/6-审查/`、`doc/7-验收/` 只读保留，历史文档不迁移、不改写。

## 检查清单

检查步骤不手写：先按变更路径运行 `scripts/static_owner_router.py`（或调用 `route_review_pipeline()`），由**已加载的来源映射**推导出本轮适用的有序步骤，再逐步检查并逐项写证据。步骤的名称、覆盖维度、检查项、判定与证据格式见 `references/style-review-pipeline.md`。

下列四类只是步骤的粗粒度视图，用于快速自检覆盖是否齐全：

| 类别 | 必查内容 | 不负责的判断 |
| --- | --- | --- |
| 格式 | UTF-8、换行、尾随空白、项目格式化规则 | 业务结果是否正确 |
| 写法 | 命名、局部习惯、函数签名、日志和注释风格 | 需求是否覆盖完整 |
| 位置 | 目录落点、依赖方向、测试资产归位、公共工具复用 | 发布或上线是否放行 |
| 可读性 | 结构、临时文件、路径漂移、局部风格跳变 | 功能测试是否充分 |

- 来源映射校验失败（退出码非 `0`）时，`6-review` 必须先修复映射，不得跳过步骤直接给结论。加载期断言含一条覆盖率断言：Owner 目录内未登记的规则 Markdown 会直接让加载失败，此时应补登记（或按 `NON_RULE_FILE_NAMES` / `NON_RULE_DIR_NAMES` 明确豁免），而不是绕过流水线。
- 无变更导致步骤为空时，记录中不输出"检查步骤"段落，也不得伪造步骤。

## 记录模板

```markdown
# 6-review：<主题>

STYLE: PASS

## 检查范围
- 测试证据：`TEST-*`
- 改动文件：`<path>`
- 规则来源：`PROJECT_STYLE.md`、本 Skill references

## 风格证据
- `STYLE-*`：<检查项与结果>

## 边界声明
- 业务正确性：N/A + 原因：由真实测试负责 + 证据：`TEST-*`
- 需求覆盖与发布放行：N/A + 原因：不属于 6-review 职责 + 证据：实施计划 `AC-*`
```

## 负向边界

- 缺少真实测试证据时，`6-review` 记录为 `FIX_REQUIRED`，不得伪造测试通过。
- 发现业务逻辑错误但没有风格问题时，记录 `STYLE: PASS`，并把逻辑问题留给真实测试或 Bug 流程。
- 发现错误目录、错误编码、尾随空白、风格跳变或未按项目规则写法时，记录 `STYLE: FIX_REQUIRED`。
- 不进行全仓格式化、无关重构、需求重新拆分或历史文档迁移。
