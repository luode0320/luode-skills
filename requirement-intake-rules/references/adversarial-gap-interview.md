# 对抗式缺口追问（吸收自 grill-me）

> 归属 owner：`requirement-intake-rules`。本文件是 `gap-routing` 的追问姿态补充，不产生独立自动触发入口。吸收来源：`softspark-ai-toolkit-grill-me`（LobeHub，v1.0.1）。吸收原则：只吸收本地缺失的"每个问题附推荐答案、魔鬼代言人反方批评、决策树依赖优先"，本地已有的"一次一个问题、先查证再提问、不满足模糊答案、直到共识"保留本地且不与本文件冲突。

## 适用场景

- 进入 `gap-routing` 后需要向用户提问确认缺口时，按本文件组织提问。
- 缺口收敛到"多个合理方向、关键假设、方案选择"需要用户拍板时，按本文件给出推荐答案并做反方批评。
- 不适用：能通过 `initial-discovery` 主动查证的内容，仍然先查证，不进入本文件。

## 核心姿态：目的不是通过，是找出漏洞

- 追问的目的是把模糊地带、依赖关系和边缘案例全部暴露出来，不是让用户尽快确认。
- 对每一个即将写入需求的假设、默认值或方向选择，默认先问"如果它是错的，后果是什么"。
- 不满足于"应该没问题""一般是这样"这类含糊回答；用户回答后，把其中的隐含假设显式复述一次再确认。

## 规则一：一次只问一个真实问题，但每个问题附推荐答案

- 保持本地 `gap-routing` 的"一次只推进一个真实关键缺口"，不要堆砌问题列表。
- 每个问题必须同时给出 agent 的**推荐答案（建议选项）**，供用户参考确认；格式：`问题 -> 推荐答案（标注"待确认建议"） -> 为什么推荐 -> 如果不选它需要承担的取舍`。
- 推荐答案只作为"供确认的建议"，不得写成已确认结论，不得在没有用户授权时按推荐答案继续推进；与 `gap-routing` 的"禁止 Agent 猜测、P2 默认值必须记录授权人"保持兼容。
- 用户明确否决推荐答案时，追问一句"你否决的核心理由是什么"，把理由作为新信息回填，而不是立即换一个推荐答案。

## 规则二：魔鬼代言人（Devil's Advocate）反方批评

- 对每个**主要决策**（方向选择、方案选型、默认值、边界定义、关键假设），在确认前执行一次反方批评：列出这个决策最可能失败的方式、被忽略的约束、反向证据。
- 反方批评只针对决策本身，不针对用户；输出控制在 3 条以内，按严重度排序，避免无限抬杠。
- 用户坚持原决策时，不反复纠缠；记录"用户已知晓反方风险仍坚持"，把反方风险写入需求文档的风险/未决区，由后续实施周期消化。
- 反方批评发现的真实缺口（如"这个默认值可能依赖某个未确认的接口"）必须登记为新 `GAP-*`，走 gap-routing 闭环，不能只在对话里提一句。

## 规则三：决策树依赖优先，先核心后细节

- 追问顺序按"决策树依赖"组织：先解决**核心依赖决策**（目标、边界、输入输出、成功标准），再下钻到**细节分支**（字段、格式、兼容、性能）。
- 分支决策依赖未解决时，禁止跳到下游细节；发现下游细节问题但上游未定，先把上游问题提出，而不是先问下游。
- 每个缺口登记时标注它依赖哪个已确认决策；依赖未确认的缺口保持 `blocked` 状态。

## 规则四：能从工件查证的，绝不提问

- 问题若可通过读取需求文档、代码、schema、历史记录、URL、GitHub、官方资料回答，一律走 `initial-discovery` 查证，不占用用户提问名额。
- 用户回答中提到可查证的线索（如"这个逻辑跟 XX 模块一样"），先查证再追问，不基于用户口头描述继续猜。

## 与现有规则的边界

- 一次一个问题、禁止猜测、先查证再提问、直到共识后回填：以 `gap-routing.md` 与 `requirement-domain-shared-contract.md` 为准，本文件不改变这些语义。
- 缺口 ID、P0/P1/P2、回填与删除：以 `gap-routing.md` 的"极致完整性缺口闸门"为准，本文件只补充提问姿态与推荐答案格式。
- 暂停条件：以 `pause-triggers.md` 为准；本文件不新增暂停条件，只要求暂停前先把未决问题与推荐答案留档。

## 输出格式

- 进入追问时，先输出一句"本轮只确认一个缺口"，再给出问题 + 推荐答案 + 反方批评（如适用）。
- 每个问题占用一次独立回复，不要一次性输出多个问题；用户回答后先复述确认，再进入下一个缺口。

## 设计阶段双角色自检（吸收自 java-story-develop）

> 本节补充 `implementation-planning-rules` 设计阶段的方案自检姿态，不改变本文件既有对抗式追问语义。吸收来源：`java-story-develop__skillhub`（FULL 模式 DESIGNING 阶段角色互搏机制）。

- 方案设计产出后、落盘前，执行一次双角色互搏：先以**开发工程师**视角通读需求与设计，列出不明确点、潜在风险、TODO 清单；再切换**产品/需求提出者**视角逐条回答，给出明确指导、边界说明与取舍理由。
- 双角色互搏只产出「需确认点列表 + 推荐答案」，不把互搏结论写成已确认事实；用户未确认的确认点保持 `blocked`，不得进入实施。
- 与规则二一致：每个确认点可附一次反方批评（最可能失败的方式、被忽略的约束、反向证据），输出控制在 3 条以内。
- 设计阶段互搏发现的真实缺口（默认值依赖未确认接口、边界遗漏、兼容问题）必须登记为新 `GAP-*` 或写入设计文档风险区，不能只在对话里提一句；与 `gap-routing.md` 的缺口闭环保持一致。
- 用户否决某条互搏结论时，记录否决理由，更新设计文档与记忆，不反复纠缠。
