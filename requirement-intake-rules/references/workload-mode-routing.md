# 需求规模分档路由（吸收自 java-story-develop）

> 归属 owner：`requirement-intake-rules`。本文件是需求接入时的规模分档路由，不产生独立自动触发入口。吸收来源：`java-story-develop__skillhub`（LobeHub 安装包）。吸收原则：只吸收「按改动规模选流程深度」的显式分档与升级/降级判定，本地已有的「一次一个问题、禁止猜测、极致完整性、AC-* 可测条件、P2 授权」保留本地且不与本文件冲突。

## 适用场景

- 需求接入时，先按改动规模与影响面判定本轮流程深度，避免「小改动走重型流程」或「大需求走轻量流程」两种失衡。
- 分档只决定流程深度与文档粒度，不改变本地红线的任何语义（禁止猜测、AC-* 冻结完成条件、极致完整性、授权边界）。

## 三档判定（改动规模 → 流程深度）

| 档位 | 判定条件（满足其一） | 流程深度 | 文档粒度 |
|------|---------------------|----------|----------|
| **SIMPLE（轻量）** | 1~2 个文件、无新增表、接口签名微调、简单 bug fix | 需求确认 → 修改 → 验证，实时沟通 | 单文档记录「需求 → 改了什么 → 验证结果」 |
| **QUICK（标准）** | 3~5 个文件、有业务逻辑变更、无库表变化 | 分析现状 → 设计方案 → 编码实现 | 关键点记录 + 完成条件确认，跳过重型需求主文档 |
| **FULL（完整）** | 跨模块、数据库加表/改表、对接外部系统、流程重组、多角色多子系统 | 澄清 → 分析 → 设计 → 实现 → 反馈闭环 | 正式需求主文档 + 分析 + 设计 + 反馈，按 `artifact-storage-rules` 落盘 |

> 用户明确说「走完整流程 / 按规范来」时按 FULL 执行；信息不足无法判断时，先完成环境探测与范围侦察再定档，禁止过早定档。

## 定档时机与校准

1. 定档在需求接入侦察完成后、进入实施规划前执行一次。
2. 侦察后发现实际涉及面比用户描述更广时，**主动建议升级档位**，不沿用用户口头描述的低档。
3. 编码中发现范围扩大（新增模块、新增表、新增外部依赖）时，按 `requirement-change-rules` 走变更闭环，必要时升级档位；档位调整须用户确认。
4. 档位只影响流程深度，不影响 `AC-*`、追踪矩阵、权限/兼容/数据/异常边界的冻结。

## 与本地规则的边界

- SIMPLE 档的「单文档」不等于放弃验证：仍须有完成条件、验证记录与改动文件清单；`artifact-delivery-gate-rules` 的落盘核验不因档位而豁免。
- QUICK 档的「跳过重型需求主文档」由 INIT 阶段的口头确认 + 关键点记录替代；需求一旦进入 `implementation-planning-rules`，`AC-*` 仍按既有规则冻结。
- FULL 档的正式文档结构与编号以 `artifact-storage-rules` 与 `requirement-structure-template.md` 为准，不复制外部 skill 的 `story/` 目录形态。
- 状态机（INIT → ANALYZING → DESIGNING → IMPLEMENTING → DELIVERED）本地由 `task-plan-rehydration-rules` 的投影机制承载，本文件不引入 `context.json` 专属文件形态。
