# 多技能合并策略（merge-strategies）

> 归属 owner：`skill-absorption-rules`。本文件承载「内部更新通道」下的**多技能合并**执行细则——当用户要求"把这两个 skill 合并 / 技能整合 / 超级技能 / 技能组合"时，按本文件三策略裁决并落盘。
> 来源：吸收自 mimo-skill-merger v1.3.0（ClawHub `qqyougitcom/mimo-skill-merger`，MIT-0），2026-08-23 吸收，17 条原子规则裁决（合并 8 / 保留本地 6 / 拒绝 3）。
> **本地红线适配**：合并产物一律落现有 skill 的 `references/` 或正文补丁，**不新建同类 skill 目录**（与 `absorption-decision-matrix.md`「合并落点选择」一致）；不引入外部整套工作流与目录结构。

## 一、合并策略三选一（进入合并场景先决策）

对任意两个（或多个）待合并技能，先判断功能关系，再选策略：

| 策略 | 适用条件 | 做法 | 本地落点 |
|---|---|---|---|
| **吸收型**（A 吸收 B） | B 的功能是 A 的子集 / 弱化版 | B 的独特能力并入 A 作为子模块，A 保持主体 | 新能力落 A 的 `references/`，A 的 SKILL.md 补引用与触发 |
| **融合型**（A+B→C） | A、B 功能交叉但各有优势，无明确主从 | 取各自核心流程统一为一条新流程 | 融合产物落现有主 skill（按职责归属选承接者）的 `references/`，不新建 skill 目录 |
| **编排型**（A‖B → 编排层） | A、B 功能独立但高频配合使用 | 新增编排层（场景路由说明），各自 SKILL.md 主体不变 | 编排层落任一方的 `references/` 或独立 reference，双方 SKILL.md 互加引用 |

决策顺序：先问"是否存在明确主从（子集）"→ 是则吸收型；再问"合并后是否有一个清晰统一的新流程"→ 是则融合型；否则编排型兜底。

## 二、冲突处理

1. **触发条件冲突**：合并关键词 + 细化排除场景。合并后的触发词必须**同时列出「触发词」和「排除词」**，不能只保留一边——只留触发词会误触发打架，只留排除词会漏触发。
2. **流程重叠**：保留更详细的版本，简化另一个（语义零丢失前提，与吸收即整理原则一致）。
3. **输出格式**：统一为更完整的模板（变更对比见下节）。

## 三、变更对比模板（合并产物强制输出）

合并/整合类调整完成后，必须输出变更对比，逐条确认无功能丢失：

```
合并报告
源技能：{A} + {B}
合并策略：{吸收/融合/编排}
承接落点：{skill 路径}

变更：
+ {新增能力}
- {消除重复}
~ {调整内容}
```

「- 消除重复」与「~ 调整内容」必须逐条可回指（哪个 skill、哪个段落），不能只写数量。

## 四、反合理化表（防合并半途而废）

| # | 常见借口 | 反借口规则 |
|---|---------|-----------|
| 1 | "这两个技能差异太大，合并不了" | 差异大用**编排型**（保持独立 + 编排层），不是不合并的理由；至少输出编排方案。 |
| 2 | "合并后怕丢功能，算了" | 必须输出变更对比表（+新增 / -消除 / ~调整），逐条确认无功能丢失后再合并。 |
| 3 | "触发词合并后会冲突" | 冲突就细化排除场景；合并后的触发词必须同时列出「触发词」和「排除词」。 |

## 五、边界（与同域 skill 的分工）

- `skill-audit-rules`：多技能职责重叠的**只读审计**，输出重叠清单与边界结论；本文件负责审计后的**实际合并落盘**（写）。
- `skill-split-preserve-rules`：体积超标 / 职责过重的**拆分**；本文件是**合并**，方向相反，两者不冲突。
- 合并落盘后必须跑同域冗余扫描（SKILL.md 第 5 步四项检查：重复段落 / 门控层叠 / 散落产物 / 引用链），防止合并本身引入交叉重复。
