# 吸收三态裁决矩阵

> 归属 owner：`skill-absorption-rules`。本文件是外部 skill 精华逐条裁决的唯一标准；不产生独立自动触发入口。

## 裁决三态

对每条外部精华（原子规则，一句话可独立判定）必须归入且仅归入一种裁决：

| 裁决 | 判定条件 | 动作 |
| --- | --- | --- |
| `保留本地` | 本地已有同义或更强规则（覆盖更全、更具体、已有真实场景验证） | 不吸收；在裁决表记录"本地更强"及对应本地文件 |
| `合并` | 本地缺失该规则，或本地版本明显更弱（只有原则没有细节） | 吸收为 reference 或补进现有 SKILL.md 正文，同步 References 引用 |
| `拒绝` | 与本地红线/工作流冲突、为吸收而吸收、一次性低频、外部专属形态（整套工作流、目录结构、`.codebuddy/specs/` 等） | 不吸收；在裁决表记录拒绝理由 |

## 判定顺序

1. 先判断是否冲突（拒绝候选）：违反本地红线（如"测试不可跳过""禁止猜测写成结论""不新增同类 skill 目录"）、或属于外部整套工作流的一部分、或外部专属目录形态 -> `拒绝`。
2. 再判断本地是否已有更强（保留候选）：本地 SKILL.md / references 里能找到同义或更具体的规则，且经过真实场景使用 -> `保留本地`。
3. 都不满足时才是 `合并`。

## 形态分离原则（2026-08-19 补，源自 thread-title-rules 修复型吸收）

外部产物的「机制形态」与「规则精华」必须分开裁决，不能因形态不匹配而整包拒绝，也不能把外部机制照搬进本地：

- 机制形态（hook 事件点、专属 CLI 安装命令、宿主专属配置文件、宿主专属存储/表结构）——与目标宿主不匹配时判 `拒绝`，理由注明"宿主无关 / 机制形态不迁移"。
- 规则精华（触发时机、生成/降级策略、幂等与原子保护语义、边界与失败路由）——即使来自被拒绝形态的外部产物，仍按三态正常裁决，通常判 `合并`。
- 典型拆分示例：外部 hook 的"message:received 无标题才生成、失败降级截断首条消息、不覆盖已有标题、写入前原子重查"是精华（合并）；其"openclaw hooks enable 安装、写 OpenClaw sessions.json label"是机制（拒绝，替换为目标宿主的原生存储适配）。

## 修复型吸收（宿主失效场景，2026-08-19 补）

当用户反馈"本地 skill 不生效"且根因是宿主绑定（skill 依赖外部宿主专属工具/配置，如 Codex 专属 MCP）时：

1. 先侦察目标宿主真实暴露的能力：环境变量中的会话/任务 ID 元数据、原生持久化存储（DB/JSON 表结构）、官方文档能力清单；禁止臆测。
2. 依据真实能力新增适配路径（如宿主原生表写入脚本 + 契约文档），保留原宿主路径不动，两条路径互斥分流。
3. 会话 ID 等身份元数据只取可信来源（宿主注入的环境变量/元数据），禁止列表猜测；涉及凭据的环境变量不得回显全文。
4. 适配脚本遵守与本地既有脚本一致的设计风格（幂等、写前备份、原子保护、回读校验、稳定 JSON 输出、--check 只读）。
5. **宿主存储字段独占性验证（2026-08-19 实测教训）**：向宿主原生存储写入前，必须区分「主进程/服务独占字段」与「用户数据字段」——先做一次最小写入实验，等待一个宿主回写周期（实测约 2 分钟）再回读，若被回写覆盖则该字段独占、禁止作为写入目标，改选用户数据字段（如 WorkBuddy `sessions.title` 为主进程自动摘要槽、被回写覆盖，`custom_title` 用户改名槽、写入存活且 UI 显示）。仅凭"字段存在且有语义"不足以证明可写；最终以 UI 实测显示为准。

## 整理优先于增补（2026-08-19 补，防体系臃肿）

外部精华裁决后，凡是判 `合并` 的条目，落盘前必须同步检查目标 skill 的存量，把「整理去重」作为落盘的必做前置：

- 目标 SKILL.md / references 中存在与新增内容同义的重复段落 → 合并（语义零丢失）。
- 存在冗余引用、失效链接、已过时规则 → 删除或更新。
- 每条 `合并` 裁决至少对应一次存量整理动作；纯新增、零整理的落盘视为不合格，除非给出正当理由（如目标文件本就精简、无重复可清）。
- 裁决表「整理建议」列未填写的 `合并` 条目，回退到判定阶段补查，不直接落盘。

## 同域去重扫描（2026-08-20 补，防交叉冗余）

目标文件内的整理只解决"本地内部重复"，解决不了"吸收内容投放后与**同域兄弟 skill** 交叉重复"的问题——8/19 吸收 api-test-automation-pro 时，`test-case-generation.md` 压缩了 -568 字节、棘轮评分 92.1 通过，但 4 级样本矩阵在 test-strategy 与 functional-validation 逐字重复残留、双根落点在三个 skill 各写一遍，直到 8/20 复杂度检查才暴露。因此合并条目落盘后、评分收口前，必须对本次调整触达的**同域 skill 集合**执行四项扫描（**内部更新通道同样适用**，主动调整自有 skill 引入的交叉冗余同理对待）：

1. **重复段落**：新增/修改的关键规则（样本矩阵、门控表、落点规则、判定标准）是否与同域其他 skill 逐字或高度重复 → 收敛为「单一权威 + 引用」，下游只留域专属补充（如功能验证的"异常路径对照"属于域专属，可保留）。
2. **门控/概念层叠**：新增规则是否与同域既有规则形成多套术语、嵌套门控或重复清单 → 合并为一张清单（如 apifox 的"必须询问"与"三重门控"合并为门控与确认清单）。
3. **散落产物**：吸收过程是否在仓库根目录产生空模板、未引用占位文件、与命名约定不符的孤立文件 → 删除或归位（如 skills 根目录散落的 `release-test-plan.yaml` 219B 空模板）。
4. **引用链**：收敛后引用可达、无断链、UTF-8 无乱码。

扫描结论必须写入收口说明与裁决表：扫描了哪几个同域 skill、发现 X 处、清理 Y 处、PASS/FAIL。发现可清理冗余（三项中任一）未在同一吸收闭环内清理，该次吸收视为未完成，不得收口。

## 合并落点选择

- 优先落点：目标域 skill 的 `references/` 新增一个 reference（最小侵入、可追溯），或补进现有 reference 的相关小节。
- 次选落点：目标 SKILL.md 正文（仅当规则是高频核心动作、且正文已有同类条目）。
- 禁止落点：新建同类 skill 目录（除非职责边界稳定且现有 skill 明显承接不住，需与本 skill 的 `references/evolution-decision-matrix.md` 决策矩阵一致）。

## 反例（不得判为合并）

- 外部有"破冰寒暄"类交互（如问用户最喜欢的电影）而本地是工程化文档体系 -> `拒绝`，理由：风格不兼容、为吸收而吸收。
- 外部规则本地已有"一次一个问题"且更严格 -> `保留本地`，理由：本地更强。
- 外部"阶段问答链 / 子代理链 / 整套流程编排" -> `拒绝`，理由：本地四域 skill 已覆盖对应职责，不复制整套流程。

## 输出格式

裁决表必须可回指：

| 外部来源 | 外部精华 | 本地现状 | 裁决 | 落点 / 理由 |
| --- | --- | --- | --- | --- |

- 每条裁决都要有"本地现状"列的具体出处（文件/规则名），不能写"感觉已有"。
- `拒绝` 与 `保留本地` 都必须给理由，不能只写结论。
