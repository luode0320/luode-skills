# 安全机制

## 目标

本文件定义 long-run-loop-rules 的安全机制，防止无限循环、API 账单爆炸、死循环和资源耗尽。

## 硬性限制

### 1. max_iterations（最大迭代次数）

- 必须设置，默认 50
- 达到上限后标记 Goal blocked，输出汇总报告
- 防止因完成标记未匹配、prompt 歧义或 bug 导致无限循环

### 2. max_runtime（最大运行时间）

- 默认 480 分钟（8 小时）
- 从第一次 worker 创建开始计时
- 达到上限后标记 Goal blocked
- 适用于过夜跑场景，防止意外超时

### 3. 人工检查点（checkpoint）

- 默认每 10 轮暂停一次
- 暂停时输出当前汇总：
  - 已完成轮次
  - 各轮产出摘要
  - 预估成本
  - 剩余工作概述
- 用户确认后继续，或终止

### 4. 成本预警

- 默认阈值：10 美元、50 美元、100 美元
- 每次迭代后更新预估成本
- 达到阈值时暂停并通知用户
- 用户可以选择继续或终止

## 智能检测

### 1. 死循环检测

算法：对比最近 N 轮（默认 5 轮）的产出变化（`scripts/detect_dead_loop.py`）

判定条件（无进展类判定，仅在文件变更数与 diff 行数两路信号均缺失/为零时生效）：
- 最近 N 轮文件变更数与 diff 行数均为 0
- 最近 N 轮的 worker 输出内容高度相似（字符 3-gram Jaccard 相似度 > 0.95）
- 若 worker 摘要报告了文件变更数或 diff 行数（任一 > 0），视为有进展信号，不判定死循环
- 注意：worker 摘要可能只报告文件变更数而不报告 diff 行数，此时 diff 行数缺失属于信息缺失，不单独作为死循环证据

处理：
- 连续 3 轮判定为死循环 -> 熔断
- 强制标记 Goal blocked
- 输出死循环检测报告（含相似度、最近 N 轮变更统计）

### 2. 速率限制

- 默认每小时最多 100 次迭代
- 超过速率限制时暂停 5 分钟再继续
- 防止 API 账单爆炸

### 3. 智能熔断

场景：连续多次检测到完成标记但未正常退出

处理：
- 连续 3 次检测到完成标记且标记存在 -> 强制退出
- 输出熔断报告

### 4. 反馈信号处理（结构化错误 + 根因分析）

> 来源：吸收 `loop-engineering` 反模式「忽略反馈信号」。仅死循环检测覆盖"无进展"不够，错误类反馈同样需要结构化处理。

要求：
- 每轮失败时结构化解析反馈信号：错误类型、位置、出现次数、已尝试的修复清单
- 引入"修复回诊"步骤：每轮修复前，先检查上一轮修复是否真的生效
- 同一错误连续出现 2 次 -> 强制触发根因分析，禁止继续"换着姿势修复"
- 同一错误连续出现 5 次且无法自解 -> 升级通知人工
- 根因分析结论与修复动作写入当轮状态文件（`worker_summaries`），供后续轮次追溯

### 5. 最小可行循环（防过度工程）

> 来源：吸收 `loop-engineering` 反模式「过度工程」。不是所有任务都需要循环。

判定流程（进入循环前先过一遍）：
1. 任务真的需要多轮吗？-> 单次调用 / 脚本 / if-else / cron 能解决，就不用循环
2. 有清晰的反馈信号吗？-> 没有反馈信号支撑的循环注定空转，重新评估
3. 需要循环时，用最小设计起步（max_iterations <= 5 起步，验证有效再放大）

复杂度判定：循环相关配置/编排代码超过业务逻辑 3 倍长度，即为过度工程信号，应简化。
本 skill 的 `max_iterations` 默认 50 是上限参考，不是起步值。

### 6. 独立验证（防反馈信号污染）

> 来源：吸收 `loop-engineering` 反模式「反馈信号污染」。生成者与验证者同体 = 自证清白。

风险：worker 输出完成标记后控制器即收口，但 worker 自报的"完成"可能是确认偏差（自己写代码、自己跑测试、自己判通过）。

要求：
- **完成标记只是 worker 的自报信号，不是完成依据**；控制器必须做独立验证后才能收口
- 独立验证的手段清单与执行细节见 `completion-marker-pattern.md`「独立验证（控制器职责，强制）」节（单一权威，此处不重复）
- 生成与验证分离：同一任务的生成与验证不得由同一 worker 单独完成；验证优先走外部工具（测试、lint、类型检查），其次独立 worker
- 验证者自身也要抽查：其判定是否与真实结果一致，防止验证者也漂移

## 异常处理

### Worker 创建失败

| 失败类型 | 重试策略 | 最大重试次数 |
|---|---|---|
| create_thread 工具返回错误 | 立即重试，每次间隔 10 秒 | 3 |
| wait_threads 超时 | 重新创建 worker | 3 |
| worker 输出为空 | 重新创建 worker | 3 |

超过最大重试次数后标记 Goal blocked。

### 状态文件异常

| 异常类型 | 处理方式 |
|---|---|
| 状态文件不存在 | 重新调用 loop_controller.py start |
| 状态文件损坏（JSON 解析失败） | 备份损坏文件，重建状态文件 |
| 状态文件写入失败 | 记录阻断事实，不阻止已完成的 worker 结果展示 |
| 状态文件路径不可用 | 降级为内存中维护状态 |

### 脚本执行异常

| 异常类型 | 处理方式 |
|---|---|
| Python 脚本不存在 | 使用内置模拟逻辑替代 |
| Python 解释器不可用 | 使用 shell 替代命令 |
| 脚本返回非零退出码 | 重试 1 次，失败后使用内置逻辑 |

### 工具不可用

| 工具 | 不可用时的处理 |
|---|---|
| create_thread | 降级为 L1 内部续跑模式 |
| wait_threads | 降级为 L1 内部续跑模式 |
| check_completion_marker.py | 直接在输出文本中搜索标记字符串 |
| detect_dead_loop.py | 跳过死循环检测，仅保留硬性限制 |
| loop_controller.py | 在内存中维护状态，不写入文件 |

## 安全边界汇总

### 必须遵守

1. 每个循环必须设置 max_iterations
2. 每轮迭代后必须检测完成标记
3. 达到上限或死循环时必须停止，不得继续
4. 人工检查点暂停时，必须等待用户确认才能继续
5. 成本超过阈值时，必须通知用户
6. 同一错误连续出现 2 次时，必须触发根因分析，不得继续盲修
7. 收口前必须对 worker 自报的完成标记做独立验证（见「6. 独立验证」）

### 禁止行为

1. 没有 max_iterations 就启动循环
2. 忽略完成标记检测直接继续
3. 用户未确认时自动通过人工检查点
4. 死循环判定后仍继续该任务
5. 绕过速率限制
6. 忽略成本预警继续迭代
7. 仅凭 worker 自报完成标记收口，未做独立验证
8. 同一错误连续出现 2 次仍不触发根因分析
