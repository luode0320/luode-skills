# 循环模式库

> 本文件是 long-run-loop-rules 的**模式选择参考**。本 skill 的主路径（Goal 触发 + 完成标记 + 线程接力）对应下文 **模式 5：Goal-Driven Exploration**；其余模式按场景选用。来源：吸收 `loop-engineering`（skillhub）patterns.md，已压缩去平台绑定。

## 一、八种循环模式

### 1. 巡逻循环（Patrol Loop）

**适用场景**：系统健康巡检、周期数据校验、定时巡查

**核心思想**：固定间隔唤醒，检查一批条件，仅在条件不满足时执行动作，否则保持静默。

**关键要点**：
- 间隔不宜过短（浪费资源）或过长（漏报）
- 检查点覆盖关键指标，避免过度监控制造噪音
- 推荐状态机：healthy -> degraded -> critical，分级响应
- 健康基线必须明确，模糊条件导致误报/漏报

### 2. 采集-转换-归档（Collect-Transform-Archive）

**适用场景**：数据采集管道、日志聚合、ETL、信息源汇总

**核心思想**：三个阶段松耦合，各自可独立替换，失败局部重试。

**关键要点**：
- 三阶段职责清晰，互不耦合（采集者不关心数据如何存储）
- 归档必须幂等写入，避免重复采集产生冗余数据
- 死信队列（dead_letter_queue）是必配组件，异常数据不得静默丢弃
- 退避策略防止对采集源过度请求

### 3. 观察-告警-修复（Observe-Alert-Remediate）

**适用场景**：运维自动化、自愈系统、服务可靠性保障

**核心思想**：完整反馈环——检测异常 -> 自动修复 -> 验证 -> 不可修复则升级。

**关键要点**：
- **修复动作必须带验证步骤**；修了不验证等于没修
- 自动修复要有边界（白名单操作），避免越修越糟
- 升级路径分级：记录 -> 通知 -> 人工介入
- 记录每次修复的完整上下文，供事后分析

### 4. 批处理队列（Batch Processing Queue）

**适用场景**：任务队列消费、Worktree 驱动的批量处理、异步工作流

**核心思想**：入队与消费解耦，支持多个并发 Worker，结果集中聚合。

**关键要点**：
- 任务幂等——同一任务可能被消费多次
- 任务设置超时，防止单个任务阻塞整个队列
- 聚合时分类结果：成功 / 失败 / 超时
- 队列必须持久化，防止进程崩溃丢任务

### 5. 目标驱动探索（Goal-Driven Exploration）★ 本 skill 主路径

**适用场景**：典型 /goal 场景、自主 Agent 任务、开放式问题求解

**核心思想**：plan-act-observe 循环，直到可验证的完成条件满足或达到最大迭代数。

**关键要点**：
- 目标必须可验证——有明确判定标准，而非模糊的"做好"
- 需要回溯机制，不是所有路径都通向目标
- 设置 max_iterations 防无限循环，超时返回当前最优结果
- 每轮观察记录在案，形成可追踪的执行轨迹

### 6. 多智能体评审（Multi-Agent Deliberation）

**适用场景**：代码评审、方案评估、创意生成与筛选、质量保障

**核心思想**：多个 Agent 扮演不同角色，生成 -> 交叉评审 -> 迭代改进 -> 收敛。

**关键要点**：
- 角色设计要有区分度（激进派、保守派、用户视角、安全审计）
- 评审标准提前定义，避免无休止争论
- 设 max_rounds 防无限迭代，通常 2-3 轮即可收敛
- 择优可用投票、加权评分或主席裁决

### 7. 增量构建（Incremental Build）

**适用场景**：代码变更感知、增量处理、热重载、持续集成

**核心思想**：检测变更 -> 计算影响范围 -> 只处理受影响部分 -> 验证。

**关键要点**：
- 依赖图是决定增量计算准确性的核心数据结构
- 变更检测粒度决定效率：文件级 < 函数级 < 模块级
- 构建失败必须有明确的回滚/恢复策略
- since_last_build 状态必须持久化，重启后不得丢失

### 8. 自愈（Self-Healing）

**适用场景**：服务自恢复、自动故障处理、降级与熔断

**核心思想**：检测故障 -> 按风险递增的策略逐级尝试恢复 -> 每级失败升级 -> 恢复后验证。

**关键要点**：
- 恢复策略按风险从低到高排序：重试 -> 降级 -> 回滚 -> 通知
- 每个恢复级别都要验证，不得假定"执行了=修好了"
- 记录完整事件报告，供事后根因分析
- 熔断器（circuit breaker）是自愈的常见前置组件

## 二、模式选择指南

| 场景 | 推荐模式 | 理由 |
|------|----------|------|
| 定时健康检查、监控告警 | 巡逻循环 | 定时触发 + 条件检查，开销低 |
| 数据采集、日志聚合 | 采集-转换-归档 | 松耦合管道，各阶段可独立替换 |
| 运维自动化、服务自愈 | 观察-告警-修复 | 完整反馈环，自动修复 + 升级路径 |
| 异步任务、批处理 | 批处理队列 | 入队消费解耦，Worker 可横向扩展 |
| 开放式探索、自主 Agent | 目标驱动探索 ★ | plan-act-observe 循环，支持回溯 |
| 代码评审、方案评估 | 多智能体评审 | 多角色交叉评审，消除单视角盲区 |
| CI/CD、热重载、增量处理 | 增量构建 | 只处理变更部分，避免全量重建 |
| 自动故障恢复、熔断降级 | 自愈 | 分级恢复策略，每级验证 |
| 复杂系统 | 组合使用 | 巡逻发现异常 -> 自愈修复 -> 管道处理 |

## 三、组合建议

- **巡逻循环 + 自愈**：巡逻发现异常后直接触发自愈流程
- **采集-转换-归档 + 增量构建**：采集后按增量影响确定处理范围
- **目标驱动探索 + 多智能体评审**：探索过程中对关键决策做多角色评审
- **批处理队列 + 观察-告警-修复**：队列消费异常触发监控告警循环
